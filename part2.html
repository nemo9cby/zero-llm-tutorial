II

第 II 部 应用篇：制作 StoryBot

第二台机器人 StoryBot 用 2.2 GB 的儿童故事训练，会自己编出一个完整的小故事。分词器、模型、训练还是那三步，但数据大了三百多倍，每一步都要换上更工程化、更现代的做法。

CodeBot 写的是代码，StoryBot 写的是故事。从这一部开始，我们从生成程序转向用自然语言创作。数据从 6.5 MB 增加到 2.2 GB，模型换成了今天的 LLM 普遍采用的结构，训练也用上了学习率调度、混合精度和验证集。节奏还是“分词器 → 模型 → 训练”，只是每一步都要面对规模带来的新问题。

还是先来看结果。原书作者在 Hugging Face 上发布了 StoryBot 预训练过程中的三个 checkpoint：第 500 步、第 5,000 步和训练结束时的第 40,000 步。我们让它们用同一个随机种子各写一个故事（在 CPU 上生成，提示词是 <|endoftext|>，意思是“从头开始写一个新故事”）。

第 500 步的故事只是“像英语”：猫“liked to help other feels”，这已经不成句子了；人物也凭空出现又消失。到第 5,000 步，句子大多通顺了，但情节还会跑偏，刚出场的“小动物”隔了一句就成了“拿着红旗的小学生”（a pupil with a red flag）。训练结束时，Lucy 的故事有开头、有转折，最后落到“要听妈妈的话”这个儿童故事式的道理上。遗憾的是，细看仍有破绽：厨房里有“a small door on the door”；Lucy 刚刚记着妈妈的话没碰冷饮，下一句两人又一起分着吃了。

切换到种子 1 会看到一个有趣的现象：三个阶段的故事都以同一句 “Once upon a time, there was a fat cat named Tom.” 开头。这是因为同一个种子让每一步抽样用的随机数完全相同。直观上，只要开头几步的概率分布相差不大，同一个随机数就会落在同一个词上；分布差得远了，故事才各自分开。

II.1 数据集

StoryBot 的训练数据是 TinyStories，出自 Eldan 与 Li 2023 年的论文《TinyStories: How Small Can Language Models Be and Still Speak Coherent English?》（arXiv:2305.07759）。这是一批由 GPT-3.5 和 GPT-4 生成的短篇故事，用词限制在三四岁孩子通常能听懂的范围内。论文的出发点是：像 GPT-2 small 这样约 1.25 亿参数的模型，在一般文本上训练后也很少能写出连贯的英文；如果把语言变简单，小得多的模型能不能做到？StoryBot 只有 2,270 万个参数，本页开头那个连贯的故事就是答案。

原书用的是其中的 V2-GPT4 版本（TinyStoriesV2-GPT4-{train,valid}.txt）。按 Hugging Face 上的数据集说明，这个版本只收录 GPT-4 生成的故事（说明里说，原始版本中由 GPT-3.5 生成的那部分质量较差）。原始版本里由 GPT-4 生成的故事，它全都收录了，规模却比这一部分大得多。许可证是 CDLA-Sharing-1.0。

原书把两个文件改名为 storybot/tiny_stories_train.txt 和 tiny_stories_valid.txt，内容与斯坦福 CS336 作业所用的文件逐字节相同：原书数据集的文件列表和 roneneldan/TinyStories 的文件列表给出的 SHA-256 一样，训练集开头是 6418d412de72888f，验证集开头是 6874bae9a4c1a4e7（2026-10-12 查证）。验证集已经下载到本地，可以自己算一遍：

大约每 9 篇故事就有 1 篇比上下文窗口长，模型在训练时永远无法一眼看完它们。生成时情况更微妙。原书 StoryBot 的 generate 每一步只把新 token 送进模型，KV cache 不会丢掉开头，所以写到 256 个 token 以后，模型仍然看得见故事的开头；只是从这以后，每个新 token 的位置都被钳在 255（5.5.5 节会看到这个坑）。本页开头的故事都限制在 255 个新 token 以内，就是为了避开这个问题；原书的 06_generate.py 写的是 300。

def test_storybot_cache_keeps_the_beginning(dlfs6_path):
    """storybot/utils.generate 只把新 token 送进模型（use_cache=True），所以截断 ids 的那两行管不到模型：
    KV cache 越过 max_context_len 以后照样变长。WebBot 的模型则只保留最近 max_context_len 个。"""
    import torch
    from storybot.model import GPT as StoryGPT
    from webbot.model import GPT as WebGPT
    src = (pp.DLFS6 / "storybot/utils.py").read_text(encoding="utf-8")
    assert "ids = ids[:, -model.max_context_len:]" in src and "logits = model(next_id, use_cache=True)" in src
    assert pp.script_hparams("ch06/06_generate.py")["max_new_tokens"] == 300          # 书中生成 300 个 token
    torch.manual_seed(0)
    held = {}
    for name, model in (("storybot", StoryGPT(100, 8, 32, 4, 2, 64)), ("webbot", WebGPT(100, 8, 32, 4, 2, 2, 64))):
        model.eval()
        model.clear_cache()
        x = torch.tensor([[1]])
        with torch.no_grad():
            for _ in range(20):                                   # 20 次 decode，上下文上限只有 8
                x = model(x, use_cache=True)[:, -1:].argmax(-1)
        held[name] = model.blocks[0].attn.k_cache.size(2)
    assert held == {"storybot": 20, "webbot": 8}

II.2 开发流程

StoryBot 的开发同样分三章，每一章都是在第 I 部的基础上“升级”：

章 主题 相对第 I 部的变化
第 4 章 分词器 算法还是 BPE，但第 1 章的实现处理 2.2 GB 太慢。依次加上去重、增量更新、分块读取、多进程并行，再加速编码，最后用 memmap 写出 .bin
第 5 章 模型 在 GPT-2 的骨架上换零件：RoPE 位置编码、SwiGLU、RMSNorm，去掉 dropout 和 bias，取消权重共享，再加上生成用的 KV cache
第 6 章 训练 AdamW 的原理与实现、warmup 加线性衰减到 0 的学习率调度、bf16 混合精度、带验证集的预训练、用 LLM 当裁判来评估，最后用 DPO 让它更爱写快乐的结局

模型有 22,696,448 个参数，约为 CodeBot 的 2 倍。预训练的超参数写在 ch06/05_pretrain.py 里：

40,000 步 × 32 × 256 一共是 3.28 亿个 token，只相当于把训练集看了 0.61 遍。脚本还在第 500 步和第 5,000 步各存了一个中间 checkpoint，再加上训练结束时的 model_pretrain.pt，就是本页开头三个故事的来源。严格地讲，文件名里的 500 是从 0 数起的循环变量 i，保存发生在这一次循环的 optimizer.step() 之后，所以 model_iter_500.pt 已经更新了 501 次；同理，model_iter_5000.pt 更新了 5,001 次。

CS336 对照StoryBot 就是 CS336 A1 的 TinyStories 基线

CS336 A1 的 TinyStories 实验配置是：词表 10,000、上下文 256、d_model 512、d_ff 1,344、RoPE θ = 10,000、4 层、16 个头，训练 327,680,000 个 token，与上面的超参数逐项相同。A1 还给了一个低资源版本：把预算降到 4,000 万个 token，目标放宽到 2.00；讲义里的参考运行用的是 32 × 5,000 × 256 = 4,096 万个 token，与 StoryBot 的 model_iter_5000.pt（4,097 万个 token）几乎相同。A1 的验收目标是完整验证集上的 loss：完整预算下 ≤ 1.45，低资源版本 ≤ 2.00。

本部要点

StoryBot 的三个零件都比 CodeBot 更“工业化”：分词器要能在合理时间内吃下 2.2 GB 的文本，模型换上了今天的 LLM 普遍采用的零件，训练要靠学习率调度、混合精度和验证集来保驾护航。从官方 checkpoint 的三个故事可以看出，同一个模型看过的 token 越多，故事越连贯。这条训练在一张 H100 上只要 16 分钟，本书原样重跑的结果达到了 CS336 的目标。

本部所学的内容

  • 官方 StoryBot checkpoint 看过的 token 越多，验证集上的 loss 越低，故事越连贯；同一个种子下，三个阶段的开头可以完全相同（验证 II-a）。
  • TinyStories V2-GPT4 只收录 GPT-4 生成的故事，训练集约 274 万篇，每个 token 平均 4.12 字节（验证 II.1-a）。
  • 200 篇样本里有 114 篇以 Once upon a time 开头，只用了 1,976 个不同的词（验证 II.1-b、验证 II.1-c）。
  • 10.9% 的故事超过上下文长度 256（验证 II.1-d）。
  • StoryBot 的预训练是 3.28 亿 token、训练集的 0.61 遍；model_iter_5000.pt 更新了 5,001 次，看过约 4,097 万 token，接近 CS336 低资源参考运行的 4,096 万（验证 II.2-a）。
  • 本书在一张 H100 上原样重跑：预训练 16 分钟，连同 DPO 共 1.17 美元；完整验证集 loss 第 5,000 步 1.662、训练结束 1.304，达到 CS336 的两个目标（验证 II.2-b）。
