UTF-8 编码的原理

第 1 章把 str.encode("utf-8") 当作黑盒来用。本附录打开这个黑盒：码位怎样变成字节，为什么结果总在 0–255 之间，哪些字节序列不合法，以及 errors="replace" 究竟替换了什么。

1.2 节里，我们把 str.encode("utf-8") 当作一个黑盒来用：A 变成 1 个字节，あ 变成 3 个字节，😁 变成 4 个字节。字节级分词器之所以成立，靠的是两条性质：任何文字都能写成一串 0–255 的整数；这串整数还能原样变回文字。这两条性质来自 Unicode 编码的设计，DLFS6 选的是其中的 UTF-8。

黑盒也留下了几个疑问。为什么 ASCII 字符只占 1 个字节，汉字却要 3 个？验证 1.2-b 里，半个汉字为什么解不出来？用 errors="replace" 时，两个坏字节为什么只变成了一个 �？

本附录就来打开这个黑盒。我们先比较 UTF-32、UTF-16、UTF-8 三种编码，然后从位模式出发，亲手实现 UTF-8 的编码器和解码器，并把它们与 Python 内置的实现逐字节对拍。最后回到分词器，看看这些规则藏在 DLFS6 代码的哪些地方。

A.1 三种编码：UTF-32、UTF-16 与 UTF-8

Unicode 给每个字符规定了一个码位，范围是 0 到 0x10FFFF（1.1 节）。码位只是一个整数。要把它存进文件、在网络上传输，还得规定怎样把这个整数写成字节，这种规定就是编码（encoding）。常用的编码有三种：UTF-32、UTF-16 和 UTF-8。

先来看结果。下面把 A、あ、😁 分别用三种编码写成字节。编码名后面的 -be 表示高位字节在前（big-endian），这样写出来的字节顺序与码位的十六进制写法一致：

验证 A-a同一个字符，三种编码
for ch in ["A", "あ", "😁"]:
    print(f"{ch}  U+{ord(ch):04X}")
    for enc in ["utf-32-be", "utf-16-be", "utf-8"]:
        b = ch.encode(enc)
        print(f"    {enc[:6].upper():<6}  {len(b)} 字节  {b.hex(' ').upper()}")

UTF-32 最简单：每个码位固定占 4 个字节，字节就是码位本身。代价是浪费，A 只需要 7 位，却占了 32 位，前 3 个字节全是 0。

UTF-16 以 2 个字节为一个单位。U+FFFF 以内的码位直接写成一个单位；更大的码位放不下，就拆成两个单位，叫作代理对（surrogate pair）。为此，Unicode 专门把 U+D800–U+DFFF 这一段码位留了出来，永远不分配给任何字符。拆法是先减去 0x10000，剩下的 20 位一分为二，高 10 位加到 0xD800 上，低 10 位加到 0xDC00 上。以 😁 为例：

\begin{aligned} &v = \text{0x1F601} - \text{0x10000} = \text{0xF601}\\[-3pt] &\quad{\footnotesize\text{（先减去 0x10000，剩下的不超过 20 位）}}\\[2pt] &v = \underbrace{0000111101}_{\text{0x03D}}\;\underbrace{1000000001}_{\text{0x201}}\\[-3pt] &\quad{\footnotesize\text{（写成 20 位，一分为二）}}\\[2pt] &\text{0xD800} + \text{0x03D} = \text{0xD83D}\\[-3pt] &\quad{\footnotesize\text{（高 10 位）}}\\[2pt] &\text{0xDC00} + \text{0x201} = \text{0xDE01}\\[-3pt] &\quad{\footnotesize\text{（低 10 位）}} \end{aligned}

两半拼起来正是上面输出里的 D8 3D DE 01。用代码再算一遍：

JavaScript 的字符串按 UTF-16 的单位计数，所以 "😁".length 是 2，而 Python 的 len("😁") 是 1（MDN：String.length，2026-10 查证；单位的个数见验证 A-b 的最后一行）。所以本附录的交互图在逐字符处理文字时，用 [...text] 按码位切分，避免把一个 emoji 劈成两半。

UTF-8 是变长的：ASCII 字符只占 1 个字节，而且这个字节就等于码位本身。所以一个纯 ASCII 的文件，原封不动就是合法的 UTF-8 文件。另外，除了 U+0000 本身，UTF-8 的输出里不会出现值为 0 的字节（验证 A-f 会在全部码位上确认）；而用 UTF-16、UTF-32 写英文时，每个字符都带着值为 0 的字节（上面 A 的两行就是例子）。

那么，为什么“任何字符都能写成 0–255 的数列”呢？分两步看。第一，Unicode 给每个字符都分配了一个码位，最大是 0x10FFFF，最多 21 位。第二，三种编码都按固定的规则把这个整数切成若干个 8 位的块，而且能原样拼回去（验证 A-f 会在全部码位上确认这一点）。8 位的块只能取 0–255。所以字节级分词器用哪一种编码都行，真正的区别在于长度：

A.2 UTF-8 的位模式

UTF-8 的规则可以写成一张表。码位越大，需要的位数越多，就用越多的字节来装：

码位范围 可装的位数（x 的个数） 字节序列（x 是码位的二进制位） 字节数
U+0000–U+007F 7 0xxxxxxx 1
U+0080–U+07FF 11 110xxxxx 10xxxxxx 2
U+0800–U+FFFF 16 1110xxxx 10xxxxxx 10xxxxxx 3
U+10000–U+10FFFF 21 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx 4

每个字节开头的几位是固定的标记，剩下的 x 位用来装码位。规律只有两条：第一个字节开头有几个 1，这个字符就占几个字节（单字节的 ASCII 例外，开头是 0）；其余的字节一律以 10 开头。我们把第一个字节叫作首字节（lead byte），把以 10 开头的字节叫作后续字节（continuation byte）。数一数 x 的个数：2 字节能装 5+6=11 位，3 字节能装 4+6+6=16 位，4 字节能装 3+6+6+6=21 位，正好是表中第二列的数。码位本身的位数可以更少，比如 é 是 U+00E9，只有 8 位，装进 2 字节的模板时，前面补 0 凑满 11 位。

开头的第一个问题也有了答案：ASCII 字符的码位小于 0x80，落在第 1 行；あ 是 U+3042，深度学习入门 这几个字的码位都在 U+4E00–U+9FFF 之间（验证 A-c 的最后一行），都落在第 3 行，所以要 3 个字节。

下面手算 あ 的编码，每一步下面用小字写着理由：

\begin{aligned} &\operatorname{ord}(\text{あ}) = \text{0x3042}\\[-3pt] &\quad{\footnotesize\text{（查码位）}}\\[2pt] &\text{0x0800} \le \text{0x3042} \le \text{0xFFFF}\\[-3pt] &\quad{\footnotesize\text{（表的第 3 行：3 个字节）}}\\[2pt] &\text{0x3042} = 0011\;000001\;000010_{(2)}\\[-3pt] &\quad{\footnotesize\text{（16 位，按 4+6+6 切开）}}\\[2pt] &\to 1110\mathbf{0011}\;\;10\mathbf{000001}\;\;10\mathbf{000010}\\[-3pt] &\quad{\footnotesize\text{（依次填进模板）}}\\[2pt] &= \text{E3 81 82} = 227,\ 129,\ 130\\[-3pt] &\quad{\footnotesize\text{（与 1.2 节的输出一致）}} \end{aligned}

把表格翻译成代码，就是下面的 utf8_encode。>> 把码位右移，取出高位的那一组；& 0x3F 只保留低 6 位；| 把标记位和数据位拼在一起：

验证 A-d亲手实现 UTF-8 编码器，手算 あ
def utf8_encode(cp):
    """按 UTF-8 的位模式，把一个码位编码成字节值的列表。"""
    if not 0 <= cp <= 0x10FFFF or 0xD800 <= cp <= 0xDFFF:
        raise ValueError(f"U+{cp:04X} 不是可以编码的字符")  # 原因见 A.4 节
    if cp < 0x80:       # 7 位 ：0xxxxxxx
        return [cp]
    if cp < 0x800:      # 11 位：110xxxxx 10xxxxxx
        return [0xC0 | (cp >> 6),
                0x80 | (cp & 0x3F)]
    if cp < 0x10000:    # 16 位：1110xxxx 10xxxxxx 10xxxxxx
        return [0xE0 | (cp >> 12),
                0x80 | ((cp >> 6) & 0x3F),
                0x80 | (cp & 0x3F)]
    # 21 位：11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
    return [0xF0 | (cp >> 18),
            0x80 | ((cp >> 12) & 0x3F),
            0x80 | ((cp >> 6) & 0x3F),
            0x80 | (cp & 0x3F)]

cp = ord("あ")
b = utf8_encode(cp)
groups = f"{cp >> 12:04b} {(cp >> 6) & 0x3F:06b} {cp & 0x3F:06b}"
steps = [(f"U+{cp:04X}", "码位"),
         (f"{cp:016b}", "写成 16 位"),
         (groups, "按 4+6+6 切开"),
         (" ".join(f"{x:08b}" for x in b), "填进模板"),
         (" ".join(f"{x:02X}" for x in b) + f" = {b}", "字节")]
for value, why in steps:
    print(f"{value:<28}（{why}）")
assert b == [227, 129, 130] == list("あ".encode("utf-8"))
assert ord("é").bit_length() == 8 and len(utf8_encode(ord("é"))) == 2   # 8 位，装进 11 位的模板

答案（先想一想再展开）

0x1F601 落在第 4 行，要 4 个字节。写成 21 位是 000 011111 011000 000001（按 3+6+6+6 切开），填进模板得到 11110000 10011111 10011000 10000001，也就是 F0 9F 98 81 = 240、159、152、129。这正是 1.2 节 hello世界😁 编码结果的最后 4 个 id。

一个例子对上了，不等于所有码位都对。下面从四类码位里各随机抽 2,000 个，再加上每一类的上下边界，与 Python 的 str.encode 逐个比较。代理区 U+D800–U+DFFF 两边都应该拒绝：

验证 A-e四类码位抽样对拍，代理区两边都拒绝
import numpy as np

rng = np.random.default_rng(0)
classes = [(0x0000, 0x007F), (0x0080, 0x07FF),
           (0x0800, 0xFFFF), (0x10000, 0x10FFFF)]
dropped = {}
for n, (lo, hi) in enumerate(classes, start=1):
    drawn = [lo, hi] + [int(c) for c in rng.integers(lo, hi + 1, size=2000)]
    cps = [c for c in drawn if not 0xD800 <= c <= 0xDFFF]  # 代理区另行检查
    dropped[n] = len(drawn) - len(cps)
    for c in cps:
        b = utf8_encode(c)
        assert len(b) == n and bytes(b) == chr(c).encode("utf-8")
    print(f"U+{lo:04X}–U+{hi:04X}：{len(cps)} 个码位，都是 {n} 字节，"
          "与 str.encode 一致")
print(f"第 3 类抽到的 {2000 + 2:,} 个码位里有 {dropped[3]} 个落进代理区，已先剔除")
assert dropped == {1: 0, 2: 0, 3: 68, 4: 0}

def try_encode(encode, c):
    try:
        return encode(c).hex(" ").upper()
    except (ValueError, UnicodeEncodeError):
        return "拒绝"

for c in (0xD7FF, 0xD800, 0xDFFF, 0xE000):
    mine = try_encode(lambda c: bytes(utf8_encode(c)), c)
    ref = try_encode(lambda c: chr(c).encode("utf-8"), c)
    print(f"U+{c:04X} → {mine}（Python：{ref}）")
    assert mine == ref

第 3 类的范围包含了代理区，抽到的码位里有 68 个落在代理区里。它们先被剔除，留给最后四行单独检查，所以这一类只剩 1,934 个。

抽样能发现大多数错误，但我们可以做得更彻底：把全部 1,112,064 个可编码的码位一次性对拍。这个数是 0 到 0x10FFFF 的 1,114,112 个码位，减去代理区的 2,048 个。码位从小到大排列时，字节数也是从小到大的，所以把四类码位分别用数组运算编好，再依次拼起来，就应该等于“所有字符连成的字符串”的 UTF-8 编码。构造这个字符串时，我们借用了 A.1 节的结论：UTF-32 的字节就是码位本身，所以把码位数组按 UTF-32 解码，就得到了包含全部字符的字符串。

验证 A-f全部 1,112,064 个码位逐字节对拍（NumPy 向量化）
cps = np.arange(0x110000, dtype=np.uint32)
cps = cps[(cps < 0xD800) | (cps > 0xDFFF)]                 # 去掉代理区
c1, c2, c3, c4 = (cps[(cps >= lo) & (cps <= hi)] for lo, hi in classes)
# 与 utf8_encode 完全相同的位运算，只是一次算一整个数组
b1 = c1[:, None]

A.3 解码与自同步

解码是编码的逆过程：读首字节，数开头有几个 1，就知道这个字符一共几个字节；去掉每个字节的标记位，把剩下的数据位拼起来，就得到码位。以 E3 81 82 为例：

\begin{aligned} &\text{E3 81 82}\\ &= 1110\,0011\;\;10\,000001\;\;10\,000010_{(2)}\\[-3pt] &\quad{\footnotesize\text{（写成二进制）}}\\[2pt] &\to 0011\;000001\;000010_{(2)}\\[-3pt] &\quad{\footnotesize\text{（去掉标记位）}}\\[2pt] &= \text{0x3042} = \text{あ}\\[-3pt] &\quad{\footnotesize\text{（拼起来就是码位）}} \end{aligned}

这里有一个容易被忽略的设计：三种字节的取值范围互不重叠。ASCII 是 00–7F，后续字节是 80–BF，首字节则落在 C2–F4（剩下的 C0、C1、F5–FF 永远不会出现，原因见 A.4 节）。我们用 A.2 节的全部编码结果来确认这一点：

A.4 不合法的字节序列

UTF-8 的规则也决定了哪些字节序列不合法。归纳起来有下面五种情况：

情况 例子 为什么不合法
孤立的后续字节 80 后续字节前面必须有首字节
序列被截断 E4 B8 首字节 E4 说一共 3 个字节，只来了 2 个
超长编码（overlong） C0 80、E0 80 80 同一个码位只允许最短的写法
代理区 ED A0 80（U+D800） 这段码位留给 UTF-16 的代理对，不是字符
超出 U+10FFFF F4 90 80 80 Unicode 的码位到 0x10FFFF 为止

开头的第二个问题也有了答案：半个“世” E4 B8 正是第 2 种情况。首字节 E4 说一共 3 个字节，却只来了 2 个，序列在中途就断了。

前两种情况直接违反了 A.2 节的模板，后三种则需要解释一下。

先看超长编码。如果不管规矩，硬把 C0 80 按模板拆开，数据位是 00000 和 000000，拼起来就是 U+0000。可 U+0000 明明只需要一个字节 00。如果两种写法都算合法，同一段文字就会有多种字节表示，分词器给出的 token 序列也就不再唯一。更危险的是安全检查：一个程序禁止输入里出现 NUL 字节 00，却放过了 C0 80，后面的解码器又把它还原成了 NUL。这正是 UTF-8 的规范 RFC 3629 在第 10 节举的例子，所以规范要求只接受最短的写法（RFC 3629，2026-10 查证）。这也解释了首字节为什么从 C2 开始：C0 和 C1 开头的 2 字节序列只能装下小于 0x80 的码位，必然是超长编码。

再看后两种。代理区 U+D800–U+DFFF 是 A.1 节里留给 UTF-16 的“零件”，单独出现没有意义。至于上限，早期的规范 RFC 2279 允许最多 6 个字节；RFC 3629 把范围收窄到 0x10FFFF，也就是 UTF-16 能表示的范围，于是最多 4 个字节。这样一来，首字节 F5–FF 就永远不会出现了：F5–F7 开头的 4 字节序列表示的码位都超过了 0x10FFFF；F8–FD 属于已经废除的 5、6 字节格式；FE 和 FF 则连旧规范里都没有用到（RFC 2279，2026-10 查证）。

把这些规则合起来，就是 Unicode 标准中的“合法 UTF-8 字节序列”表（Unicode 16.0 第 3.9.3 节，表 3-7，2026-10 查证）。它的关键在于：第 2 个字节允许的范围取决于首字节：

码位范围 首字节 第 2 个 第 3 个 第 4 个
U+0000–U+007F 00–7F
U+0080–U+07FF C2–DF 80–BF
U+0800–U+0FFF E0 A0–BF 80–BF
U+1000–U+CFFF E1–EC 80–BF 80–BF
U+D000–U+D7FF ED 80–9F 80–BF
U+E000–U+FFFF EE–EF 80–BF 80–BF
U+10000–U+3FFFF F0 90–BF 80–BF 80–BF
U+40000–U+FFFFF F1–F3 80–BF 80–BF 80–BF
U+100000–U+10FFFF F4 80–8F 80–BF 80–BF

加粗的四格各自排除了一种不合法的情况：

  • E0 后面不能是 80–9F，否则是超长编码；
  • ED 后面不能是 A0–BF，否则落进代理区；
  • F0 后面不能是 80–8F，否则是超长编码；
  • F4 后面不能是 90–BF，否则超出 0x10FFFF。

把这张表原样搬进代码，就是下面的 TABLE_3_7 和解码器 utf8_decode。遇到不合法的序列时，它与 Python 一样抛出 UnicodeDecodeError，并且报告出错的起止位置和原因。errors="replace" 那一支在 A.5 节解释：

验证 A-j照着表 3-7 实现解码器：五种不合法情况与 Python 报错一致
# 表 3-7 的每一行：(首字节范围, 总字节数, 第 2 个字节的范围)
TABLE_3_7 = [((0xC2, 0xDF), 2, (0x80, 0xBF)),
             ((0xE0, 0xE0), 3, (0xA0, 0xBF)),   # 排除超长编码
             ((0xE1, 0xEC), 3, (0x80, 0xBF)),
             ((0xED, 0xED), 3, (0x80, 0x9F)),   # 排除代理区
             ((0xEE, 0xEF), 3, (0x80, 0xBF)),
             ((0xF0, 0xF0), 4, (0x90, 0xBF)),   # 排除超长编码
             ((0xF1, 0xF3), 4, (0x80, 0xBF)),
             ((0xF4, 0xF4), 4, (0x80, 0x8F))]   # 不超过 U+10FFFF

def lookup(b0):
    """首字节 → (总字节数, 第 2 个字节的下限, 上限)；不能当首字节时长度为 0。"""
    for (first, last), length, (lo, hi) in TABLE_3_7:
        if first <= b0 <= last:
            return length, lo, hi
    return 0, 0, 0

def utf8_decode(data, errors="strict"):
    """按表 3-7 解码。errors 取 "strict" 或 "replace"。"""
    out, i, n = [], 0, len(data)
    while i < n:
        b0 = data[i]
        if b0 < 0x80:                          # ASCII
            out.append(chr(b0))
            i += 1
            continue
        length, lo, hi = lookup(b0)
        j = i + 1                              # j 停在第一个“不对”的字节上
        while j < i + length and j < n and lo <= data[j] <= hi:
            lo, hi = 0x80, 0xBF                # 第 3、4 个字节都是 80–BF
            j += 1
        if length and j == i + length:         # 完整而且合法
            cp = b0 & (0x7F >> length)         # 首字节里的数据位
            for k in range(i + 1, j):
                cp = (cp << 6) | (data[k] & 0x3F)  # 每个后续字节 6 位
            out.append(chr(cp))
        elif errors == "strict":
            reason = ("invalid start byte" if length == 0 else
                      "unexpected end of data" if j == n else
                      "invalid continuation byte")
            raise UnicodeDecodeError("utf-8", bytes(data), i, j, reason)
        else:
            out.append(chr(0xFFFD))  # data[i:j] 换成一个 U+FFFD（A.5 节）
        i = j
    return "".join(out)

def outcome(decode, data):
    """解码成功返回文字；失败返回 (起点, 终点, 原因)。"""
    try:
        return decode(data)
    except UnicodeDecodeError as e:
        return (e.start, e.end, e.reason)

def python_decode(data):
    return data.decode("utf-8")

bad = {"孤立的后续字节": b"\x80", "序列被截断": b"\xe4\xb8",
       "超长编码": b"\xc0\x80", "超长编码（3 字节）": b"\xe0\x80\x80",
       "代理区 U+D800": b"\xed\xa0\x80",
       "超出 U+10FFFF": b"\xf4\x90\x80\x80"}
for name, data in bad.items():
    mine = outcome(utf8_decode, data)
    assert mine == outcome(python_decode, data)
    start, stop, reason = mine
    print(f"{data.hex(' ').upper():<12} {start}–{stop}  {reason:<25} {name}")

A.5 errors="replace"：一段坏字节换成几个 �

现在可以回答开头的问题了。严格模式遇到坏字节就报错；errors="replace" 则把坏字节换成替换字符 U+FFFD（显示为 �）然后继续。问题在于“换几个”：两个坏字节，是换成一个 � 还是两个？

Unicode 标准推荐的做法叫“按最大子部分替换”（第 3.9.6 节，2026-10 查证）。从出错的位置开始，找出最长的一段字节，这段字节要么是某个合法序列的开头，要么只有 1 个字节；这一段叫作最大子部分（maximal subpart），整段只换成一个 U+FFFD，然后从它后面接着解码。标准本身并不强制这种做法，但 Python 的解码器遵守它（下面的验证会逐字对拍），浏览器里的 TextDecoder 也遵守它（WHATWG Encoding 标准的 UTF-8 解码器，2026-10 查证）。

A.4 节解码器里的变量 j 正是为此设计的：它从首字节往前走，停在第一个“不对”的字节上，data[i:j] 就是最大子部分。于是：

  • 半个“世” E4 B8：这两个字节是合法序列 E4 B8 96 的开头，属于同一个最大子部分，只换成一个 �。这就是验证 1.2-b 的输出。
  • 超长编码 C0 80：C0 不可能是任何合法序列的开头，单独成一段；80 是孤立的后续字节，又成一段，所以换成两个 �。
  • 代理区 ED A0 80：ED 后面只允许 80–9F，A0 不对，于是 ED 单独成一段，A0、80 各成一段，一共三个 �。
验证 A-l按最大子部分替换：与 errors=replace 的结果逐字相同

小结

本附录打开了 str.encode("utf-8") 这个黑盒。UTF-8 用首字节开头的 1 的个数表示字节数，用 10 标记后续字节，把码位的二进制位依次填进模板。我们照着规则实现了编码器，并在全部 1,112,064 个码位上与 Python 逐字节对拍。三类字节的取值范围互不重叠，这让 UTF-8 可以从任意位置同步，也让 DLFS6 能放心地在原始字节里寻找 <|endoftext|> 来切分大文件。

规则的另一面是“不合法”：截断、孤立的后续字节、超长编码、代理区、超出 0x10FFFF。我们照着 Unicode 的表 3-7 实现了解码器，它的报错位置、原因和替换结果都与 Python 完全一致。errors="replace" 按最大子部分替换，所以半个汉字只换成一个 �；而逐个 token 解码会把一个汉字变成三个 �。

本附录所学的内容

  • 每个字符的码位不超过 0x10FFFF（21 位），三种编码都把它切成 8 位的块，还能原样拼回去，所以任何字符都能写成 0–255 的数列；对英文和代码，UTF-8 最短（验证 A-a、验证 A-c、验证 A-f）。
  • UTF-8 按“首字节标记 + 每个后续字节 6 位”的模板编码，あ 是 E3 81 82；这条规则在全部 1,112,064 个码位上与 Python 一致（验证 A-d、验证 A-f）。
  • 首字节、后续字节、ASCII 的取值范围互不重叠，有 13 个字节值永远不出现；因此 UTF-8 可以自同步（验证 A-g、验证 A-h）。
  • 把切点挪到 <|endoftext|> 上，每一块都能单独解码，这就是 find_chunk_boundaries 的做法（验证 A-i）。
  • 超长编码、代理区、超出 0x10FFFF 都不合法，表 3-7 用首字节的范围（排除 C0、C1、F5–FF）和四格加粗的第 2 字节范围把它们一并排除（验证 A-j、验证 A-k）。
  • errors="replace" 把每个最大子部分换成一个 U+FFFD：半个“世”是一个 �，逐 token 解码是三个；替换有损，流式输出要用增量解码（验证 A-l、验证 A-m）。
