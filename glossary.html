术语与命名对照

同一个量，在不同的代码库里有不同的名字；同一个词，在不同的场合又指不同的东西。这一页把本书的术语、各家代码的参数名、强化学习训练的指标名对齐在一起，并拆开几个最容易混淆的词。

读论文、读代码、看训练日志的时候，最耽误时间的往往不是概念本身，而是名字。DLFS6 叫 embed_dim 的那个数，Hugging Face 叫 hidden_size，CS336 叫 d_model，GPT-2 的代码叫 n_embd；概念完全相同，第一次见到时却很容易以为是四样东西。反过来，“epoch”“step”“batch”这些词，在不同的场合又各有所指。

这一页分四部分。Y.1 是本书的术语表，每个术语都指向它第一次出现的小节。Y.2 是参数名的对照，Y.3 是强化学习训练指标的对照。Y.4 拆开几个一词多义的词。正文里也有两张小一些的对照表：2.10.1 节的方框对齐了 CodeBot 的参数名，3.9.3 节的专栏对齐了最常用的几个强化学习指标。这一页把它们扩展到更多的代码库，并逐项核对出处。

表格很多，可以先用下面的搜索框：输入中文或英文都行，大小写、空格和下划线都不计较。

Y.1 术语表

术语按主题分组。“首次出现”指向本书里第一次正式讲解它的小节；中文一列沿用正文的写法：正文里直接用英文的术语，写成“英文（中文译名）”，如 Attention（注意力）、KV cache（KV 缓存）；token、logits 这样正文从不翻译、也没有统一译名的词，只写英文。最后一组是一词多义的词，它们在 Y.4 里逐个拆开。

def test_cs336_clipping_and_lr_schedules():
    """X.3 梯度裁剪 / 学习率调度 rows (and the glossary's 学习率调度 row): which training scripts clip the gradient
    and which change the learning rate step by step; the others keep the constant set when the optimizer is made."""
    scripts = ("ch03/01_pretrain.py", "ch03/03_sft.py", "ch03/09_grpo.py", "ch06/05_pretrain.py", "ch06/08_dpo.py",
               "ch09/01_pretrain.py")
    clips = {s for s in scripts if "clip_grad_norm_" in src(s)}
    scheduled = {s for s in scripts if "param_group['lr'] = lr" in src(s) and "def get_lr(" in src(s)}
    assert clips == {"ch03/09_grpo.py", "ch06/05_pretrain.py", "ch09/01_pretrain.py"}
    assert scheduled == {"ch06/05_pretrain.py", "ch09/01_pretrain.py"}
    for s in set(scripts) - scheduled:                                  # one constant learning rate, no scheduler
        assert "lr_scheduler" not in src(s) and "param_group" not in src(s), s
    assert {s: consts(s)["learning_rate"] for s in sorted(set(scripts) - scheduled)} == {
        "ch03/01_pretrain.py": 3e-4, "ch03/03_sft.py": 3e-4, "ch03/09_grpo.py": 7e-6, "ch06/08_dpo.py": 5e-6}
    assert "torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)" in src("ch03/09_grpo.py")
    assert consts("ch06/05_pretrain.py")["grad_clip"] == consts("ch09/01_pretrain.py")["grad_clip"] == 1.0

你可能会困惑hidden_size 到底是哪个数？

这个困惑很自然。在经典的多层感知机里，“hidden size”说的是隐藏层的宽度；Transformer 的 FFN 正好也有一个隐藏层，StoryBot 里它有 1,344 个神经元。于是看到 Hugging Face 配置里的 hidden_size，很容易以为它指的是 FFN 中间那一层。

其实不是。Hugging Face 的 hidden_size 是残差流的宽度，也就是每个 token 的向量在层与层之间传递时的维数：DLFS6 的 embed_dim、CS336 的 d_model、GPT-2 的 n_embd。FFN 中间那一层另有名字：intermediate_size，对应 DLFS6 的 ff_dim、CS336 的 d_ff。上面验证单元里的 GPT2Config.attribute_map 写得最直白：hidden_size 就是 n_embd 的别名。

你可能会困惑指标名以 critic/ 开头，说明有 critic 吗？

在 PPO 里，critic 是一个学习出来的价值网络，它估计“从这里往后能拿多少奖励”，用作基线。所以看到 veRL 日志里的 critic/rewards/mean，自然会以为训练里有一个 critic。

前缀本身说明不了有没有 critic。veRL 在计算数据指标的函数里，不论用什么算法，都把奖励、得分、advantage 和回报的统计放在 critic/ 这个分组下面。真正需要价值网络的只有 critic/values/* 和 critic/vf_explained_var：它们写在 if use_critic: 分支里，没有价值网络时，日志里根本不会出现这几项（上面的验证单元核对了这几行源码的位置）。需要价值网络的算法（比如 PPO）在 veRL 里确实有 critic，这时日志里才多出这几项；GRPO 则没有：它用同一道题的一组回答的平均奖励作基线，DLFS6 的 advantages = rewards - rewards.mean() 就是这一行。

手算一个小例子。三道题，每题采 4 个回答，奖励分别是 [1, 1, 0, 0]、[1, 0, 0, 0] 和 [1, 1, 1, 1]。第 1 组的 advantage 是 [+0.5, +0.5, −0.5, −0.5]，按回答平均是 0。可是 veRL 先把每条回答的 advantage 复制到它的每个 token 上，再在全部回答 token 上平均。假设第 1 组答对的两条回答各 5 个 token，答错的两条各 20 个 token，按 token 平均就是 (0.5\times5\times2 - 0.5\times20\times2)\div50 = -0.3：

print(f"frac_mixed = {np.mean(~same):.3f}，frac_all_good = {np.mean(same & (groups[:, 0] == 1)):.3f}，"
      f"frac_all_bad = {np.mean(same & (groups[:, 0] == 0)):.3f}")

assert abs(groups.mean() - 7 / 12) < 1e-12 and abs(adv.mean()) < 1e-12 and not adv[2].any()

L = np.array([5, 5, 20, 20])                     # 第 1 组：答对的两条短，答错的两条长

所以 critic/rewards/mean 是按回答平均的奖励，critic/advantages/mean 却是按 token 平均的。组内 advantage 的和是 0，只有各回答一样长时，按 token 的平均才是 0；答错的回答更长时，它就偏负。它反映的是长度和对错之间的关系，不是学习信号。真正告诉你“还有没有学习信号”的，是 tinker-cookbook 的 frac_all_good 与 frac_all_bad：全对或全错的组，advantage 全是 0。

带走一句话：critic/ 只是 veRL 的分组名，不是“有 critic”的证据；GRPO 的基线是组均值，不是一个网络。

Y.4 一词多义

最后是几个在不同场合指不同东西的词。

probe

“probe”至少有两种常见用法。在可解释性研究里，探针（probe）指在模型的隐藏状态上训练一个简单的分类器（通常是线性的），看某种信息能不能从中读出来。在做实验的日常对话里，“先 probe 一下”往往指训练开始前，先用现成的模型把任务跑一遍，看看它的基础通过率，也就是“第 0 步”的评估。

你可能会困惑“先 probe 一下”到底指什么？

同一个词指两件完全不同的事，听的人自然会困惑：是要训练一个分类器，还是只跑一遍评估？在训练强化学习之前说“probe”，通常指后一种：不改动任何参数，用基础模型做一遍题，记下通过率作为起点。

这一步看起来简单，但小样本的通过率很不稳定。8 道题对了 5 道，看起来是 62.5%，可它的 95% 置信区间是 [0.31, 0.86]，从三成到八成多都有可能。这个区间是 Wilson 区间：

\frac{\hat p + \dfrac{z^2}{2n} \pm z\sqrt{\dfrac{\hat p(1-\hat p)}{n} + \dfrac{z^2}{4n^2}}}{1 + \dfrac{z^2}{n}}

这里，\hat p = k/n 是观测到的通过率，n 是题数，z = 1.96 对应 95%。手算 5/8：\hat p = 0.625，z^2/n = 0.480，中心是 (0.625 + 0.240) \div 1.480 = 0.584，半宽是 1.96 \times \sqrt{0.0293 + 0.0150} \div 1.480 = 0.279，区间就是 [0.31, 0.86]。

作者发布的 SFT 权重在 81 道加法题上贪心解码答对 44 道（54.3%），我们按书自己训练的 SFT checkpoint 也是 44 道（勘误 E15 的本地验证）。这个通过率的区间是 [0.44, 0.65]：

验证 Y.4-a5/8 的 95% Wilson 区间是 [0.31, 0.86]（中心 0.584，半宽 0.279）；44/81 是 [0.44, 0.65]
def wilson(k, n, z=1.96):
    p = k / n
    center = (p + z * z / (2 * n)) / (1 + z * z / n)
    half = z * np.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / (1 + z * z / n)
    return center - half, center + half

那么，训练之后再测一次，怎样判断提升是真的呢？两次都用同一组题，两次都对或者都错的题不提供信息，要看的是结果变了的题。假设有 21 道题的结果变了：13 道是训练后才做对的，8 道反而从对变成了错。如果训练其实没有效果，每道题往哪边变就像抛一次硬币；抛 21 次，出现 13 比 8 或者更悬殊的结果，概率是 0.38。这就是符号检验（sign test）。13 比 8 还说明不了训练有效，要到 16 比 5，p 值才低于 0.05：

from math import comb

def sign_test(better, worse):            # 双侧符号检验：只看结果变了的题
    n, k = better + worse, max(better, worse)
    return min(1.0, 2 * sum(comb(n, i) for i in range(k, n + 1)) / 2 ** n)

for better, worse in ((13, 8), (15, 6), (16, 5)):
    print(f"变好 {better}、变差 {worse}：双侧 p = {sign_test(better, worse):.3f}")

epoch

epoch 指把数据完整过一遍，但“一遍”可以有不同的数法。第 3 章的 CodeBot 预训练常被说成“过了 61 个 epoch”：20,000 步 × 32 个窗口 × 256 个 token，约是语料 2,677,398 个 token 的 61 倍。可是从 DataLoader 的角度看，数据集里的每个样本是一个起点不同的窗口，共有 2,677,142 个，20,000 步只取了其中 640,000 个，连一遍都没有过完。两种说法都对，只是“一遍”的单位不同：一个按 token 算，一个按窗口算。

微调的数据少，epoch 就多了起来。数的时候要以 DataLoader 实际给出的 batch 为准：SFT 的 1,092 条样本每个 epoch 分成 35 个 batch，最后一个只有 4 条，所以 500 步是 14.3 遍，而不是粗算的 500 × 32 ÷ 1,092 ≈ 14.7 遍。顺带交代一下本书的用词：把数据过一遍叫一个 epoch，说有多少时用“遍”（如 14.3 遍）；训练模型时说的“轮”只用来数 GRPO 的迭代，一轮是一次生成加两次更新（见下面的 step）。

验证 Y.4-c同一次预训练：按 token 是 61.2 个 epoch，按 DataLoader 的样本只有 0.24 个；SFT 的 500 步是 14.3 遍

step

step 至少有四种意思。在 DLFS6 的训练循环里，一次 iteration 通常就是一次参数更新（一个 optimizer step）。但有了梯度累积，一次更新要先跑好几个 micro-step：WebBot 每次更新累积 4 个 micro-batch，每张卡每步处理 32 × 4 × 1,024 = 131,072 个 token。GRPO 的一次 iteration（本书叫“一轮”）包含一次生成和两次更新，也就是两个 optimizer step。生成时的一个 decode step，则是让模型多吐出一个 token 的那一次前向计算。

context

context 最常见的意思是上下文长度：模型一次最多能看见多少个 token，CodeBot 和 StoryBot 是 256，WebBot 是 1,024。这是一次前向计算的上限。可是在聊天和智能体的场合，“上下文”还常指整段对话历史，以及“这次任务一共消耗了多少 token”。两者经常被混为一谈。

batch

batch 听上去是一个数，可是先要问清楚它数的是什么。预训练里，一次参数更新背后有三层：每张卡一次前向算多少条序列（micro-batch），每张卡累积几次，一共几张卡。三者之积才是全局 batch（global batch size，常缩写成 gbs）。WebBot 在 8 张卡上是 32 × 4 × 8 = 1,024 条序列，约 105 万个 token（推导见 9.3 节的验证 9.3-e）。原书记进 wandb 的 effective_batch_size 只乘了前两项，不论几张卡都是 128（勘误 E45）。

卡数来自 torchrun 给每个进程设的环境变量：WORLD_SIZE 是进程总数，RANK 是全局编号（0 到 WORLD_SIZE − 1），LOCAL_RANK 是本机内的编号，用来选 GPU。原书用 LOCAL_RANK == 0 判断谁来记日志、存模型，多台机器时每台都有一个这样的进程（验证 9.3-c）。

小结

名字的问题，说到底是“同一个东西，不同的叫法”和“同一个叫法，不同的东西”。前者靠对照表解决：遇到陌生的参数名，先找它在 DLFS6 里叫什么，再看它出现在哪些矩阵的形状里；后者靠追问一句“这里指的是哪一种”。判断一个参数到底是什么，最可靠的办法往往是算一算参数量：残差流的宽度会以平方的形式出现。

本章所学的内容：

  • Hugging Face 的 GPT2Config 把 hidden_size 直接映射到 n_embd：它是残差流的宽度，不是 FFN 中间层（验证 Y.2-a）。
  • 一层 Transformer 的参数量约为 12d^2，所以平方出现的那个数就是残差流宽度（验证 Y.2-b）。
  • veRL、tinker-cookbook 与 CS336 A5 的指标名都能在源码或讲义原文里找到，名字不同，看的东西相通（验证 Y.3-a）。
  • critic/rewards/mean 是按回答平均的奖励；critic/advantages/mean 按 token 平均，各回答不一样长时一般不是 0，也不是学习信号（验证 Y.3-b）。
  • 8 道题对 5 道的 95% 区间是 [0.31, 0.86]；前后对比时 13 比 8 的符号检验 p = 0.38：小样本的评估要带上区间和检验（验证 Y.4-a、验证 Y.4-b）。
  • “一遍”和“一批”都要问数的是什么：同一次预训练，按 token 是 61.2 个 epoch，按样本只有 0.24 个；强化学习的 batch 是“题数 × 每题的回答数”，DLFS6 的 81 道题分成 256、256、136 条回答（验证 Y.4-c、验证 Y.4-f）。
  • 上下文窗口限制单次请求，累计消耗随轮数按平方增长（验证 Y.4-e）。
