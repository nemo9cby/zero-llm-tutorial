第 III 部 挑战篇：制作 WebBot

第三台机器人 WebBot 读的是 12 GB 的真实网页文本，模型有 1.5 亿个参数，要用数据中心级的 GPU 训练。原书在这一部只给提示、不给完整步骤；本教程照样一节一节地写，并在每一节配上能在本地运行的最小验证。

最后一台机器人是 WebBot。它面对的不再是整理好的小程序或儿童故事，而是真实的网页文本：有噪声，文体五花八门，话题无所不包。前两台机器人用过的技术，在这里还管用吗？这是第 III 部要回答的问题。

原书在这一部换了写法：它明确表示不再给出详细的实现步骤，只提示需要思考的要点和方向，请读者调动前两部学到的知识，自己把 WebBot 做出来（原书第 III 部扉页的试读，2026-10-12 查证）。所以第 7–9 章的代码很少：仓库里只有分词器的两个脚本、webbot/ 下的模型和生成函数，以及训练和生成的两个脚本，第 8 章甚至没有代码目录。本教程照样按原书的小节来写，凡是原书只给提示的地方，都配上一段可以在本地运行的最小验证，并在 GPU 实战手册 里给出真正去训练的命令和预算。

前两部的扉页都先展示了完成后的机器人。WebBot 做不到这一点：原书作者没有发布 WebBot 的权重（2026-10-12 查证时，Hugging Face 的文件列表里，webbot/ 下只有数据和分词器，没有 model_pretrain.pt）；本书也只跑了正式训练的前 200 步，完整的预训练还没有跑。所以我们反过来，先看看训练开始之前的 WebBot。

下面用的是原书 ch09/02_generate.py 里的 5 个提示词和它的温度 0.5，模型按 ch09/01_pretrain.py 的超参数构造、随机初始化（种子 0），每个提示词生成 30 个 token（原书生成 100 个，这里截短是为了让本地验证跑得快）。有一点要先说明：每个提示词生成之前，我们都把随机种子重置为 0，所以五次抽样用的是同一串随机数。为了对照，我们又给每个提示词换一个种子（100–104），各生成一次：

验证 III-a未训练的 WebBot：分布近乎平坦，五段输出的重合来自同一个随机种子
import json
import itertools
import math

rec = json.load(open("data/part3/preview.json", encoding="utf-8"))
for prompt, out in zip(rec["prompts"], rec["outputs"]):
    print(f"{prompt}｜{out[len(prompt):][:70]}…")

def shared(ids):                       # 两两之间有几个相同的 token（按集合计）
    return [len(set(a) & set(b)) for a, b in itertools.combinations(ids, 2)]

def tv(p, q):                          # 总变差距离：½ Σ |p − q|
    return 0.5 * sum(abs(a - b) for a, b in zip(p, q))

same, indep = shared(rec["continuation_ids"]), shared(rec["continuation_ids_indep"])
n = sum(len(x) for x in rec["continuation_ids"]) / 5
print(f"五段都用种子 0：两两之间平均有 {sum(same) / len(same):.1f} 个相同的 token（每段约 {n:.0f} 个）")
print(f"每段换一个种子：两两之间平均有 {sum(indep) / len(indep):.1f} 个相同的 token")
fs = rec["first_step"]
print(f"第一个新 token 的分布：最大的概率只有 {min(fs['max_prob']):.3%}–{max(fs['max_prob']):.3%}"
      f"（均匀分布是 {1 / fs['vocab_size']:.3%}）")
print(f"五个提示词的分布，两两之间的总变差距离 {min(fs['tv']):.2f}–{max(fs['tv']):.2f}")
print(f"初始 loss {rec['init_loss']:.4f}，ln 50000 = {math.log(50_000):.4f}")
assert tv([0.5, 0.5], [1.0, 0.0]) == 0.5                 # 手算：要把 0.5 的概率从第 2 项挪到第 1 项
assert min(same) >= 9 and max(indep) == 0                # 重合只在共用同一串随机数时出现
assert max(fs["max_prob"]) < 0.002 and min(fs["tv"]) > 0.5
assert abs(rec["init_loss"] - math.log(50_000)) < 0.2

验

五段输出都是语法和意义都不成立的词串，这在意料之中：未训练的模型给出的分布几乎是平的，最可能的那个 token 也不到 0.2% 的概率，抽样就像在 5 万个词里随手抓。

那么，五段输出为什么有三分之一的 token 相同呢？原因不在模型，而在随机数：五次生成用的是同一串随机数。直观上，分布越平，抽中哪个 token 越是由随机数决定，同一串随机数也就常常抽中同一个 token；第 II 部扉页的 StoryBot 也有这个现象。每段换一个种子，两两之间相同的 token 就降到了 0。严格地讲，模型并没有无视提示词。我们用总变差距离（total variation distance）\tfrac12\sum_i |p_i - q_i| 衡量两个分布差多远：它是把一个分布改成另一个时要挪动的概率，0 表示完全相同，1 表示毫不重叠。比如 (0.5, 0.5) 和 (1, 0) 之间要挪 0.5。五个提示词给出的下一个 token 分布，两两之间的距离在 0.53–0.59。训练要做的，是把这些又平又乱的分布变尖，而且尖在合适的词上。初始 loss 也和第 0 章说的一样，比 ln 50000 略高一点。

def test_webbot_untrained_preview_matches_record(dlfs6_path):

    rec = recorded("part3/preview.json")
    new = pp.webbot_preview()
    assert new["prompts"] == pp.WEBBOT_PROMPTS
    for k in ("outputs", "continuation_ids", "indep_seeds", "outputs_indep", "continuation_ids_indep"):
        assert new[k] == rec[k], k
    for k in ("max_prob", "entropy", "tv"):
        assert all(abs(a - b) < 1e-3 for a, b in zip(new["first_step"][k], rec["first_step"][k])), k
    assert abs(new["init_loss"] - rec["init_loss"]) < 1e-3
    bots = {b["id"]: b for b in recorded("ch00/bots.json")["bots"]}
    assert abs(rec["init_loss"] - bots["webbot"]["init_loss"]) < 1e-3   # 与第 0 章同一个随机初始化
    src = (pp.DLFS6 / "ch09/02_generate.py").read_text(encoding="utf-8")
    assert all(f'"{p}"' in src for p in pp.WEBBOT_PROMPTS) and "temperature = 0.5" in src

    # 页面上的结论：重合只在五次生成共用同一串随机数（每次都 manual_seed(0)）时出现
    def shared(ids):
        return [len(set(a) & set(b)) for a, b in itertools.combinations(ids, 2)]

    # 模型并没有无视提示词：五个下一个 token 分布两两差得很远，只是都很平

III.1 数据集

WebBot 的数据是 OpenWebText（OWT）。它的来历要从 GPT-2 说起：OpenAI 训练 GPT-2 时，收集了 Reddit 上至少获得 3 个赞（karma）的帖子所链接的网页，称为 WebText（见 GPT-2 论文 2.1 节），但没有公开。OpenWebText 是 Gokaslan 与 Cohen 按同样的思路重新收集的开放版本（OpenWebText Corpus）。原书用的是斯坦福 CS336 课程整理的样本 stanford-cs336/owt-sample，koki0702/zero-llm-data 的说明标注它与 OpenWebText 都是 MIT 许可。

验

结果有两层意思。第一，领域很重要：每个分词器都在自己的训练数据上最省。在故事上，只有 1 万词表的 StoryBot 分词器甚至比 5 万词表的 WebBot 略胜一筹；反过来，用 TinyStories 训练出的词表放到网页上，每个 token 只装 3.22 个字节。第二，词表大小也很重要：CodeBot 只有 1,000 个 token，哪怕在自己的代码数据上，也比不过 5 万词表的 WebBot 分词器。同一份网页文本，CodeBot 的分词器切出的 token 是 WebBot 的 2.30 倍，模型要读的序列也就长了一倍多。WebBot 需要在网页文本上重新训练一个更大的词表，这是第 7 章的起点。

这张表每格只用了约 100 万字节的样本（网页约 200 篇），具体数值会随样本而变，差别可达一成：CodeBot 在完整的 TinyCodes 上是 2.42，比表里的 2.21 高 9%；WebBot 在 OWT 验证集前 200 万个 token（约 890 万字节）上是 4.46，比表里的 4.61 低 3%（验证 III.1-b、验证 III.1-c）。比较谁大谁小没有问题；引用具体数值时，要说明是在哪份样本上测的。

你可能会困惑上下文长度 1,024 是谁定的？

读训练脚本时，context_len = 1024、n_layer = 12 这样的数字看起来像是随手写下的“魔法数字”。想知道它们从哪来，是很自然的疑问。答案通常有三个出处：照搬一个成熟的配置、看数据的统计、算算力的账。对 WebBot 的 1,024 来说，能直接给出这个数的只有第一样；数据和算力给的是取舍，正好拿来检验它。

第一，它和 GPT-2 small 的“身材”一样。Hugging Face 上 GPT-2 的配置文件 写着 n_ctx 1024、n_embd 768、n_layer 12、n_head 12、词表 50,257（2026-10-11 查证）。在这五项配置里，WebBot 只改了词表，换成自己训练的 50,000；五项之外的结构并不相同（III.2 节）。上下文长度与 GPT-2 small 相同，至于原书是不是有意照搬，我们没有看到说明。

第二，数据：上下文从 256 加到 1,024，能被一眼看完的网页从 9% 升到 68%；再加到 2,048 是 90%。哪一档都不是“刚好够用”，这是取舍。

第三，算力：每个头的 Attention 分数是一张上下文长度 × 上下文长度的表，1,024 比 256 大 16 倍。但摊到每个 token 上，这部分在总计算量里占比很小。按 Kaplan 等人的估算（arXiv:2001.08361 表 1），训练时每个 token 约要

6N' + 6 L \, n_\text{ctx} \, d

次浮点运算。这里，N' 是去掉 token embedding 后的参数量（embedding 只是查表，不做乘法），L 是层数，n_\text{ctx} 是上下文长度，d 是向量宽度；第二项就是 Attention 分数那部分。拿 WebBot 算一算：6N' \approx 6 \times 1.14\text{ 亿} \approx 6.8 亿，第二项在 n_\text{ctx} = 1{,}024 时是 6 \times 12 \times 1{,}024 \times 768 \approx 0.57 亿，在 256 时是 0.14 亿。所以 1,024 只比 256 多约 6% 的计算量。

验证 III.1-d1,024：与 GPT-2 small 相同；数据和算力给的是取舍

想一想用 8 张 GPU 跑这个脚本，会比 1 张快 8 倍吗？
答案（先想一想再展开）

不会。脚本从不读取 GPU 的张数，每张卡都要跑满 max_iters = 100000 步。多卡并行时，每张卡用不同的随机种子（torch.manual_seed(42 + RANK)）抽取训练窗口，处理的是不同的数据，梯度取平均后一起更新。所以墙钟时间和单卡差不多，读过的 token 却变成了 8 倍：从 131 亿变成 1,049 亿。全局 batch 也一样变大：32 条 × 4 次累积 × 8 张卡 = 1,024 条序列。想在 8 张卡上保持单卡的 token 预算，要把 max_iters 除以 8，改成 12,500。第 9 章讲分布式训练时会回到这一点。

本部要点

第 III 部没有现成的终点可看，但起点和路线都能验证：未训练的 WebBot 只会从近乎平坦的分布里随手抓词，原书脚本在 H100 上的前 200 步也确实让 loss 降了下来；它要学的网页文本又长又杂，三分之一的文档比上下文还长；前两台机器人的分词器算法可以复用，词表却必须在网页上重新训练；而整个预训练需要约 10¹⁹ 次浮点运算，在一张 H100 上要跑十个多小时。

本部所学的内容

  • 未训练的 WebBot 输出近乎随机的词串；五段输出的重合来自同一个随机种子，换种子就消失；初始 loss 比 ln 50000 略高（验证 III-a、验证 III-b）。
  • OWT 验证集有 59,059 篇文档，中位数 696 个 token，32.0% 超过上下文长度 1,024（验证 III.1-a、验证 III.1-b）。
  • 在约 100 万字节的网页样本上，WebBot 的分词器每个 token 装 4.61 字节，CodeBot 的只装 2.01 字节；领域和词表大小都有影响（验证 III.1-c）。
  • 上下文长度 1,024 与 GPT-2 small 相同；数据和算力给的是取舍：从 256 加到 1,024，看得完的网页从 9% 升到 68%，每个 token 的计算量只多约 6%（验证 III.1-d）。
  • WebBot 的参数略多于一半在 token embedding 和输出层；加 GPU 不会缩短训练时间，而是增加训练的 token 数（验证 III.2-a、验证 III.2-b）。
  • 一张 H100 上的单卡预训练：计时探针实测每步 0.317 秒（MFU 按 6ND 的口径约 38%，按矩阵乘加 Attention 的口径约 31%），训练约 8.8 小时，加上验证约 10.4 小时（验证 III.2-c、验证 III.2-d）。
