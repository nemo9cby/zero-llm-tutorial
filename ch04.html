分词器【应用篇】：让 BPE 快起来

第 1 章的 BPE 在 6.5 MB 的代码语料上要训练将近一个小时，而 StoryBot 的语料有 2.2 GB。本章不换算法，只换实现：每做一处改进，都先证明结果与朴素版逐项相同，再量一量快了多少、剩下的时间花在哪里。

第 1 章，我们从“一个字符一个编号”出发，一路写出了 BPE 分词器，并用它把 TinyCodes 编码成了 CodeBot 的训练数据。那份实现完全照着算法的定义来写：每学一条合并规则，就把整个语料从头数一遍、再从头合并一遍。代码短，道理也清楚。代价是慢：在 6.5 MB 的 TinyCodes 上学 743 条规则，本章测量时用了 52 分钟的 CPU 时间（同机满载，实际等了 77 分钟）。第 1 章 1.7.3 节提到的是另一次完整运行，机器的负载不同，时间也不一样。

第 II 部的 StoryBot 要读的是 TinyStories，一个 2.2 GB 的英文小故事语料，词表也从 1,000 扩大到 10,000。语料大了约 343 倍，合并次数从 743 变成 9,743。朴素实现每一步都要把全部语料扫一遍，工作量大致与“合并次数 × 语料字节数”成正比，两个倍数相乘，工作量是 CodeBot 的四千多倍。照这个比例粗算，第 1 章的代码要连续跑五个多月。内存也撑不住：它会把整个文件读成一个字符串，再为每一次出现的单词各存一份字节列表。

五个多月是按“每一步的工作量都和第一步一样”算的，实际会少一些：高频词最先被合成一个 token，合并越往后，序列越短，每一步要扫描的 id 也越少。在 TinyStories 验证集上学 9,743 条规则时，平均每一步只剩第一步的 27%，而 TinyCodes 的 743 步平均剩 53%。按这个比例打个折，也还要将近三个月，总之是以月计。

本章的做法是：算法一步不改，只改实现。训练这一侧分四步：去重（4.1）、增量更新（4.2）、分块读取（4.3）、多进程并行（4.4）。接着评估训练好的分词器（4.5）。然后编码也提速两步：按优先级合并（4.6）、分块并行并写成二进制文件（4.7）。每一步我们都回答三个问题：改了什么？为什么结果和朴素版逐项相同？快了多少，剩下的时间又花在哪里？如果你读过《深度学习进阶：自然语言处理》第 4 章“word2vec 的高速化”，会觉得这个节奏很眼熟：那一章也是先点出瓶颈，再一节解决一个。

4.1.2 去除重复

想法很简单：既然 ' the' 出现了 N 次，就不必存 N 份，只记一行“' the'：N 次”。数 pair 的时候，把这个词内部的每个 pair 都加上 N。这就像点钞：一万张同面额的钞票扎成一捆，写上“一万张”，以后每次盘点都只看捆上的数字，不必再一张一张地数。

严格地讲，我们要的是每个 pair 在整个语料里出现的次数 N(a,b)。按不同的预分词分组来数，就是

N(a,b) = \sum_{w} c_w \, n_w(a,b)

这里，w 遍历所有不同的预分词，c_w 是 w 出现的次数，n_w(a,b) 是 pair (a,b) 在 w 内部出现的次数。朴素版对 w 的每一次出现各数一遍，等于把 c_w 个相同的 n_w(a,b) 加起来，所以两种数法的结果必然相等。

来算一个能心算的例子。语料里有 low 5 次、lower 2 次、newest 6 次、widest 3 次。pair (e, s) 在 newest 和 widest 里各出现一次，所以 N(e,s) = 6 \times 1 + 3 \times 1 = 9；(s, t) 同样是 9。两者并列第一。原书挑 pair 的规则是比较 (次数, 第一个 id, 第二个 id)，s 的字节值 115 大于 e 的 101，所以第一条合并规则是 st。

验证 4.1-c按次数加权计数 == 把每次出现展开后计数
from collections import defaultdict

4.1.3 改进版的 BPE 训练

下面是改进后的 train_bpe。与第 1 章相比，改动集中在三处：

日文注释的意思依次是：按特殊 token 切分；对每段文本做预分词；用 tqdm 显示进度；把预分词转成 ID 序列；对每个 ID 序列，按它的出现次数加权统计 pair 频次；没有 pair 时的处理；选出最频繁的 pair；合并每个 ID 序列并更新；执行合并。注释掉的那一行 max(pair_counts, key=pair_counts.get) 是另一种挑 pair 的写法，4.2 节会说明它为什么不行。

首先，预分词之后不再存列表，而是用 pretoken_counts 数次数。其次，ids_counts 把每个不同的预分词变成字节元组，作为字典的键，值是出现次数。这里必须用元组：列表是可变的，不能当字典的键。最后，count_pairs 多了一个参数 weight，计数时每个 pair 加的是出现次数而不是 1；合并时也一样，结果累加进 new_ids_counts。

注意count_pairs 的签名变了

第 1 章的 count_pairs(ids, counts=None) 在这里变成了 count_pairs(ids, weight=1, counts=None)，新参数插在了中间。如果你把两个版本混着用，按位置传 counts，它会被当成 weight，然后在 counts[pair] += weight 处报错。storybot/tokenizer.py 用的是新签名，codebot/tokenizer.py 用的是旧签名，两个模块的函数不能互换。

直觉上会担心：把一万次出现压成一行，会不会丢掉什么信息？不会，因为三件事同时成立。第一，计数是可加的：上面的公式已经说明，加权计数等于展开计数。第二，merge 只看序列本身：两个相同的序列合并之后仍然相同，所以同一个预分词的一万次出现永远“步调一致”。第三，每一步挑出的 pair 都相同：原书的 max 用 (次数, id0, id1) 作 key，这是一个全序，结果与字典里的顺序无关（4.2 节会看到少了它会怎样）。

4.2.2 用缓存做增量更新

想法是：维护一张 pair 计数表，合并之后只修改受影响的那几行，而不是每一步从头重算。这就像记账：每发生一笔交易，只改动相关账户的余额，而不是每天把所有流水从头加一遍。

严格地讲，我们要始终保持下面这个等式成立：

N(a,b) = \sum_{w} c_w \, n_w(a,b)

这里的符号与 4.1.2 节相同，只是 w 现在是“当前”的序列（已经做过若干次合并）。把 pair p 合并成新 token t 时，不含 p 的序列不变，它们的贡献也不变；含有 p 的序列 w 变成 w'，贡献从 c_w\,n_w 变成 c_w\,n_{w'}。所以只要对受影响的每个 w 做两件事：减去 c_w \cdot（w 的所有 pair），再加上 c_w \cdot（w' 的所有 pair），等式就继续成立。

还是用玩具语料手算第一步。合并 st 之后，newest（6 次）里的 pair 从 ne, ew, we, es, st 变成 ne, ew, we, e·st，widest（3 次）同理。于是 N(e,s) = 9 - 6 - 3 = 0，N(s,t) 也变成 0，两行从表里删掉；新出现的 N(e, st) = 6 + 3 = 9。ne 被减去 6 又加回 6，保持不变。low 和 lower 根本不用碰。

剩下的问题是：怎样不扫描全部序列，就找出“含有 p 的序列”？答案是再维护一张倒排索引（inverted index）pair_to_ids：每个 pair 对应一个集合，里面是含有它的所有序列。原书管它叫“缓存”（キャッシュ）。下图可以一步一步地看这两张表怎样变化。

日文注释的意思依次是：缓存；登记到缓存；没有 pair 时的处理；选出最频繁的 pair；从缓存里取出含有 best_pair 的 ID 序列；以后用不到了，删掉；只更新受影响的 ID 序列；删除旧的 ID 序列；加入新的 ID 序列；减去旧 pair 的频次；加上新 pair 的频次。

循环之前，先全量数一次 pair，同时建好倒排索引。循环里，挑出 best_pair 之后，从索引里取出含有它的序列集合 affected_ids，然后对其中每个序列做三件事：把出现次数挪到合并后的新元组上，减去旧序列的全部 pair，加上新序列的全部 pair。计数降到 0 的 pair 直接删掉，免得下一步的 max 还要看它。

有两个细节值得注意。第一，del pair_to_ids[best_pair] 之后，循环里减旧 pair 时会执行 pair_to_ids[best_pair].discard(...)，defaultdict 会悄悄新建一个空集合。这无害，只是留下一个空条目（验证 4.2-b 的最后一行数过：每个合并过的 pair 都留下了一个）。第二，affected_ids 这个集合对象在进入循环之前就已经从字典里摘了下来，所以循环中修改 pair_to_ids 不会影响正在遍历的集合。

想一想循环里写的是 ids_counts[tuple(new_ids)] = ids_count，用的是 = 而不是 +=。这样会不会覆盖掉别的序列的次数？
答案（先想一想再展开）

不会。两个不同的预分词，字节串一定不同；而合并只是把相邻的 id 换成一个新 id，序列拼出来的字节串不变。所以两个不同的序列永远不会合并成同一个元组，= 和 += 的效果相同。验证 4.2-b 里 len(ids_counts) 始终等于最初的个数，就是这个性质。

不一定。次数并列时，max 返回字典里先插入的那个，而两种实现往字典里插入 pair 的顺序不同。下面的框解释原因，验证 4.2-d 找出了第一个分歧点。

你可能会困惑为什么非要写 (pair_counts[pair], pair[0], pair[1]) 这样一个奇怪的 key？

第 1 章 1.3 节的专栏讨论过平票：两个 pair 次数相同时挑哪个。如果只写 max(pair_counts, key=pair_counts.get)，平票时 max 会返回字典里先插入的那个。在朴素版里这也许无所谓，但增量版不断地删除、重新插入 pair，字典里的顺序与全量重算时完全不同。于是同一个算法的两种实现，迟早会在某一次平票时分道扬镳：只要那一刻两个字典里并列者的先后顺序不同就够了。在下面的样本上，第 10 条合并就有并列，但两边碰巧挑了同一个；到第 13 条，两边挑的就不一样了。

要继续提速，就得换掉这次全表扫描。一个办法是用堆（heap），把“找最大值”从扫描全表变成取堆顶。麻烦在于计数每一步都在变，而 Python 的 heapq 不支持修改堆里的元素。

常用的绕法叫惰性删除（lazy deletion）：计数变了，不去改旧条目，而是把新的计数再压进堆里；取堆顶时，如果它记的计数与计数表里的对不上，说明它已经过期，扔掉再取下一个。还有一个小问题：Python 的 heapq 是最小堆，先弹出最小的。所以把三项都取负号：(-次数, -id0, -id1) 最小的那一项，就是 (次数, id0, id1) 最大的那一项，弹出顺序与原书的 key 完全一致。合并循环只有十几行：

# web/data/ch04/bpe_ext.py（本教程的扩展代码，不是原书代码）
def heap_merge_loop(ids_counts, num_merges):
    """train_bpe_heap 的合并循环部分（预分词之后）。ids_counts 会被修改。"""
    pair_counts, pair_to_ids = init_cache(ids_counts)
    heap = [(-c, -a, -b) for (a, b), c in pair_counts.items()]
    heapq.heapify(heap)
    merge_rules = {}
    for step in range(num_merges):
        while heap and pair_counts.get((-heap[0][1], -heap[0][2])) != -heap[0][0]:
            heapq.heappop(heap)                              # 过期条目：这个 pair 的计数已经变了
        if not heap:
            break
        _, a, b = heap[0]
        best_pair = (-a, -b)
        merge_rules[best_pair] = 256 + step
        changed = set()
        apply_merge(ids_counts, pair_counts, pair_to_ids, best_pair, 256 + step, changed)
        for pair in changed:
            if pair in pair_counts:
                heapq.heappush(heap, (-pair_counts[pair], -pair[0], -pair[1]))
    return merge_rules

open(file_path) 没有指定编码，Python 会用操作系统的默认编码。简体中文 Windows 的默认编码是 GBK（cp936），读 TinyStories 的验证集时会抛出 UnicodeDecodeError，位置是 position 30846（从 0 数起）。那里是右弯引号 ”，UTF-8 编码是 e2 80 9d，后面跟着句号 2e。GBK 每次读两个字节：它先把 e2 80 读成了汉字“鈥”，剩下的 9d 后面跟着 2e，凑不成合法的字符。弯引号、破折号、省略号的 UTF-8 编码都以 e2 80 开头，所以在中文 Windows 上看到“鈥”这样的乱码，往往就是它们被当成 GBK 读了。纯 ASCII 的 TinyCodes 不会触发这个问题，所以第 1 章一直没有暴露出来。解决办法是打开 Python 的 UTF-8 模式：运行前设置环境变量 PYTHONUTF8=1，或者用 python -X utf8 启动（Python 文档）；也可以在 open 里写明 encoding="utf-8"。从 Python 3.15 起，UTF-8 模式默认开启（PEP 686），本章实验用的 3.12 还不是。

4.3.2 内存消耗的原因

那么，为什么一个 100 MiB 的文件会吃掉 660 MiB 内存呢？罪魁祸首是 CPython 存储字符串的方式。CPython 不是给每个字符固定分配几个字节，而是看整个字符串里最宽的那个字符：最宽的字符不超过 U+00FF（ASCII 和西欧字母），每个字符占 1 字节；最宽的字符在 U+0100 到 U+FFFF 之间，每个字符占 2 字节；只要出现一个 U+FFFF 以上的字符（比如 emoji），整个字符串的每个字符都占 4 字节。这个规则来自 PEP 393。

4.3.3 部分读取文件

一次只读一小块，切在哪里呢？不能随便切。如果切点落在一个单词中间，比如把 " little" 切成 " lit" 和 "tle"，预分词的结果就变了，学出来的合并规则也会跟着变。安全的切点是 <|endoftext|>：它把故事彼此隔开，训练时本来就要先按它切开（第 1 章 1.5 节）。

find_chunk_boundaries 做的就是这件事。它先把文件按字节数等分，再把每个内部切点向后挪到最近的一个 <|endoftext|> 的开头：

日文注释的意思依次是：以二进制模式打开文件；取得文件大小；按等间距计算各块的起点；最后加上文件末尾；从边界往后预读的字节数；调整边界的位置（寻找结束 token）；从边界的估计位置开始；读一个缓冲区大小的数据；到达文件末尾时；在读到的数据里查找结束 token；找到了，就把那个位置作为新的边界；没找到，就移到下一个缓冲区的位置；去掉重复、排序后返回。

设文件大小为 S、块数为 k。初始切点是 0, \lfloor S/k \rfloor, 2\lfloor S/k \rfloor, \dots, (k-1)\lfloor S/k \rfloor，最后补上文件末尾 S。对每个内部切点，从那里开始每次读 4,096 字节，在读到的数据里找 <|endoftext|>；找到了，切点就挪到它的第一个字节；读到文件末尾也没找到，切点就是 S。最后 sorted(set(...)) 去掉重复的切点。

所以边界数最多是“<|endoftext|> 的个数 + 2”（加的 2 是文件的首尾）。块数越多，切点越密，边界数越接近这个上限，但并不单调。原因有两个。第一，两个 <|endoftext|> 之间如果没有落下任何初始切点，后一个就不会成为边界，比一块还短的故事就可能这样被跳过；块数比故事数还多时，好几个初始切点也会挪到同一个 <|endoftext|> 上。第二，\lfloor S/k \rfloor 是向下取整的，块数很大时，最后一个初始切点 (k-1)\lfloor S/k \rfloor 离文件末尾可能还有一大段，这一段里的 <|endoftext|> 除了第一个，都不会成为边界。

注意二进制读取会看到 \r：Windows 的 CRLF 陷阱

Windows 上的 Git 常常设置了 core.autocrlf=true（《Pro Git》就建议 Windows 用户这样设置，本章所用的机器也是如此），检出文件时会把文本文件的换行从 \n 改成 \r\n。用文本模式读文件（open(path).read()，4.1、4.2 节的写法），Python 会把 \r\n 还原成 \n，问题被悄悄掩盖了；而 4.3 节起改用二进制模式读取，\r 原样保留。在 CRLF 版的 TinyCodes 上训练，第 2 条合并规则就会变成 \r\n，从这一条起，规则的顺序就与官方的 merge_rules.pkl 对不上了。规避的办法是克隆前执行 git config --global core.autocrlf false，或者在仓库里加一个 .gitattributes，写上 *.txt -text。TinyStories 是直接下载的，不受影响。

4.4 改进 BPE 训练④：并行化

4.4.1 Python 中的并行处理

预分词的各个块之间互不依赖，天然适合并行。不过在 CPython 的默认构建里，多线程帮不上纯 Python 计算的忙：同一时刻只有一个线程能执行 Python 字节码，这把锁叫作 GIL（全局解释器锁）。从 3.13 起，CPython 也可以编译成不带 GIL 的“自由线程”版本（见同一词条），但原书和本章用的都是默认构建。所以原书用的是多进程：multiprocessing.Pool 启动若干个独立的 Python 进程，把任务分给它们。

from multiprocessing import Pool

def square(x):            # 工作函数：必须定义在模块的顶层
    return x * x

if __name__ == "__main__":
    with Pool(processes=4) as pool:
        print(list(pool.imap(square, range(8))))   # [0, 1, 4, 9, 16, 25, 36, 49]

pool.imap 把任务逐个分给空闲的进程，并按任务的顺序返回结果。这段代码里有两处写法必不可少。

第一，if __name__ == "__main__": 必须写。原因在子进程的启动方式（start method）。Windows 只有一种启动方式，叫 spawn：启动一个全新的 Python 解释器，再把主模块重新导入一遍。macOS 默认也是 spawn。Linux 过去默认用 fork，直接复制父进程；从 Python 3.14 起改成了 forkserver（Python 文档）。

spawn 和 forkserver 都要求主模块能被新的解释器安全地导入（文档的编程指南专门讲了这一条）。没有守卫的话，子进程一导入主模块，就又去创建自己的进程池，结果报出 RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase，错误信息里还附上了正确的写法。父进程那边则不断补上新的子进程，一直等下去。

第二，工作函数必须能被子进程“找到”。spawn 出来的子进程只认识能 import 到的函数。如果工作函数定义在 python -c 的命令行代码里，子进程会报 AttributeError: Can't get attribute 'square' on <module '__main__' …>；如果脚本是从标准输入喂给 Python 的（python - < script.py），子进程连主模块都读不到，报的是 OSError: [Errno 22] Invalid argument: '…<stdin>'。更糟的是，父进程的 pool.imap 会一直等下去，既不报错也不退出。

本地验证spawn 的四种失败：python -c 里的工作函数（Process 立即失败，Pool 一直挂起）、从标准输入喂脚本、脚本没有 __main__ 守卫

答案（先想一想再展开）

(20.8 + 92.1) / (5.6 + 92.1) \approx 1.15 倍。进程再多，也超不过 (20.8 + 92.1) / 92.1 \approx 1.23 倍：合并循环占了八成多的时间，并行帮不上它。

你可能会困惑开了 8 个进程，为什么总时间没快 8 倍？

这是并行最常见的落差。这就像包饺子：八个人一起擀皮、包馅，快得很，可锅只有一口，煮饺子的时间一分钟也省不下来。

严格地讲，设可以并行的部分单进程要 T_p 秒，只能串行的部分要 T_s 秒，用 n 个进程，启动等开销为 T_o，总加速比是

S(n) = \frac{T_p + T_s}{T_p / n + T_s + T_o}

这里，T_p 是预分词，T_s 是合并循环。心算一个例子：T_p = 12 秒、T_s = 30 秒、不计开销，8 个进程时总时间是 1.5 + 30 = 31.5 秒，加速比只有 42 / 31.5 \approx 1.33。进程再多也超不过 42 / 30 = 1.4。这就是 Amdahl 定律（Amdahl's law，见维基百科，2026 年 10 月查看）：加速比的上限由串行部分决定。

你可能会困惑这些数字是谁定的：num_processes=8、num_chunks=64、4096……

vocab_size（04 的入口是 10,000）：决定学几条规则，10000 - 257 = 9743。训练是贪心的，词表只决定在哪一步停下，前面的规则不变（验证 4.2-a）。

num_processes（04 的入口传 8；storybot 的 train_bpe 默认 8，encode_file 默认 4）：进程池里有几个进程。超过物理核心数（本机 8 个）之后，预分词几乎不再变快（上面的表）。

num_chunks（04、07 默认 64；storybot 的 train_bpe 默认 8）：文件切成几块。块多，任务分得匀，每块也小、省内存。只切 8 块的话，2.2 GB 的训练集每块约 278 MB，每个子进程都要把一整块读进内存。

buffer_size（4,096，写死在 find_chunk_boundaries 里）：找边界时每次向后读多少字节。它只影响找边界的快慢；跨在两次读取之间的 <|endoftext|> 会被跳过，结果仍然正确（验证 4.3-d）。

你可能会困惑词表是 10,000，为什么合并规则只有 9,743 条？

因为词表里还有两类不是“学”出来的 token。最开始的 256 个 token 就是 256 个字节值，任何文本都能用它们表示；最后还要留 1 个位置给特殊 token <|endoftext|>。所以合并规则的条数是 10000 - 256 - 1 = 9743，特殊 token 的 id 是 256 + 9743 = 9999。第 1 章 1.3 节还没有特殊 token，那时写的是 vocab_size - 256，1.5 节起才变成 - 257。

4.6.2 高效的编码处理

改进的想法是：不再按规则表从头试到尾，而是只看序列里现有的相邻对，从中挑出优先级最高的那个先合并，重复这个过程，直到没有可合并的对为止。规则的优先级就是它的 id：id 越小，学到得越早，优先级越高。这就像按号叫人：第 1 章的做法是把 9,743 个号码从头喊到尾，看谁在场；新做法是先看在场的有谁，直接叫其中号码最小的那位。

  1. 第 r 条规则把 pair (a, b) 合并成 256 + r。a 和 b 在第 r 步之前就已经存在，所以 a, b < 256 + r：每条规则只用到比自己“老”的 token。

4.6.3 实现改进版

ch04/06_encode_optimize.py 只改写了 _encode_text，原书用 ❶–❹ 标出了四个步骤：

日文注释的意思依次是：不存在的 pair 优先级最低；取得当前的 pair（❶）；找出优先级最高的 pair（❷）；确认还能不能合并（❸）；执行合并（❹）。

❶ 用 count_pairs 取出当前序列里所有的相邻对；❷ 用 min 找出优先级最高的那个，不在规则表里的 pair 优先级记为无穷大；❸ 如果最好的那个也不在规则表里，说明已经没有可合并的了，结束；❹ 否则执行合并，回到 ❶。每一轮的代价与序列长度成正比，而与规则条数无关：查优先级只是一次字典查找。

轮数呢？每合并一轮，序列至少短一个 token，所以一个 L 字节的预分词最多合并 L-1 轮。' accomplishment' 最后合成了一个 token，正好是 15 - 1 = 14 轮（验证 4.6-a）。轮数和每一轮的代价都与 L 成正比，所以最坏是 L^2 量级。TinyStories 验证集里最长的预分词只有 23 个字节（4.1.1 节的本地验证），这不成问题；一长串没有空格的字母会被预分词成一个很长的词，代价就按 L^2 增长。

4.7.3 用 np.memmap 高效写出

所有块都编码完之后，主进程先把各块的 token 数加起来，得到总长度，然后创建一个这么长的 np.memmap，再按块的顺序把缓存文件逐个拷进去：

日文注释的意思依次是：计算 token 总数；创建 memmap 文件；分批把缓存写进 memmap。

np.memmap 是内存映射文件（memory-mapped file）上的数组：用起来与普通的 NumPy 数组一样，数据却直接存在磁盘文件里，操作系统按需把用到的部分调入内存。主进程因此不必同时拿着全部 token。第 6 章（6.5.1 节）读数据时也是同一个办法：np.memmap(data_path, dtype=np.uint16, mode='r')，训练时随机取窗口，用到哪里读哪里。

为什么是 uint16？它能表示 0 到 65,535 的整数，StoryBot 的词表是 10,000，第 III 部 WebBot 的是 50,000，都装得下。每个 token 只占 2 字节：验证集的 5,465,873 个 token 正好是 10,931,746 字节。换成 Python 列表，每个元素是一个 8 字节的指针（64 位 Python）；整数对象本身是共享的，同一个 id 不管出现多少次，都指向同一个对象。实测下来，列表约 8.6 字节/token（多出的 0.6 是列表预留的空位），是 uint16 的 4 倍多。

@pytest.mark.slow
def test_uv_run_uses_the_project_of_the_working_directory(tmp_path):

    a script inside third_party/dlfs6 gets the tutorial's environment (NumPy 2, as measured in this chapter); after

    book = (DLFS6 / "pyproject.toml").read_text(encoding="utf-8")
    assert '"torch>=2.5.0"' in book and '"numpy>=1.24.0,<2.0.0"' in book
    assert "workspace" not in (ROOT / "pyproject.toml").read_text(encoding="utf-8")   # the submodule is its own project

        head = (DLFS6 / rel).read_text(encoding="utf-8").splitlines()[:2]
        assert head == ["import os, sys", "os.chdir(os.path.join(os.path.dirname(os.path.abspath(__file__)), '..'))"]
    outer = tmp_path / "tutorial"
    inner = outer / "third_party" / "book"
    inner.mkdir(parents=True)
    for d, name in [(outer, "tutorial"), (inner, "book")]:
        (d / "pyproject.toml").write_text(f'[project]\nname = "{name}"\nversion = "0.1.0"\nrequires-python = ">=3.11"\n'
                                          'dependencies = []\n', encoding="utf-8")
    (inner / "probe.py").write_text("import sys\nprint(sys.prefix)\n", encoding="utf-8")
    env = {k: v for k, v in os.environ.items() if k not in ("VIRTUAL_ENV", "UV_PROJECT_ENVIRONMENT")}

    def prefix(cwd, script):
        proc = subprocess.run([uv, "run", "--offline", "python", script], cwd=cwd, env=env, capture_output=True,
                              text=True, encoding="utf-8", timeout=300)
        if proc.returncode != 0:
            pytest.skip(f"uv could not create a probe environment offline: {proc.stderr[-300:]}")
        return os.path.normcase(os.path.realpath(proc.stdout.strip()))

小结

本章没有发明任何新算法。BPE 还是第 1 章的那个 BPE，学到的规则一条不差，编出来的 id 一个不差；变的只是实现。训练这一侧，我们先把重复的预分词折叠成计数（4.1），再只更新受影响的序列（4.2），然后按 <|endoftext|> 分块读取、省下内存（4.3），最后把预分词分给多个进程（4.4）。编码这一侧，我们把“逐条试遍所有规则”换成“只合并现有 pair 中优先级最高的”（4.6），再分块并行编码、用 np.memmap 写成 uint16 的二进制文件（4.7）。放到完整的 2.2 GB 训练集上，原书的 04 在本机 9.4 分钟就学完了 9,743 条规则，07 再用 37.8 分钟把训练集编码成 5.4 亿个 token，两者的输出都与官方发布的文件完全相同。

每一步改进都遵循同一个顺序：先证明结果不变，再测量快了多少，最后问剩下的时间花在哪里。这个顺序把我们一路带到了 Amdahl 定律面前：增量更新之后，合并循环里 96.5% 的时间都花在 max() 的全表扫描上，而这一部分无法靠多开进程来加速。第 III 部会回到这个问题：第 7 章先定位瓶颈，再用 Rust/C++ 重写。

本章所学的内容：

  • 去重之后按次数加权计数，与逐次出现计数完全相等；配合全序的平票规则，去重版学出的规则与朴素版逐项相同。（验证 4.1-c、验证 4.1-e）
  • 增量更新只修改含有被合并 pair 的序列，计数表每一步都等于全量重算的结果；前提是 max 的 key 是全序，只按次数比较时，平票由字典顺序决定，增量版与全量版会分道扬镳。（验证 4.2-b、验证 4.2-d）
  • 整读大文件时，一个 emoji 就能让字符串的内存变成 4 倍；按 <|endoftext|> 分块读取，计数与整读完全相同，切在词中间则不然。（验证 4.3-a、验证 4.3-e）
  • 并行只能加速预分词，合并循环始终串行，总加速比受 Amdahl 定律限制。（验证 4.4-a）
  • StoryBot 的词表是 256 个字节 + 9,743 条合并规则 + 1 个特殊 token；在故事上平均每个 token 4.18 字节，是 CodeBot 分词器的两倍多，而“你好，世界”的 15 个字节只能各自成为一个 token。（验证 4.5-a、验证 4.5-b、验证 4.5-c）
  • 按优先级（id）合并的编码器与逐条套用全部规则的编码器逐 token 相同，因为每条规则只用到比自己早的 token。（验证 4.6-a、验证 4.6-b）
  • 在 <|endoftext|> 处分块编码再拼接等于整体编码；uint16 每个 token 占 2 字节，上限 65,535，astype 越界时会悄悄回绕。（验证 4.7-a、验证 4.7-c、验证 4.7-e）
