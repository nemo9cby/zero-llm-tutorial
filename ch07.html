分词器【挑战篇】：WebBot 的分词器

第 III 部的语料换成了 11.9 GB 的网页文章。分词器的算法还是第 4 章那一套，规模却大到让我们不得不先找出瓶颈、再请 Rust 帮忙。原书在这一章只给提示，我们给每一节都配上了能亲手运行的最小验证。

第 4 章，我们用去重、增量更新、分块读取和多进程四步改造了 BPE 的训练，又把编码改成了按优先级合并、分块并行，每一步都先证明了结果与朴素版逐项相同。2.2 GB 的 TinyStories 因此不再是问题，StoryBot 的分词器顺利训练完成。

第 III 部的主角 WebBot 要读的是 OpenWebText（下文简称 OWT）：为了复现 GPT-2 的训练数据而从网上收集的英文文章。原书用的是它的一个样本，训练集有 11.9 GB，内容也从儿童故事换成了五花八门的网页。词表随之扩大到 50,000，与 GPT-2 的 50,257 相当。原书的第 7 章只有两个十几行的脚本，分词器的代码全部复用第 4 章的 storybot/tokenizer.py。第 III 部是“挑战篇”，原书在这里只给方向和要点，不再给出详细的实现步骤。

本章照样沿着原书的六个小节往下走。先看 WebBot 的分词器：作者在 11.9 GB 上训练好的规则，我们在小样本上重现它的开头（7.1）。再找出训练慢在哪里（7.2），用 Rust 写成的实现替换最慢的部分（7.3）；然后讨论怎样添加特殊 token（7.4），看看 BPE 以外的几种分词器（7.5），最后问一个更根本的问题：能不能干脆不要分词器（7.6）？

每个分词器都在自己“读过”的那类文字上最省 token。CodeBot 只读过 Python 代码：换行连同缩进的前三个空格，在它那里是一个 token（第四个空格按 GPT-2 的预分词规则归了后面的 print），WebBot 却要拆成 4 个。StoryBot 只读过儿童故事，在故事上与 WebBot 打成平手。WebBot 读过各式各样的网页，在网页、网址和 emoji 上都是三者中最少的。词表有多大、在什么语料上训练，这两件事一起决定了一段文字会变成多少个 token。

WebBot 把缩进拆得这么碎，是因为它的词表里一个只由空白组成的 token 也没有（StoryBot 有 5 个，CodeBot 有 17 个）。原因在预分词。OWT 的文章几乎不缩进，连续的空白主要是段落之间的 \n\n；而 GPT-2 的规则 \s+(?!\S) 总要把最后一个空白留给后面的词，\n\n 于是被切成了两个 \n。两个空白很少出现在同一个预分词里，自然学不出把它们合并的规则（验证 7.1-d 在 100 KB 的样本上数了一数）。

真正干活的是第 4 章的 train_bpe。与第 4 章的训练脚本（ch04/04_bpe_parallel.py）相比，改的是词表大小（50,000）和训练数据（webbot/owt_train.txt）。num_chunks=64 则与第 4 章那个脚本里的默认值相同：函数整理进 storybot/tokenizer.py 时，默认值改成了 8，所以这里要显式地传 64。

词表为什么是 50,000

词表越大，常见的词越有机会整个变成一个 token，同一段文字切出来的 token 就越少。那么，词表是不是越大越好呢？不是。模型的 embedding 和输出层都要为每个 token 准备一个向量。WebBot 的向量是 768 维，而且这两个矩阵不共享（第 5 章 5.3 节），所以与词表有关的参数一共是

2Vd = 2 \times 50000 \times 768 = 76{,}800{,}000

这里，V 是词表大小，d 是向量的维数。在 WebBot 的全部参数里，这占多大比例？

验证 7.1-bWebBot 的参数有一半在词表上
def gpt_params(vocab, d=768, n_layer=12, n_head=12, n_kv_head=4, ff=2048):
    """webbot/model.py 的 GPT 各部分参数量（无 bias，RMSNorm 只有缩放）。"""
    head = d // n_head
    # W_q、W_o 各 d×d；GQA：K、V 只有 4 个头，所以 W_k、W_v 只有 W_q 的三分之一
    attn = 2 * d * n_head * head + 2 * d * n_kv_head * head
    block = attn + 3 * d * ff + 2 * d     # SwiGLU 的三个矩阵 + 两个 RMSNorm
    return {"embed": vocab * d, "blocks": n_layer * block, "norm": d,
            "unembed": d * vocab}

def vocab_share(q):                       # 与词表有关的参数所占的比例
    return (q["embed"] + q["unembed"]) / sum(q.values())

p = gpt_params(50_000)
total = sum(p.values())
print(f"WebBot 的参数: {total:,}")
print(f"  embedding 层 + 输出层: {p['embed'] + p['unembed']:,}"
      f"（{vocab_share(p):.1%}）")
print(f"  12 个 Transformer 块:  {p['blocks']:,}")
for v in [1_000, 10_000, 50_000, 100_000]:
    share = vocab_share(gpt_params(v))
    print(f"词表 {v:>7,} 时，与词表有关的参数占 {share:.0%}")
assert total == 152_316_672
assert round(vocab_share(gpt_params(100_000)), 2) == 0.67      # 三分之二

瓶颈会随规模变大

设第 t 步时有 P_t 种不同的 pair，max 每比较一个 pair 平均花 c 秒，那么合并循环里挑 pair 的总时间约为

T_{\max} \approx c \sum_{t=1}^{M} P_t

这里，M 是要学的规则条数。P_t 会越来越大：每学一条规则，就多出一个新 token，它和左右邻居又组成了新的 pair。拿 1 MB 的样本来说，第 1 步只有 1,942 种 pair，第 1,743 步已经有 22,233 种，1,743 步合计要比较约 2,956 万次。按下面实测表的 1 MB 一行，平均每比较一个 pair 约 0.31 微秒（这就是 c，由同一次测量反推），所以

T_{\max} \approx 0.31\times10^{-6}\ \text{秒} \times 2.956\times10^{7} \approx 9.3\ \text{秒}

占了这次训练 11.7 秒里的八成。每次比较不到 1 微秒，架不住次数多。

你可能会困惑profile 说 max() 占了八成时间，是 Python 的 max 太慢吗？

直觉上会怪罪 max 本身。验证 7.2-b 的表里，max 的“自身”时间也确实有 10 秒，比 lambda 的 7.7 秒还多。不过，这 10 秒主要是调用 lambda 的代价：每看一个 pair，max 都要为这个 Python 函数准备一次调用，再比较它返回的三元组，cProfile 把这些都记在了 max 的名下。max 本身是用 C 写的，只要不回头调用 Python 函数，遍历一个字典是很快的。

那为什么不换一个 key 呢？清单里被注释掉的第 159 行 max(pair_counts, key=pair_counts.get)，key 是 C 写的 dict.get，不用调用 Python 函数。它的问题在平票：几个 pair 次数相同时，它选字典里先遇到的那个，结果取决于各个 pair 进入字典的先后（第 1 章 1.3 节 的专栏）。第 160 行的 lambda 返回 (次数, id0, id1)，平票时的选择只取决于 pair 本身。还有一种写法两全其美：max(zip(counts.values(), counts)) 比较的正是同样的 (次数, (id0, id1))，而全程不调用 Python 函数。下面的验证单元比较这三种写法。

以上，我们找到了两个瓶颈：训练时 max() 对全部 pair 的反复扫描，以及编码时逐个预分词的合并循环。两者都是“Python 解释器里的小循环被执行了千万次”。下一节，我们把这些循环交给编译型语言。

7.3 用 Rust/C++ 加速

上一节的两个瓶颈有一个共同点：每次操作本身很简单（比较两个数、查一次字典），慢在 Python 解释器执行每一步都有固定的开销。用 Rust 或 C++ 这样的编译型语言重写，这份开销几乎就消失了。另外还有一个好处：它们可以在一个进程里开多个线程真正并行地计算（Python 的线程做不到这一点，原因是第 4 章 4.4 节 讲过的 GIL），不必像第 4 章那样启动多个进程，也不必在进程之间来回序列化数据。

好消息是，这样的实现已经有了，不必自己写。OpenAI 的 tiktoken 就是一个核心用 Rust 写成的 BPE 编码器（openai/tiktoken）。它的 Rust 核心只负责编码和解码，不负责训练；合并规则可以由我们自己提供。

这里有一个容易忽略的细节。原书的合并规则是“哪两个 token 相邻就合并”，优先级挂在 id 对 (a, b) 上；tiktoken 的规则是“哪两段相邻、拼起来的字节串在表里就合并”，优先级挂在拼出来的字节串上。tiktoken 附带的教学版实现 _educational.py 第 99 行写的就是 mergeable_ranks.get(pair[0] + pair[1])，Rust 核心（src/lib.rs）也是按字节切片查表（都是 0.14.0 版，2026 年 10 月查看）。这两种说法一定等价吗？不一定。下面人为构造三条规则，同一个词就能编出不同的结果：

def encode_pair_rank(word, merges):
    """原书的做法：优先级挂在“哪两个 token 相邻”上。"""
    rank = {pair: r for r, pair in enumerate(merges)}
    parts = list(word)
    while True:
        cands = [(rank[p], i) for i, p in enumerate(zip(parts, parts[1:]))
                 if p in rank]
        if not cands:
            return parts
        r, i = min(cands)
        parts[i:i + 2] = [parts[i] + parts[i + 1]]

def encode_bytes_rank(word, merges):
    """tiktoken 的做法：优先级挂在“拼起来的字节串”上。"""
    rank = {a + b: r for r, (a, b) in enumerate(merges)}
    parts = list(word)
    while True:
        cands = [(rank[a + b], i)
                 for i, (a, b) in enumerate(zip(parts, parts[1:]))
                 if a + b in rank]
        if not cands:
            return parts
        r, i = min(cands)
        parts[i:i + 2] = [parts[i] + parts[i + 1]]

两种做法都先合并了 bc（第 0 条）。接下来，原书只认 (ab, c) 这一对，眼前却是 (a, bc)，于是停下；tiktoken 只看 a 和 bc 拼起来是 abc，而 abc 在表里，于是继续合并。这三条规则在真实的训练里不会出现：bc 先学会之后，语料里就不再有 ab 后面紧跟单独一个 c 的情形，第 2 条规则根本学不出来。tiktoken 的作者在源码注释里也写明了这一点：只要按现在的方式训练 BPE，两种做法就等价；把合并的优先级和 token id 脱钩，就会破坏它（src/lib.rs 第 145–147 行）。

def test_every_webbot_token_encodes_to_itself(sb, tok):
    """Both ranking rules (DLFS6: by id pair, tiktoken: by merged bytes) rebuild every token from its bytes."""
    rules = tok.merge_rules
    by_bytes = {tok.id_to_bytes[i]: i for i in range(tok.end_token_id)}

    def pair_rank(bs):
        ids = list(bs)
        while len(ids) > 1:
            best = min(sb.count_pairs(ids), key=lambda p: rules.get(p, float("inf")))
            if best not in rules:
                break
            ids = sb.merge(ids, best, rules[best])
        return ids

    def bytes_rank(bs):
        parts = [bytes([x]) for x in bs]
        while True:
            cands = [(by_bytes[a + c], i) for i, (a, c) in enumerate(zip(parts, parts[1:])) if a + c in by_bytes]
            if not cands:
                return [by_bytes[p] for p in parts]
            _, i = min(cands)
            parts[i:i + 2] = [parts[i] + parts[i + 1]]

    for i in range(256, tok.end_token_id):
        bs = tok.id_to_bytes[i]
        assert pair_rank(bs) == [i] == bytes_rank(bs), i

因为多进程能做的，tiktoken 也能做，而且做得更省。原书的 8 个进程，每一个都还在按上表第一行的速度编码，理想情况下合起来也只是它的 8 倍；而 tiktoken 一个线程就是它的几十倍。单线程的速度比较的是“每份计算本身有多快”，并行度是在这之上再乘的系数。此外，多进程还要付出启动进程、序列化数据的代价（第 4 章 4.4 节），线程则没有。

tokenizers 快，有两层原因。第一层是算法。它的训练器用一个堆维护 pair 的次数：计数变了不去改堆里的旧条目，弹出堆顶时如果发现它记的次数已经过期，就换成当前的次数放回去；每一步只更新含有这个 pair 的词（trainer.rs 第 491–522 行，0.23.3 版，2026 年 10 月查看）。这与第 4 章 4.2 节 扩展里的惰性删除堆是同一个思路，所以规则从 1,743 条增加到 9,743 条，它的耗时只从 1.4 秒增加到 1.8 秒。第二层才是语言和并行。同样的堆用纯 Python 写，在这份样本上比原书快 2.6 倍，从 1,743 条到 9,743 条也只多花了约三成时间；tokenizers 用 Rust 写成，合并时还用多个线程同时处理各个词（同一文件第 563–566 行），又快了约 10 倍（两次测量时机器的负载不同，只看量级）。

C++ 方面，Google 的 SentencePiece 是一个用 C++ 写成的分词器库（7.5 节会介绍它）。无论 Rust 还是 C++，第一步都是把被执行千万次的小循环从解释器里拿出来；成熟的实现往往还同时换掉了数据结构。

7.4 添加特殊 token

到目前为止，WebBot 只有一个特殊 token：<|endoftext|>，表示“一篇文章到此结束”。可是，要把模型做成对话助手，还需要更多的记号，比如“下面是用户说的话”“下面是助手的回答”“这一轮到此为止”。第 3 章的 SFT 用 Alpaca 模板里的 ### Instruction:、### Response: 这样的普通文字来充当这些记号（ch03/03_sft.py）。有的对话模型更进一步，给每个记号分配一个专门的特殊 token。例如 Llama 3 用 <|start_header_id|> 和 <|end_header_id|> 把角色名（system、user、assistant）括起来，用 <|eot_id|> 表示一轮对话结束（Llama 3 的提示格式说明，2026 年 10 月查看）。这样，正文里碰巧出现的同样文字就不会被当成模板的一部分。

先回顾原书是怎样处理那唯一一个特殊 token 的：

re.split 的模式带着捕获组，切开之后特殊 token 本身也保留在结果里（第 1 章 1.5 节）。是特殊 token，就直接输出它的 id；否则照常做预分词和 BPE。要再添加几个特殊 token，需要改动五个地方：

  1. 分配 id。接在 49,999 后面，依次是 50,000、50,001……，不打乱已有的 id。它们仍然小于 65,535，uint16 的 .bin 文件不受影响。
  2. 编码。切分时要同时认出所有特殊 token。
  3. 训练。如果要重新训练合并规则，训练前也要按所有特殊 token 切开语料，保证没有任何合并规则跨过它们，原书对 <|endoftext|> 就是这样做的。只给已有的分词器添加新记号时，规则不用动。
  4. 模型。embedding 和输出层各要多出相应的行。
  5. 解码。id_to_bytes 里要加上新 id 对应的字节，vocab_size 随之增加；否则原书的 decode 遇到新 id 会抛出 KeyError（下面的验证单元试了一下）。

第 2 条和第 4 条各有一个容易踩的坑，我们逐个来看。

长的优先

假设我们加了一个特殊 token <|endoftext|><|endoftext|>（这正是 CS336 测试里用的例子）。它的开头恰好是另一个特殊 token。把它们拼成一个正则 A|B 去切分时，Python 的正则是按顺序尝试的：只要 A 能匹配，就不会再看 B，哪怕 B 更长。所以，写模式之前要先把特殊 token 按长度从长到短排好：

给模型添加新的行

新 token 在 embedding 和输出层里的那一行该初始化成什么？一种简单而稳妥的做法是取已有各行的平均（Hewitt, 2021，2026 年 10 月查看）。logit 是隐藏向量与输出层各行的内积，内积对行是线性的，所以新 token 的 logit 恰好等于旧 logits 的平均；旧 token 的 logits 则完全不变。

那么，新 token 一开始分到多少概率呢？设旧的 logits 是 z_1, \dots, z_V，平均值是 \bar z。由 Jensen 不等式，e^{\bar z} 不超过各个 e^{z_i} 的平均，所以

p_{\text{新}} = \frac{e^{\bar z}}{\sum_{i=1}^{V} e^{z_i} + e^{\bar z}} \le \frac{1}{V+1}

这里，V 是旧词表的大小，右边正是均匀分布的那一份。也就是说，无论隐藏向量是什么，新 token 的概率都不会超过“均匀乱猜”；词表越大，这个上限越小。V = 1{,}000 时上限是 1/1001 \approx 0.000999：

验证 7.4-b新 token 的那一行取已有各行的平均：它的 logit 等于旧 logits 的平均，概率不超过 1/(V+1)

你可能会困惑特殊 token 不就是一串字符吗？用户输入它，为什么会出问题？

直觉上，<|endoftext|> 只是 13 个普通字符，和 hello 没有什么两样。区别在于编码器怎样对待它：把它当作特殊 token，它就是词表里唯一的那个 id，模型在训练中只在文章的边界见过它；当作普通文字，它就是 <、|、end……这样一串普通的 token，与正文里的其他符号没有区别。

所以，分词器需要两种模式。处理我们自己拼出来的模板时，特殊 token 要变成特殊 id；处理用户的输入时，要把它们当作普通文字，或者干脆拒绝。tiktoken 的默认行为是后者：encode 遇到文本里的特殊 token 会直接报错，要么用 allowed_special 明确允许，要么改用 encode_ordinary 把它当普通文字。原书的 encode 没有这个开关，图 7-1 里的复选框演示的就是这两种模式的区别。

7.5 其他分词器

到目前为止，三台机器人用的都是同一种分词器：字节级 BPE。它不是唯一的选择。这一节介绍另外几种常见的分词器，每一种都写一个最小的 Python 版本，看看它们与 BPE 的区别在哪里。

WordPiece

WordPiece 是 BERT 使用的分词器。它和 BPE 一样从小单位出发、逐步合并，但有两处不同。

第一处在编码。WordPiece 不记录合并的顺序，只保留一张词表；编码一个单词时，从左往右，每次取词表里能匹配上的最长的一段。单词中间的片段带 ## 前缀，表示“紧接着前面，不是新词的开头”。BERT 源码的注释里有一个例子：unaffable 被切成 un、##aff、##able（google-research/bert 的 tokenization.py）。如果某一段在词表里一个也找不到，整个单词就变成 [UNK]：

验证 7.5-bWordPiece 的编码：每次取最长的一段
def wordpiece(word, vocab, unk="[UNK]"):
    """BERT 的 WordPiece 编码：从左往右，每次取词表里最长的一段。
    词中间的片段带 ## 前缀。"""
    pieces, start = [], 0
    while start < len(word):
        end = len(word)
        while end > start:
            sub = word[start:end] if start == 0 else "##" + word[start:end]
            if sub in vocab:
                break
            end -= 1
        else:              # 一段也匹配不上：整个单词变成 [UNK]
            return [unk]
        pieces.append(sub)
        start = end
    return pieces

第二处在训练。BPE 每次合并出现次数最多的 pair；WordPiece 则按下面的得分挑选：

\mathrm{score}(a, b) = \frac{n(ab)}{n(a)\, n(b)}

这里，n(ab) 是 a、b 相邻出现的次数，n(a)、n(b) 是它们各自出现的次数。两个片段如果各自都很常见，它们挨在一起的次数多，可能只是因为它们本身就多，所以得分并不高；两个片段都不太常见、却几乎总是一起出现，得分才高。Google 没有公开 WordPiece 训练算法的实现，上面的公式取自 Hugging Face 课程的 WordPiece 一节（2026 年 10 月查看）。我们用课程里的玩具语料手算一遍：hug 10 次、pug 5 次、pun 12 次、bun 4 次、hugs 5 次。##u 一共出现 36 次，##g 20 次，##s 5 次；##u ##g 相邻 20 次，得分是 20 / (36 \times 20) = 1/36；##g ##s 相邻只有 5 次，得分却是 5 / (20 \times 5) = 1/20，是最高的。

Unigram 与 Viterbi 算法

Unigram 分词器（Kudo, 2018）换了一个角度：不记录合并的顺序，而是给词表里的每个 token 一个概率 p(x)，并且假设各个 token 互相独立。这里的 unigram 与《深度学习进阶：自然语言处理》4.2 节负采样里的 unigram 分布是同一个意思：不看上下文，只看每个单位自己出现的概率。一个单词切成 x_1, x_2, \dots, x_m 的概率是

P(x_1, \dots, x_m) = \prod_{i=1}^{m} p(x_i)

分词器要在所有可能的切法里，找出这个乘积最大的那一种。切法的数量随单词长度指数增长，不能一一枚举。好在有动态规划：设 \mathrm{best}[i] 是前 i 个字符的最优切法的对数概率，那么

\mathrm{best}[i] = \max_{j < i} \Big( \mathrm{best}[j] + \log p(w_{j:i}) \Big)

这里，w_{j:i} 是第 j+1 到第 i 个字符组成的片段，也就是 Python 的 word[j:i]（左闭右开），只考虑在词表里的片段；起点是 \mathrm{best}[0] = 0（空串的概率是 1）。这就是 Viterbi 算法。它像导航软件规划路线：到每个路口，只记住到达这里的最好走法，不必把所有路线都列出来。严格地讲，前 i 个字符的最优切法，最后一段一定是某个 w_{j:i}，而它前面的部分也必须是前 j 个字符的最优切法（否则换成更好的，整体就更好），所以记住每个 \mathrm{best}[j] 就够了。

训练则反过来：从一张很大的初始词表出发（比如语料里所有的子串），反复删掉一批 token，直到词表缩小到想要的大小。每次删的是“删了之后对语料的总概率影响最小”的那些；单个字符永远不删，保证任何单词都能切（Hugging Face 课程的 Unigram 一节有完整的推演）。Kudo 的论文在每一轮删除之前，还用 EM 算法反复重估各个 token 的概率；简单起见，下面的例子只按出现次数算一次概率。

我们用上面的玩具语料，把各个单词的全部子串当作初始词表（单词本身除外；不过 hug 是 hugs 的子串，所以仍在词表里），按出现次数算概率。手算 hug 的四种切法：hug 出现 15 次，概率 15/210 \approx 0.0714；hu + g 是 \frac{15}{210} \times \frac{20}{210} \approx 0.0068；h + ug 也是 0.0068；h + u + g 最小。最优的是不切。换成 Viterbi 的递推，是从左往右填三个格子：

  • \mathrm{best}[1] = \log p(\texttt{h})；
  • \mathrm{best}[2] = \max\big(\mathrm{best}[1] + \log p(\texttt{u}),\ \log p(\texttt{hu})\big)；
  • \mathrm{best}[3] = \max\big(\mathrm{best}[2] + \log p(\texttt{g}),\ \mathrm{best}[1] + \log p(\texttt{ug}),\ \mathrm{best}[0] + \log p(\texttt{hug})\big) = \log\frac{15}{210}。

import math
from itertools import product
sub_freq = Counter()
for w, c in corpus.items():
    for i in range(len(w)):
        for j in range(i + 1, len(w) + 1):
            sub_freq[w[i:j]] += c

vocab_u = {w[i:j] for w in corpus for i in range(len(w))
           for j in range(i + 1, len(w) + 1) if (i, j) != (0, len(w))}
total = sum(sub_freq[s] for s in vocab_u)
logp = {s: math.log(sub_freq[s] / total) for s in vocab_u}
print(f"初始词表: {len(vocab_u)} 个子串，频次总和 {total}")

def viterbi(word):
    """返回 (最优切法, best)：best[i] 是前 i 个字符最优切法的对数概率。"""
    best, back = [0.0] + [-math.inf] * len(word), [0] * (len(word) + 1)
    for i in range(1, len(word) + 1):
        for j in range(i):
            piece = word[j:i]                  # 第 j+1 到第 i 个字符
            if piece in logp and best[j] + logp[piece] > best[i]:
                # 记住最后一段从哪里开始
                best[i], back[i] = best[j] + logp[piece], j
    pieces, i = [], len(word)
    while i > 0:
        pieces.insert(0, word[back[i]:i])
        i = back[i]
    return pieces, best

def all_segmentations(word):
    """把每一种切法都列出来（只用来核对）。"""
    for cuts in product([0, 1], repeat=len(word) - 1):
        pieces, start = [], 0
        for k, cut in enumerate(cuts, 1):
            if cut:
                pieces.append(word[start:k])
                start = k
        pieces.append(word[start:])
        if all(p in logp for p in pieces):
            yield pieces, sum(logp[p] for p in pieces)

SentencePiece

SentencePiece（Kudo & Richardson, 2018）不是一种新算法，而是一个用 C++ 写成的分词器库。它实现了 Unigram 和 BPE 两种算法（另有 word、char 两种简单模式），默认用 Unigram（google/sentencepiece 的训练选项，2026 年 10 月查看）。它的特点是不需要针对某种语言的预分词器：空格被换成一个普通的符号 ▁（U+2581），之后片段的边界由几条与语言无关的规则决定。默认设置下有三条：片段不跨过空格，▁ 只出现在片段的开头；片段不跨过不同的文字，例如拉丁字母与汉字；数字与其他字符分开（对应的选项是 split_by_whitespace、split_by_unicode_script、split_by_number）。解码时，只要把各段拼起来、再把 ▁ 换回空格即可，不需要任何与语言有关的规则：

严格地讲，SentencePiece 默认还会先对文字做 NFKC 规范化，并去掉多余的空格，所以还原出来的是规范化之后的文字；这两项都可以在训练时关掉（见它的 normalization 文档）。上面的 legal 也只是这些规则的简化版，只检查了 ▁ 的位置和拉丁字母与汉字的混用。

GPT-2 的预分词正则是为用空格分词的语言设计的：一整段没有空格的中文被当作一个预分词，在 BPE 看来就是一个很长的“单词”。SentencePiece 不假设文字用空格分词，同一套规则用在中文、日文和英文上，空格只是一个普通的 ▁，Kudo 和 Richardson 因此称它“与语言无关”。Llama 2 的分词器就是用 SentencePiece 实现的 BPE：词表 32k，数字拆成单个数位，词表里没有的 UTF-8 字符退回到字节（Touvron et al., 2023，2.2 节）。

小结：四种分词器

  • 字节级 BPE（三台机器人、GPT-2）：训练时反复合并次数最多的 pair，保存有顺序的合并规则；编码时按学到的顺序合并。没有不认识的字，最坏退回到字节。
  • WordPiece（BERT）：训练时反复合并得分最高的 pair，只保存词表；编码时每次取最长的一段。有一段匹配不上，整个词就变成 [UNK]。
  • Unigram（SentencePiece 默认用它）：从大词表出发逐步删除，保存词表和每个 token 的概率；编码时用 Viterbi 算法找概率最大的切法。见过的字符都能切，没见过的依实现而定。
  • 以单词为单位（《深度学习进阶》的 word2vec）：统计词频，保存词表；编码时查表。词表里没有的词变成 <unk>。

以上是 BPE 之外的几种分词器。它们的共同点是：都要先在语料上训练一张词表，而这张词表决定了模型看到的世界。下一节问一个更激进的问题：能不能不要这张表？

7.6 不用分词器的方法

分词器带来了不少麻烦。第一，它要单独训练，训练语料的偏好会被带进词表（图 7-1 里，CodeBot 和 StoryBot 对中文束手无策）。第二，它会产生“半个字符”的 token，单独解码不出完整的字符（图 7-1 里显示成 \xe2\x80 这样的字节）。第三，同一个词前面有没有空格、大小写是否相同，都会变成毫不相干的 id，模型只能从数据里慢慢学会它们是同一个词。后两点可以直接数一数：

最彻底的办法，是直接把字节交给模型：词表只有 256 个字节（再加特殊 token），不需要训练，没有不认识的字。这就是第 1 章 1.2 节的字节级分词器。它的代价，第 1 章也说过了：序列变长。现在我们可以精确地算一算，长了多少，又贵了多少。

设分词器平均每个 token 装 r 个字节。同一段文字，字节级模型的序列长度是 BPE 的 r 倍。Transformer 里与位置数成正比的部分（各层的矩阵乘法、KV cache）也变成 r 倍；Attention 要计算每两个位置之间的分数，与位置数的平方成正比，变成 r^2 倍。WebBot 在整个 OWT 训练集上的 r 可以由 7.1 节的两个文件算出来：11,920,511,059 字节的文字编码成了 2,649,004,800 个 token，r \approx 4.50，于是 r^2 \approx 20.2。

我们按 WebBot 的结构来算这笔账：12 层，每层的向量是 768 维（验证 7.1-b 里用过这些数字）。有一处要提醒：WebBot 的 12 个 query 头共用 4 组 K、V，这叫 GQA（第 5 章 5.5 节 提过，8.3 节 细讲），所以每个位置的 KV cache 只有 12 KiB。下面算一算，WebBot 的 1,024 个位置能看到多少文字，字节级模型要看到同样多的文字又需要多少计算。

回到字节级模型。它的账已经算清了：好处是 7.6 节开头那三条麻烦全都没有了，代价是更长的序列和成倍的计算。它也消除不了语言之间的差别：UTF-8 里一个汉字占 3 个字节，同样 23 个字的示例“中文”，字节级模型要 69 个位置，WebBot 只要 54 个（验证 7.0-a）。所以，研究者们努力的方向，是把这份计算省回来。目前有几条思路。

  • 直接用字节训练标准的 Transformer。 ByT5（Xue et al., 2021）只对 T5 的结构做了很小的改动，就直接在 UTF-8 字节上训练，并且报告字节级模型可以与 token 级的对手相当。代价正是本节算出的序列更长、计算更多，论文专门分析了参数量、训练 FLOPs 和推理速度上的取舍。
  • 把字节分组成 patch。 MegaByte（Yu et al., 2023）把字节序列切成固定长度的 patch，用一个小的局部模型处理 patch 内部的字节、一个大的全局模型处理 patch 之间的关系。大模型看到的位置数因此缩小为原来的几分之一，可以建模上百万字节长的序列。
  • 按预测难度动态分组。 Byte Latent Transformer（BLT，Pagnoni et al., 2024）根据“下一个字节有多难预测”（熵）来决定 patch 的边界：容易预测的地方用长 patch，难预测的地方用短 patch，把计算花在真正需要的地方。论文报告，它是第一个在大规模上（参数到 8B）赶上基于分词器的 LLM 的字节级模型。

后两种方法其实是把“分词”搬进了模型内部：先把字节分组，再交给大模型。MegaByte 按固定长度分组；BLT 更进一步，用一个小的字节级模型估计每个位置的预测难度，由它决定在哪里分组，不再需要一张事先训练好的词表。

你可能会困惑分词器不同的两个模型，loss 能直接比较吗？

直觉上，loss 越低越好，两个模型的 loss 可以直接比较。可是交叉熵 loss 的单位是“每个 token 多少 nats”（nats 是什么单位，见第 2 章 2.4 节），而两个分词器的 token 不一样大：StoryBot 的一个 token 平均装 4.1 个字节，字节级模型的一个 token 只有 1 个字节。这就像比较两辆车的油耗，一辆报“每箱油跑多远”，另一辆报“每升跑多远”，得先换成同一个单位。严格地讲，要换算成与分词器无关的单位：每字节多少比特（bits per byte）。

\text{bits per byte} = \frac{\ell}{\ln 2 \cdot r}

这里，\ell 是每个 token 的 loss（nats），除以 \ln 2 把 nats 换成 bits（1 nat 约 1.4427 bits），再除以每个 token 的字节数 r。举个例子：我们在 H100 上实际跑出的 StoryBot（运行记录 storybot-h100），验证 loss 是 1.3036 nats/token，每个 token 4.117 字节，换算下来约 0.46 bits/byte；CS336 给 TinyStories 定的目标 loss 1.45，对应约 0.51。一个对 256 个字节一律均匀乱猜的字节级模型，是 \ln 256 / \ln 2 = 8 bits/byte。

当然，换算只消除了分词器的影响，消除不了数据的差别。StoryBot 读的是用语简单的儿童故事，WebBot 读的是五花八门的网页，后者本来就更难预测。差多少呢？可以借一个通用的压缩器粗略地量一量：压缩器也是在预测下一个字节，越好预测，压得越小。同样取 1 MB，lzma 把 TinyStories 压到每字节约 1.8 比特，把 OWT 只压到约 2.6 比特。同样是 TinyStories，StoryBot 这个“压缩器”只要 0.46 比特，约是 lzma 的四分之一。所以，即使换算成 bits per byte，WebBot 的数字也不能拿来和 StoryBot 比，只能和同样在 OWT 上评估的模型比。BLT 这类研究在比较字节级模型和基于分词器的模型时，用的正是 bits per byte。

以上就是不用分词器的几种思路。字节级模型省掉了分词器的种种麻烦，却要为更长的序列付出代价；MegaByte、BLT 这样的方法，正是在设法把这份代价省回来。

小结

本章拿到了 WebBot 的分词器（词表 50,000），并在小样本上重现了它的训练。算法和代码都是第 4 章的，新的问题全部来自规模。我们先用一个 100 KB 的样本在浏览器里重现了官方规则的前 10 个 token，在本机上用 1 MB 的样本逐条重现了前 15 条；又把官方的 owt_valid.bin 整个解码、整个重新编码，确认它就是这份规则的产物。接着，我们用 cProfile 找到了训练的瓶颈：max() 每一步都把全部 pair 比较一遍，pair 的种数随规模增长，单是 290 MB 的验证集，光这一行就要约 2 小时。编码这一侧，九成以上的预分词本身就是一个 token，整词查表就能省下大部分工作。

然后，我们把编码交给了 Rust 写的 tiktoken、把训练交给了 Rust 写的 tokenizers。在比较速度之前，先核对了结果：两种“优先级”的定义在原理上并不等价，在我们核对过的全部文本和全部 49,743 个 token 上却逐个 id 相同；tokenizers 学到的 1,743 个 token 也与原书相同，只是从一次平票开始顺序不同。最后三节讨论了添加特殊 token 的要点，介绍了 WordPiece、Unigram 和 SentencePiece，并且算了一笔账：不用分词器，同样的文字要多付出数倍的计算。

本章所学的内容：

  • WebBot 的词表 = 256 个字节 + 49,743 条合并规则 + 1 个特殊 token。词表越大，每个 token 装的字节越多，但增长越来越慢；embedding 和输出层的参数却随词表线性增长，在 WebBot 的 1.52 亿个参数中占了一半。（验证 7.1-a、验证 7.1-b、验证 7.1-d）
  • 最先学到的合并规则由最常见的字节对决定，小样本就能重现：100 KB 重现了官方的前 10 个 token，1 MB 逐条重现了前 15 条规则。（验证 7.1-e、验证 7.1-f）
  • 原书的训练循环里，max() 连同它的 key 函数（每一步对每种 pair 调用一次）占了八成时间；pair 的种数随步数和语料增长，290 MB 的验证集上要比较 233.9 亿次，全量训练要以小时计。（验证 7.2-a、验证 7.2-b、验证 7.2-d）
  • tiktoken 按“拼出来的字节串”排优先级，原书按“id 对”，两者在原理上不等价；装上 WebBot 的规则，在我们核对过的全部文本（包括整个验证集）上却逐个 id 相同。tiktoken 单线程的编码速度是原书的几十倍。（验证 7.3-a、验证 7.3-b、验证 7.3-c）
  • 多个特殊 token 要按长度从长到短匹配；用户输入里的特殊 token 不能直接编码成特殊 id。（验证 7.4-a、验证 7.4-c）
  • WordPiece 按 n(ab)/(n(a)\,n(b)) 挑选合并，编码时每次取最长的一段；Unigram 给每个 token 一个概率，用 Viterbi 算法找概率最大的切法，结果与穷举一致。（验证 7.5-c、验证 7.5-d）
  • 字节级模型没有分词器，但同样的文字需要 4.5 倍的位置、约 20 倍的 Attention 计算；不同分词器的 loss 要换算成 bits per byte 才能比较。（验证 7.6-b、验证 7.6-d）

分词器准备好了：OWT 变成了 26 亿个 token，按验证集的平均 4.50 字节/token 计，WebBot 的 1,024 个位置大约能装下 4.6 KB 的英文。下一章，我们来搭建读这些 token 的模型。它有 1.5 亿个参数，那么，这个规模是怎么定下来的呢？
