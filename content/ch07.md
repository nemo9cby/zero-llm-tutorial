第 4 章，我们用去重、增量更新、分块读取和多进程四步改造了 BPE 的训练，又把编码改成了按优先级合并、分块并行，每一步都先证明了结果与朴素版逐项相同。2.2 GB 的 TinyStories 因此不再是问题，StoryBot 的分词器顺利训练完成。

第 III 部的主角 WebBot 要读的是 OpenWebText（下文简称 OWT）：为了复现 GPT-2 的训练数据而从网上收集的英文文章。原书用的是它的一个样本，训练集有 11.9 GB，内容也从儿童故事换成了五花八门的网页。词表随之扩大到 50,000，与 GPT-2 的 50,257 相当。原书的第 7 章只有两个十几行的脚本，分词器的代码全部复用第 4 章的 `storybot/tokenizer.py`。第 III 部是“挑战篇”，原书在这里只给方向和要点，不再给出详细的实现步骤。

本章照样沿着原书的六个小节往下走。先训练并检查 WebBot 的分词器（7.1），再找出它慢在哪里（7.2），用 Rust 写成的实现替换最慢的部分（7.3）；然后讨论怎样添加特殊 token（7.4），看看 BPE 以外的几种分词器（7.5），最后问一个更根本的问题：能不能干脆不要分词器（7.6）？原书只给提示的地方，我们都补上了可以亲手运行的最小验证。

每个分词器都在自己“读过”的那类文字上最省 token。CodeBot 只读过 Python 代码：换行连同缩进的前三个空格，在它那里是一个 token（第四个空格按 GPT-2 的预分词规则归了后面的 ` print`），WebBot 却要拆成 4 个。StoryBot 只读过儿童故事，在故事上与 WebBot 打成平手。WebBot 读过各式各样的网页，在网页、网址和 emoji 上都是三者中最少的。词表有多大、在什么语料上训练，这两件事一起决定了一段文字会变成多少个 token。

### 词表为什么是 50,000

词表越大，常见的词越有机会整个变成一个 token，同一段文字切出来的 token 就越少。那么，词表是不是越大越好呢？不是。模型的输入端（embedding）和输出端（unembedding）都要为每个 token 准备一个向量。WebBot 的向量是 768 维，而且这两个矩阵不共享（第 5 章 [5.3 节](ch05.html#s5-3)），所以与词表有关的参数一共是

$$2Vd = 2 \times 50000 \times 768 = 76{,}800{,}000$$

这里，$V$ 是词表大小，$d$ 是向量的维数。在 WebBot 的全部参数里，这占多大比例？

```verify id=7.1-b title="WebBot 的参数有一半在词表上"
def gpt_params(vocab, d=768, n_layer=12, n_head=12, n_kv_head=4, ff=2048):
    """webbot/model.py 的 GPT 各部分参数量（没有 bias；RMSNorm 只有一个缩放向量）。"""
    head = d // n_head
    attn = d * n_head * head + 2 * d * n_kv_head * head + n_head * head * d   # W_q, W_k, W_v, W_o
    block = attn + 3 * d * ff + 2 * d                                         # SwiGLU 的三个矩阵 + 两个 RMSNorm
    return {"embed": vocab * d, "blocks": n_layer * block, "norm": d, "unembed": d * vocab}

p = gpt_params(50_000)
total = sum(p.values())
print(f"WebBot 的参数: {total:,}")
print(f"  embedding + unembedding: {p['embed'] + p['unembed']:,}（{(p['embed'] + p['unembed']) / total:.1%}）")
print(f"  12 个 Transformer 块:     {p['blocks']:,}")
for v in [1_000, 10_000, 50_000, 100_000]:
    q = gpt_params(v)
    print(f"词表 {v:>7,} 时，与词表有关的参数占 {(q['embed'] + q['unembed']) / sum(q.values()):.0%}")
assert total == 152_316_672
```

1.5 亿个参数里，有一半在“记住每个 token 长什么样”。词表再翻一倍，这个比例就到了三分之二。

```localcheck verify/test_ch07.py::test_webbot_parameter_counts title="用原书的 webbot.model.GPT 数参数（meta 设备，不分配内存）"
```

参数是随词表线性增长的，换来的压缩又有多少呢？这里可以利用 BPE 的一个性质：合并规则是按顺序学出来的，只用前 $k$ 条，同样是一个合法的分词器，词表大小是 $256 + k + 1$。我们用前 0、743、9,743 和 49,743 条规则（恰好对应字节级、CodeBot、StoryBot 和 WebBot 的词表大小）去编码同一段 OWT 文本。

文本从哪里来呢？OWT 的验证集原文有 290 MB，好在作者在 Hugging Face 上也放了编码好的 `owt_valid.bin`，只有 129 MB。BPE 的解码是无损的，把官方的 token 解码回去，得到的正是分词器当初看到的原文（本节末尾会在本机上核对整个文件）。我们截取它开头的 24 篇文章，约 100 KB：

```verify id=7.1-c title="样本：官方 owt_valid.bin 的开头，解码回文字" files=data/ch07/owt_head.bin
import numpy as np
head_ids = np.fromfile("data/ch07/owt_head.bin", dtype=np.uint16).tolist()   # 官方的 token，uint16
sample = tok.decode(head_ids)
n_bytes = len(sample.encode("utf-8"))
print(f"{len(head_ids):,} 个官方 token → {n_bytes:,} 字节，{sample.count('<|endoftext|>')} 篇文章")
print(f"平均每个 token {n_bytes / len(head_ids):.2f} 字节")
print(repr(sample[:64]))
assert len(head_ids) == 21_427 and sample.count("<|endoftext|>") == 24 and sample.endswith("<|endoftext|>")
```

```verify id=7.1-d title="词表越大，每个 token 装的字节越多，但增长越来越慢"
from collections import Counter
docs = sample.split("<|endoftext|>")
pieces = Counter(p for d in docs for p in sbt.pretokenize(d))     # 不同的预分词 → 出现次数
ratio = []
for k in [0, 743, 9_743, 49_743]:
    t = sbt.BPETokenizer(dict(list(rules.items())[:k]))           # 只用前 k 条规则
    seg = {p: t._encode_text(p) for p in pieces}                  # 每种预分词只编码一次
    n_tok = sum(len(seg[p]) * c for p, c in pieces.items()) + len(docs) - 1
    ratio.append(n_bytes / n_tok)
    print(f"词表 {256 + k + 1:>6,}: {n_tok:>7,} 个 token，平均每个 {ratio[-1]:.2f} 字节")
full_seg = seg                                                    # 全部规则的编码结果，7.2 节和 7.3 节还要用
assert ratio == sorted(ratio) and ratio[3] - ratio[2] < ratio[2] - ratio[1]   # 越来越多，但增长越来越慢
```

词表从 1,000 扩大到 10,000，每个 token 多装了约 1.5 个字节；再扩大 5 倍到 50,000，只多装了约 0.7 个字节。收益越来越小，参数却线性增长。50,000 是在两者之间取的一个折中，与 GPT-2 的选择相当。顺带一提，在 1 MB 的 OWT 文本上，GPT-2 的分词器（tiktoken 的 `gpt2`，50,257 个 id）平均每个 token 4.52 字节，WebBot 是 4.61 字节，略多一点，毕竟它就是在 OWT 上训练的。

### 缩小版的训练

完整的训练要先下载 11.9 GB 的文本，再跑上好几个小时（7.2 节会估算具体要多久）。好在有一个现象，让我们可以先在小规模上验证：最先学到的合并规则，只取决于最常见的那几对字节，而这些在任何一段足够长的英文网页里都差不多。

我们在浏览器里用原书的 `train_bpe`，在这 100 KB 的样本上学 10 条规则。浏览器里开不了进程，所以我们把模块里的 `Pool` 换成一个按顺序执行的替身。`Pool` 在 `train_bpe` 里只负责并行地数预分词，最后把各块的计数加起来，按顺序做，结果完全相同（本节的本地验证用真正的进程池对照过）。

::: think 只用 100 KB 的样本学 10 条规则，学到的会和官方在 11.9 GB 上学到的前 10 条一样吗？顺序呢？
:::
::: answer
学到的 10 个 token 一样，顺序有几处不同。下面的验证单元给出实际结果；顺序为什么会变，本节稍后用一对次数几乎相同的 pair 来解释。
:::

```verify id=7.1-e title="在 100 KB 的样本上学 10 条规则：与官方最先学到的 10 个 token 相同"
class SerialPool:                     # 替身：接口与 multiprocessing.Pool 相同，但只在当前进程里按顺序执行
    def __init__(self, processes=None): pass
    def __enter__(self): return self
    def __exit__(self, *exc): return False
    def imap(self, func, items): return map(func, items)

import os, tempfile
sbt.Pool = SerialPool
path = os.path.join(tempfile.mkdtemp(), "owt_head.txt")
with open(path, "wb") as f:                                    # train_bpe 读的是文件
    f.write(sample.encode("utf-8"))
mine = sbt.train_bpe(path, 256 + 10 + 1, num_chunks=4)         # 原书的 train_bpe，只学 10 条
learned = [sbt.BPETokenizer(mine).id_to_bytes[i].decode() for i in mine.values()]
official = [show(i) for i in range(256, 266)]
print("样本上学到的:", learned)
print("官方的前 10 个:", official)
print("作为集合是否相同:", set(learned) == set(official))
assert set(learned) == set(official)
```

顺序有几处不同（比如 ` a` 和 `he` 换了位置），但学到的 10 个 token 与官方在 11.9 GB 上最先学到的 10 个完全相同。样本再大一些，连顺序也开始吻合。我们在本机上用越来越大的 OWT 样本各学 1,743 条规则，数一数与官方规则逐条相同（同样的 pair、同样的 id、同样的顺序）的前缀有多长：

```verify id=7.1-f title="缩小版训练：样本越大，与官方逐条相同的前缀越长（本机实测）" files=data/ch07/bench.json
bench = json.load(open("data/ch07/bench.json", encoding="utf-8"))
print(f"测量于 {bench['date']}，{bench['machine']['cpu']}，Python {bench['machine']['python']}")
print("每个样本学 1,743 条规则，与官方的规则比较：")

assert prefix == sorted(prefix) and prefix[2] == 15
```

只用 1 MB，前 15 条规则就与在 11.9 GB 上学到的一字不差；用 8 MB 时是前 20 条。1 MB 到 4 MB 都停在第 16 条，原因是 `an` 和 `is` 这两个 pair 的次数几乎一样：在 1 MB 的样本里，`an` 只比 `is` 多 3.7%，4 MB 时只多 0.2%，而全量语料选了 `is`。次数这样接近的两个 pair，样本稍有不同就会改变它们的先后。

## 7.2 定位瓶颈

“训练要好几个小时”，这只是一句印象。时间到底花在哪里？是读文件、预分词，还是合并循环？在动手优化之前，我们先测量。这件事有现成的工具：Python 自带的**性能剖析器**（profiler）`cProfile`，它记录每个函数被调用了多少次、花了多少时间。

浏览器里的 Python 也带着 `cProfile`。我们在 100 KB 的样本上让 `train_bpe` 学 60 条规则，看看哪个函数被调用得最多：

调用次数最多的不是 `count_pairs`，也不是 `merge`，而是第 160 行的一个 `lambda`。它是什么呢？

第 160 行用 `max` 挑出出现次数最多的 pair，`lambda` 是 `max` 的 key 函数。`max` 要把字典里的每一个 pair 都拿来比一比，所以每学一条规则，这个 `lambda` 就要被调用“当前 pair 的种数”那么多次。60 步加起来，就是上面的十几万次。

调用次数多，不等于花的时间多。时间要在本机上测，浏览器里的计时并不可靠。下面是本机上用 `cProfile` 剖析 1 MB 样本、学 1,743 条规则的结果（`verify/_ch07_record.py` 记录在 `bench.json` 里）：

### 瓶颈会随规模变大

设第 $t$ 步时有 $P_t$ 种不同的 pair，`max` 每比较一个 pair 平均花 $c$ 秒，那么合并循环里挑 pair 的总时间约为

$$T_{\max} \approx c \sum_{t=1}^{M} P_t$$

这里，$M$ 是要学的规则条数。$P_t$ 会越来越大：每学一条规则，就多出一个新 token，它和左右邻居又组成了新的 pair。拿 1 MB 的样本来说，第 1 步只有 1,942 种 pair，第 1,743 步已经有 22,233 种，1,743 步合计要比较约 2,956 万次。每次比较不到 1 微秒，但架不住次数多：下面实测表的 1 MB 一行，列出了这部分的实际耗时。

语料越大，不同的词越多，$P_t$ 也越大。下面是本机在 6 个样本上的实测：

```verify id=7.2-c title="样本越大，每一步要比较的 pair 越多（本机实测）"
rows_s = bench["train"]["scaling"]
print("学 1,743 条规则的总时间 = max() + 其余：")
for r in rows_s:
    print(f"{r['bytes'] / 1e6:>5.2f} MB  {r['wall_s']:>4.1f} 秒 = max() {r['max_s']:>4.1f} 秒（{r['max_share']:.0%}）"
          f"+ 其余 {r['wall_s'] - r['max_s']:>4.1f} 秒")
print("每一步要比较的 pair 种数（第 1 步 → 第 1,743 步）、比较的总次数、平均每次的耗时：")
for r in rows_s:
    print(f"{r['bytes'] / 1e6:>5.2f} MB  {r['pairs_first_step']:>5,} → {r['pairs_last_step']:>6,} 种，"
          f"共 {r['pairs_scanned'] / 1e4:>5,.0f} 万次，每次 {r['ns_per_pair']} 纳秒")
growth = [b["pairs_last_step"] / a["pairs_last_step"] for a, b in zip(rows_s, rows_s[1:])]
print("样本每大一倍，最后一步的 pair 种数变成原来的:", ", ".join(f"{g:.2f}" for g in growth), "倍")

```

样本每大一倍，最后一步的 pair 种数大约多三成。这与第 4 章 [4.1 节](ch04.html#s4-1) 的 Heaps 定律是同一类规律：新的组合一直在出现，只是越来越慢。另外，`max()` 所占的比例在大样本上有所下降，那是因为预分词和更新计数这些“其余”的工作也随语料变多了，而不是 `max` 变快了。

那么，放到 11.9 GB、49,743 条规则的全量训练上，要花多少时间呢？我们只能外推，下面把每个假设都写清楚：

```verify id=7.2-d title="粗略外推：全量训练光挑 pair 就要以小时计"
import math
x = np.log([r["bytes"] for r in rows_s])
y = np.log([r["pairs_last_step"] for r in rows_s])
slope = np.polyfit(x, y, 1)[0]                       # pair 种数 ∝ (语料字节数)^slope
last = rows_s[-1]                                    # 8 MB 的样本
p_full = last["pairs_last_step"] * (11_920_511_059 / last["bytes"]) ** slope
hours = 49_743 * p_full * last["ns_per_pair"] * 1e-9 / 3600
print(f"pair 种数大约与语料大小的 {slope:.2f} 次方成正比")
print(f"外推到 11.9 GB：学到第 1,743 条时约有 {p_full:,.0f} 种 pair")
print(f"假设 49,743 步每步都比较这么多，每次 {last['ns_per_pair']} 纳秒：约 {hours:.0f} 小时")
assert 0.3 < slope < 0.5 and hours > 3
```

这个估计有两处偏乐观。第一，$P_t$ 在第 1,743 步之后还会继续增长，我们却假设它停住了。第二，它只算了 `max` 的时间，没算合并本身。另一方面，每次比较的耗时取决于机器，测量时这台机器很忙（`bench.json` 的 `machine` 一栏记录了当时的负载），换一台空闲的机器会快一些。但量级不会错：是“小时”，不是“分钟”。CS336 给 OWT 训练 32K 词表的时间上限定在 12 小时，也是这个量级。

::: confusion profile 说 max() 占了八成时间，是 Python 的 max 太慢吗？
直觉上会怪罪 `max` 本身。其实 `max` 是用 C 写的内置函数，遍历一个字典非常快；慢的是它每看一个 pair，都要回头调用一次 Python 写的 `lambda`：建一个三元组、查一次字典、再比较大小。一次调用只要零点几微秒，可是在 1 MB 的样本上，它要被调用近 3,000 万次。

所以，把 key 写得更短不会有本质的改变；真正的问题是“每一步都把所有 pair 重新看一遍”。解决的办法有两条路。一条是换数据结构：用堆（优先队列）维护 pair 的次数，每一步只处理变化了的那几个，第 4 章 [4.2 节](ch04.html#s4-2) 的扩展就是这样做的。另一条是换语言：让这个循环在编译型语言里运行，省掉解释器在每一次比较上的开销。下一节走的是第二条路。
:::

### 编码这一侧

训练只做一次，编码却要处理全部 11.9 GB。第 4 章的编码器（`_encode_text`）对每个预分词反复执行“数 pair、挑优先级最高的、合并”，直到没有可合并的为止：

在本机上，原书的 `encode` 每秒只能编码零点几 MB；而单是用 Python 的 `regex` 做预分词，速度就是它的 20 倍左右（7.3 节的表）。可见时间几乎都花在 `_encode_text` 的循环里。可是，这个循环真的有必要吗？我们数一数样本里的预分词，有多少编码之后本来就是 1 个 token：


既然九成以上的预分词本身就在词表里，那么先查一次表，查到就直接输出它的 id，查不到再走合并循环，就能省掉大部分工作。这个“整词查表”的捷径在纯 Python 里就能把编码提速数倍（7.3 节的表）。不过，它与原书的编码器结果相同，需要一个前提：词表里的每个 token，拿它自己的字节去编码，得到的都是它自己。这一点我们在 7.3 节验证。

以上，我们找到了两个瓶颈：训练时 `max()` 对全部 pair 的反复扫描，以及编码时逐个预分词的合并循环。两者都是“Python 解释器里的小循环被执行了千万次”。下一节，我们把这些循环交给编译型语言。

## 7.3 用 Rust/C++ 加速

上一节的两个瓶颈有一个共同点：每次操作本身很简单（比较两个数、查一次字典），慢在 Python 解释器执行每一步都有固定的开销。用 Rust 或 C++ 这样的编译型语言重写，这份开销几乎就消失了。另外还有一个好处：它们可以在一个进程里开多个线程真正并行地计算，不必像第 4 章那样启动多个进程，也不必在进程之间来回序列化数据。

好消息是，这样的实现已经有了，不必自己写。OpenAI 的 **tiktoken** 就是一个核心用 Rust 写成的 BPE 编码器（[openai/tiktoken](https://github.com/openai/tiktoken)）。它的 Rust 核心只负责编码和解码，不负责训练；合并规则可以由我们自己提供。

### 把 WebBot 的规则装进 tiktoken

tiktoken 要的是一张“字节串 → 优先级”的表，以及预分词用的正则。WebBot 的 token id 恰好就是学到的顺序，可以直接当优先级用：

```python
import tiktoken
from storybot.tokenizer import BPETokenizer

tok = BPETokenizer.load_from("webbot/merge_rules.pkl")
ranks = {tok.id_to_bytes[i]: i for i in range(tok.end_token_id)}   # 字节串 -> id（id 越小，学得越早）
PATTERN = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""
enc = tiktoken.Encoding("webbot-50k", pat_str=PATTERN, mergeable_ranks=ranks,
                        special_tokens={"<|endoftext|>": tok.end_token_id})
enc.encode(text, allowed_special="all")     # 与 tok.encode(text) 逐个相同（见下文的验证）
```

这里有一个容易忽略的细节。原书的合并规则是“哪两个 token 相邻就合并”，优先级挂在 id 对 $(a, b)$ 上；tiktoken 的规则是“哪两段相邻、拼起来的字节串在表里就合并”，优先级挂在拼出来的字节串上。tiktoken 附带的教学版实现 `_educational.py` 里写的就是 `mergeable_ranks.get(pair[0] + pair[1])`，Rust 核心也是按字节切片查表。这两种说法一定等价吗？不一定。下面人为构造三条规则，同一个词就能编出不同的结果：

```verify id=7.3-a title="两种优先级的定义，在人为构造的规则上会给出不同结果"
def encode_pair_rank(word, merges):
    """原书的做法：优先级挂在“哪两个 token 相邻”上。"""
    rank = {pair: r for r, pair in enumerate(merges)}
    parts = list(word)
    while True:
        cands = [(rank[p], i) for i, p in enumerate(zip(parts, parts[1:])) if p in rank]
        if not cands:
            return parts
        r, i = min(cands)
        parts[i:i + 2] = [parts[i] + parts[i + 1]]

def encode_bytes_rank(word, merges):
    """tiktoken 的做法：优先级挂在“拼起来的字节串”上。"""
    rank = {a + b: r for r, (a, b) in enumerate(merges)}
    parts = list(word)
    while True:
        cands = [(rank[a + b], i) for i, (a, b) in enumerate(zip(parts, parts[1:])) if a + b in rank]
        if not cands:
            return parts
        r, i = min(cands)
        parts[i:i + 2] = [parts[i] + parts[i + 1]]

toy = [("b", "c"), ("a", "b"), ("ab", "c")]          # 第 0、1、2 条规则
print("按 id 对排优先级:", encode_pair_rank("abc", toy))
print("按字节串排优先级:", encode_bytes_rank("abc", toy))
assert encode_pair_rank("abc", toy) == ["a", "bc"] and encode_bytes_rank("abc", toy) == ["abc"]
```

两种做法都先合并了 `bc`（第 0 条）。接下来，原书只认 `(ab, c)` 这一对，眼前却是 `(a, bc)`，于是停下；tiktoken 只看 `a` 和 `bc` 拼起来是 `abc`，而 `abc` 在表里，于是继续合并。这三条规则在真实的训练里不会出现：`bc` 先学会之后，语料里就不再有 `ab` 后面紧跟单独一个 `c` 的情形，第 2 条规则根本学不出来。可是，“真实的规则里不会出现”只是一个论证，不是证明。把 WebBot 的规则交给 tiktoken 之前，我们要用数据核对一遍。先在样本的全部预分词上比较两种做法：

```verify id=7.3-b title="WebBot 的规则：样本里的每个预分词，两种做法的结果都相同"
rank_bytes = {tok.id_to_bytes[a] + tok.id_to_bytes[b]: r for r, (a, b) in enumerate(rules)}

def bytes_rank_ids(piece):
    """tiktoken 的合并方式，用 Python 写出来；输出 token id。"""
    parts = [bytes([b]) for b in piece.encode("utf-8")]
    while True:
        cands = [(rank_bytes[a + b], i) for i, (a, b) in enumerate(zip(parts, parts[1:])) if a + b in rank_bytes]
        if not cands:
            break
        r, i = min(cands)
        parts[i:i + 2] = [parts[i] + parts[i + 1]]
    return [256 + rank_bytes[p] if len(p) > 1 else p[0] for p in parts]

same = sum(bytes_rank_ids(p) == full_seg[p] for p in pieces)       # full_seg[p] = 原书的 tok._encode_text(p)
print(f"样本里 {len(pieces):,} 种不同的预分词，两种做法结果相同的: {same:,}")
assert same == len(pieces)
```

### 快了多少

结果相同，才有资格比较速度。下面是本机在同一段 2 MB 的 OWT 文本上的实测，每一行都与原书的输出逐个 id 核对过：

这张表可以分三层来读。第一行到第二行，语言没变，只是加了整词查表，就快了数倍，这是算法的功劳。第三行是一个上限：只要预分词还用 Python 的 `regex` 来做，纯 Python 的编码器就不可能比它更快。tiktoken 连预分词也在 Rust 里完成，单线程就越过了这个上限，开 8 个线程还能更快。按这个速度，编码整个 11.9 GB 训练集的时间，从“小时”变成了“分钟”。

## 7.4 添加特殊 token

到目前为止，WebBot 只有一个特殊 token：`<|endoftext|>`，表示“一篇文章到此结束”。可是，要把模型做成对话助手，还需要更多的记号，比如“下面是用户说的话”“下面是助手的回答”“这一轮到此为止”。第 3 章的 SFT 用 Alpaca 模板里的 `### Instruction:`、`### Response:` 这样的普通文字来充当这些记号（`ch03/03_sft.py`）。许多对话模型更进一步，给每个记号分配一个专门的特殊 token，这样，正文里碰巧出现的同样文字就不会被当成模板的一部分。

先回顾原书是怎样处理那唯一一个特殊 token 的：

```listing storybot/tokenizer.py#L234-L251
```

`re.split` 的模式带着捕获组，切开之后特殊 token 本身也保留在结果里（第 1 章 [1.5 节](ch01.html#s1-5)）。是特殊 token，就直接输出它的 id；否则照常做预分词和 BPE。要再添加几个特殊 token，需要改动四个地方：

1. **分配 id**。接在 49,999 后面，依次是 50,000、50,001……，不打乱已有的 id。它们仍然小于 65,535，`uint16` 的 `.bin` 文件不受影响。
2. **编码**。切分时要同时认出所有特殊 token。
3. **训练**。训练前也要按所有特殊 token 切开语料，保证没有任何合并规则跨过它们，原书对 `<|endoftext|>` 就是这样做的。
4. **模型**。embedding 和 unembedding 各要多出相应的行。

第 2 条和第 4 条各有一个容易踩的坑，我们逐个来看。

### 长的优先

假设我们加了一个特殊 token `<|endoftext|><|endoftext|>`（这正是 CS336 测试里用的例子）。它的开头恰好是另一个特殊 token。把它们拼成一个正则 `A|B` 去切分时，Python 的正则是按顺序尝试的：只要 `A` 能匹配，就不会再看 `B`，哪怕 `B` 更长。所以，写模式之前要先把特殊 token 按长度从长到短排好：

```verify id=7.4-a title="多个特殊 token：按长度从长到短排列，才能认出长的那个"
import regex as re
def encode_with_specials(text, specials, longest_first=True):
    """支持多个特殊 token：先按特殊 token 切开，其余部分照常做预分词和 BPE。"""
    order = sorted(specials, key=len, reverse=True) if longest_first else list(specials)
    pattern = "(" + "|".join(re.escape(s) for s in order) + ")"
    out = []
    for part in re.split(pattern, text):
        if part in specials:
            out.append(specials[part])
        else:
            out.extend(i for p in sbt.pretokenize(part) for i in tok._encode_text(p))
    return out

specials = {"<|endoftext|>": 49_999, "<|endoftext|><|endoftext|>": 50_000}   # 新的 token 接在 49,999 后面
text = "a<|endoftext|><|endoftext|>b"
print("长的优先:  ", encode_with_specials(text, specials))
print("按给定顺序:", encode_with_specials(text, specials, longest_first=False))
assert encode_with_specials(text, specials) == [ord("a"), 50_000, ord("b")]
assert encode_with_specials(text, specials, longest_first=False) == [ord("a"), 49_999, 49_999, ord("b")]
```

### 给模型添加新的行

新 token 的 embedding 和 unembedding 该初始化成什么？一种简单而稳妥的做法是取已有各行的平均。它有一个好性质：logit 是隐藏向量与 unembedding 各行的内积，内积对行是线性的，所以新 token 的 logit 恰好等于旧 logits 的平均，不会比最大的那个更大。它一开始只分到很小的概率，原来的输出分布几乎不受影响；旧 token 的 logits 则完全不变。

```verify id=7.4-b title="新 token 的那一行取已有各行的平均：它的 logit 等于旧 logits 的平均"
rng = np.random.default_rng(0)
V, d = 1_000, 64                                       # 缩小尺寸的演示：1,000 个旧 token
W_unembed = rng.normal(0, 0.02, size=(V, d))           # unembedding 的权重，每行对应一个 token
h = rng.normal(size=d)                                  # 某个位置最后一层的输出
W_new = np.vstack([W_unembed, W_unembed.mean(axis=0)])  # 新 token：取已有各行的平均
logits_old, logits_new = W_unembed @ h, W_new @ h
probs = np.exp(logits_new - logits_new.max())
probs /= probs.sum()
print(f"旧 token 的 logits 变了吗: {not np.allclose(logits_new[:V], logits_old)}")
print(f"新 token 的 logit {logits_new[V]:.6f}，旧 logits 的平均 {logits_old.mean():.6f}")
print(f"新 token 分到的概率 {probs[V]:.6f}，均匀分布是 {1 / (V + 1):.6f}，旧 token 里最大的是 {probs[:V].max():.6f}")
assert np.allclose(logits_new[:V], logits_old) and np.isclose(logits_new[V], logits_old.mean())
```

在原书的 `webbot.model.GPT` 上也是一样：把 `embed` 和 `unembed` 换成多出两行的新层，旧 token 的输出一个不变，新 token 的 logit 等于旧 logits 的平均。

### 用户输入里的特殊 token

还有一个坑与安全有关。原书的 `encode` 对输入一视同仁：只要文字里出现 `<|endoftext|>` 这串字符，就把它编码成特殊 token。如果这段文字来自用户，会发生什么呢？

::: confusion 特殊 token 不就是一串字符吗？用户输入它，为什么会出问题？
直觉上，`<|endoftext|>` 只是 13 个普通字符，和 `hello` 没有什么两样。区别在于编码器怎样对待它：把它当作特殊 token，它就是词表里唯一的那个 id，模型在训练中只在文章的边界见过它；当作普通文字，它就是 `<`、`|`、`end`……这样一串普通的 token，与正文里的其他符号没有区别。

## 7.5 其他分词器

到目前为止，三台机器人用的都是同一种分词器：字节级 BPE。它不是唯一的选择。这一节介绍另外几种常见的分词器，每一种都写一个最小的 Python 版本，看看它们与 BPE 的区别在哪里。

### 以单词为单位

最直观的做法是按空格把文字切成单词，每个单词一个 id。如果你读过《深度学习进阶：自然语言处理》第 2 章，那里的语料预处理就是这样做的（2.3.1 节）；用到的 PTB 语料还事先把稀有词替换成了 `<unk>`。问题在于，总会有词表里没有的词，它们只能统一变成 `<unk>`，信息就此丢失。会丢多少呢？我们用样本的前一半建词表，看看后一半里有多少词不认识：

```verify id=7.5-a title="以单词为单位：新文本里总有不认识的词"
words = re.findall(r"\p{L}+", sample)                  # 简单起见，只把连续的字母当作单词
half = len(words) // 2
known = set(words[:half])                               # 前一半出现过的所有词都进词表
unseen = [w for w in words[half:] if w not in known]
print(f"前一半: {half:,} 个词，其中不同的有 {len(known):,} 个，全部收进词表")
print(f"后一半: {len(words) - half:,} 个词，有 {len(unseen):,} 个（{len(unseen) / (len(words) - half):.1%}）不在词表里，只能变成 <unk>")
print("例如:", unseen[:6])
roundtrip = all(tok.decode(tok.encode(w)) == w for w in unseen)
print("WebBot 的字节级 BPE 原样编码、解码这些词:", roundtrip)
assert roundtrip and len(unseen) / (len(words) - half) > 1 / 3
```

即使前一半出现过的每个词都收进了词表，后一半仍有三分之一以上的词不认识。样本只有 100 KB，所以这个比例偏高。语料再大，这个比例会下降，但不会降到 0：第 4 章 [4.1 节](ch04.html#s4-1) 的 Heaps 定律告诉我们，不同的词随语料一直在增加，只是越来越慢。人名、地名、新造的词总是层出不穷。字节级 BPE 从根上避开了这个问题：最坏情况下，任何文字都能拆成 256 个字节之一，没有不认识的东西。

### WordPiece

**WordPiece** 是 BERT 使用的分词器。它和 BPE 一样从小单位出发、逐步合并，但有两处不同。

第一处在编码。WordPiece 不记录合并的顺序，只保留一张词表；编码一个单词时，从左往右，每次取词表里能匹配上的最长的一段。单词中间的片段带 `##` 前缀，表示“紧接着前面，不是新词的开头”。BERT 源码的注释里有一个例子：`unaffable` 被切成 `un`、`##aff`、`##able`（[google-research/bert 的 tokenization.py](https://github.com/google-research/bert/blob/master/tokenization.py)）。如果某一段在词表里一个也找不到，整个单词就变成 `[UNK]`：

```verify id=7.5-b title="WordPiece 的编码：每次取最长的一段"
def wordpiece(word, vocab, unk="[UNK]"):
    """BERT 的 WordPiece 编码：从左往右，每次取词表里最长的一段；词中间的片段带 ## 前缀。"""
    pieces, start = [], 0
    while start < len(word):
        end = len(word)
        while end > start:
            sub = word[start:end] if start == 0 else "##" + word[start:end]
            if sub in vocab:
                break
            end -= 1
        else:                                  # 一段也匹配不上：整个单词变成 [UNK]
            return [unk]
        pieces.append(sub)
        start = end
    return pieces

vocab_wp = {"un", "##aff", "##able", "a", "ab", "##bc"}
print("unaffable ->", wordpiece("unaffable", vocab_wp))
print("abc       ->", wordpiece("abc", vocab_wp), "（其实 a + ##bc 就能拼出来）")
assert wordpiece("unaffable", vocab_wp) == ["un", "##aff", "##able"]
assert wordpiece("abc", vocab_wp) == ["[UNK]"]
```

第二个例子说明“每次取最长”是贪心的：先取了 `ab`，剩下的 `c` 找不到 `##c`，整个词就成了 `[UNK]`，尽管 `a` 加 `##bc` 是一种可行的切法。

第二处在训练。BPE 每次合并出现次数最多的 pair；WordPiece 则按下面的得分挑选：

$$\mathrm{score}(a, b) = \frac{n(ab)}{n(a)\, n(b)}$$

这里，$n(ab)$ 是 $a$、$b$ 相邻出现的次数，$n(a)$、$n(b)$ 是它们各自出现的次数。两个片段各自都很常见、只是碰巧经常挨在一起，得分并不高；两个都不太常见、却几乎总是一起出现，得分才高。Google 没有公开 WordPiece 训练算法的实现，上面的公式取自 [Hugging Face 课程的 WordPiece 一节](https://huggingface.co/learn/llm-course/chapter6/6)（2026 年 10 月查看）。我们用课程里的玩具语料手算一遍：`hug` 10 次、`pug` 5 次、`pun` 12 次、`bun` 4 次、`hugs` 5 次。`##u` 一共出现 36 次，`##g` 20 次，`##s` 5 次；`##u ##g` 相邻 20 次，得分是 $20 / (36 \times 20) = 1/36$；`##g ##s` 相邻只有 5 次，得分却是 $5 / (20 \times 5) = 1/20$，是最高的。

```verify id=7.5-c title="同一个语料，BPE 与 WordPiece 选择的第一个合并不同"
corpus = {"hug": 10, "pug": 5, "pun": 12, "bun": 4, "hugs": 5}       # Hugging Face 课程用的玩具语料
splits = {w: [w[0]] + ["##" + ch for ch in w[1:]] for w in corpus}
freq, pair_freq = Counter(), Counter()
for w, c in corpus.items():
    s = splits[w]
    for x in s:
        freq[x] += c
    for pair in zip(s, s[1:]):
        pair_freq[pair] += c
score = {pair: n / (freq[pair[0]] * freq[pair[1]]) for pair, n in pair_freq.items()}
for pair, n in pair_freq.most_common():
    print(f"{pair[0]:>4} + {pair[1]:<4} 相邻 {n:>2} 次，得分 {n}/({freq[pair[0]]}×{freq[pair[1]]}) = {score[pair]:.4f}")
bpe_pick, wp_pick = max(pair_freq, key=pair_freq.get), max(score, key=score.get)
print("BPE（看次数）先合并:", bpe_pick, "  WordPiece（看得分）先合并:", wp_pick)
assert bpe_pick == ("##u", "##g") and wp_pick == ("##g", "##s")
```

### Unigram 与 Viterbi 算法

**Unigram** 分词器（[Kudo, 2018](https://arxiv.org/abs/1804.10959)）换了一个角度：不记录合并的顺序，而是给词表里的每个 token 一个概率 $p(x)$，并且假设各个 token 互相独立。这里的 unigram 与《深度学习进阶：自然语言处理》4.2 节负采样里的 unigram 分布是同一个意思：不看上下文，只看每个单位自己出现的概率。一个单词切成 $x_1, x_2, \dots, x_m$ 的概率是

$$P(x_1, \dots, x_m) = \prod_{i=1}^{m} p(x_i)$$

分词器要在所有可能的切法里，找出这个乘积最大的那一种。切法的数量随单词长度指数增长，不能一一枚举。好在有动态规划：设 $\mathrm{best}[i]$ 是前 $i$ 个字符的最优切法的对数概率，那么

$$\mathrm{best}[i] = \max_{j < i} \Big( \mathrm{best}[j] + \log p(w_{j:i}) \Big)$$

这里，$w_{j:i}$ 是第 $j$ 到第 $i$ 个字符组成的片段，只考虑在词表里的片段。这就是 **Viterbi 算法**。

训练则反过来：从一张很大的初始词表出发（比如语料里所有的子串），反复删掉一批 token，直到词表缩小到想要的大小。每次删的是“删了之后对语料的总概率影响最小”的那些；单个字符永远不删，保证任何单词都能切（[Hugging Face 课程的 Unigram 一节](https://huggingface.co/learn/llm-course/chapter6/7)有完整的推演）。

我们用上面的玩具语料，把各个单词的全部子串（单词本身除外）当作初始词表，按出现次数算概率。手算 `hug` 的四种切法：`hug` 出现 15 次，概率 $15/210 \approx 0.0714$；`hu` + `g` 是 $\frac{15}{210} \times \frac{20}{210} \approx 0.0068$；`h` + `ug` 也是 $0.0068$；`h` + `u` + `g` 最小。最优的是不切。

```verify id=7.5-d title="Viterbi 算法找到的，就是所有切法里概率最大的那一种"
import math
from itertools import product
sub_freq = Counter()
for w, c in corpus.items():
    for i in range(len(w)):
        for j in range(i + 1, len(w) + 1):
            sub_freq[w[i:j]] += c
vocab_u = {w[i:j] for w in corpus for i in range(len(w)) for j in range(i + 1, len(w) + 1) if (i, j) != (0, len(w))}
total = sum(sub_freq[s] for s in vocab_u)
logp = {s: math.log(sub_freq[s] / total) for s in vocab_u}
print(f"初始词表: {len(vocab_u)} 个子串，频次总和 {total}")

def viterbi(word):
    best, back = [0.0] + [-math.inf] * len(word), [0] * (len(word) + 1)
    for i in range(1, len(word) + 1):
        for j in range(i):
            piece = word[j:i]
            if piece in logp and best[j] + logp[piece] > best[i]:
                best[i], back[i] = best[j] + logp[piece], j     # 记住最后一段从哪里开始
    pieces, i = [], len(word)
    while i > 0:
        pieces.insert(0, word[back[i]:i])
        i = back[i]
    return pieces, best[-1]

def all_segmentations(word):
    """把每一种切法都列出来（只用来核对）。"""
    for cuts in product([0, 1], repeat=len(word) - 1):
        pieces, start = [], 0
        for k, cut in enumerate(cuts, 1):
            if cut:
                pieces.append(word[start:k])
                start = k
        pieces.append(word[start:])
        if all(p in logp for p in pieces):
            yield pieces, sum(logp[p] for p in pieces)

for pieces_, lp in sorted(all_segmentations("hug"), key=lambda x: -x[1]):
    print(f"  {' + '.join(pieces_):<10} 概率 {math.exp(lp):.4f}")
print("Viterbi 的答案:", viterbi("hug")[0])
assert total == 210 and viterbi("hug")[0] == ["hug"]
for w in ["hug", "hugs", "pug", "pun", "bun", "bug", "gush"]:
    assert abs(viterbi(w)[1] - max(lp for _, lp in all_segmentations(w))) < 1e-12
```

频次总和 210 与课程中的数字一致。最后两行在 7 个单词上核对：动态规划找到的，正是穷举所有切法后概率最大的那一个。Unigram 还有一个标准 BPE 没有的能力：既然每种切法都有概率，就可以按概率随机抽样切法，让模型在训练时见到同一个词的不同切分，Kudo 把这叫作 subword regularization。BPE 后来也有了类似的做法：训练时随机跳过一部分合并，叫作 BPE-dropout（[Provilkov et al., 2020](https://arxiv.org/abs/1910.13267)）。

### SentencePiece

**SentencePiece**（[Kudo & Richardson, 2018](https://arxiv.org/abs/1808.06226)）不是一种新算法，而是一个用 C++ 写成的分词器库，实现了 BPE 和 Unigram 两种算法，默认用的是 Unigram（[google/sentencepiece](https://github.com/google/sentencepiece) 的[训练选项](https://github.com/google/sentencepiece/blob/master/doc/options.md)）。它的特点是直接在原始文字上训练，不需要预分词：空格被换成一个普通的符号 `▁`（U+2581），与其他字符一样参与切分。这样，解码时只要把各段拼起来、再把 `▁` 换回空格即可，不需要任何与语言有关的规则：

```verify id=7.5-e title="SentencePiece 的做法：空格换成 ▁，当普通字符处理"
raw = "  Hello  world.\n你好"
marked = raw.replace(" ", "▁")                    # 空格换成 ▁（U+2581）
print(repr(marked))
cut = [marked[:3], marked[3:8], marked[8:10], marked[10:]]   # 随便一种切法
print(cut, "->", repr("".join(cut).replace("▁", " ")))
assert "".join(cut).replace("▁", " ") == raw
zh_pieces = list(sbt.pretokenize("语言模型只认识整数，分词器负责把文字变成整数。"))
print("GPT-2 的正则把一整段中文当作一个预分词:")
print(zh_pieces)
assert zh_pieces == ["语言模型只认识整数", "，", "分词器负责把文字变成整数", "。"]
```

严格地讲，SentencePiece 默认还会先对文字做 NFKC 规范化，并去掉多余的空格，所以还原出来的是规范化之后的文字；这两项都可以在训练时关掉（见它的 [normalization 文档](https://github.com/google/sentencepiece/blob/master/doc/normalization.md)）。

GPT-2 的预分词正则是为空格分词的语言设计的：一整段没有空格的中文被当作一个预分词，在 BPE 看来就是一个很长的“单词”。SentencePiece 本来就不做预分词，对中文和日文一视同仁。Llama 2 的分词器就是用 SentencePiece 实现的 BPE：词表 32k，数字拆成单个数位，词表里没有的 UTF-8 字符退回到字节（[Touvron et al., 2023](https://arxiv.org/abs/2307.09288)，2.2 节）。

### 小结：四种分词器

| | 字节级 BPE | WordPiece | Unigram | 以单词为单位 |
|---|---|---|---|---|
| 谁在用 | 三台机器人、GPT-2 | BERT | SentencePiece 的默认算法 | 《深度学习进阶》的 word2vec |
| 训练 | 反复合并次数最多的 pair | 反复合并得分最高的 pair | 从大词表出发，逐步删除 | 统计词频 |
| 保存什么 | 有顺序的合并规则 | 词表 | 词表和每个 token 的概率 | 词表 |
| 编码 | 按学到的顺序合并 | 每次取最长的一段 | Viterbi：概率最大的切法 | 查表 |
| 不认识的字 | 不存在（退回字节） | 整个词变成 `[UNK]` | 见过的字符都能切，没见过的依实现而定 | `<unk>` |

以上是 BPE 之外的几种分词器。它们的共同点是：都要先在语料上训练一张词表，而这张词表决定了模型看到的世界。下一节问一个更激进的问题：能不能不要这张表？

## 7.6 不用分词器的方法

分词器带来了不少麻烦。第一，它要单独训练，训练语料的偏好会被带进词表（图 7-1 里，CodeBot 和 StoryBot 对中文束手无策）。第二，它会产生“半个字符”的 token，单独解码不出完整的字符（图 7-1 里显示成 `\xe2\x80` 这样的字节）。第三，同一个词前面有没有空格、大小写是否相同，都会变成毫不相干的 id，模型只能从数据里慢慢学会它们是同一个词。后两点可以直接数一数：

```verify id=7.6-a title="WebBot 的词表里有 157 个“半个字符”；同一个词的四种写法是四个毫不相干的 id"
half = [i for i in range(256, tok.end_token_id)
        if tok.id_to_bytes[i].decode("utf-8", errors="ignore").encode("utf-8") != tok.id_to_bytes[i]]
print(f"单独解码不出完整字符的 token: {len(half)} 个，例如 {tok.id_to_bytes[half[0]]}")
variants = {w: tok.encode(w) for w in ["the", " the", " The", "The"]}
for w, ids_w in variants.items():
    print(f"{w!r:>7} -> {ids_w}")
assert len(half) == 157
assert len({tuple(v) for v in variants.values()}) == 4 and all(len(v) == 1 for v in variants.values())
```

最彻底的办法，是直接把字节交给模型：词表只有 256 个字节（再加特殊 token），不需要训练，没有不认识的字。这就是第 1 章 [1.2 节](ch01.html#s1-2)的字节级分词器。它的代价，第 1 章也说过了：序列变长。现在我们可以精确地算一算，长了多少，又贵了多少。

设分词器平均每个 token 装 $r$ 个字节。同一段文字，字节级模型的序列长度是 BPE 的 $r$ 倍。Transformer 里与位置数成正比的部分（各层的矩阵乘法、KV cache）也变成 $r$ 倍；Attention 要计算每两个位置之间的分数，与位置数的平方成正比，变成 $r^2$ 倍。WebBot 在整个 OWT 训练集上的 $r$ 可以由 7.1 节的两个文件算出来：11,920,511,059 字节的文字编码成了 2,649,004,800 个 token，$r \approx 4.50$，于是 $r^2 \approx 20.2$。

我们按 WebBot 的结构（12 层、768 维、12 个 query 头和 4 个 KV 头、SwiGLU 宽 2,048）算一笔账：WebBot 的 1,024 个位置能看到多少文字，字节级模型要看到同样多的文字又需要多少计算。

```verify id=7.6-b title="同样一段文字：字节级模型的位置数、计算量和 KV cache"
r = owt_train_bytes / (5_298_009_600 // 2)              # owt_train.txt 的字节数 / owt_train.bin 的 token 数
ctx = 1024
n_byte = round(ctx * r)                                 # 字节级模型要这么多个位置，才能看到同样多的文字
d, L, H, KV, D, ff = 768, 12, 12, 4, 64, 2048
linear = L * (d * H * D + 2 * d * KV * D + H * D * d + 3 * d * ff)   # 每个位置都要乘一遍的矩阵

def forward_flops(n, vocab):
    """前向传播的浮点运算次数：矩阵乘法 2·n·参数，加上 QK^T 和 AV（不计因果掩码省下的一半）。"""
    return 2 * n * (linear + d * vocab) + L * 4 * n * n * H * D

kv_per_pos = 2 * L * KV * D * 2                          # K 和 V、12 层、4 个 KV 头、bf16 每个数 2 字节
print(f"整个训练集上，WebBot 平均每个 token {r:.2f} 字节（7.1 节的 100 KB 样本上是 {n_bytes / len(head_ids):.2f}）")
print(f"WebBot 的 1,024 个 token ≈ {ctx * r:,.0f} 字节的文字")
for name, n, vocab in [("BPE（词表 50,000）", ctx, 50_000), ("字节级（词表 257）", n_byte, 257)]:
    print(f"{name}：{n:,} 个位置")
    print(f"    前向 {forward_flops(n, vocab) / 1e9:,.0f} GFLOP，其中 Attention {L * 4 * n * n * H * D / 1e9:,.0f} GFLOP；"
          f"KV cache {n * kv_per_pos / 2**20:.1f} MiB")
print(f"位置数 ×{n_byte / ctx:.2f}，Attention ×{(n_byte / ctx) ** 2:.1f}，"
      f"前向总计算量 ×{forward_flops(n_byte, 257) / forward_flops(ctx, 50_000):.2f}")
p_bpe, p_byte = sum(gpt_params(50_000).values()), sum(gpt_params(257).values())   # 7.1-b 的参数计数
print(f"参数: BPE 版 {p_bpe:,}，字节级 {p_byte:,}（{p_byte / p_bpe:.1%}）")
assert abs(r - 4.50) < 0.005 and n_byte == 4_608 and kv_per_pos == 12 * 1024 and p_byte == 75_911_424
```

同样一段约 4.6 KB 的文字，字节级模型要用 4,608 个位置：前向计算量是 BPE 版的 5 倍多，Attention 的部分约 20 倍，KV cache 是 4.5 倍。字节级模型并非一无是处：embedding 和 unembedding 从 7,680 万个参数降到不足 40 万（7.1 节），整个模型小了一半。可是参数省下来了，计算却贵了好几倍。

::: confusion 上下文 1,024，到底能装多少字？
直觉上，“上下文长度 1,024”像是一个关于文字长度的承诺。其实它数的是 token，而一个 token 装多少文字，取决于分词器，也取决于语言。同样是 WebBot 的 1,024 个 token，装英文网页和装中文，能差上十倍。下面的验证单元数一数。
:::

```verify id=7.6-c title="WebBot 的 1,024 个 token：英文约 4,700 个字符，中文约 400 个字"
zh = presets[3]["text"]                                           # 示例“中文”
for name, s in [("英文网页（样本的第 1 篇）", docs[0]), ("中文（示例）", zh)]:
    n_tok = len(tok.encode(s))
    print(f"{name}：{len(s):,} 个字符，{len(s.encode('utf-8')):,} 字节 → WebBot {n_tok:,} 个 token")
```

OWT 是英文网页，WebBot 很少见到中文，每个汉字要用两个多 token，1,024 个 token 只装得下四百多个字。上下文长度是对 token 的限制，不是对文字的限制；换一个分词器，或者换一种语言，同一个“1,024”装下的文字可以差上十倍。

这正是研究者们没有放弃字节级模型的原因：只要能把计算省回来，就能同时拿到“没有分词器”的种种好处。目前有几条思路。

- **直接用字节训练标准的 Transformer。** ByT5（[Xue et al., 2021](https://arxiv.org/abs/2105.13626)）只对 T5 的结构做了很小的改动，就直接在 UTF-8 字节上训练，并且报告字节级模型可以与 token 级的对手相当。代价正是本节算出的序列更长、计算更多，论文专门分析了参数量、训练 FLOPs 和推理速度上的取舍。
- **把字节分组成 patch。** MegaByte（[Yu et al., 2023](https://arxiv.org/abs/2305.07185)）把字节序列切成固定长度的 patch，用一个小的局部模型处理 patch 内部的字节、一个大的全局模型处理 patch 之间的关系。大模型看到的位置数因此缩小为原来的几分之一，可以建模上百万字节长的序列。
- **按预测难度动态分组。** Byte Latent Transformer（BLT，[Pagnoni et al., 2024](https://arxiv.org/abs/2412.09871)）根据“下一个字节有多难预测”（熵）来决定 patch 的边界：容易预测的地方用长 patch，难预测的地方用短 patch，把计算花在真正需要的地方。论文报告，它是第一个在大规模上（参数到 8B）赶上基于分词器的 LLM 的字节级模型。

后两种方法其实是把“分词”搬进了模型内部：先把字节分组，再交给大模型。MegaByte 按固定长度分组；BLT 更进一步，用一个小的字节级模型估计每个位置的预测难度，由它决定在哪里分组，不再需要一张事先训练好的词表。

::: confusion 分词器不同的两个模型，loss 能直接比较吗？
直觉上，loss 越低越好，两个模型的 loss 可以直接比较。可是交叉熵 loss 的单位是“每个 token 多少 nats”，而两个分词器的 token 不一样大：StoryBot 的一个 token 平均装 4.1 个字节，字节级模型的一个 token 只有 1 个字节。要比较，得先换算成与分词器无关的单位：**每字节多少比特**（bits per byte）。

$$\text{bits per byte} = \frac{\ell}{\ln 2 \cdot r}$$

这里，$\ell$ 是每个 token 的 loss（nats），除以 $\ln 2$ 把 nats 换成 bits（1 nat 约 1.4427 bits），再除以每个 token 的字节数 $r$。举个例子：StoryBot 若达到 CS336 给 TinyStories 定的目标 loss 1.45，每个 token 4.117 字节，换算下来约 0.51 bits/byte；一个对 256 个字节一律均匀乱猜的字节级模型，是 $\ln 256 / \ln 2 = 8$ bits/byte。

当然，换算只消除了分词器的影响，消除不了数据的差别。StoryBot 读的是用语简单的儿童故事，WebBot 读的是五花八门的网页，后者本来就更难预测。差多少呢？可以借一个通用的压缩器粗略地量一量：压缩器也是在预测下一个字节，越好预测，压得越小。同样取 1 MB，lzma 把 TinyStories 压到每字节约 1.8 比特，把 OWT 只压到约 2.6 比特。所以，即使换算成 bits per byte，WebBot 的数字也不能拿来和 StoryBot 比，只能和同样在 OWT 上评估的模型比。BLT 这类研究在比较字节级模型和基于分词器的模型时，用的正是 bits per byte。
:::

```verify id=7.6-d title="把每个 token 的 loss 换算成每个字节的比特数"
def bits_per_byte(loss_nats_per_token, bytes_per_token):
    return loss_nats_per_token / math.log(2) / bytes_per_token

print(f"1 nat = {1 / math.log(2):.4f} bits")
print(f"字节级模型均匀乱猜: {bits_per_byte(math.log(256), 1):.2f} bits/byte")
print(f"StoryBot 达到 loss 1.45（每个 token 4.117 字节）: {bits_per_byte(1.45, 4.117):.3f} bits/byte")
assert abs(bits_per_byte(math.log(256), 1) - 8) < 1e-12
assert round(bits_per_byte(1.45, 4.117), 2) == 0.51
```


以上就是不用分词器的几种思路。字节级模型省掉了分词器的种种麻烦，却要为更长的序列付出代价；MegaByte、BLT 这样的方法，正是在设法把这份代价省回来。

## 小结

本章为 WebBot 训练了一个 50,000 词的分词器。算法和代码都是第 4 章的，新的问题全部来自规模。我们先用一个 100 KB 的样本在浏览器里重现了官方规则的前 10 个 token，在本机上用 1 MB 的样本逐条重现了前 15 条；又把官方的 `owt_valid.bin` 重新编码、整个解码，确认它就是这份规则的产物。接着，我们用 `cProfile` 找到了训练的瓶颈：`max()` 每一步都把全部 pair 扫一遍，pair 的种数随规模增长，全量训练光这一行就要以小时计。编码这一侧，九成以上的预分词本身就是一个 token，整词查表就能省下大部分工作。

然后，我们把编码交给了 Rust 写的 tiktoken、把训练交给了 Rust 写的 tokenizers。在比较速度之前，先确认了结果相同：两种“优先级”的定义在原理上并不等价，在 WebBot 的词表上却逐个 id 一致。最后三节讨论了添加特殊 token 的要点，介绍了 WordPiece、Unigram 和 SentencePiece，并且算了一笔账：不用分词器，同样的文字要多付出数倍的计算。

本章所学的内容：

- WebBot 的词表 = 256 个字节 + 49,743 条合并规则 + 1 个特殊 token。词表越大，每个 token 装的字节越多，但增长越来越慢；embedding 和 unembedding 的参数却随词表线性增长，在 WebBot 的 1.52 亿个参数中占了一半。（[验证 7.1-a](#v-7.1-a)、[验证 7.1-b](#v-7.1-b)、[验证 7.1-d](#v-7.1-d)）
- 最先学到的合并规则由最常见的字节对决定，小样本就能重现：100 KB 重现了官方的前 10 个 token，1 MB 逐条重现了前 15 条规则。（[验证 7.1-e](#v-7.1-e)、[验证 7.1-f](#v-7.1-f)）
- 原书的训练循环里，`max()` 的 key 函数每一步要对每种 pair 调用一次，占了八成时间；pair 的种数随步数和语料增长，全量训练要以小时计。（[验证 7.2-a](#v-7.2-a)、[验证 7.2-b](#v-7.2-b)、[验证 7.2-d](#v-7.2-d)）
- tiktoken 按“拼出来的字节串”排优先级，原书按“id 对”，两者在原理上不等价，在 WebBot 的词表上却逐个 id 相同；tiktoken 单线程的编码速度是原书的 50 倍左右。（[验证 7.3-a](#v-7.3-a)、[验证 7.3-b](#v-7.3-b)、[验证 7.3-c](#v-7.3-c)）
- 多个特殊 token 要按长度从长到短匹配；用户输入里的特殊 token 不能直接编码成特殊 id。（[验证 7.4-a](#v-7.4-a)、[验证 7.4-c](#v-7.4-c)）
- WordPiece 按 $n(ab)/(n(a)\,n(b))$ 挑选合并，编码时每次取最长的一段；Unigram 给每个 token 一个概率，用 Viterbi 算法找概率最大的切法，结果与穷举一致。（[验证 7.5-c](#v-7.5-c)、[验证 7.5-d](#v-7.5-d)）
- 字节级模型没有分词器，但同样的文字需要 4.5 倍的位置、约 20 倍的 Attention 计算；不同分词器的 loss 要换算成 bits per byte 才能比较。（[验证 7.6-b](#v-7.6-b)、[验证 7.6-d](#v-7.6-d)）

分词器准备好了：OWT 变成了 26 亿个 token，按验证集的平均 4.50 字节/token 计，WebBot 的 1,024 个位置大约能装下 4.6 KB 的英文。下一章，我们来搭建读这些 token 的模型。它有 1.5 亿个参数，那么，这个规模是怎么定下来的呢？
