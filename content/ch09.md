上一章我们搭好了 WebBot：一个 12 层的 Transformer，一共 152,316,672 个参数。第 7 章也已经把 OpenWebText 编码成了 26.5 亿个 token。万事俱备，只差训练。

可是 WebBot 的训练和 StoryBot 完全不是一个量级。原书的训练脚本 `ch09/01_pretrain.py` 每一步要处理 32×4 条长度为 1,024 的序列，一共跑 100,000 步，每张 GPU 要读 131 亿个 token。这带来两个问题。一个是显存：按 9.2 节在 CPU 上实测的数字推算，32 条序列光是为反向传播保存的中间结果就有 20 多 GiB。80 GB 的 H100 装得下，24 GB 的显卡就很难装下了。另一个是时间：按 9.7 节在 H100 上实测的速度外推，一张 H100 要跑 10 个多小时。

本章就围绕这两个问题展开。9.1 节的梯度累积和 9.2 节的梯度检查点都是“用时间换显存”。9.3 节反过来，用更多的 GPU 换时间；9.4 节的 ZeRO 再把多卡上重复存放的东西切开。9.5 节认识一个新的优化器 Muon，它把整个权重矩阵的更新量当成一个整体来调整。9.6 节用 Weights & Biases 记录实验。9.7 节用原书的脚本训练 WebBot，这个脚本用到了梯度累积、DDP 和 W&B。第 III 部的原书只给要点和最终脚本，我们照例为每个结论配上最小验证，在 CPU 上把原书脚本的缩小版真的跑一遍，并在 H100 上实测它的前 200 步。

## 9.1 梯度累积

先从显存说起。训练时，显存里除了模型本身，还要放下一整个 batch 的**激活**（activation），也就是前向传播时为反向传播保存下来的中间结果。batch 越大，激活越多。如果 GPU 一次放不下原书想要的 128 条序列，该怎么办呢？

答案出奇地简单：分几次算，再把梯度加起来。原书用“batch 8、累积 4 次、等效于 batch 32”的例子说明这个做法，它叫作**梯度累积**（gradient accumulation）。每次实际送进模型的那一小份叫 **micro-batch**。我们先确认它为什么成立。

训练用的 loss 是 batch 内各样本 loss 的平均。把大小为 $B$ 的 batch 平均切成 $K$ 份、每份 $b = B/K$ 个样本，平均就可以分两层来算：

$$
L=\frac{1}{B}\sum_{i=1}^{B}\ell_i=\frac{1}{K}\sum_{k=1}^{K}L_k
$$

$$
L_k=\frac{1}{b}\sum_{i\in\text{第 }k\text{ 份}}\ell_i
$$

这里，$\ell_i$ 是第 $i$ 个样本的 loss，$L_k$ 是第 $k$ 个 micro-batch 的平均 loss。求导是线性运算，所以 $\nabla L=\sum_k \nabla\!\left(L_k/K\right)$：每个 micro-batch 的 loss 先除以 $K$，算出的梯度逐份相加，结果就是大 batch 的梯度。

来手算一个例子。模型是 $y=w x$，每个样本的 loss 是 $(wx-t)^2$，它对 $w$ 的梯度是 $2(wx-t)x$。取 $w=1$ 和 4 个样本 $(x,t)=(1,2),(2,3),(3,5),(4,4)$，四个梯度依次是 $-2,-4,-12,0$，平均为 $-4.5$。拆成两个 micro-batch：前两个样本的平均梯度是 $-3$，后两个是 $-6$，各除以 $K=2$ 再相加，$-1.5-3=-4.5$，和一次算完相同。

```verify id=9.1-a title="手算：拆成 2 份、各除以 K 再相加，等于一次算完"
import numpy as np

x = np.array([1.0, 2.0, 3.0, 4.0])
t = np.array([2.0, 3.0, 5.0, 4.0])
w = 1.0

def grad(xs, ts):                       # 一个 batch 的平均 loss 对 w 的梯度
    return np.mean(2 * (w * xs - ts) * xs)

K = 2
g_big = grad(x, t)                                           # 一次看 4 个样本
g_acc = grad(x[:2], t[:2]) / K + grad(x[2:], t[2:]) / K      # 2 个 micro-batch，各除以 K
g_forgot = grad(x[:2], t[:2]) + grad(x[2:], t[2:])           # 忘了除以 K

print(f"一次算完：{g_big:+.2f}")
print(f"累积，各除以 K：{g_acc:+.2f}")
print(f"累积，忘了除以 K：{g_forgot:+.2f}")
assert g_big == -4.5 and g_acc == g_big
assert g_forgot == K * g_big
```

忘了除以 $K$，梯度就变成 $K$ 倍。用 SGD 时，这等于把学习率放大了 $K$ 倍。用 AdamW 呢？第 6 章验证过，loss 乘上一个正的常数，Adam 的更新几乎不变（[验证 6.1-d](ch06.html#v-6.1-d)），前提是没有梯度裁剪。原书在累积之后要把梯度的范数裁到 1.0（[6.5.2 节](ch06.html#s6-5-2)），这个阈值针对的是一个大 batch 的平均梯度。梯度放大 $K$ 倍以后，本来不会触发裁剪的步也被裁了，各步梯度在 $m$、$v$ 里所占的分量随之改变，更新也就不同了。下面用 5 步 Adam 确认一下。

```verify id=9.1-b title="用 AdamW 时，梯度整体放大 4 倍几乎不改变更新；裁剪到 1.0 之后就不同了"
def adam_run(grads, clip=None, lr=1e-3, b1=0.9, b2=0.999, eps=1e-8):
    p, m, v = np.zeros(3), np.zeros(3), np.zeros(3)
    for t, g in enumerate(grads, start=1):
        if clip is not None:                        # 与 clip_grad_norm_ 相同：范数超过阈值就整体缩小
            g = g * min(1.0, clip / (np.linalg.norm(g) + 1e-6))
        m, v = b1 * m + (1 - b1) * g, b2 * v + (1 - b2) * g * g
        p = p - lr * (m / (1 - b1**t)) / (np.sqrt(v / (1 - b2**t)) + eps)
    return p

rng = np.random.default_rng(0)
dirs = rng.normal(size=(5, 3))
dirs /= np.linalg.norm(dirs, axis=1, keepdims=True)
grads = dirs * np.array([0.5, 0.2, 0.8, 0.3, 0.6])[:, None]   # 5 步“大 batch 的梯度”，范数都小于 1
K = 4
print("忘了除以 K，各步梯度的范数变成:", np.array2string(np.linalg.norm(K * grads, axis=1), precision=1))
no_clip = np.abs(adam_run(K * grads) - adam_run(grads)).max()
clipped = np.abs(adam_run(K * grads, 1.0) - adam_run(grads, 1.0)).max()
moved = np.abs(adam_run(grads, 1.0)).max()
print(f"不裁剪：5 步之后参数的最大差 {no_clip:.1e}")
print(f"裁剪到 1.0：参数的最大差 {clipped:.1e}，而参数本身只移动了 {moved:.1e}")
assert no_clip < 1e-8 and clipped > 0.3 * moved
```

不裁剪时，两者只差 $10^{-10}$ 的量级；裁剪之后，差别约是参数移动量的四成。原书写的是 `loss = loss / accumulation_steps`，累积出来的正是大 batch 的平均梯度，裁剪阈值 1.0 针对的也正是它。

那么，PyTorch 里怎样把梯度“加起来”呢？其实什么都不用做。`backward()` 从来不覆盖参数的 `.grad`，只会往上加。如果你读过《深度学习入门2：自制框架》步骤 14，会记得同一个变量被使用两次时，梯度要累加成 `x.grad = x.grad + gx`，所以开始新的计算之前要先调用 `cleargrad()`。PyTorch 也是这样，`optimizer.zero_grad()` 相当于对每个参数调用一次 `cleargrad()`。梯度累积正是利用了这个性质：清零一次，连续做 $K$ 次 backward，最后更新一次参数。原书的训练循环就是这样写的：

每一步先 `zero_grad()`，然后在 `for micro_step` 循环里取 4 次 micro-batch，每次的 loss 都除以 4 再 `backward()`。4 次都做完，才裁剪梯度、更新参数。中间那段 `if ddp and micro_step < accumulation_steps - 1` 是给多卡训练准备的，我们在 9.3 节再看（它藏着一个小问题）。

上面的手算只有 4 个样本。换成更一般的情形：一个 5 维线性回归，大 batch 是 32，切成 4 份，每份 8 个样本。

```verify id=9.1-c title="32 = 4 × 8：累积 4 次的梯度等于大 batch 的梯度"
rng = np.random.default_rng(0)
B, K, D = 32, 4, 5
X = rng.normal(size=(B, D))
T = rng.normal(size=B)
W = rng.normal(size=D)

def mse_grad(X, T, W):                  # 平均平方误差对 W 的梯度
    return 2 * X.T @ (X @ W - T) / len(T)

g_big = mse_grad(X, T, W)
g_acc = np.zeros(D)
for k in range(K):                      # 每个 micro-batch 的 loss 先除以 K，梯度再相加
    s = slice(k * B // K, (k + 1) * B // K)
    g_acc += mse_grad(X[s], T[s], W) / K

print("一次算完 :", np.array2string(g_big, precision=4))
print("累积 4 次:", np.array2string(g_acc, precision=4))
print("最大差小于 1e-12:", np.abs(g_acc - g_big).max() < 1e-12)
assert np.allclose(g_acc, g_big, rtol=0, atol=1e-12)
```

不过，“等价”有一个前提：每个 micro-batch 的 loss 必须是**同样多个**样本（准确地说，同样多个参与平均的 token）的平均。如果各份的有效 token 数不同，“各自平均再平均”就不等于“整体平均”。

```verify id=9.1-d title="有效 token 数不同时，平均的平均不等于整体平均"
loss_a = np.array([4.0])               # micro-batch A：只有 1 个有效 token
loss_b = np.array([1.0, 1.0, 1.0])     # micro-batch B：3 个有效 token

mean_of_means = (loss_a.mean() + loss_b.mean()) / 2                  # 各自平均，再除以 K
token_mean = np.concatenate([loss_a, loss_b]).mean()                  # 大 batch 的真正平均
fixed = (loss_a.sum() + loss_b.sum()) / (loss_a.size + loss_b.size)   # 先求和，最后除以总 token 数

print(f"各自平均再平均: {mean_of_means:.2f}")
print(f"整体按 token 平均: {token_mean:.2f}")
assert mean_of_means == 2.5 and token_mean == 1.75 and fixed == token_mean
```

WebBot 不受影响：它的每个 micro-batch 都是 32×1,024 个 token，一个不多一个不少。第 3 章的 SFT 就不同了，`-100` 遮掉的 padding 让每条样本的有效 token 数各不相同。在那里做梯度累积，就要先把 loss 求和，最后除以整个大 batch 的有效 token 数。

最后要说清楚代价。梯度累积不改变计算量：同样多的 token 分 $K$ 次排队算完，前向和反向的总乘加次数和一次算完一样（第 8 章的 $6ND$ 只和 token 数有关）。时间上的损失来自效率：micro-batch 太小时，矩阵乘喂不饱 GPU，每秒处理的 token 就可能下降。所以它是“用时间换显存”的第一种办法，只是这里的时间花在效率上，而不是花在多出来的计算上。

::: answer
梯度不变：两种设置每一步看的都是 128 条序列，累积的结果都是这 128 条的平均梯度（当然，随机抽到的序列不同）。激活大约减半，因为同一时刻只有 16 条序列在显存里；9.2 节会按 CPU 上实测的数字算出，micro-batch 16 的激活约 11–15 GiB。总计算量不变，变的只是每次矩阵乘小了一半，GPU 的利用率可能略降。显存只有 24 GB 的卡跑 WebBot，可以试试这样改（这是按 CPU 上的测量推算的，没有在 24 GB 的卡上实测）。

## 9.2 梯度检查点

梯度累积减少的是“同一时刻有多少条序列”。可是对 WebBot 来说，就算一次只放一条序列，激活也不少。那么，激活到底是什么，又为什么非存不可呢？

拿一层 $\boldsymbol{y}=\tanh(W\boldsymbol{x})$ 来说。反向传播时，$\partial L/\partial W$ 要用到输入 $\boldsymbol{x}$，而 $\tanh$ 的导数 $1-\boldsymbol{y}^2$ 要用到输出 $\boldsymbol{y}$。所以前向时算出来的 $\boldsymbol{x}$ 和 $\boldsymbol{y}$ 都得留着，一直等到反向传播经过这一层。一个网络有多少层，就要留多少份这样的中间结果。

我们在 CPU 上实测了全尺寸 WebBot 的这笔账（fp32）：每多一条 1,024-token 的序列，前向时为反向传播保存的张量就多约 937 MiB。其中最大的单项是 logits 的 log-softmax，$1024\times 50000$ 个 fp32 数，一项就是 195 MiB。按 micro-batch 32 算，fp32 下的激活接近 30 GiB（本节最后再看打开 bf16 autocast 时的数字）。

**梯度检查点**（gradient checkpointing，也叫 activation checkpointing）的想法是：前向时不必什么都留着，只在少数位置留下“检查点”；反向传播需要某一段的中间结果时，从最近的检查点开始，把这一段的前向再算一遍。打个比方，这像玩游戏时不必每一秒都存档，只在几个关卡存档；要回到某个时刻，就读取最近的存档，再把这一小段重玩一遍。严格地讲，它用重复的前向计算换取显存：反向传播需要的张量一个都不少，只是有些张量是“现做”的。

先在一个 16 层的 $\tanh$ 网络上手算一下。普通的反向传播要存 $\boldsymbol{h}_0,\dots,\boldsymbol{h}_{16}$ 共 17 个激活。每 4 层设一个检查点，前向时只存 $\boldsymbol{h}_0,\boldsymbol{h}_4,\boldsymbol{h}_8,\boldsymbol{h}_{12},\boldsymbol{h}_{16}$ 这 5 个。反向传播走到某一段时，从段首重算段内的 3 个激活，用完就扔。于是同一时刻最多只有 $5+3=8$ 个激活，代价是 4 段各重算 3 层，共多算 12 层的前向。

```verify id=9.2-a title="16 层网络：每 4 层一个检查点，同时存的激活从 17 个降到 8 个，梯度逐位相同"
rng = np.random.default_rng(0)
n, d = 16, 8                                   # 16 层，每层的激活是 8 维向量
Ws = [rng.normal(scale=0.5, size=(d, d)) for _ in range(n)]
x0 = rng.normal(size=d)

def layer(i, h):                               # 第 i 层：h -> tanh(W_i h)
    return np.tanh(Ws[i] @ h)

def backward_segment(hs, i0, g):
    """hs[j] 是第 i0+j 层的输入（hs[-1] 是段尾的输出）；g 是 loss 对段尾输出的梯度。"""
    grads = {}
    for j in range(len(hs) - 2, -1, -1):
        dz = g * (1 - hs[j + 1] ** 2)          # tanh 的导数要用本层的输出
        grads[i0 + j] = np.outer(dz, hs[j])    # dW 要用本层的输入
        g = Ws[i0 + j].T @ dz
    return grads, g

# (1) 普通的反向传播：前向时存下全部 17 个激活
hs = [x0]
for i in range(n):
    hs.append(layer(i, hs[-1]))
g_plain, _ = backward_segment(hs, 0, np.ones(d))    # 假设 loss = sum(h_16)

# (2) 梯度检查点：只存每 4 层一个检查点，反向时逐段重算
k = 4
ckpt, h = {0: x0}, x0
for i in range(n):
    h = layer(i, h)
    if (i + 1) % k == 0:
        ckpt[i + 1] = h
g_ckpt, g, peak, recomputed = {}, np.ones(d), 0, 0
for s in range(n // k - 1, -1, -1):           # 从最后一段往前
    seg = [ckpt[s * k]]
    for i in range(s * k, s * k + k - 1):      # 重算段内的 k-1 个激活
        seg.append(layer(i, seg[-1]))
        recomputed += 1
    seg.append(ckpt[s * k + k])
    peak = max(peak, len(ckpt) + len(seg) - 2)  # 检查点 + 段内临时激活（段首段尾已算在检查点里）
    grads, g = backward_segment(seg, s * k, g)
    g_ckpt.update(grads)

same = all(np.array_equal(g_plain[i], g_ckpt[i]) for i in range(n))
print(f"普通反向传播  : 存 {len(hs)} 个激活")
print(f"每 {k} 层一个检查点: 同时最多存 {peak} 个，多算了 {recomputed} 层的前向")
print("16 层的梯度逐位相同:", same)
assert same and len(hs) == 17 and peak == 8 and recomputed == 12
```

梯度“逐位相同”并不奇怪：重算用的是同样的输入、同样的运算，得到的激活和第一次一模一样。

检查点设得越密，存的越多、重算的越少；设得越疏，存的越少、每段要重算的越多。$n$ 层、每 $k$ 层一个检查点时，同一时刻大约要存 $n/k+k$ 个激活，取 $k=\sqrt{n}$ 时最少，约为 $2\sqrt{n}$。为什么是 $\sqrt{n}$？两个正数之和不小于它们乘积开方的 2 倍，$n/k+k\ge2\sqrt{n}$，两项相等时取等号，即 $k=\sqrt{n}$。上面 16 层、每 4 层一个检查点，正好是 $16/4+4=8$，和数出来的一样。计算量方面，前向算 1 份，反向大约是前向的 2 倍（第 8 章 $6ND$ 里的 $2+4$），检查点最多再加 1 份前向，所以总计算量从约 3 份变成约 4 份。

```verify id=9.2-b title="√n 规则与计算量：3 份变 4 份"
n_layers = 64
best = min(range(1, n_layers + 1), key=lambda k: n_layers / k + k)
print(f"{n_layers} 层：k = {best} 时同时存的激活最少，约 {n_layers / best + best:.0f} 份（不用检查点是 {n_layers} 份）")
print(f"16 层、每 4 层一个：16/4 + 4 = {16 // 4 + 4}，与验证 9.2-a 数出来的 {peak} 个相同")

fwd, bwd = 1.0, 2.0                   # 6ND = 前向 2ND + 反向 4ND
plain, with_ckpt = fwd + bwd, fwd + bwd + fwd
print(f"计算量：{plain:.0f} 份 → {with_ckpt:.0f} 份（多 {with_ckpt / plain - 1:.0%}）")
assert best == 8 and n_layers / best + best == 2 * np.sqrt(n_layers) and 16 // 4 + 4 == peak
assert with_ckpt / plain - 1 < 0.34
```

原书仓库里这一节没有代码，`ch09/01_pretrain.py` 也没有用梯度检查点。在 PyTorch 里用起来很容易：把每个 Block 包进 `torch.utils.checkpoint.checkpoint`，前向时它只记住 Block 的输入，Block 内部的中间结果到反向时再算。

```python
from torch.utils.checkpoint import checkpoint

x = model.embed(ids)
for block in model.blocks:
```

## 9.3 分布式训练

前两节都是用时间换显存。现在反过来想：一张 GPU 要跑 10 个多小时，那 8 张 GPU 一起跑，是不是 1 个多小时就够了？可以，但原书的脚本至少要改两行，后面的“加卡等于加 token”再细说。如果你读过《深度学习入门：基于Python的理论与实现》8.3 节，会记得书里的例子：用 100 块 GPU，训练只快了 56 倍。那时只是一句介绍，现在我们来看看多张 GPU 究竟是怎样分工、又要怎样通信的。

最常用的分工方式叫**数据并行**（data parallelism）：每张 GPU 上都放一份完整的模型，各自读不同的数据、各自算梯度，然后把所有 GPU 的梯度求平均，大家用同一个平均梯度更新参数。因为起点相同、每一步的更新也相同，所有副本自始至终保持一致。

求平均这一步，和梯度累积是同一个道理。梯度累积是一个人把 4 份作业依次做完，数据并行是 4 个人各做一份，最后把答案平均。用公式写，$W$ 张 GPU、每张算出梯度 $\boldsymbol{g}_r$ 时，

$$
\boldsymbol{g}=\frac{1}{W}\sum_{r=0}^{W-1}\boldsymbol{g}_r
$$

这里，$\boldsymbol{g}_r$ 是第 $r$ 张 GPU 在自己那份数据上算出的平均梯度。只要每张 GPU 的数据量相同，$\boldsymbol{g}$ 就是全体数据的平均梯度。再叠加梯度累积，一次参数更新看到的就是 $W\times K$ 个 micro-batch。

```verify id=9.3-a title="4 张卡 × 每卡累积 2 次：all-reduce 求平均等于单卡的大 batch"
rng = np.random.default_rng(1)

Wt = rng.normal(size=D)

    g = np.zeros(D)
    for k in range(K):
        s = slice((r * K + k) * b, (r * K + k + 1) * b)
        g += mse_grad(X[s], T[s], Wt) / K
    local.append(g)
g_avg = np.mean(local, axis=0)               # all-reduce 求平均

print("4 卡求平均      :", np.array2string(g_avg, precision=4))
assert np.allclose(g_avg, g_big, rtol=0, atol=1e-12)
assert not np.allclose(local[0], g_big)      # 平均之前，各卡的梯度并不相同
```

### all-reduce

“把所有 GPU 的梯度求平均，再发回每一张 GPU”，这个通信操作叫 **all-reduce**。最朴素的做法是大家都把梯度发给 GPU 0，它求和后再发回去。问题在于 GPU 0：$W$ 张卡、梯度长度为 $N$ 时，它要接收 $(W-1)N$ 个数、再发出 $(W-1)N$ 个数，卡越多它越忙。

**环形 all-reduce**（ring all-reduce）让每张 GPU 只和左右邻居说话。每张 GPU 把梯度切成 $W$ 块，先做 $W-1$ 步 **reduce-scatter**：每一步把手里的一块发给右边的邻居，对方把它加到自己的同一块上。$W-1$ 步之后，每张 GPU 都有一块是全体的和。再做 $W-1$ 步 **all-gather**，把这些求好和的块沿着环传一圈。每张 GPU 一共发出 $2(W-1)$ 块，也就是 $2(W-1)N/W$ 个数，$W$ 再大也不超过 $2N$。例如 $W=4$、$N=12$ 时，每张卡发出 18 个数；朴素做法里，GPU 0 要收 36 个、再发 36 个。

```verify id=9.3-b title="环形 all-reduce：每张卡都得到总和，每张卡只发出 2(W−1)/W·N 个数"
def ring_allreduce(grads):
    """grads: W 个长度为 N 的向量（每张卡一份）。返回每张卡的结果和每张卡发出的元素个数。"""
    W = len(grads)
    chunks = [np.array_split(g.astype(float), W) for g in grads]
    sent = [0] * W
    for s in range(W - 1):                    # reduce-scatter
        msgs = [(r, (r - s) % W, chunks[r][(r - s) % W].copy()) for r in range(W)]
        for r, c, data in msgs:               # 卡 r 把第 c 块发给卡 r+1，对方加到自己的第 c 块上
            chunks[(r + 1) % W][c] += data
            sent[r] += data.size
    for s in range(W - 1):                    # all-gather：卡 r 手里的第 (r+1-s) 块已经是总和
        msgs = [(r, (r + 1 - s) % W, chunks[r][(r + 1 - s) % W].copy()) for r in range(W)]
        for r, c, data in msgs:
            chunks[(r + 1) % W][c] = data
            sent[r] += data.size
    return [np.concatenate(c) for c in chunks], sent

rng = np.random.default_rng(2)
W, N = 4, 12
grads = [rng.integers(-5, 6, size=N) for _ in range(W)]
out, sent = ring_allreduce(grads)
total = np.sum(grads, axis=0)
print("各卡相加   :", total)
print("卡 3 的结果:", out[3].astype(int))
print(f"每张卡发出 : {sent} 个数；2(W-1)/W·N = {2 * (W - 1) * N // W}")
print(f"朴素做法里 GPU 0 要收 {(W - 1) * N} 个、发 {(W - 1) * N} 个")
assert all(np.array_equal(o, total) for o in out)
assert sent == [2 * (W - 1) * N // W] * W
```

实际的通信库未必用环形算法，但环形的思路最容易看清带宽是怎样省下来的。PyTorch 的 **DDP**（`DistributedDataParallel`）在 all-reduce 之外还做了一件事：它把参数分成若干个“桶”（默认 25 MiB，见 [DDP 文档](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)的 `bucket_cap_mb`，2026-10 查证），反向传播时一个桶的梯度算好就开始通信，让通信和后面的反向计算有机会重叠起来。

### 原书的 DDP 代码

多卡训练用 `torchrun` 启动。它一次启动 $W$ 个进程，每个进程负责一张 GPU，并给每个进程设置一组环境变量（[torchrun 文档](https://docs.pytorch.org/docs/stable/elastic/run.html)列了 13 个，2026-10 查证）。原书脚本直接读的是 `RANK`（全局编号）和 `LOCAL_RANK`（在本机内的编号）。`init_process_group` 默认也从环境变量里读配置，还要用到 `WORLD_SIZE`（进程总数）、`MASTER_ADDR` 和 `MASTER_PORT`（rank 0 在哪里等大家会合，见[分布式文档](https://docs.pytorch.org/docs/stable/distributed.html)的“Environment variable initialization”）。原书的脚本开头就靠 `RANK` 判断自己是不是在 `torchrun` 下运行：

接下来是梯度累积和 DDP 交汇的地方。原书的想法是：累积的前 3 个 micro-step 先不通信，只在最后一个 micro-step 做一次 all-reduce。`model.no_sync()` 就是“这一次先别通信”的意思：


问题在于 `no_sync()` 只包住了 `loss.backward()`，前向在它外面。DDP 是在**前向**结束时决定这一轮要不要通信的。前向在 `no_sync()` 外面跑完，DDP 就已经准备好在接下来的 backward 里通信了。PyTorch 里 `DistributedDataParallel.no_sync` 的文档（torch 2.14.1 的 docstring，也见 [DDP 文档](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)，2026-10 查证）对此有明确的警告：

> The forward pass should be included inside the context manager, or else gradients will still be synchronized.

我们用 gloo 后端在 CPU 上起了 2 个真正的进程来验证。模型是原书的 GPT（缩小了尺寸），每步累积 4 个 micro-batch，再用一个通信钩子数一数 all-reduce 发生了几次。按原书的写法，4 个 micro-step 每一步都做了 all-reduce，计数是 `[1, 1, 1, 1]`；把前向也放进 `no_sync()`，计数变成 `[0, 0, 0, 1]`。两种写法最后得到的梯度相同，也都等于单进程把 8 个 micro-batch 当成一个大 batch 算出的梯度。


也就是说，原书的代码算得对，只是没有省下通信：每一步做了 4 次 all-reduce，而不是 1 次。在一台机器内部的高速互联上这未必明显，跨机器训练时就可能成为瓶颈（这一点我们还没有在 GPU 上测过）。修正的办法是把前向也放进去：

```python
import contextlib

for micro_step in range(accumulation_steps):
    batch_x, batch_y = get_batch(train_data, context_len, micro_batch_size, device)
    sync = (not ddp) or micro_step == accumulation_steps - 1
    with contextlib.nullcontext() if sync else model.no_sync():   # 前向和反向都在里面
        with autocast(device_type='cuda', dtype=torch.bfloat16):
            logits = model(batch_x)
            loss = F.cross_entropy(logits.view(-1, logits.size(-1)), batch_y.view(-1))
            loss = loss / accumulation_steps
        loss.backward()
```

nanoGPT 用的是另一种写法：在前向之前直接设置 `model.require_backward_grad_sync = (micro_step == gradient_accumulation_steps - 1)`，注释里说 `no_sync()` 做的也只是切换这个变量（[nanoGPT train.py](https://github.com/karpathy/nanoGPT/blob/master/train.py)）。

### 加卡等于加 token

`torchrun --nproc_per_node=8` 原样运行这个脚本，会快 8 倍吗？不会。`max_iters = 100000` 是写死的，每个进程每一步照样处理自己的 32×4 条序列。于是 8 张卡每一步处理的 token 是 1 张卡的 8 倍；跑完 100,000 步的时间和 1 张卡差不多，读过的 token 却变成了 8 倍。想用 8 张卡、在约 1/8 的时间里读完同样多的 token，就要把 `max_iters` 改成 12,500。

别忘了学习率调度也是按步数写的。`warmup_iters = 500` 在 8 张卡上是 5.2 亿个 token，相当于单卡的 4,000 步，所以它也要除以 8，取 63 步，学习率随 token 的变化才和单卡一致（[GPU 实战手册 G.3](gpu.html#sG-3) 和 `gpu/jobs.py` 也是这样改的）。即便改了这两行，也不是单卡训练的 8 倍速版：每次参数更新的全局 batch 变成 1,024 条序列（约 105 万个 token），更新次数少了 8 倍，学习率 6e-4 是否仍然合适，要靠实验才知道。

nanoGPT 的做法是把梯度累积的次数除以卡数（`gradient_accumulation_steps //= ddp_world_size`），并且先断言能整除；原书的累积次数是 4，只能这样除到 4 张卡。更一般的办法是缩小每张卡的 batch，让全局 batch 保持 128 条：8 张卡各用 micro-batch 16、累积 1 次。这样步数、学习率调度和优化过程都与单卡相同。代价是评估仍有 101 次，只在 rank 0 上跑，其余 7 张卡空等（账单见 [G.3](gpu.html#sG-3)）。

```verify id=9.3-d title="max_iters 固定时，加卡等于加 token；按 token 对齐要改 max_iters 和 warmup_iters 两行"
micro, accum, ctx, max_iters, warmup = 32, 4, 1024, 100_000, 500      # ch09/01_pretrain.py
for world in (1, 2, 8):
    per_step = micro * accum * ctx * world
    print(f"{world} 张卡：每步 {per_step:>9,} 个 token，100,000 步共 {per_step * max_iters / 1e9:6.1f} B")

print(f"warmup 读的 token：单卡 500 步 {warmup * one / 1e6:.1f}M；8 卡不改 {warmup * eight / 1e6:.1f}M"
      f"（= 单卡 {warmup * eight // one:,} 步）；8 卡 {warmup_8} 步 {warmup_8 * eight / 1e6:.1f}M")
```

::: confusion “全局 batch”到底是多少？
“batch size”听上去是一个数，所以很自然地会去配置里找一个叫 batch 的值。可是在多卡训练里，一次参数更新背后有三层：每张卡一次算多少条（micro-batch），每张卡累积几次（accumulation），一共几张卡（world size）。全局 batch 是三者的乘积：

$$B_{\text{全局}}=b\times K\times W$$

这里，$b$ 是每张卡一次算的条数（micro-batch），$K$ 是每张卡累积的次数，$W$ 是卡数。WebBot 在 8 张卡上是 $32\times4\times8=1024$ 条序列，也就是 1,048,576 个 token。可是原书写进 wandb 的 `effective_batch_size` 是 `micro_batch_size * accumulation_steps`，不论几张卡都记作 128（9.6 节）。

强化学习里的“batch”又是另一回事。第 3 章的 GRPO 每次取 32 道题，每道题生成 $G=8$ 个回答，一共 256 条轨迹；这 256 条一次前向算完，同一批数据做 2 次参数更新。CS336 作业 5 的默认值同样是 256 条（32 道题 × 8），但是分成 32 次梯度累积，每次 8 条（[作业 5](https://github.com/stanford-cs336/assignment5-alignment)）。轨迹的长度各不相同，所以按 token 数算，每一步的 batch 还会变化。

```verify id=9.3-e title="同一个“batch”，三种算法"
micro, accum, world, ctx = 32, 4, 8, 1024
global_seqs = micro * accum * world
print(f"WebBot 全局 batch：{micro} × {accum} × {world} = {global_seqs} 条序列 = {global_seqs * ctx:,} 个 token")
print(f"wandb 里记的 effective_batch_size：{micro * accum}")
prompts, G, n_update = 32, 8, 2                 # ch03/09_grpo.py（本地测试会核对这三个数）
print(f"GRPO：每次生成 {prompts} × {G} = {prompts * G} 条轨迹，同一批做 {n_update} 次参数更新")
print(f"CS336 作业 5：{prompts * G} 条分 32 次累积，每次 {prompts * G // 32} 条")
assert global_seqs * ctx == 1_048_576 and prompts * G == 256
```

那 batch 该取多大呢？平均梯度的噪声随 batch 的平方根缩小：batch 翻 4 倍，噪声减半（验证 9.3-f）。所以 batch 越大，梯度越稳，但收益递减：过了某个“临界 batch”，再加大 batch 几乎不再减少需要的步数，只是多花算力（McCandlish et al., 2018，[arXiv:1812.06162](https://arxiv.org/abs/1812.06162)）。实践里常按 token 计。GPT-3 的论文给 1.25 亿参数的模型用的是每步约 50 万个 token、学习率 6e-4（[arXiv:2005.14165](https://arxiv.org/abs/2005.14165) 表 2.1）；nanoGPT 的 12×40×1,024 ≈ 49 万个 token 和 6e-4 与它一致。WebBot 单卡每步 13 万个 token，约为它的 1/4。

强化学习里也是同一个道理。每道题的 $G$ 个回答决定这一组的基线准不准，题数决定一步里有几组。第 3 章和 CS336 作业 5 的默认值都是 32 组 × 8 = 256 条；如果只用 8 题 × 8 = 64 条，一步只有 8 组，按独立样本粗算，梯度噪声约是 256 条时的 2 倍。

```verify id=9.3-f title="batch 翻 4 倍，平均梯度的噪声减半"
rng = np.random.default_rng(5)
g = rng.normal(loc=1.0, scale=4.0, size=(1000, 1024))   # 1000 次抽样；单个样本的“梯度”均值 1、标准差 4
for B in (16, 64, 256, 1024):
    print(f"batch {B:5d}：平均梯度的标准差 {g[:, :B].mean(axis=1).std():.3f}（4/√B = {4 / np.sqrt(B):.3f}）")
ratio = g[:, :64].mean(axis=1).std() / g[:, :256].mean(axis=1).std()
print(f"64 条与 256 条的噪声之比：{ratio:.2f}")
print(f"每步的 token：nanoGPT {12 * 40 * 1024:,}；WebBot 单卡 {32 * 4 * 1024:,}，是 nanoGPT 的 {32 * 4 / (12 * 40):.0%}")
assert abs(ratio - 2) < 0.15                            # batch 翻 4 倍，噪声减半
assert abs(32 * 4 * 1024 / 500_000 - 0.26) < 0.01        # 约为 GPT-3 论文 50 万 token 的 1/4
```

带走一句话：说 batch 时，要同时说清楚**单位**（序列、token 还是轨迹）和**层级**（每张卡一次、每次参数更新，还是每次生成）。batch 越大梯度越稳，但收益递减。
:::

## 9.4 ZeRO

数据并行解决了时间问题，却让显存问题换了个样子：每张 GPU 上都有一份完整的模型、一份完整的梯度、一份完整的优化器状态。$W$ 张卡就有 $W$ 份一模一样的东西。这些除激活以外的部分合称**模型状态**（model states），它们到底占多少呢？

先算原书的写法。参数用 fp32 存（计算时由 autocast 临时转成 bf16），梯度也是 fp32，AdamW 还要为每个参数存一阶矩 $m$ 和二阶矩 $v$，也都是 fp32。于是每个参数要 $4+4+4+4=16$ 个字节。ZeRO 论文按另一种混合精度来记账：fp16 的参数和梯度各 2 字节，外加 fp32 的主参数、$m$、$v$ 共 12 字节，合计 $2+2+12$，也是 16 字节。

```verify id=9.4-a title="AdamW 的模型状态：每个参数 16 字节"
dlfs6 = {"fp32 参数": 4, "fp32 梯度": 4, "Adam m": 4, "Adam v": 4}                 # 原书：参数 fp32 + autocast
zero_paper = {"fp16 参数": 2, "fp16 梯度": 2, "fp32 主参数": 4, "Adam m": 4, "Adam v": 4}
print("原书的写法:", sum(dlfs6.values()), "字节/参数；ZeRO 论文的记账:", sum(zero_paper.values()), "字节/参数")

n_webbot = 152_316_672
print(f"WebBot   : {n_webbot * 16 / 1e9:6.2f} GB（{n_webbot * 16 / 2**30:.2f} GiB）")
for name, n in [("15 亿参数", 1.5e9), ("75 亿参数", 7.5e9)]:
    print(f"{name}: {n * 16 / 1e9:6.1f} GB")
assert sum(dlfs6.values()) == sum(zero_paper.values()) == 16
assert round(n_webbot * 16 / 2**30, 2) == 2.27
```


WebBot 的模型状态只有 2.44 GB，和 9.2 节估算的 20 多 GiB 激活比起来不值一提。但模型一大，情况就反过来了。ZeRO 论文举的例子是：15 亿参数的 GPT-2，光是 fp16 的参数只要 3 GB，加上梯度和 Adam 的状态却要 24 GB；75 亿参数的模型要 120 GB，一张 80 GB 的卡连模型状态都放不下，更别说激活了。

**ZeRO**（Zero Redundancy Optimizer）的想法是消除这种冗余：既然 $W$ 张卡上存的是同样的东西，不如每张卡只存 $1/W$。论文把它分成三个阶段（Rajbhandari et al., 2020，[arXiv:1910.02054](https://arxiv.org/abs/1910.02054)）：

| 阶段 | 切分什么 | 每张卡的模型状态 | 通信量（相对 DDP） |
|---|---|---|---|
| DDP | 不切分 | $16\Psi$ | 1 倍 |
| ZeRO-1 | 优化器状态 | $4\Psi + 12\Psi/N_d$ | 1 倍 |
| ZeRO-2 | 再加上梯度 | $2\Psi + 14\Psi/N_d$ | 1 倍 |
| ZeRO-3 | 再加上参数 | $16\Psi/N_d$ | 1.5 倍 |

这里，$\Psi$ 是参数量，$N_d$ 是数据并行的卡数（就是 9.3 节的 $W$）。论文把每个参数的优化器状态占的字节数记作 $K$（这里是 12）；为了不和 9.1 节的累积次数 $K$ 混淆，表里直接写成了数字。论文的例子是 $\Psi=7.5\text{B}$、$N_d=64$：每张卡从 120 GB 依次降到 31.4 GB、16.6 GB 和 1.88 GB。

```verify id=9.4-b title="ZeRO 的三个阶段：75 亿参数、64 张卡（与论文表 1 对照）"
def zero_gb(psi, nd, stage, k=12):
    """每张卡上的模型状态（GB）：参数 2、梯度 2、优化器状态 k 字节/参数。"""
    p, g, o = 2 * psi, 2 * psi, k * psi
    if stage >= 1: o /= nd
    if stage >= 2: g /= nd
    if stage >= 3: p /= nd
    return (p + g + o) / 1e9

for nd in (4, 64):
    print(f"N_d = {nd:2d}:", "  ".join(f"stage {s}: {zero_gb(7.5e9, nd, s):6.2f}" for s in range(4)))
assert [round(zero_gb(7.5e9, 64, s), 2) for s in range(4)] == [120.0, 31.41, 16.64, 1.88]
assert [round(zero_gb(7.5e9, 4, s), 1) for s in range(4)] == [120.0, 52.5, 41.2, 30.0]
```

（$N_d=4$ 时 ZeRO-2 的精确值是 41.25 GB，论文表 1 写作 41.3。）

通信量为什么不变呢？回忆 9.3 节：环形 all-reduce 本来就是 reduce-scatter 和 all-gather 两步。论文也是这样分析的，标准的 DDP 每步通信 $2\Psi$。ZeRO-2 只是把这两步拆开，在中间插进“各自更新自己那一块”：先 reduce-scatter，每张卡只拿到自己那 $1/N_d$ 的平均梯度；用它更新自己那 $1/N_d$ 的参数；再 all-gather，把更新后的参数拼回完整的一份。总通信量仍是 $2\Psi$。ZeRO-3 连参数也只存一块，前向和反向时都要临时把参数收集起来，通信量变成 $3\Psi$，是 DDP 的 1.5 倍。

ZeRO 只改变“谁存什么”，不改变算法。下面用 NumPy 模拟 4 张卡上的 ZeRO-1：每张卡只保存 1/4 参数的 Adam 状态，更新完再拼起来。3 步之后，参数与普通的 Adam 逐位相同。

```verify id=9.4-c title="ZeRO-1：每张卡只存 1/4 的 Adam 状态，参数与普通 Adam 逐位相同"
def adam_step(p, g, m, v, t, lr=1e-2, b1=0.9, b2=0.999, eps=1e-8):
    m = b1 * m + (1 - b1) * g
    v = b2 * v + (1 - b2) * g * g
    m_hat, v_hat = m / (1 - b1 ** t), v / (1 - b2 ** t)
    return p - lr * m_hat / (np.sqrt(v_hat) + eps), m, v

rng = np.random.default_rng(3)
nd, n = 4, 10                                   # 4 张卡，10 个参数
p_ref = rng.normal(size=n)
m_ref, v_ref = np.zeros(n), np.zeros(n)
p_gpu = [p_ref.copy() for _ in range(nd)]       # 每张卡都有完整的参数
shards = np.array_split(np.arange(n), nd)       # Adam 状态按块分给 4 张卡
m_sh = [np.zeros(len(s)) for s in shards]
v_sh = [np.zeros(len(s)) for s in shards]
for t in range(1, 4):
    g_avg = np.mean([rng.normal(size=n) for _ in range(nd)], axis=0)    # 各卡梯度的平均
    p_ref, m_ref, v_ref = adam_step(p_ref, g_avg, m_ref, v_ref, t)       # 普通的 DDP + Adam
    parts = []
    for r, idx in enumerate(shards):            # reduce-scatter 之后，卡 r 只更新自己那一块
        part, m_sh[r], v_sh[r] = adam_step(p_gpu[r][idx], g_avg[idx], m_sh[r], v_sh[r], t)
        parts.append(part)
    p_gpu = [np.concatenate(parts) for _ in range(nd)]                   # all-gather
print("每张卡保存的 Adam 状态个数:", [2 * len(s) for s in shards], "；不切分时每张卡都是", 2 * n)
print(f"与普通 Adam 的最大差: {np.abs(p_gpu[0] - p_ref).max():.1e}")
assert all(np.array_equal(p, p_ref) for p in p_gpu)
```

PyTorch 自带 ZeRO-1 的实现：`torch.distributed.optim` 里的 `ZeroRedundancyOptimizer`。我们同样用 2 个 gloo 进程跑了 3 步 AdamW：两个进程各自只存一部分参数的 $m$ 和 $v$，合起来恰好是一整份，更新后的参数与单进程的普通 AdamW 一致。

## 9.5 Muon 优化器

前四节都在解决“怎样把训练装下、怎样算得更快”。这一节换个方向：同样的计算量，能不能学得更快？原书的 WebBot 仍然用 AdamW，这一节在仓库里没有代码。我们来看 Muon 到底做了什么，并用 PyTorch 自带的实现核对。

如果你读过《深度学习入门：基于Python的理论与实现》6.1 节，会记得 Momentum 像一个在碗里滚动的小球：速度 $\boldsymbol{v}$ 不断累积梯度，参数沿着速度的方向移动。Adam 在此之上，为每个参数单独按梯度的大小缩放步长。**Muon**（MomentUm Orthogonalized by Newton-Schulz）走的是另一条路：它不逐个缩放参数，而是把一整个权重矩阵的更新量当成一个整体来“整形”。

### 把更新量“正交化”

一个二维权重矩阵的梯度 $G$，可以做奇异值分解 $G=U\Sigma V^\top$。这里，$U$、$V$ 的各列是两组互相垂直的单位向量，可以看成更新的各个“方向”；$\Sigma$ 是对角矩阵，对角线上的奇异值是各个方向上的大小。Muon 的作者观察到，Transformer 里 SGD-Momentum 和 Adam 给出的更新矩阵往往“几乎是低秩的”：被少数几个方向主导，其余方向的奇异值很小。他推测，这些幅度小的“稀有方向”对学习同样重要。Muon 的做法是把所有奇异值都换成 1，也就是用 $UV^\top$ 代替 $G$：方向保留，各方向的步长拉平。

可是对每个矩阵每一步都做 SVD 太慢了。Muon 用 **Newton–Schulz 迭代**近似地完成这件事：先把 $G$ 除以它的 Frobenius 范数（这样所有奇异值都不超过 1），再反复执行

$$
X \leftarrow aX + b\,(XX^\top)X + c\,(XX^\top)^2X
$$

这里，$X$ 一开始是归一化后的 $G$，系数取 $(a,b,c)=(3.4445,\,-4.7750,\,2.0315)$。这个迭代不改变奇异向量 $U$、$V$。为什么呢？把 $X=U\Sigma V^\top$ 代进去：$XX^\top=U\Sigma^2U^\top$，所以 $(XX^\top)X=U\Sigma^3V^\top$，$(XX^\top)^2X=U\Sigma^5V^\top$。三项都是 $U(\cdot)V^\top$ 的形状，变的只有中间的对角矩阵，也就是说，每个奇异值 $x$ 都被送进同一个多项式 $p(x)=ax+bx^3+cx^5$。系数是 Muon 的作者 Keller Jordan 挑的：让 $p$ 在 0 附近的斜率尽可能大，小奇异值就能很快长大。

来手算一个最小的例子。$G=\mathrm{diag}(3,1)$，两个方向的大小差 3 倍。除以 Frobenius 范数 $\sqrt{10}$ 之后是 $0.949$ 和 $0.316$。把 $0.316$ 代进 $p$：$3.4445\times0.316-4.7750\times0.0316+2.0315\times0.0032\approx0.94$，一步就从 0.316 涨到了 0.94。迭代 5 步以后，两个奇异值分别是 0.753 和 1.134，两者之比从 3 倍变成了约 1.5 倍。注意，原来大的那个方向（3）反而变成了小的那个（0.753）。这就是下面要说的“在 1 附近来回跳”：Muon 不在乎谁大谁小，只要都在 1 附近。

```verify id=9.5-a title="diag(3, 1)：5 步之后两个方向的大小几乎拉平"
import numpy as np

def ns5(G, steps=5, a=3.4445, b=-4.7750, c=2.0315, eps=1e-7):
    """Newton–Schulz 正交化（与 PyTorch 的 torch.optim.Muon 用同一个公式）。"""
    X = G / (np.linalg.norm(G) + eps)          # Frobenius 范数归一化：奇异值都不超过 1
    tall = X.shape[0] > X.shape[1]
    if tall:
        X = X.T                                # 让 X Xᵀ 是较小的那个方阵
    for _ in range(steps):
        A = X @ X.T
        X = a * X + (b * A + c * A @ A) @ X
    return X.T if tall else X

G = np.diag([3.0, 1.0])
O = ns5(G)
s = np.linalg.svd(O, compute_uv=False)
print("NS5(G) =", np.array2string(O, precision=4).replace("\n", " "))
print("奇异值 :", np.array2string(s, precision=4), f"，之比 {s.max() / s.min():.2f}（原来是 3）")
assert np.allclose(O, np.diag(np.diag(O)))     # 奇异向量（这里是坐标轴）没变
assert np.allclose(np.sort(s), [0.7530, 1.1337], atol=1e-4)
assert O[0, 0] < O[1, 1]                       # 原来大的方向（3）反而变小了
```

注意结果并不是精确的 1。Muon 故意如此：为了 5 步就能把很小的奇异值也拉起来，系数选得很“激进”，代价是迭代不再收敛到 1，而是在 1 附近来回跳。作者的目标是让它落在 $[0.7,1.3]$ 左右。经典的三次迭代 $X\leftarrow1.5X-0.5(XX^\top)X$ 能精确收敛到 1，但在 0 附近的斜率只有 1.5，小奇异值要很多步才长得起来：要 11 步才进入同一个区间，15 步才收敛到 1。

```verify id=9.5-b title="五次迭代 5 步就把 [0.01, 1] 送进 [0.68, 1.14]；经典三次迭代要 11 步才进入同一区间、15 步才收敛到 1"
def ns_scalar(x, coeffs, steps):
    a, b, c = coeffs
    for _ in range(steps):
        x = a * x + b * x**3 + c * x**5
    return x

quintic, cubic = (3.4445, -4.7750, 2.0315), (1.5, -0.5, 0.0)

for name, co in [("五次（Muon）", quintic), ("三次（经典）", cubic)]:
    for steps in (5, 10, 11, 15):
        y = ns_scalar(xs, co, steps)
        print(f"{name} {steps:2d} 步：落在 [{y.min():.3f}, {y.max():.3f}]")
q5 = ns_scalar(xs, quintic, 5)
print(f"区间外更小的 0.001：五次迭代 5 步之后只到 {ns_scalar(0.001, quintic, 5):.2f}")
assert 0.68 < q5.min() and q5.max() < 1.14 and abs(ns_scalar(0.001, quintic, 5) - 0.47) < 0.01
assert ns_scalar(xs, cubic, 10).min() < 0.68 < ns_scalar(xs, cubic, 11).min()
assert not np.allclose(ns_scalar(xs, cubic, 14), 1) and np.allclose(ns_scalar(xs, cubic, 15), 1)
```

“只作用在奇异值上”这句话值得亲手确认。下面造一个 $64\times32$ 的矩阵，奇异值从 1 到 0.01 相差 100 倍，再分别用矩阵迭代和标量多项式计算：两者给出的奇异值相差不到 $10^{-12}$。迭代后的矩阵与理想的 $UV^\top$ 方向几乎相同。

### Muon 的一步

有了正交化，Muon 的一步就很简单了。对每个二维权重矩阵 $\Theta$（形状为 $d_{\text{out}}\times d_{\text{in}}$，这一步的梯度是 $G_t$）：

$$
\begin{aligned}
M_t &\leftarrow \mu M_{t-1} + G_t\\
O_t &\leftarrow \mathrm{NS}_5\!\left(G_t+\mu M_t\right)\\
\Theta_t &\leftarrow (1-\eta\lambda)\,\Theta_{t-1}-\eta\,s\,O_t
\end{aligned}
$$

这里，$M$ 是动量，$\mu$ 是动量系数（PyTorch 默认 0.95），$\eta$ 是学习率，$\lambda$ 是权重衰减，$s=\sqrt{\max(1,d_{\text{out}}/d_{\text{in}})}$。第一行是动量，和 SGD-Momentum 一样；第二行用 Nesterov 动量（当前梯度加上 $\mu$ 倍的动量）再正交化；第三行先做解耦权重衰减，再沿 $O_t$ 更新。$s$ 让输出比输入宽的矩阵每步多走一些，这是 Keller Jordan 原始实现里的缩放。PyTorch 的文档把动量记作 $B_t$、把形状记作 $A\times B$，读源码时对照即可。

来手算第 1 步。取 $\Theta_0=0$、$G_1=\mathrm{diag}(3,1)$、$\mu=0.95$、$\eta=0.02$。第 1 步的动量就是 $G_1$，Nesterov 的输入是 $G_1+0.95\,G_1=1.95\,G_1$。Newton–Schulz 一开始就除以范数，把 1.95 吃掉了，所以 $O_1$ 和验证 9.5-a 一样，是 $\mathrm{diag}(0.753,\,1.134)$。方阵的 $s=1$，权重衰减对 0 不起作用，于是 $\Theta_1=-0.02\,O_1=\mathrm{diag}(-0.0151,\,-0.0227)$。

```verify id=9.5-d title="手算 Muon 的第 1 步：Θ₁ = −η·NS₅(1.95·G₁) = diag(−0.0151, −0.0227)"
G1 = np.diag([3.0, 1.0])
mu, lr, wd = 0.95, 0.02, 0.1
M1 = mu * np.zeros_like(G1) + G1                # 第 1 步：M₀ = 0，所以 M₁ = G₁
O1 = ns5(G1 + mu * M1)                          # Nesterov 的输入是 1.95·G₁
s_scale = np.sqrt(max(1, G1.shape[0] / G1.shape[1]))
Theta1 = (1 - lr * wd) * np.zeros_like(G1) - lr * s_scale * O1   # Θ₀ = 0，权重衰减对 0 不起作用
print("O₁ 的对角线:", np.array2string(np.diag(O1), precision=4))
print("Θ₁ 的对角线:", np.array2string(np.diag(Theta1), precision=4))
assert np.allclose(O1, ns5(G1))                 # 1.95 倍被 Frobenius 归一化吃掉
assert np.allclose(np.diag(Theta1), [-0.01506, -0.02267], atol=1e-5)
```

PyTorch 的实现把动量写成指数平均（`buf.lerp_(grad, 1 - momentum)`），与上式只差一个常数倍。Newton–Schulz 一开始就会除以范数，所以这个常数倍在数学上不影响结果，和上面手算时 1.95 被吃掉是同一个道理。

::: column 为什么 Muon 不用在 embedding 上
embedding 的“矩阵”其实是一张查找表：一个 batch 里只有出现过的 token 那几行有梯度。直观上，把这张表当成一个线性变换去“正交化”并不自然。作者说，embedding 需要不同的优化方式，这一点可以从 modular norm 的理论推出来；而输出层也该用 AdamW，则主要来自实验。PyTorch 的 `torch.optim.Muon` 只接受二维参数，但它文档里的例子把所有二维参数都交给了 Muon，这样 embedding 也会被算进去，和作者的建议并不一致。可见，一个优化器用在哪些参数上、怎样和别的优化器配合，往往和更新规则本身一样需要留意。
:::

::: answer
`val/loss` 是在固定的验证集上算的平均（缩小版是 65,536 个 token，原书是全部 6,450 万个 token），每次评估用的数据都一样；`train/loss` 每一步都换一批随机抽取的新数据，本身就带着抽样的噪声。数量上也差得远：缩小版的 `train/loss` 只看一个 micro-batch 的 8 × 128 = 1,024 个 token，`val/loss` 看 65,536 个，多 64 倍。就算 `val/loss` 也每次换一批新数据，按 9.3 节的平方根规律（[验证 9.3-f](#v-9.3-f)），它的抽样噪声也只有 `train/loss` 的约 1/8（相邻 token 并不独立，这只是粗略的估计）。两条曲线回答的问题也不同：前者看“模型在没见过的数据上有多好”，后者只是训练过程的一个粗略信号。
:::

### 超参数从哪来

先看原书的超参数：

| 超参数 | 值 | 来源 | 改了会怎样 |
|---|---|---|---|
| 上下文、宽度、层数、头数 | 1024、768、12、12 | GPT-2 small 的形状（<code class="nowrap">context_len</code>、<code class="nowrap">embed_dim</code>、<code class="nowrap">n_layer</code>、<code class="nowrap">n_head</code>），nanoGPT 相同 | 参数量和每个 token 的计算量随之改变（第 8 章的 $6ND$） |

| 词表大小 | 50,000 | 第 7 章训练的 BPE（<code class="nowrap">vocab_size</code>）；nanoGPT 用 GPT-2 的 50,257 | 要重训分词器、重新编码数据；embedding 和 unembed 各有“词表 × 768”个参数，合起来约占一半（9.5 节） |

| 学习率 | 6e-4 | 与 nanoGPT 相同（<code class="nowrap">learning_rate</code>）；GPT-3 论文给 1.25 亿参数的模型也用 6e-4 | 我们没有扫过；它和每步的 token 数是一起定的（9.3 节的“全局 batch”框） |
| warmup 步数 | 500 | 原书的选择（<code class="nowrap">warmup_iters</code>）；nanoGPT 是 2,000 | 之后线性降到 0（第 6 章的 D2Z，nanoGPT 是余弦降到 6e-5）；多卡按 token 对齐时要一起除以卡数（9.3 节） |

| micro-batch × 累积次数 | 32 × 4 | 每卡每步 131,072 个 token（<code class="nowrap">micro_batch_size</code>、<code class="nowrap">accumulation_steps</code>）；nanoGPT 12 × 40，每步约 49 万 | 乘积不变时，换一种拆法梯度不变（9.1 节）；micro-batch 决定激活占多少显存（9.2 节） |

| 训练步数 | 100,000 | 每卡 131 亿 token，约为参数量的 86 倍，相当于把 OWT 训练集读 4.9 遍（<code class="nowrap">max_iters</code>）；nanoGPT 是 600,000 | 训练时间与它成正比（验证 9.7-d）；多卡按 token 对齐时要除以卡数（9.3 节） |
| 评估间隔 | 1,000 | 原书的选择（<code class="nowrap">eval_interval</code>）；nanoGPT 每 2,000 步，而且只抽 200 个 batch 估计 | 每次都在全部 6,450 万个验证 token 上评估，H100 上约 56 秒，全程 101 次约 1.6 小时；改成 5,000 约省 1.2 小时，代价是验证曲线只剩 21 个点（验证 9.7-d） |

### 在 CPU 上跑一遍缩小版

完整的 WebBot 在 CPU 上跑不动，但脚本本身可以。我们把 `ch09/01_pretrain.py` 复制一份，改动分三类，逐行清单在图 9-6 下方的“相对原书改动的 15 行”里（最后一行属于 `02_generate.py`，后面再说）。第一类把模型缩小到 CPU 跑得动：宽 128、2 层、上下文 128。第二类把训练缩短：只跑 300 步，每步仍累积 4 次，每次 8 条序列。第三类绕开这台机器做不了的事。这台 Windows 机器没有 C++ 编译器，只好去掉 `torch.compile`（报错是 `InvalidCxxCompiler: Compiler: cl is not found`，[8.5 节](ch08.html#s8-5)的本地测试复现过）。5.3 GB 的 `owt_train.bin` 也不下载，改用 `owt_valid.bin` 的前 90% 训练，紧接着的 65,536 个 token 用来验证。

```verify id=9.7-e title="实测速度相当于 MFU 约 31%（6·N_mm 加 attention 的记账）"
N_total, L, ctx, d = 152_316_672, 12, 1024, 768
N_mm = N_total - 50_000 * d - (2 * L + 1) * d   # 去掉输入 embedding（查表）和 25 个 RMSNorm 的权重（逐元素乘）
per_token = 6 * N_mm + 6 * L * ctx * d           # 6ND，加上 attention 的矩阵乘（因果，按一半算）
h100 = 1979e12 / 2                               # H100 的稠密 bf16 峰值（CS336 讲义的 facts.py 写作 1979e12 / 2）
tokens_per_s = 32 * 4 * 1024 / s_step            # s_step 来自验证 9.7-d
mfu = per_token * tokens_per_s / h100
print(f"每个 token {per_token / 1e6:.1f} MFLOP；每秒 {tokens_per_s:,.0f} 个 token；MFU {mfu:.1%}")
print(f"若按 6 × 全部参数记账：{6 * N_total * tokens_per_s / h100:.1%}")
assert N_mm == 113_897_472 and 0.30 < mfu < 0.32
```

实测约 31%。如果按 6 乘全部参数记账（把 embedding 查表也算成矩阵乘），同一个速度会算成 38%：两种说法指的是同一个速度，只是分子不同。

## 本章小结

本章围绕“显存放不下、时间等不起”这两个问题，把训练大模型的常用技巧走了一遍。梯度累积和梯度检查点都用时间换显存：前者把大 batch 拆开依次算，后者把激活扔掉、用到时再算。数据并行用更多的 GPU 换时间，它的数学和梯度累积是同一回事，难点在通信；我们还看到原书的 `no_sync` 没有包住前向，每个 micro-step 都在通信。ZeRO 把数据并行里重复存放的模型状态切开分摊；Muon 把动量矩阵“正交化”，让各个方向的步长拉平。最后，我们用 W&B 记录实验，在 CPU 上把原书脚本的缩小版和它的 DDP 分支都真的跑了一遍，又在 H100 上实测了全尺寸 WebBot 的前 200 步，据此推算出完整训练的时间和费用。

至此，CodeBot、StoryBot、WebBot 三台机器人都已登场。“分词器 → 模型 → 训练”这个节奏，我们在三种规模上各走了一遍。

本章所学的内容：

- 每个 micro-batch 的 loss 先除以累积次数 $K$，再把梯度加起来，结果与一次算完的大 batch 相同；忘了除以 $K$ 就是 $K$ 倍（[验证 9.1-a](#v-9.1-a)、[验证 9.1-c](#v-9.1-c)），用 AdamW 时影响主要来自梯度裁剪（[验证 9.1-b](#v-9.1-b)）。前提是各 micro-batch 的有效 token 数相同（[验证 9.1-d](#v-9.1-d)）。
- 梯度检查点只存少数检查点、反向时重算，梯度逐位不变；$n$ 层时每 $\sqrt{n}$ 层设一个最省，计算量从约 3 份变成约 4 份（[验证 9.2-a](#v-9.2-a)、[验证 9.2-b](#v-9.2-b)）。CPU 上的本地测试里，全尺寸 WebBot 每条序列的激活从约 937 MiB 降到约 240 MiB；micro-batch 32 在 fp32 下约 29 GiB，bf16 autocast 下约 22 GiB（[验证 9.2-c](#v-9.2-c)）。
- 数据并行里各卡的梯度求平均，等于单卡的大 batch（[验证 9.3-a](#v-9.3-a)）；环形 all-reduce 让每张卡只发出 $2(W-1)N/W$ 个数（[验证 9.3-b](#v-9.3-b)）。原书的 `max_iters` 是写死的，加卡等于加 token；想让 8 张卡读同样多的 token，`max_iters` 和 `warmup_iters` 都要除以 8（[验证 9.3-d](#v-9.3-d)）。
- 全局 batch = micro-batch × 累积次数 × 卡数；强化学习里的 batch 是“题数 × 每题的回答数”条轨迹（[验证 9.3-e](#v-9.3-e)）。batch 翻 4 倍，平均梯度的噪声减半（[验证 9.3-f](#v-9.3-f)）。
- AdamW 的模型状态是每个参数 16 字节（[验证 9.4-a](#v-9.4-a)）。ZeRO-1、2、3 依次切分优化器状态、梯度和参数，75 亿参数、64 张卡时每张卡从 120 GB 降到 1.88 GB（[验证 9.4-b](#v-9.4-b)），而更新出的参数不变（[验证 9.4-c](#v-9.4-c)）。
- Muon 用 Newton–Schulz 迭代把每个奇异值送进同一个多项式，5 步就把 $[0.01,1]$ 送进 $[0.68,1.14]$，经典的三次迭代要 11 步（[验证 9.5-b](#v-9.5-b)、[验证 9.5-c](#v-9.5-c)）；它只用于隐藏层的矩阵，在 WebBot 里约占一半参数（[验证 9.5-e](#v-9.5-e)）。
- 原书每步记录的 `train/loss` 只是 rank 0 最后一个 micro-batch 的 loss（[验证 9.6-a](#v-9.6-a)）。按 H100 上 200 步的实测速度外推，完整训练 WebBot 要 1 张 H100 约 10.4 小时、约 41 美元（[验证 9.7-d](#v-9.7-d)）。
