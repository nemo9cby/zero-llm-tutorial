第 7 章我们在 OpenWebText 的约 119 亿字节上训练出了 WebBot 的分词器，词表有 50,000 个 token。数据和词表都已备齐，接下来轮到模型。第 5 章的 StoryBot 已经具备现代 LLM 的骨架：RoPE、SwiGLU、RMSNorm，生成时还有 KV cache。WebBot 原样继承这副骨架，只是规模大了一圈：参数从 2,270 万增加到 1.52 亿，上下文从 256 拉长到 1,024。

规模一变，问题就跟着变了。模型该做多大，数据该喂多少？注意力那个 N×N 的分数矩阵还放得下吗？生成时 KV cache 要吃掉多少显存？在 StoryBot 的尺度上，这些问题都可以不管；到了 WebBot，就一个也绕不开。本章按原书目录逐个回答：8.1 节用 scaling law 给模型定尺寸，8.2 节和 8.3 节用 Flash Attention 与 GQA 给注意力减负，8.4 节介绍让参数量与计算量脱钩的 MoE，8.5 节看 `torch.compile` 怎样让同样的计算跑得更快，8.6 节讨论上下文超过 1,024 时会发生什么、又该怎样扩展。

有一件事需要先交代。原书第 III 部只给要点、不给完整步骤，仓库里也没有 `ch08/` 这个目录。本章能落成代码的部分，都直接写进了 `webbot/model.py`（Flash Attention 与 GQA）和 `ch09/01_pretrain.py`（`torch.compile`）；MoE 和上下文扩展则一行代码也没有。所以本章分两种做法：书里有代码的地方，我们读懂它、再用 PyTorch 对拍；书里没有代码的地方，我们用 NumPy 写一个最小版本，再用验证单元把结论钉住。

## 8.1 选择模型规模

给 WebBot 选尺寸，本质上是在回答一个预算问题：手里的算力是固定的，应该把它花在更大的模型上，还是花在更多的数据上？回答之前，我们先把账算清楚：WebBot 到底有多少参数，训练一遍要花多少计算量。

### 把参数一个一个数出来

WebBot 的每个 Transformer 块（代码里的 `Block`）由 attention、SwiGLU 和两个 RMSNorm 组成，所有线性层都不带 bias。于是一个 Block 的参数量可以写成：

$$N_\text{block} = \underbrace{2E d_h H + 2E d_h H_{kv}}_{\text{attention}} + \underbrace{3E\,d_\text{ff}}_{\text{SwiGLU}} + \underbrace{2E}_{\text{RMSNorm}}$$

这里，$E$ 是 embedding 维度（`embed_dim`，768），$d_h$ 是每个头的维度（`head_dim`，64）。$H$ 和 $H_{kv}$ 分别是 query 头和 KV 头的个数（12 和 4），$d_\text{ff}$ 是 SwiGLU 的隐藏层宽度（`ff_dim`，2,048）。第一项是 $W_q$ 和 $W_o$，第二项是 $W_k$ 和 $W_v$。代入数字：attention 是 $2\times768\times64\times12 + 2\times768\times64\times4 = 1{,}179{,}648 + 393{,}216 = 1{,}572{,}864$，SwiGLU 是 $3\times768\times2048 = 4{,}718{,}592$，再加上 1,536 个 RMSNorm 权重，每层合计 6,292,992。12 层之外，还有输入 embedding 和输出层 unembed（都是 50,000×768），以及最后一个 RMSNorm。

```verify id=8.1-a title="WebBot 的参数量可以完全手算出来"
import numpy as np

def webbot_params(V=50000, E=768, H=12, KV=4, L=12, FF=2048):
    D = E // H                                       # 每个头的维度 head_dim = 64
    attn = E * H * D + 2 * E * KV * D + H * D * E    # W_q；W_k 与 W_v；W_o（都没有 bias）
    ffn = 3 * E * FF                                 # SwiGLU 的 W、V、O
    block = attn + ffn + 2 * E                       # 再加两个 RMSNorm 的权重
    return {"embed": V * E, "blocks": L * block, "norm": E, "unembed": E * V,
            "attn": attn, "ffn": ffn, "block": block}

def total_params(p):
    return p["embed"] + p["blocks"] + p["norm"] + p["unembed"]

p = webbot_params()
N = total_params(p)
for name in ["embed", "blocks", "norm", "unembed"]:
    print(f"{name:8s}{p[name]:>13,}  {p[name] / N:6.1%}")
print(f"total   {N:>13,}")
assert p["block"] == 6_292_992
assert N == 152_316_672        # 与 webbot/model.py 打印的 152,316,672 一致
```

输出里最醒目的一点是：输入 embedding 和输出层合起来占了一半。词表 5 万、宽度 768，光这两张表就有 7,680 万个参数，而真正做计算的 12 个 Block 只有 7,552 万个。词表越大，这笔“固定开销”越重，这也是第 7 章权衡词表大小时的一个考虑。

::: confusion 12·L·d² 里的 d 到底是哪个数？
读 scaling law 的文献，常会看到一个估算：不计 embedding 的参数量 $N \approx 12\,L\,d^2$（Kaplan 等，[arXiv:2001.08361](https://arxiv.org/abs/2001.08361) 2.1 节）。看到 $d$，自然会犹豫：它是 `embed_dim`、`hidden_size`，还是 `d_model`？其实这几个是同一个量，只是不同代码库起的名字不同：DLFS6 叫 `embed_dim`，Kaplan 的论文和 CS336 叫 $d_\text{model}$，Hugging Face 的配置叫 `hidden_size`，GPT-2 的配置叫 `n_embd`。它们都指残差流的宽度，在 WebBot 里是 768。

系数 12 又从哪来？Kaplan 假设的是 GPT-2 式的 Block：attention 的 Q、K、V、O 四个 $d\times d$ 矩阵共 $4d^2$，FFN 的两个 $d\times 4d$ 矩阵共 $8d^2$，合计 $12d^2$。WebBot 的 Block 不完全一样。SwiGLU 有三个矩阵，但宽度只有 $\tfrac{8}{3}d$，$3\times\tfrac{8}{3}d^2$ 恰好也是 $8d^2$；GQA 让 K、V 只剩 4 个头，各自缩成 $d^2/3$，于是 attention 只有 $2d^2 + 2\cdot\tfrac{d^2}{3} = \tfrac{8}{3}d^2$。每层合计约 $10.67d^2$，比 $12d^2$ 少 11%。可以带走的结论是：$12Ld^2$ 是 GPT-2 式结构的速算，换了结构就要重新数。
:::

```verify id=8.1-b title="12·L·d² 是 GPT-2 式结构的速算：WebBot 每层只有约 10.67d²"
L, d = 12, 768
non_emb = p["blocks"] + p["norm"]                     # 去掉输入 embedding 与输出层
print(f"WebBot 的非 embedding 参数: {non_emb:,}")
print(f"12·L·d² 的估算         : {12 * L * d**2:,}")
print(f"每层 attention = {p['attn'] / d**2:.3f} d²，SwiGLU = {p['ffn'] / d**2:.3f} d²")
assert p["ffn"] == 8 * d**2                           # SwiGLU(8d/3) 与 4d 的 FFN 一样都是 8d²
assert abs(p["attn"] / d**2 - 8 / 3) < 1e-12          # GQA：Q、O 各 d²，K、V 各 d²/3
assert abs(non_emb / (12 * L * d**2) - 0.889) < 1e-3  # 比速算少 11%
```

### 训练一遍要多少计算量：6ND

参数数清楚了，再来算计算量。训练时，每个参数在每个 token 上大约要花 6 次浮点运算，所以训练一遍的总计算量是

$$C \approx 6ND$$

这里，$N$ 是参数量，$D$ 是训练用的 token 数，$C$ 的单位是 FLOP（做一次乘法或一次加法，记作一次）。那么，6 是从哪里来的？前向时，每个权重对每个 token 做一次乘法和一次加法，这是 2 次。反向时，要分别求对输入的梯度和对权重的梯度，各是一次与前向同样大小的矩阵乘法，于是是前向的 2 倍，也就是 4 次。$2 + 4 = 6$。

我们用一个 4→3 的线性层把这笔账逐项核对一遍，顺便用数值微分确认，反向的那两次矩阵乘法算的确实是梯度：

```verify id=8.1-c title="反向传播恰好是两次与前向同样大小的矩阵乘法，所以是 6ND"
rng = np.random.default_rng(0)
T, d_in, d_out = 5, 4, 3                 # 5 个 token 经过一个 4→3 的线性层
X = rng.normal(size=(T, d_in))           # (T, d_in)
W = rng.normal(size=(d_in, d_out))       # (d_in, d_out)：12 个参数
dY = rng.normal(size=(T, d_out))         # 上游传回来的梯度

def matmul_flops(a, b):                  # (m×k)@(k×n)：m·n 个输出，各做 k 次乘法和 k 次加法
    m, k = a.shape
    return 2 * m * k * b.shape[1]

fwd = matmul_flops(X, W)                              # 前向 Y = XW
bwd = matmul_flops(dY, W.T) + matmul_flops(X.T, dY)   # 反向 dX = dY·Wᵀ，dW = Xᵀ·dY
print(f"前向 {fwd} FLOPs，反向 {bwd} FLOPs，合计 = {(fwd + bwd) // (T * W.size)} × token 数 × 参数量")
assert bwd == 2 * fwd and fwd + bwd == 6 * T * W.size

# 用中心差分确认 dW = Xᵀ·dY 确实是 loss = Σ (XW)⊙dY 对 W 的梯度
loss = lambda W_: np.sum((X @ W_) * dY)
eps, num = 1e-6, np.zeros_like(W)
for i in range(d_in):
    for j in range(d_out):
        e = np.zeros_like(W)
        e[i, j] = eps
        num[i, j] = (loss(W + e) - loss(W - e)) / (2 * eps)
err = np.abs(num - X.T @ dY).max()
assert err < 1e-6                        # 最后几位与机器有关，只断言上界
print("dW 与数值梯度一致：最大差小于 1e-6")
```

Kaplan 等人的论文正是这样定义训练计算量的：前向约 $2N$，反向约是前向的两倍，合计每个 token $6N$。严格地讲，attention 里“$Q$ 乘 $K^\top$”和“乘 $V$”这两步不涉及参数，会另外多出一项与上下文长度成正比的计算。在 1,024 的上下文下，它只占 8% 左右；8.6 节会看到，上下文一长，它就不能忽略了（[验证 8.6-d](#v-8.6-d)）。

拿什么来衡量“86 个 token/参数”是多还是少？答案是 Chinchilla。2022 年，Hoffmann 等人训练了 400 多个模型后得出结论：在算力固定时，模型大小每翻一倍，训练 token 也应该翻一倍（[arXiv:2203.15556](https://arxiv.org/abs/2203.15556)）。他们按这个结论训练的 Chinchilla 有 700 亿参数、1.4 万亿 token，正好每个参数 20 个 token，“20 token/参数”从此成了常用的经验值。论文附录 F 注明，参数量把 embedding 也算在内，所以我们拿 WebBot 的全部 1.52 亿参数来比。

这样一比，StoryBot 的 14.4 略低于 20，WebBot 的 86 则是它的 4 倍多。如果只追求“这点算力下 loss 最低”，同样的 $1.2\times10^{19}$ FLOPs 应该分给一个约 3 亿参数的模型、约 63 亿个 token。

:::
::: answer
要看目标是什么。Chinchilla 回答的是“训练花多少，loss 最低”，没有算推理的成本。模型一旦训练好，要被调用成千上万次，每次生成的开销都与参数量成正比。LLaMA 的论文就明确站在推理这一边：作者认为最理想的模型不是训练最快的，而是推理最快的，一个小模型训练得更久，最终在推理上更省（[arXiv:2302.13971](https://arxiv.org/abs/2302.13971)）。LLaMA-7B（论文表 2 记为 6.7B）用了 1.0 万亿 token，约 149 token/参数。WebBot 的 86 也是“小模型、多训练”这条路。

另一个约束是数据量。OWT 样本只有 26.5 亿个 token，WebBot 要把它重复看约 4.95 遍。Muennighoff 等人发现，重复不超过 4 遍时，loss 和全用新数据几乎一样；重复更多，追加算力的收益会逐渐趋近于零（[arXiv:2305.16264](https://arxiv.org/abs/2305.16264)）。WebBot 刚好越过这条线一点。
:::

### IsoFLOP：同样的算力，换不同的分法

“20 token/参数”只是一条经验规则。它背后的方法值得看一眼，因为 CS336 的作业 3 让学生亲手做的正是这件事。Chinchilla 论文的第二种方法叫 **IsoFLOP**（等算力曲线）：固定一个计算预算 $C$，训练一系列大小不同的模型。模型越大，能分到的 token 就越少（$D = C/6N$）。把每个模型最终的 loss 画成 $N$ 的函数，会得到一条 U 形曲线：模型太小，容量不够；模型太大，数据不够。曲线的最低点，就是这个预算下的最优规模 $N_\text{opt}(C)$。换几个 $C$ 重复一遍，就能拟合出 $N_\text{opt}$ 随 $C$ 增长的规律，论文给出的是 $N_\text{opt} \propto C^{0.49}$，几乎就是平方根。

我们没有算力训练几百个模型，但可以借用别人拟合好的结果。Chinchilla 论文的第三种方法把 loss 直接写成 $N$ 和 $D$ 的函数：

$$L(N, D) = E + \frac{A}{N^\alpha} + \frac{B}{D^\beta}$$

这里，$E$ 是数据本身的熵，也就是无限大的模型、无限多的数据也降不下去的部分；第二项是“模型太小”的代价，第三项是“数据太少”的代价。常数取 Besiroglu 等人 2024 年的复现拟合：$E = 1.8172$，$A = 482.01$，$B = 2085.43$，$\alpha = 0.3478$，$\beta = 0.3658$（[arXiv:2404.10102](https://arxiv.org/abs/2404.10102)）。不用原论文的常数，是因为复现论文指出：原常数推出的最优比例约为每参数 70 个 token，与 Chinchilla 自己采用的 20 对不上，而重新拟合的结果约为 20。

在 $D = C/6N$ 的约束下对 $N$ 求导，令导数为 0，可以解出最低点：

$$N_\text{opt}(C) = G\left(\frac{C}{6}\right)^{\frac{\beta}{\alpha+\beta}},\qquad G = \left(\frac{\alpha A}{\beta B}\right)^{\frac{1}{\alpha+\beta}}$$

这里，$G$ 只是由四个常数凑成的系数，约为 0.1196；指数 $\beta/(\alpha+\beta)$ 约为 0.513。把 WebBot 的 $C \approx 1.2\times10^{19}$ 代进去，$C/6 \approx 2.0\times10^{18}$，它的 0.513 次方约为 $2.4\times10^{9}$，乘以 0.1196，得到 $N_\text{opt} \approx 2.9$ 亿。与“20 倍规则”给出的 3.2 亿相差不远。

```verify id=8.1-e title="IsoFLOP 曲线的最低点：闭式解、约 20 token/参数、平坦的谷底"
E0, A, B, alpha, beta = 1.8172, 482.01, 2085.43, 0.3478, 0.3658   # Besiroglu 等 (2024)

def loss_fit(N, D):
    return E0 + A / N**alpha + B / D**beta

def n_opt(C):                         # 在 D = C/(6N) 上令 dL/dN = 0 的解
    G = (alpha * A / (beta * B)) ** (1 / (alpha + beta))
    return G * (C / 6) ** (beta / (alpha + beta))

Ns = np.logspace(7, 10, 3001)         # 1,000 万到 100 亿参数
i = np.argmin(loss_fit(Ns, C / (6 * Ns)))
print(f"WebBot 的 C 下：网格最低点 N = {Ns[i] / 1e6:.0f}M，闭式解 {n_opt(C) / 1e6:.0f}M")
for c in [1e18, 1e20, 1e22, 1e24]:
    n = n_opt(c)
    print(f"C = {c:.0e}：N_opt = {n:9.3g}，D_opt / N_opt = {c / 6 / n**2:4.1f}")
No = n_opt(C)
gap = lambda f: loss_fit(No * f, C / (6 * No * f)) - loss_fit(No, C / (6 * No))
print(f"WebBot 的 N / N_opt = {N / No:.2f}，多付出的 loss = {gap(N / No):.3f}")
print(f"偏离最优 2 倍：+{gap(2):.3f}；偏离 4 倍：+{gap(4):.3f}")
assert abs(Ns[i] / n_opt(C) - 1) < 0.002                   # 闭式解就是网格上的最低点
assert all(17 < c / 6 / n_opt(c)**2 < 26 for c in [1e18, 1e20, 1e22, 1e24])   # “约 20”
assert gap(N / No) < 0.03 and gap(2) < 0.04 and gap(4) > 0.1
```

`F.scaled_dot_product_attention`（下文简称 SDPA）其实是一个调度员。本机 PyTorch 2.14.1 的文档字符串写明，它背后有三种实现：FlashAttention-2、Memory-Efficient Attention，以及一个按公式直译的 C++ 实现，会根据输入自动挑选。那么，Flash Attention 是怎样避开那个 C×C 矩阵的？

### 关键的一步：online softmax

直观上，Flash Attention 像是在一张小书桌上统计一本厚书：不把整本书摊开，而是一章一章地读，边读边更新笔记，读完最后一章，结论也就出来了。严格地讲，它把 Q、K、V 切成小块，每次只把一小块搬进 GPU 芯片上又小又快的 SRAM 里计算，从而大大减少对显存（HBM）的读写（Dao 等，[arXiv:2205.14135](https://arxiv.org/abs/2205.14135)）。它算出的结果与普通 attention 相同（只差浮点舍入），不是近似。

难点在 softmax。softmax 的分母要对一整行求和，还要先知道这一行的最大值（为了数值稳定）。如果一次只看得到一小块分数，怎么办？

如果你读过《深度学习入门》3.5.2 节，会记得 softmax 的溢出对策：先减去最大值再取指数，结果不变。**online softmax** 把这个技巧往前推了一步（Milakov 与 Gimelshein，[arXiv:1805.02867](https://arxiv.org/abs/1805.02867)）：最大值不必事先知道，可以边读边更新。读到更大的值时，就把之前累加的和乘上 $e^{m - m'}$，相当于把旧的和“补减”到新的基准上：

$$m' = \max\Big(m,\ \max_j x_j\Big),\qquad \ell' = \ell\, e^{m - m'} + \sum_j e^{x_j - m'}$$

这里，$m$ 和 $\ell$ 是读到目前为止的最大值，以及以 $m$ 为基准的指数和；带撇的是读完新的一块之后的值，$x_j$ 是这一块里的数。读完最后一块，$\ell$ 就等于 $\sum e^{x - \max x}$，与一次性计算的结果相同。我们手算 $x = [1, 3, 2, 5]$，分两块读：

- 读完 $[1, 3]$：$m = 3$，$\ell = e^{1-3} + e^{0} = 1.1353$。
- 读完 $[2, 5]$：$m' = 5$，$\ell' = 1.1353\times e^{3-5} + e^{2-5} + e^{0} = 0.1537 + 0.0498 + 1 = 1.2034$。
- 一次性计算：$e^{-4} + e^{-2} + e^{-3} + e^{0} = 1.2034$，相同。

```verify id=8.2-b title="online softmax：分块读、边读边修正，结果与一次性计算相同"
x = np.array([1.0, 3.0, 2.0, 5.0])
m, l = -np.inf, 0.0                         # 当前最大值，以及以 m 为基准的指数和
for chunk in (x[:2], x[2:]):                # 一次只读两个数
    m_new = max(m, chunk.max())
    l = l * np.exp(m - m_new) + np.exp(chunk - m_new).sum()   # 旧的和补减到新基准
    m = m_new
    print(f"读完 {chunk.tolist()}：m = {m:.0f}，l = {l:.4f}")
direct = np.exp(x - x.max()).sum()
print(f"一次性计算：{direct:.4f}")
assert abs(l - direct) < 1e-15
assert np.allclose(np.exp(x - m) / l, np.exp(x) / np.exp(x).sum())   # 由 m、l 得到的就是 softmax
```

### 分块计算 attention

同样的技巧可以用在 attention 的输出上。输出是 softmax 权重与 V 的加权和，我们维护一个没有归一化的累加器 $O$，每当最大值变大，就像对 $\ell$ 那样把它也乘上 $e^{m - m'}$，最后再整体除以 $\ell$。对第 $i$ 块 query 和第 $j$ 块 key，一次更新是：

$$S = \frac{Q_i K_j^\top}{\sqrt{d}},\quad m' = \max\big(m, \operatorname{rowmax}(S)\big),\quad P = e^{S - m'}$$

$$\ell' = e^{m - m'}\,\ell + \operatorname{rowsum}(P),\qquad O' = e^{m - m'}\,O + P\,V_j$$

这里，$Q_i$ 是第 $i$ 块 query（$B_r$ 行），$K_j$、$V_j$ 是第 $j$ 块 key 和 value（$B_c$ 行），$m$、$\ell$、$O$ 都按行维护；全部块处理完后，令 $O \leftarrow O/\ell$。这就是 FlashAttention-2 论文中前向算法的骨架（[arXiv:2307.08691](https://arxiv.org/abs/2307.08691)）。加上因果掩码时还有一个额外的好处：完全落在对角线右上方的块里全是 $-\infty$，可以整块跳过。我们用 NumPy 实现它，再和朴素的写法对拍：

```verify id=8.2-c title="分块 + online softmax 与朴素 attention 相同（误差 1e-16 量级），且只用到 Br×Bc 个分数"
def attention_naive(Q, K, V, causal=True):
    T, d = Q.shape
    S = Q @ K.T / np.sqrt(d)                          # (T, T)：一次摆出全部分数
    if causal:
        S = np.where(np.tril(np.ones((T, len(K)), dtype=bool)), S, -np.inf)
    P = np.exp(S - S.max(axis=1, keepdims=True))
    return (P / P.sum(axis=1, keepdims=True)) @ V

def attention_flash(Q, K, V, causal=True, Br=16, Bc=16):
    T, d = Q.shape
    O, lse = np.empty_like(Q), np.empty(T)
    stats = {"tiles": 0, "peak": 0}
    for i0 in range(0, T, Br):                        # 外层：一块 query（Br 行）
        q = Q[i0:i0 + Br]
        rows = np.arange(i0, i0 + len(q))[:, None]
        m = np.full(len(q), -np.inf)                  # 每行的当前最大值
        l = np.zeros(len(q))                          # 每行的指数和
        acc = np.zeros_like(q)                        # 每行还没归一化的输出
        for j0 in range(0, len(K), Bc):               # 内层：一块 key / value（Bc 行）
            if causal and j0 > rows[-1, 0]:
                break                                 # 整块都在对角线右上方：跳过
            k, v = K[j0:j0 + Bc], V[j0:j0 + Bc]
            s = q @ k.T / np.sqrt(d)                  # (Br, Bc)：只算这一小块
            if causal:
                cols = np.arange(j0, j0 + len(k))[None, :]
                s = np.where(cols <= rows, s, -np.inf)
            m_new = np.maximum(m, s.max(axis=1))
            p = np.exp(s - m_new[:, None])
            scale = np.exp(m - m_new)                 # 最大值变了，旧的累加量要重新缩放
            l = scale * l + p.sum(axis=1)
            acc = scale[:, None] * acc + p @ v
            m = m_new
            stats["tiles"] += 1
            stats["peak"] = max(stats["peak"], s.size)
        O[i0:i0 + Br] = acc / l[:, None]
        lse[i0:i0 + Br] = m + np.log(l)               # 每行的 log-sum-exp，留给反向传播
    return O, lse, stats

rng = np.random.default_rng(0)
T, d = 64, 16
Q, K, V = (rng.normal(size=(T, d)) for _ in range(3))
O, lse, st = attention_flash(Q, K, V)
err = np.abs(O - attention_naive(Q, K, V)).max()
print(f"分块与朴素的最大差: {err:.1e}")
print(f"访问的块: {st['tiles']} / {(T // 16) ** 2}；同时存在的分数最多 {st['peak']} 个（朴素版 {T * T} 个）")
assert err < 1e-12 and st["tiles"] == 10 and st["peak"] == 16 * 16

# 不加掩码、长度不是块大小的整数倍时，结果也一样
Q5, K5, V5 = (rng.normal(size=(50, d)) for _ in range(3))
for causal in (True, False):
    O5, _, _ = attention_flash(Q5, K5, V5, causal=causal, Br=16, Bc=8)
    assert np.abs(O5 - attention_naive(Q5, K5, V5, causal=causal)).max() < 1e-12
```

### 反向传播怎么办

朴素实现会把 softmax 的结果 $P$（每个头 $T\times T$ 个数）留给反向传播。Flash Attention 不保存 $P$，只为每一行保存一个数，即 log-sum-exp：$\text{lse} = m + \log \ell$。反向传播时，再从 $Q$、$K$ 逐块重算分数，用 $P = e^{S - \text{lse}}$ 把概率原样恢复出来。多算一遍矩阵乘法，换来不必存、也不必读那个 $T\times T$ 的矩阵。

```verify id=8.2-d title="只存每行一个 log-sum-exp，就能在反向时原样重算出 softmax 概率"
S = Q @ K.T / np.sqrt(d)
S = np.where(np.tril(np.ones((T, T), dtype=bool)), S, -np.inf)
P = np.exp(S - S.max(axis=1, keepdims=True))
P /= P.sum(axis=1, keepdims=True)            # 朴素版要存下的 (T, T) 概率
P_again = np.exp(S - lse[:, None])           # Flash 版：用每行一个 lse 重算
print(f"重算的概率与原概率的最大差: {np.abs(P_again - P).max():.1e}")
print(f"需要保存的数：朴素版 {P.size} 个，Flash 版 {lse.size} 个")
assert np.abs(P_again - P).max() < 1e-12
```

那么，在 GPU 上它到底快多少？我们手头的验证只覆盖了“结果相同”和“内存线性”这两点。速度要在 GPU 上测，这里引用论文的报告。FlashAttention 在序列长度 1K 的 GPT-2 上加速约 3 倍，在 BERT-large（序列长度 512）上端到端加速 15%（[arXiv:2205.14135](https://arxiv.org/abs/2205.14135)）。FlashAttention-2 改进了 GPU 上的任务划分，又比前一版快约 2 倍，在 A100 上达到理论峰值算力的 50%–73%（[arXiv:2307.08691](https://arxiv.org/abs/2307.08691)）。

## 8.3 Grouped-Query Attention（GQA）

训练时的显存问题，Flash Attention 已经解决了。生成文本时还有另一笔开销：第 5 章的 KV cache。生成每一个新 token，attention 都要用到前面所有 token 的 K 和 V，所以我们把它们缓存下来。每多一个 token，缓存就多出

$$\text{每 token 字节数} = 2 \times L \times H_{kv} \times d_h \times b$$

这里，2 表示 K 和 V 各一份，$L$ 是层数，$H_{kv}$ 是 KV 头的个数，$d_h$ 是每个头的维度，$b$ 是每个数的字节数（bf16 为 2）。假如 WebBot 用普通的多头注意力（**MHA**，multi-head attention），每个 query 头都有自己的 K、V，$H_{kv} = 12$，那么每个 token 要 $2\times12\times12\times64\times2 = 36{,}864$ 字节，也就是 36 KiB；1,024 个 token 是 36 MiB，batch 为 32 时超过 1 GiB。

占地方还不是全部。生成时每走一步，都要把整个缓存从显存里读一遍，而这一步的计算量却很小，速度于是卡在显存带宽上。Shazeer 在 2019 年提出的 **MQA**（multi-query attention）让所有头共用一份 K、V，大大减少了这部分读取，代价是质量略有下降（[arXiv:1911.02150](https://arxiv.org/abs/1911.02150)）。**GQA**（grouped-query attention）取两者之间：把 query 头分成几组，每组共用一份 K、V（Ainslie 等，[arXiv:2305.13245](https://arxiv.org/abs/2305.13245)）。论文的结论是，经过少量继续训练（uptraining）的 GQA，质量接近 MHA，速度接近 MQA。

WebBot 用的是 12 个 query 头、4 个 KV 头，每 3 个 query 头共用一份 K、V。代码上的改动只有两处：K、V 投影的输出维度从 `H * D` 变成 `KV * D`，

### 第 h 个 query 头用哪个 KV 头？

12 个 query 头、4 个 KV 头，谁和谁一组？PyTorch 的约定是：第 $h$ 个 query 头使用第 $\lfloor h / (H/H_{kv}) \rfloor$ 个 KV 头。以 6 个 query 头、2 个 KV 头为例，分组是 $[0, 0, 0, 1, 1, 1]$：相邻的头一组。SDPA 的文档字符串给出了等价的参考实现，`enable_gqa` 那两行用的正是 `repeat_interleave`，即把每个 KV 头复制 3 份、挨着排放。如果手写时误用了 `repeat`（整体平铺），得到的是 $[0, 1, 0, 1, 0, 1]$，也就是另一种分组。

```verify id=8.3-a title="GQA 的分组：repeat_interleave 与定义一致，平铺（repeat）是另一种分组"
def softmax(z, axis=-1):
    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=axis, keepdims=True)

def causal_attn(q, k, v):                     # 单个头：q、k、v 都是 (T, d)
    s = q @ k.T / np.sqrt(q.shape[-1])
    s = np.where(np.tril(np.ones((len(q), len(k)), dtype=bool)), s, -np.inf)
    return softmax(s) @ v

rng = np.random.default_rng(1)
H, KV, T, d = 6, 2, 5, 4                      # 6 个 query 头，2 个 KV 头
g = H // KV                                   # 每组 3 个 query 头
Q = rng.normal(size=(H, T, d))
K, V = rng.normal(size=(KV, T, d)), rng.normal(size=(KV, T, d))

ref = np.stack([causal_attn(Q[h], K[h // g], V[h // g]) for h in range(H)])   # 定义：第 h 头用第 h // g 个 KV 头
Kr, Vr = np.repeat(K, g, axis=0), np.repeat(V, g, axis=0)   # 相当于 torch 的 repeat_interleave → (H, T, d)
Kt, Vt = np.tile(K, (g, 1, 1)), np.tile(V, (g, 1, 1))       # 相当于 torch 的 Tensor.repeat（平铺）
inter = np.stack([causal_attn(Q[h], Kr[h], Vr[h]) for h in range(H)])
tiled = np.stack([causal_attn(Q[h], Kt[h], Vt[h]) for h in range(H)])
print("repeat_interleave 的分组:", [h // g for h in range(H)])
print("repeat（平铺）的分组    :", [h % KV for h in range(H)])
print(f"与定义的最大差：interleave {np.abs(inter - ref).max():.1e}，平铺 {np.abs(tiled - ref).max():.2f}")
assert np.allclose(inter, ref) and not np.allclose(tiled, ref)
```

## 8.4 Mixture of Experts（MoE）

8.1 节说，模型越大，loss 越低；可是每个 token 的计算量也跟着参数量涨（$6N$）。有没有办法让参数变多，而每个 token 的计算量不变？**MoE**（混合专家）的想法是：把 FFN 复制成 $E$ 份，称为**专家**（expert），每个 token 只交给其中 $k$ 个专家处理，由一个小小的 **router**（路由器）决定交给谁。

直观上，router 像医院的分诊台：病人很多，科室也很多，分诊台看一眼症状，把每个人送到最合适的一两个科室，其余科室这位病人就不用去了。严格地讲，router 是一个从 $d$ 维映射到 $E$ 维的线性层 $W_g$，对它的输出取最大的 $k$ 个，再做 softmax 作为权重。Mixtral 8x7B 的 MoE 层写作（[arXiv:2401.04088](https://arxiv.org/abs/2401.04088) 2.1 节）：

$$y = \sum_{i=0}^{E-1} \operatorname{softmax}\big(\operatorname{Top}k(x W_g)\big)_i \cdot \operatorname{SwiGLU}_i(x)$$

这里，$x$ 是一个 token 的向量，$\operatorname{Top}k$ 只保留最大的 $k$ 个 logits，其余视为 $-\infty$（softmax 后就是 0），$\operatorname{SwiGLU}_i$ 是第 $i$ 个专家，结构与 WebBot 的 FFN 相同。Mixtral 有 8 个专家，每个 token 选 2 个。手算一个例子：某个 token 对 4 个专家的 logits 是 $[2.0, 1.0, 0.5, -1.0]$，取前 2 名，即专家 0 和 1，权重为 $\operatorname{softmax}([2, 1]) = [0.731, 0.269]$。它与“先对 4 个数做 softmax，再在前 2 名上重新归一化”是同一回事。

```verify id=8.4-a title="先取 top-k 再 softmax，等于先 softmax 再在 top-k 上重新归一化"
z = np.array([2.0, 1.0, 0.5, -1.0])           # 一个 token 对 4 个专家的 router logits
top = np.argsort(-z)[:2]                      # logits 最大的 2 个专家
g1 = softmax(z[top])                          # Mixtral 的写法：先取 top-2，再 softmax
p = softmax(z)
g2 = p[top] / p[top].sum()                    # 另一种写法：先 softmax，再在 top-2 上归一化
print("选中的专家:", top.tolist(), " 全体 softmax:", np.round(p, 4).tolist())
print("两种写法的门控权重:", np.round(g1, 4).tolist(), np.round(g2, 4).tolist())
assert top.tolist() == [0, 1] and np.allclose(g1, g2) and abs(g1[0] - 0.7311) < 1e-4
```

### 一个最小的 MoE 层

实现 MoE 层，最直白的写法是让每个专家都算一遍全部 token，再按门控权重加权求和。这样结果正确，却把省下的计算全浪费了。真正的实现是“分派”：每个专家只处理分给自己的 token。我们把两种写法都写出来，确认结果相同：

```verify id=8.4-b title="只算被选中的专家（稀疏分派）与全部都算（稠密）结果相同，计算量只有 k/E"
rng = np.random.default_rng(2)
T, d, ff, E, k = 12, 8, 16, 4, 2             # 12 个 token，4 个专家，每个 token 选 2 个
X = rng.normal(size=(T, d))
Wg = rng.normal(size=(d, E))                 # router 的权重
experts = [{n: rng.normal(size=s) * 0.3 for n, s in [("W", (d, ff)), ("V", (d, ff)), ("O", (ff, d))]}
           for _ in range(E)]

def swiglu(x, e):                            # 与 WebBot 的 SwiGLU 同一个结构
    a = x @ e["W"]
    return (a / (1 + np.exp(-a)) * (x @ e["V"])) @ e["O"]

logits = X @ Wg                              # (T, E)
top = np.argsort(-logits, axis=1)[:, :k]     # (T, k)：每个 token 选中的专家
gate = np.zeros((T, E))
for t in range(T):
    gate[t, top[t]] = softmax(logits[t, top[t]])

dense = sum(gate[:, [e]] * swiglu(X, experts[e]) for e in range(E))   # 每个专家都算全部 token
sparse, load = np.zeros_like(X), []
for e in range(E):                           # 每个专家只算分给自己的 token
    idx = np.nonzero(gate[:, e])[0]
    load.append(len(idx))
    if len(idx):
        sparse[idx] += gate[idx, e:e + 1] * swiglu(X[idx], experts[e])
print(f"稀疏与稠密的最大差: {np.abs(sparse - dense).max():.1e}")
print(f"各专家处理的 token 数: {load}，合计 {sum(load)} = {T} × {k}（稠密做法是 {T * E}）")
assert np.abs(sparse - dense).max() < 1e-12
assert sum(load) == T * k and ((gate > 0).sum(axis=1) == k).all()
```

注意输出里的负载：4 个专家分别收到 3、10、3、8 个 token，很不均匀。这正是 MoE 训练中最常见的麻烦。

### 负载均衡

如果 router 偏爱少数几个专家，这几个专家收到的 token 最多，得到的训练也最多，于是变得更好，router 就更偏爱它们；其余专家几乎学不到东西。Switch Transformer 用一个辅助 loss 来对抗这种“富者愈富”（Fedus 等，[arXiv:2101.03961](https://arxiv.org/abs/2101.03961) 式 (4)）：

$$\mathcal{L}_\text{aux} = \alpha \cdot E \cdot \sum_{i=1}^{E} f_i\, P_i$$

这里，$f_i$ 是这一批 token 里（按 router 的最大值）被分给第 $i$ 个专家的比例，$P_i$ 是 router 给第 $i$ 个专家的平均概率，$\alpha$ 是这项 loss 的权重，论文取 $10^{-2}$。我们先手算两个极端。完全均匀时，$f_i = P_i = 1/E$，$E\sum f_i P_i = E\cdot E\cdot\frac{1}{E^2} = 1$；全部挤到一个专家时，$f_1 = P_1 = 1$，其余为 0，结果是 $E$。$f_i$ 是计数得来的，不可导，梯度只经过 $P_i$：$\partial\mathcal{L}_\text{aux}/\partial P_i = \alpha E f_i$。负载越重的专家，它的概率被往下压得越狠。

```verify id=8.4-c title="负载均衡 loss：均匀时为 1，全部挤到一个专家时为 E，梯度与负载成正比"
def aux_loss(probs, assign, E):
    f = np.bincount(assign, minlength=E) / len(assign)   # 实际分到每个专家的 token 比例
    P = probs.mean(axis=0)                               # router 给每个专家的平均概率
    return E * np.sum(f * P), f, P                       # Switch Transformer 式 (4)，不含 α

n = 64
uniform = aux_loss(np.full((n, E), 1 / E), np.arange(n) % E, E)[0]
collapsed = aux_loss(np.tile(np.eye(E)[0], (n, 1)), np.zeros(n, int), E)[0]
probs = softmax(logits)                                  # 上一个验证里那个 router 的概率
toy, f, P = aux_loss(probs, probs.argmax(axis=1), E)
print(f"完全均匀: {uniform:.2f}；全部挤到一个专家: {collapsed:.2f}；上面的 router: {toy:.2f}")
print(f"f = {np.round(f, 3).tolist()}，P = {np.round(P, 3).tolist()}")
grad = np.array([(np.sum(f * (P + 1e-6 * np.eye(E)[i])) - np.sum(f * (P - 1e-6 * np.eye(E)[i]))) * E / 2e-6
                 for i in range(E)])            # 对 P_i 的数值导数
print(f"对 P_i 的梯度 = {np.round(grad, 3).tolist()}（就是 E·f_i）")
assert abs(uniform - 1) < 1e-12 and abs(collapsed - E) < 1e-12 and toy > 1
assert np.allclose(grad, E * f)
```

除了辅助 loss，实际的系统还会给每个专家设一个**容量**（capacity）：一批 token 里，每个专家最多处理多少个。Switch Transformer 的定义是“每批 token 数 ÷ 专家数 × capacity factor”（式 (3)）；超出容量的 token 被丢弃，它跳过这一层的专家，只经由残差连接原样传到下一层。

```verify id=8.4-d title="容量不够时 token 会被丢弃：capacity factor 1.0 丢 6 个，2.0 只丢 1 个"
first = top[:, 0]                              # 按 top-1 分配（Switch Transformer 的做法）
print("各专家收到的 token:", np.bincount(first, minlength=E).tolist())
drops = []
for cf in [1.0, 1.5, 2.0]:
    cap = int(T / E * cf)                      # 每批 token 数 ÷ 专家数 × capacity factor（向下取整）
    used, dropped = np.zeros(E, int), 0
    for e in first:
        if used[e] < cap:
            used[e] += 1
        else:
            dropped += 1                       # 超出容量：跳过专家，只走残差连接
    drops.append(dropped)
    print(f"capacity factor {cf}：每个专家容量 {cap}，丢弃 {dropped} 个 token")
assert drops == [6, 4, 1]
```

### 总参数与激活参数

MoE 模型通常同时报两个数：**总参数**（所有专家加起来）和**激活参数**（每个 token 实际用到的）。训练和推理的计算量看激活参数，显存看总参数。我们用 Mixtral 论文表 1 公开的结构数一数，再给 WebBot 设想一个 MoE 版本：每层 8 个专家、每个 token 选 2 个，每个专家和原来的 FFN 一样大。

```verify id=8.4-e title="Mixtral 8x7B：总参数 46.7B，每个 token 只激活 12.9B"
def moe_params(dim, layers, heads, kv, head_dim, hidden, vocab, n_exp, topk):
    attn = 2 * dim * heads * head_dim + 2 * dim * kv * head_dim
    expert = 3 * dim * hidden                    # 一个 SwiGLU 专家
    per_layer = attn + dim * n_exp + 2 * dim     # attention、router、两个 RMSNorm
    shared = 2 * vocab * dim + dim               # embedding、输出层、最后的 RMSNorm
    return (shared + layers * (per_layer + n_exp * expert),     # 总参数
            shared + layers * (per_layer + topk * expert))      # 每个 token 激活的参数

t_mix, a_mix = moe_params(4096, 32, 32, 8, 128, 14336, 32000, n_exp=8, topk=2)   # Mixtral 论文表 1
t_web, a_web = moe_params(768, 12, 12, 4, 64, 2048, 50000, n_exp=8, topk=2)      # 假想的 WebBot-MoE
print(f"Mixtral 8x7B：总参数 {t_mix / 1e9:.2f}B，每个 token 激活 {a_mix / 1e9:.2f}B")
print(f"WebBot-MoE  ：总参数 {t_web / 1e6:.1f}M，每个 token 激活 {a_web / 1e6:.1f}M")
print(f"AdamW 的静态显存（每参数 16 字节）：WebBot-MoE {16 * t_web / 1e9:.1f} GB，原版 {16 * N / 1e9:.1f} GB")
t64, a64 = moe_params(768, 12, 12, 4, 64, 2048, 50000, n_exp=64, topk=2)   # 专家增加到 64 个，仍选 2 个
print(f"WebBot-MoE 换成 64 个专家：总参数 {t64 / 1e9:.2f}B（{t64 / t_web:.1f} 倍），激活 {a64 / 1e6:.1f}M")
assert round(t_mix / 1e9) == 47 and round(a_mix / 1e9) == 13    # 论文：47B 参数，13B 激活
assert t_web == 548_752_128 and a_web == 209_013_504
assert t64 == 3_720_162_048 and a64 == 209_529_600
```

Mixtral 的两个数与论文摘要里的“47B 参数、每个 token 只用 13B”一致。WebBot-MoE 的总参数是原版的 3.6 倍，每个 token 的计算量只是原版的 1.37 倍（激活 2.09 亿对 1.52 亿）。代价在显存上：fp32 的权重、梯度和 AdamW 的两个状态，每个参数共 16 字节，所有专家都得放得下，静态显存从 2.4 GB 涨到 8.8 GB。专家太多、一张卡放不下时，就要把不同的专家放到不同的 GPU 上（专家并行），token 在卡与卡之间来回发送，这又是另一套工程了。

## 8.5 torch.compile

前面几节改的都是“算什么”。这一节换个角度：同样的计算，能不能算得更快？`ch09/01_pretrain.py` 里有一行看起来毫不起眼的代码（モデル＝模型）：

```listing ch09/01_pretrain.py#L140-L153
```

如果你读过《深度学习入门2：自制框架》的专栏 B，会记得深度学习框架分两类：Define-by-Run（边执行边建立计算图，好调试，能直接写 `if` 和 `for`）和 Define-and-Run（先定义整张图再执行，便于优化，比如把乘法和加法融合成一步）。PyTorch 平时属于前者，即所谓的 eager 模式：每个运算一执行就交给一个独立的 kernel。`torch.compile` 让它在不改代码的前提下获得后者的好处。按 PyTorch 2.0 的官方介绍（[pytorch.org/get-started/pytorch-2.0](https://pytorch.org/get-started/pytorch-2.0/)），它由几部分组成：

- **TorchDynamo** 借助 Python 的帧求值钩子，把 Python 代码捕获成一张图；
- **AOTAutograd** 提前把反向传播也追踪成图；
- **TorchInductor** 把图编译成更快的代码：在 GPU 上生成 Triton kernel，在 CPU 上生成多线程的 C++ 代码。

### 融合省下的是什么

有了整张图，编译器就能把相邻的运算**融合**（fusion）成一个 kernel。以 SwiGLU 里的 `F.silu(a) * b` 为例：eager 模式下这是两个 kernel，`silu` 读入 `a`、写出中间结果，乘法再读入中间结果和 `b`、写出结果；融合之后只需读入 `a` 和 `b`、写出一次结果。这类逐元素运算，每个数只做几次乘加，时间几乎全花在显存读写上，所以少搬多少数据，大致就快多少。这是直观的估计，真实的加速要在 GPU 上测。

```verify id=8.5-a title="SwiGLU 的 silu(a)*b：逐个执行要搬 5 个张量，融合后只搬 3 个"
elems = 32 * 1024 * 2048                      # 一个 micro-batch 里 SwiGLU 的中间张量 (B, T, ff_dim)
mib = elems * 2 / 2**20                       # bf16：每个张量 128 MiB
eager = (1 + 1) * mib + (2 + 1) * mib         # silu：读 a、写 s；乘法：读 s 和 b、写 g
fused = (2 + 1) * mib                         # 融合成一个 kernel：读 a 和 b、写 g
print(f"每个张量 {mib:.0f} MiB；逐个执行搬 {eager:.0f} MiB，融合后 {fused:.0f} MiB（少 {1 - fused / eager:.0%}）")
assert mib == 128 and abs(eager / fused - 5 / 3) < 1e-12
```

## 8.6 扩展上下文长度

WebBot 能看到的上下文是 1,024 个 token。这一节回答三个问题：这个数从哪来？超过它会发生什么？能不能不重新预训练，就把它拉长？

::: confusion 1024 这个上限是谁规定的？
顺着代码找一遍就清楚了。它来自 `ch09/01_pretrain.py` 里的 `context_len = 1024`（[8.1 节的代码清单](#s8-1)），这个值作为 `max_context_len` 传给 `GPT`，在三个地方起作用：

1. 训练时，`get_batch` 每次切出长 1,024 的窗口，模型从来没见过 1,024 及以后的位置；
2. RoPE 的 cos、sin 表正好有 1,024 行（见下面的代码清单）；
3. 生成时，KV cache 最多保留 1,024 个位置。

至于为什么偏偏是 1,024：WebBot 的宽度 768、12 层、12 个头、上下文 1,024，与 GPT-2 small 的配置完全相同（Hugging Face 上的 [config.json](https://huggingface.co/openai-community/gpt2/blob/main/config.json)：`n_embd` 768、`n_layer` 12、`n_head` 12、`n_ctx` 1024）。原书没有明说，看起来是有意对齐。可以带走的结论是：上下文长度不是模型的天性，而是训练时定下的一组约定，想改就得在这三处一起动手。
:::

### 超过上限时，代码做了什么

先看 RoPE 的前向（「offsetを考慮して位置エンコーディングを取得」＝考虑 offset 来取位置编码）：


第 33–34 行是关键：如果 `offset + context_len` 超出表的长度，就把 `offset` 钳在 `max_context_len - context_len`。生成时每次只送入 1 个 token（`context_len` 为 1），所以过了第 1,024 个位置之后，每一个新 token 都被当作位置 1,023 来旋转。再看 KV cache 的处理（「コンテキスト長制限: キャッシュが長すぎる場合は古い部分を切り捨て」＝上下文长度限制：缓存过长时，丢掉最旧的部分）：

```listing webbot/model.py#L101-L108
```

WebBot 的缓存像一个滑动窗口，只保留最近 1,024 个位置的 K、V；第 5 章的 StoryBot 没有这几行，缓存会一直变长。但两者的位置都被冻结在了最后一格。我们用 NumPy 照搬这段 RoPE，看看冻结的后果：

```verify id=8.6-a title="超过 1,024 后位置被钳在 1,023：位置 1,500 的 query 看位置 1,000 的 key，像是只隔了 23"
def rope_cache(theta, D, max_len, pos_scale=1.0):
    inv_freq = 1.0 / theta ** (2.0 * np.arange(D // 2) / D)          # (D/2,)
    angles = (np.arange(max_len) / pos_scale)[:, None] * inv_freq     # (max_len, D/2)
    return np.cos(angles), np.sin(angles)

def rope(x, cos, sin, offset=0):            # x: (T, D)，逐行照搬 webbot/model.py 的 RoPE.forward
    T = x.shape[0]
    if offset + T > cos.shape[0]:            # 第 33–34 行：超出表的长度，就把 offset 钳住
        offset = cos.shape[0] - T
    c, s = cos[offset:offset + T], sin[offset:offset + T]
    xe, xo = x[:, 0::2], x[:, 1::2]
    out = np.empty_like(x)
    out[:, 0::2] = xe * c - xo * s
    out[:, 1::2] = xe * s + xo * c
    return out

rng = np.random.default_rng(3)
cos, sin = rope_cache(10000.0, 64, 1024)    # WebBot：head_dim 64，表长 1024
q, k = rng.normal(size=(1, 64)), rng.normal(size=(1, 64))
k_old = rope(k, cos, sin, offset=1000)      # 缓存里一个位置 1,000 的 key
s1100 = (rope(q, cos, sin, offset=1100) @ k_old.T).item()
s1500 = (rope(q, cos, sin, offset=1500) @ k_old.T).item()
s23 = (rope(q, cos, sin, offset=23) @ rope(k, cos, sin, offset=0).T).item()
print(f"query 在 1,100：{s1100:.6f}；在 1,500：{s1500:.6f}；一对相距 23 的 q、k：{s23:.6f}")
assert np.array_equal(rope(q, cos, sin, 1100), rope(q, cos, sin, 1023))
assert abs(s1100 - s1500) < 1e-12 and abs(s1500 - s23) < 1e-9
```

位置 1,100 和位置 1,500 的 query 得到了完全相同的分数，而且都等于“相距 23”的那个分数。RoPE 的好处是分数只依赖相对位置（第 5 章），可一旦位置被冻结，相对位置也就错了：模型以为它们只隔了 23 个位置。这不会报错，生成的文本只是悄悄变差。下面的本地测试在原书的两个模型上确认了这一行为：

### 为什么不能直接外推

那为什么不干脆把 cos、sin 表算长一点，让位置继续往后走？回忆第 5 章：RoPE 把向量的维度两两配成一对，第 $i$ 对在位置 $m$ 处旋转的角度是 $m\,\omega_i$，其中 $\omega_i = \theta^{-2i/d_h}$。$i$ 小的那几对转得快，1,024 个位置内要转好多圈，什么角度都见过；$i$ 大的那几对转得慢，**波长** $2\pi/\omega_i$ 比 1,024 还长，训练时只转过了圆周的一部分。外推到 1,024 之后，这些慢的维度会转到训练时从未见过的角度上。

```verify id=8.6-b title="WebBot 的 32 对维度里，有 14 对在 1,024 个位置内转不满一圈"
slow_pairs = {}
for name, D, L in [("WebBot", 64, 1024), ("StoryBot", 32, 256)]:
    omega = 10000.0 ** (-2.0 * np.arange(D // 2) / D)   # 第 i 对维度每前进一个位置转过的角度
    wavelength = 2 * np.pi / omega                      # 转满一圈需要的位置数
    slow = np.nonzero(wavelength > L)[0]
    slow_pairs[name] = (len(slow), slow[0])
    print(f"{name}：{D // 2} 对中有 {len(slow)} 对（i ≥ {slow[0]}）在 {L} 个位置内转不满一圈，"
          f"最长的波长 {wavelength[-1]:,.0f}")
assert slow_pairs == {"WebBot": (14, 18), "StoryBot": (9, 7)}
```

### 两种扩展方法：位置插值与 NTK-aware

第一种方法是**位置插值**（Position Interpolation，简称 PI，Chen 等，[arXiv:2306.15595](https://arxiv.org/abs/2306.15595)）。想把上下文从 $L$ 扩到 $L'$，就令 $s = L'/L$，把位置 $m$ 换成 $m/s$。这样一来，所有位置都被压回训练时的范围 $[0, L)$ 之内，没有任何一个角度是陌生的。代价是相邻 token 的间隔从 1 变成了 $1/s$：转得最快、本来负责区分相邻 token 的那几对维度，分辨率也跟着降低了。论文用不超过 1,000 步的微调来适应这一点，把 LLaMA 的上下文扩到了 32,768。

第二种方法叫 **NTK-aware**，由网友 bloc97 在 2023 年的一篇网络帖子里提出，后来 YaRN 的论文把它整理成了式子（Peng 等，[arXiv:2309.00071](https://arxiv.org/abs/2309.00071)）。它不动位置，而是改 RoPE 的底数：

$$\theta' = \theta \cdot s^{\frac{d_h}{d_h - 2}}$$

这里，$\theta$ 是原来的底数（WebBot 是 10,000），$d_h$ 是每个头的维度，$s$ 同上。这个指数选得很巧：最快的那一对（$i = 0$）的 $\omega_0 = \theta'^{0} = 1$，完全不变；最慢的那一对（$i = d_h/2 - 1$）恰好被放慢 $s$ 倍，在 $L'$ 个位置内转过的角度与训练时大致相同；中间的各对平滑过渡。用 YaRN 论文的话说，它把插值的压力分摊到各个维度上：高频少缩，低频多缩。以 WebBot 为例，$s = 2$ 时 $\theta' = 10000 \times 2^{64/62} \approx 20{,}452$。

```verify id=8.6-c title="NTK-aware：最高频不变，最低频恰好放慢 s 倍；PI 则把位置压回训练范围"
D, theta, s = 64, 10000.0, 2.0              # WebBot 的 head_dim，把 1,024 扩到 2,048
i = np.arange(D // 2)
omega = theta ** (-2.0 * i / D)
theta_ntk = theta * s ** (D / (D - 2))      # NTK-aware：只改底数
omega_ntk = theta_ntk ** (-2.0 * i / D)
print(f"NTK-aware 的新底数: {theta_ntk:,.0f}")
print("第 0、8、16、24、31 对被放慢的倍数:", np.round(omega / omega_ntk, 3)[[0, 8, 16, 24, 31]].tolist())
pos_pi = np.arange(2048) / s                # PI：位置 m 换成 m/s
print(f"PI 之后最大的位置: {pos_pi.max()}（训练时见过 0 到 1023），相邻 token 的间隔: {pos_pi[1]}")
assert omega_ntk[0] == omega[0] == 1.0                # 最高频的那一对完全不变
assert abs(omega[-1] / omega_ntk[-1] - s) < 1e-9      # 最低频的那一对恰好放慢 s 倍
assert np.all(np.diff(omega / omega_ntk) > 0)         # 中间平滑过渡
assert pos_pi.max() < 1024
```

### 长上下文的账单

能扩展，并不等于扩展是免费的。KV cache 随上下文长度线性增长（8.3 节）；attention 的计算量也随长度增长：第 $t$ 个 token 要和 $t$ 个 key 做内积，再对 $t$ 个 value 加权求和。在因果掩码下平均起来，训练时每个 token 在 attention 上约花 $6LTd$ 次运算（$T$ 为上下文长度），而参数部分是 $6N$。$T$ 一长，前者就会反超后者。这里的 $N$ 应该只算参与矩阵乘法的参数，输入 embedding 只是查表，不算在内。

```verify id=8.6-d title="WebBot 的上下文超过约 12,000 后，attention 的计算量超过所有参数矩阵乘的总和"
N_mm = N - 50000 * 768                      # 参与矩阵乘的参数（输入 embedding 只是查表）
L_, d_ = 12, 768
T_, dh = 1024, 64
exact = sum(4 * t * dh for t in range(1, T_ + 1)) / T_      # 第 t 个 token 看 t 个 key：QKᵀ 与乘 V 各 2·t·d_h
print(f"单个头前向，每 token 的精确平均 {exact:,.0f}，近似 2·T·d_h = {2 * T_ * dh:,}")
for T in [1024, 4096, 32768]:
    att = 6 * L_ * T * d_                   # 训练时 attention 部分每个 token 的 FLOPs
    print(f"上下文 {T:>6,}：attention {att / 1e6:7.1f}M，参数部分 6N = {6 * N_mm / 1e6:.1f}M，比值 {att / (6 * N_mm):.2f}")
T_cross = N_mm / (L_ * d_)
print(f"两者相等的上下文长度：{T_cross:,.0f}")
assert abs(exact / (2 * T_ * dh) - 1) < 1e-3
assert 12_000 < T_cross < 12_500
```

在 1,024 的上下文下，attention 只占参数部分的 8%；到 4,096 是 33%；超过约 12,000 以后，attention 就成了大头。Flash Attention 让显存只随长度线性增长，计算量却仍然随长度的平方增长。这就是长上下文昂贵的根本原因。

::: confusion 上下文只有 1,024，为什么一段对话能处理几千个 token？
这个直觉很自然：既然窗口只有 1,024，总量怎么能超过 1,024？关键在于，窗口限制的是**一次请求**（一次前向）能看到的 token 数，而“处理了多少 token”统计的是**所有请求之和**。聊天程序每一轮都会把完整的历史重新发一遍，所以累计的 token 数大约随轮数的平方增长。比如每轮新增 100 个 token、聊 10 轮：第 10 轮的请求是 1,000 个 token，没有超过窗口；10 次请求加起来却处理了 5,500 个 token。可以带走的结论是：上下文窗口是单次请求的上限，累计消耗是所有请求的和，两者不是一个量。扩展上下文，扩的是前者。
:::

```verify id=8.6-e title="每轮新增 100 个 token、聊 10 轮：单次请求最多 1,000，累计 5,500"
per_turn, turns, window = 100, 10, 1024
requests = [per_turn * k for k in range(1, turns + 1)]    # 每一轮都把完整的历史重新发一遍
print("每次请求的长度:", requests)
print(f"单次请求的峰值 {max(requests):,}（不超过窗口 {window:,}），累计处理 {sum(requests):,} 个 token")
assert max(requests) <= window and sum(requests) == 5500
```

::: cs336 位置编码的底数与长上下文
CS336 作业 3 的训练 API 用的模型把 RoPE 的底数设成了 $10^6$（DLFS6 是 $10^4$）；底数越大，最慢那一对维度的波长越长，模型能分辨的位置范围也越大。讲义第 3 讲在架构部分提到了滑动窗口注意力（SWA）与不用位置编码（NoPE）的混合方案，第 10 讲讨论怎样压缩 KV cache 的显存。本节的 PI 与 NTK-aware 属于“训练之后再扩展”，与“训练时就用大底数”是两条可以叠加的路。
:::

## 小结

本章给 WebBot 的模型定了尺寸，并给它配上了大模型必备的几样工具。我们先把 1.52 亿个参数逐个数清，用 $6ND$ 算出训练要 $1.2\times10^{19}$ 次运算，再用 Chinchilla 的 20 token/参数和 IsoFLOP 曲线看出：WebBot 走的是“小模型、多训练”的路，代价很小。接着，Flash Attention 用 online softmax 把 attention 切成小块计算，结果与普通写法一致，显存却从平方降到线性；GQA 让每 3 个 query 头共用一份 K、V，KV cache 从 36 KiB/token 降到 12 KiB/token。原书没有代码的 MoE 和上下文扩展，我们用 NumPy 和真实的 StoryBot 权重亲手做了实验：MoE 用总参数换激活参数，NTK-aware 不做微调也能把 StoryBot 的上下文翻倍。

模型准备好了，但 131 亿个 token 还没有喂进去。下一章，我们要面对的是训练本身的规模问题：一张卡放不下一个 batch 怎么办，多张卡怎样协同。

**本章所学的内容**

- WebBot 的参数量 152,316,672 可以完全手算出来，其中一半是 embedding 与输出层；$12Ld^2$ 只是 GPT-2 式结构的速算（[验证 8.1-a](#v-8.1-a)、[验证 8.1-b](#v-8.1-b)）。
- 训练计算量 $C \approx 6ND$：前向 2 次、反向 4 次，反向恰好是两次同样大小的矩阵乘法（[验证 8.1-c](#v-8.1-c)）。
- WebBot 每个参数看 86 个 token，是 Chinchilla 20 的 4 倍多；IsoFLOP 曲线的谷底很平，它只多付出约 0.03 的 loss（[验证 8.1-d](#v-8.1-d)、[验证 8.1-e](#v-8.1-e)）。
- Flash Attention 靠 online softmax 分块计算，结果与普通 attention 相同，只需保存每行一个 log-sum-exp（[验证 8.2-c](#v-8.2-c)、[验证 8.2-d](#v-8.2-d)）。
- GQA 的分组是 `repeat_interleave`，不是 `repeat`；WebBot 的 KV cache 从 36 KiB/token 降到 12 KiB/token（[验证 8.3-a](#v-8.3-a)、[验证 8.3-b](#v-8.3-b)）。
- MoE 的稀疏分派与稠密计算结果相同，计算量只有 $k/E$；负载均衡 loss 在均匀时为 1、坍缩时为 $E$（[验证 8.4-b](#v-8.4-b)、[验证 8.4-c](#v-8.4-c)）。
- 超过 `max_context_len` 后，原书代码把位置钳在最后一格；NTK-aware 改底数，保持最高频不变、最低频恰好放慢 $s$ 倍（[验证 8.6-a](#v-8.6-a)、[验证 8.6-c](#v-8.6-c)）。

按 MFU 35% 估算，一张 H100 要连续跑将近 10 个小时，才能把这 131 亿个 token 喂完。能不能把这件事拆给 8 张卡，而结果一模一样？这就是第 9 章的故事。
