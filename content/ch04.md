第 1 章，我们从“一个字符一个编号”出发，一路写出了 BPE 分词器，并用它把 TinyCodes 编码成了 CodeBot 的训练数据。那份实现完全照着算法的定义来写：每学一条合并规则，就把整个语料从头数一遍、再从头合并一遍。代码短，道理也清楚。代价是慢：在 6.5 MB 的 TinyCodes 上学 743 条规则，本机用了 52 分钟的 CPU 时间（同机满载，实际等了 77 分钟）。

第 II 部的 StoryBot 要读的是 TinyStories，一个 2.2 GB 的英文小故事语料，词表也从 1,000 扩大到 10,000。语料大了约 343 倍，合并次数从 743 变成 9,743。朴素实现每一步都要把全部语料扫一遍，工作量大致与“合并次数 × 语料字节数”成正比，两者相乘，是 CodeBot 的四千多倍。照这个比例粗算，第 1 章的代码要连续跑五个多月。内存也撑不住：它会把整个文件读成一个字符串，再为每一次出现的单词各存一份字节列表。


本章的做法是：算法一行不改，只改实现。训练这一侧分四步：去重（4.1）、增量更新（4.2）、分块读取（4.3）、多进程并行（4.4）。接着评估训练好的分词器（4.5）。然后编码也提速两步：按优先级合并（4.6）、分块并行并写成二进制文件（4.7）。每一步我们都回答三个问题：改了什么？为什么结果和朴素版逐项相同？快了多少，剩下的时间又花在哪里？如果你读过《深度学习进阶：自然语言处理》第 4 章“word2vec 的高速化”，会觉得这个节奏很眼熟：那一章也是先点出瓶颈，再一节解决一个。

## 4.1 改进 BPE 训练①：去重

### 4.1.1 原实现的问题

先回顾第 1 章的训练函数，它整理在 `codebot/tokenizer.py` 里：

```listing codebot/tokenizer.py#L31-L59
```

前半段把语料按 `<|endoftext|>` 切开、做预分词，然后把**每一次出现**的预分词都转成一份字节列表，存进 `ids_list`。后半段是合并循环：每一步都遍历整个 `ids_list` 数一遍相邻对（pair），挑出最多的那个，再遍历一遍把它合并掉。

下方的曲线来自实测：我们在验证集和训练集开头的不同长度上，分别数了出现次数和不同的预分词个数。语言学里管这种“词汇量随语料增长得越来越慢”的规律叫 **Heaps 定律**（Heaps' law），常写成 $U \approx k N^{\beta}$。这里，$N$ 是出现次数，$U$ 是不同的预分词个数，$\beta$ 是一个小于 1 的指数。在双对数坐标上它是一条直线，$\beta$ 就是斜率：

```verify id=4.1-e title="出现次数涨 100 倍，不同的预分词只涨不到 5 倍" files=data/ch04/bench.json
import json, math
rows = [r for r in json.load(open("data/ch04/bench.json", encoding="utf-8"))["heaps"] if r["file"] == "train_prefix.txt"]
first, last = rows[0], rows[-1]
n_ratio, u_ratio = last["occurrences"] / first["occurrences"], last["unique"] / first["unique"]
beta = math.log(u_ratio) / math.log(n_ratio)
print(f"出现次数 {first['occurrences']:,} -> {last['occurrences']:,}（{n_ratio:.1f} 倍）")
print(f"不同的预分词 {first['unique']:,} -> {last['unique']:,}（{u_ratio:.1f} 倍）")
print(f"双对数坐标下的斜率 beta = {beta:.2f}")
print(f"外推：语料再大 21 倍（整份训练集），不同的预分词约变为现在的 {21 ** beta:.1f} 倍")
assert n_ratio > 99 and u_ratio < 5 and 0.30 < beta < 0.36
```

训练集的前 100 MiB 里有 21,808 个不同的预分词。按这个斜率外推，整份 2.2 GB 的训练集大约是它的 2.7 倍，五六万个；出现次数却会多出 20 倍。所以语料越大，去重省下的工作越多。外推毕竟只是外推，这里只看量级。

### 4.1.2 去除重复

想法很简单：既然 `' the'` 出现了 N 次，就不必存 N 份，只记一行“`' the'`：N 次”。数 pair 的时候，把这个词内部的每个 pair 都加上 N。这就像唱票：一万张写着同一个名字的选票，不必一张一张念，记下“某某，一万票”就够了。

严格地讲，我们要的是每个 pair 在整个语料里出现的次数 $N(a,b)$。按不同的预分词分组来数，就是

$$N(a,b) = \sum_{w} c_w \, n_w(a,b)$$

这里，$w$ 遍历所有不同的预分词，$c_w$ 是 $w$ 出现的次数，$n_w(a,b)$ 是 pair $(a,b)$ 在 $w$ 内部出现的次数。朴素版对 $w$ 的每一次出现各数一遍，等于把 $c_w$ 个相同的 $n_w(a,b)$ 加起来，所以两种数法的结果必然相等。

来算一个能心算的例子。语料里有 `low` 5 次、`lower` 2 次、`newest` 6 次、`widest` 3 次。pair `(e, s)` 在 `newest` 和 `widest` 里各出现一次，所以 $N(e,s) = 6 \times 1 + 3 \times 1 = 9$；`(s, t)` 同样是 9。两者并列第一。原书挑 pair 的规则是比较 `(次数, 第一个 id, 第二个 id)`，`s` 的字节值 115 大于 `e` 的 101，所以第一条合并规则是 `st`。

```verify id=4.1-b title="按次数加权计数 == 把每次出现展开后计数"
from collections import defaultdict
words = {"low": 5, "lower": 2, "newest": 6, "widest": 3}

weighted = defaultdict(int)              # 去重：每个词只数一遍，乘上次数
for w, c in words.items():
    bk.count_pairs(tuple(w.encode()), c, weighted)

expanded = defaultdict(int)              # 朴素：每一次出现都数一遍（第 1 章的 count_pairs）
for w, c in words.items():
    for _ in range(c):
        bk.count_pairs_v1(list(w.encode()), expanded)

show = lambda pair: bytes(pair).decode()
print({show(p): n for p, n in sorted(weighted.items(), key=lambda kv: -kv[1])[:4]})
best = max(weighted, key=lambda pair: (weighted[pair], pair[0], pair[1]))
print("第一条合并:", show(best))
assert weighted == expanded
assert show(best) == "st" and weighted[best] == weighted[tuple(b"es")] == 9
```

这个玩具语料来自 CS336 作业 1 的[讲义](https://github.com/stanford-cs336/assignment1-basics)（讲义注明它取自 Sennrich 等人的论文），讲义也是用“`(e, s)` 与 `(s, t)` 并列”这一步来说明平票规则的。用原书的训练器跑它，前 6 条合并依次是 `s t`、`e st`、`o w`、`l ow`、`w est`、`n e`，与讲义给出的结果一致（[验证 4.1-d](#v-4.1-d) 会顺便跑一遍）。

:::

### 4.1.4 改进版的运行验证

::: confusion 去重之后，结果还和原来一样吗？
直觉上会担心：把一万次出现压成一行，会不会丢掉什么信息？答案是不会，因为两件事同时成立。第一，计数是可加的，上面的公式已经说明，加权计数与展开计数相等。第二，`merge` 只看序列本身：两个相同的序列，合并之后仍然相同，所以同一个预分词的一万次出现永远“步调一致”，用一行加权记录代替它们不会出错。

还有第三个条件容易被忽略：每一步挑出的 pair 必须相同。原书的 `max` 用 `(次数, id0, id1)` 作 key，这是一个全序，挑出来的 pair 与字典里的顺序无关。4.2 节会看到，少了它会发生什么。
:::

现在让朴素版和去重版在同一段文字上各学 43 条规则（词表 300），逐项比较。顺便数一数两者每一步要扫描多少字节：


扫描的字节少了几倍，时间就省几倍吗？我们在更大的输入上实测：TinyStories 验证集的前 499,577 字节，词表 1,000。这段文字有 120,503 次出现、3,523 个不同的预分词，每一步要扫描的字节从 491,504 降到 22,792，少了 21.6 倍。实测的 CPU 时间是朴素版 185 秒、去重版 13.8 秒，快了 13 倍左右（[图 4-1](#fig-4-1) 的第一组）。

## 4.2 改进 BPE 训练②：增量更新

### 4.2.1 当前的问题

去重之后，每一步仍然要做两件全量的事：把所有不同的序列重新数一遍 pair，再把它们全部合并一遍。可是，一次合并只会改变**含有**那个 pair 的序列，其余的序列原封不动。那么，每一步到底有多少序列真的变了呢？

```verify id=4.2-a title="每一步只有少数几个序列受影响" files=data/ch04/bpe_ext.py
import bpe_ext as bx                     # 本教程的扩展代码：ch04/02 的循环 + 几个计数器
stats = {}
rules = bx.train_incremental(text, 400, stats=stats)  # 学 143 条
aff = sorted(stats["affected"])
print(f"不同的预分词: {stats['unique']:,} 个")
print(f"每一步受影响的: 平均 {sum(aff) / len(aff):.1f} 个，中位数 {aff[len(aff) // 2]} 个，最多 {aff[-1]} 个")
assert sum(aff) / len(aff) < 0.05 * stats["unique"]
# 训练是贪心的：词表 400 的前 43 条规则，就是词表 300 的全部规则
assert list(rules.items())[:len(dedup)] == list(dedup.items())
```

在这一小段文字上，每一步平均只有百分之一二的序列受到影响。语料越大，这个比例越小：在整份 TinyStories 验证集上学 9,743 条规则，13,111 个不同的预分词里，每一步平均只有 7.05 个受到影响，中位数只有 1 个。

### 4.2.2 用缓存做增量更新

想法是：维护一张 pair 计数表，合并之后只修改受影响的那几行，而不是每一步从头重算。这就像记账：每发生一笔交易，只改动相关账户的余额，而不是每天把所有流水从头加一遍。

严格地讲，我们要始终保持下面这个等式成立：

$$N(a,b) = \sum_{w} c_w \, n_w(a,b)$$

这里的符号与 4.1.2 节相同，只是 $w$ 现在是“当前”的序列（已经做过若干次合并）。把 pair $p$ 合并成新 token $t$ 时，不含 $p$ 的序列不变，它们的贡献也不变；含有 $p$ 的序列 $w$ 变成 $w'$，贡献从 $c_w\,n_w$ 变成 $c_w\,n_{w'}$。所以只要对受影响的每个 $w$ 做两件事：减去 $c_w \cdot$（$w$ 的所有 pair），再加上 $c_w \cdot$（$w'$ 的所有 pair），等式就继续成立。

还是用玩具语料手算第一步。合并 `st` 之后，`newest`（6 次）里的 pair 从 `ne, ew, we, es, st` 变成 `ne, ew, we, e·st`，`widest`（3 次）同理。于是 $N(e,s) = 9 - 6 - 3 = 0$，$N(s,t)$ 也变成 0，两行从表里删掉；新出现的 $N(e, st) = 6 + 3 = 9$。`ne` 被减去 6 又加回 6，保持不变。`low` 和 `lower` 根本不用碰。

剩下的问题是：怎样不扫描全部序列，就找出“含有 $p$ 的序列”？答案是再维护一张**倒排索引**（inverted index）`pair_to_ids`：每个 pair 对应一个集合，里面是含有它的所有序列。原书管它叫“缓存”（キャッシュ）。下图可以一步一步地看这两张表怎样变化。

循环之前，先全量数一次 pair，同时建好倒排索引。循环里，挑出 `best_pair` 之后，从索引里取出含有它的序列集合 `affected_ids`，然后对其中每个序列做三件事：把出现次数挪到合并后的新元组上，减去旧序列的全部 pair，加上新序列的全部 pair。计数降到 0 的 pair 直接删掉，免得下一步的 `max` 还要看它。

有两个细节值得注意。第一，`del pair_to_ids[best_pair]` 之后，循环里减旧 pair 时会执行 `pair_to_ids[best_pair].discard(...)`，`defaultdict` 会悄悄新建一个空集合。这无害，只是留下一个空条目。第二，`affected_ids` 这个集合对象在进入循环之前就已经从字典里摘了下来，所以循环中修改 `pair_to_ids` 不会影响正在遍历的集合。

::: think 循环里写的是 `ids_counts[tuple(new_ids)] = ids_count`，用的是 `=` 而不是 `+=`。这样会不会覆盖掉别的序列的次数？

::: confusion 为什么非要写 `(pair_counts[pair], pair[0], pair[1])` 这样一个奇怪的 key？

要继续提速，就得换掉这次全表扫描。一个办法是用**堆**（heap），把“找最大值”从扫描全表变成取堆顶。麻烦在于计数每一步都在变，而 Python 的 `heapq` 不支持修改堆里的元素。常用的绕法叫**惰性删除**（lazy deletion）：计数变了，不去改旧条目，而是把新的计数再压进堆里；取堆顶时，如果它记的计数与计数表里的对不上，说明它已经过期，扔掉再取下一个。堆里的元素写成 `(-次数, -id0, -id1)`，弹出顺序就与原书的 key 完全一致。这个实现在 `bpe_ext.py` 的 `train_bpe_heap` 里，不是原书的代码，可以当作一个扩展练习。在整份验证集上，合并循环从 66.8 秒（CPU 时间）降到 2.8 秒，快了 24 倍，学到的 9,743 条规则逐项相同（[图 4-1](#fig-4-1) 的“合并循环”一组）。先在浏览器里用小样本确认结果不变：


### 4.3.2 内存消耗的原因

罪魁祸首是 CPython 存储字符串的方式。CPython 不是给每个字符固定分配几个字节，而是看整个字符串里**最宽**的那个字符：最宽的字符不超过 U+00FF（ASCII 和西欧字母），每个字符占 1 字节；最宽的字符在 U+0100 到 U+FFFF 之间，每个字符占 2 字节；只要出现一个 U+FFFF 以上的字符（比如 emoji），整个字符串的每个字符都占 4 字节。这个规则来自 [PEP 393](https://peps.python.org/pep-0393/)。

```verify id=4.3-a title="一个 emoji 让整个字符串的内存变成 4 倍"
def bytes_per_char(ch, n=100_000):
    """字符串每多一个字符，内存多几个字节（与对象头的大小无关）。"""
    return (sys.getsizeof(ch * 2 * n) - sys.getsizeof(ch * n)) / n

for ch in ["a", "…", "🍌"]:
    print(f"{ch!r}  U+{ord(ch):04X}  每个字符占 {bytes_per_char(ch):.0f} 字节")
plain = "a" * 1_000_000
print(f"100 万个 'a' 末尾加一个 '🍌'，内存变成原来的 {sys.getsizeof(plain + '🍌') / sys.getsizeof(plain):.2f} 倍")
assert [bytes_per_char(c) for c in "a…🍌"] == [1, 2, 4]
```

TinyStories 验证集里最宽的字符是省略号 `…`（U+2026），所以整读之后每个字符占 2 字节；训练集的前 100 MiB 里出现了一个 🍌（U+1F34C），于是整个字符串每个字符占 4 字节：104,813,654 个字符，光这一个字符串就占了 419 MB。验证集的字符串则是 22,493,387 个字符、45 MB。这就是内存暴涨里最大的一块。

讽刺的是，按 `<|endoftext|>` 切开之后，每个故事各自决定自己的宽度，而含有 U+00FF 以上字符的故事只占 2.6%（验证集）到 2.7%（训练集的前 100 MiB）。切开之后各段字符串加起来，验证集只要 23.9 MB，训练集的前 100 MiB 只要 111 MB，而整串分别是 45 MB 和 419 MB。也就是说，问题不在文本本身，而在“把整个文件放进同一个字符串”这个做法。解决办法自然是：一次只读一小块。

### 4.3.3 部分读取文件

一次只读一小块，切在哪里呢？不能随便切。如果切点落在一个单词中间，比如把 `" little"` 切成 `" lit"` 和 `"tle"`，预分词的结果就变了，学出来的合并规则也会跟着变。安全的切点是 `<|endoftext|>`：它把故事彼此隔开，训练时本来就要先按它切开（第 1 章 1.5 节）。

`find_chunk_boundaries` 做的就是这件事。它先把文件按字节数等分，再把每个内部切点向后挪到最近的一个 `<|endoftext|>` 的开头：

```listing ch04/03_bpe_chunk.py#L36-L77
```

设文件大小为 $S$、块数为 $k$。初始切点是 $0, \lfloor S/k \rfloor, 2\lfloor S/k \rfloor, \dots$，最后补上文件末尾 $S$。对每个内部切点，从那里开始每次读 4,096 字节，在读到的数据里找 `<|endoftext|>`；找到了，切点就挪到它的第一个字节；读到文件末尾也没找到，切点就是 $S$。最后 `sorted(set(...))` 去掉重复的切点：块数比故事数还多时，好几个初始切点会挪到同一个 `<|endoftext|>` 上。

::: column 预分词的内存效率
把预分词的结果存在哪里，决定了训练要多少内存。本章的几个版本恰好代表了三种做法。

第 1 章的朴素版为每一次出现都存一个字节列表。Python 的列表是对象，一个 4 字节的单词变成列表之后，光列表本身就占 88 字节（64 位 Python），几百万次出现就是几百 MB。4.1 节的去重版只保留“不同的预分词 → 次数”的字典，条目数只有一万多，而且随语料增长得很慢（[图 4-2](#fig-4-2)）。4.3 节再进一步：一次只读一块，`finditer` 一次只产出一个匹配，任何时刻内存里只有“当前这一块”和那张小字典。

我们在 TinyStories 验证集上实测了几种写法的峰值内存：

| 写法 | 内存里放着什么 | 峰值内存 |
|---|---|---:|
| 第 1 章：每次出现存一个列表 | 541 万个 `list[int]` | 661 MiB |
| 整读，并把所有预分词放进一个列表 | 一个大字符串 + 541 万个 `str` | 364 MiB |
| 4.1、4.2：整读，按故事边读边数 | 一个大字符串 + 一万多项的字典 | 102 MiB |
| 4.3：分块读取 + 生成器 | 一块（约 350 KB）+ 一万多项的字典 | 36 MiB |

（与 4.3.1 节的表格同样的测法。）换一个更细的量法也能看到同样的差距：用 Python 自带的 `tracemalloc` 只统计 Python 对象分配的内存，在 1 MB 的故事上，朴素版的预分词阶段峰值约 27.6 MB，去重版约 4.0 MB，分块版约 2.2 MB。

CS336 作业 1 的讲义也给了同样的建议：用 `re.finditer` 逐个处理预分词，而不是用 `re.findall` 一次性存下所有结果。

## 4.4 改进 BPE 训练④：并行化

### 4.4.1 Python 中的并行处理

预分词的各个块之间互不依赖，天然适合并行。不过在 CPython 里，多线程帮不上纯 Python 计算的忙：同一时刻只有一个线程能执行 Python 字节码，这把锁叫作 GIL（[全局解释器锁](https://docs.python.org/3/glossary.html#term-global-interpreter-lock)）。所以原书用的是多进程：`multiprocessing.Pool` 启动若干个独立的 Python 进程，把任务分给它们。

```python
from multiprocessing import Pool

def square(x):            # 工作函数：必须定义在模块的顶层
    return x * x

if __name__ == "__main__":
    with Pool(processes=4) as pool:
        print(list(pool.imap(square, range(8))))   # [0, 1, 4, 9, 16, 25, 36, 49]
```

`pool.imap` 把任务逐个分给空闲的进程，并按任务的顺序返回结果。这段代码里有两处写法不是可有可无的。

第一，`if __name__ == "__main__":` 必须写。子进程怎样启动，取决于**启动方式**（start method）：Windows 只有 spawn，即启动一个全新的 Python 解释器，再重新导入主模块；macOS 默认也是 spawn；Linux 在 Python 3.13 及以前默认 fork（直接复制父进程），从 3.14 起默认 forkserver（见 [Python 文档](https://docs.python.org/3/library/multiprocessing.html#contexts-and-start-methods)；我们也直接查看了 3.12 与 3.14 的 `multiprocessing/context.py` 源码）。在 spawn 方式下，子进程会重新执行主模块的顶层代码；没有这道守卫，子进程又会去创建进程池。

第二，工作函数必须能被子进程“找到”。spawn 出来的子进程只认识能 import 到的函数。如果工作函数定义在 `python -c` 的命令行代码里，子进程会报 `AttributeError: Can't get attribute 'square' on <module '__main__' …>`；如果脚本是从标准输入喂给 Python 的（`python - < script.py`），子进程连主模块都读不到，报的是 `OSError: [Errno 22] Invalid argument: '…<stdin>'`。更糟的是，父进程的 `pool.imap` 会一直等下去，既不报错也不退出。

```localcheck verify/test_ch04.py::test_spawn_needs_importable_worker title="在 python -c 里定义工作函数：Process 立即失败，Pool 则一直挂起"
```

最后，进程不是免费的。spawn 一个进程要重新导入 `regex`、`tqdm` 等模块，任务的参数和结果还要序列化（pickle）后在进程之间传递。在本机满载时，启动一个进程池、让每个进程做一个空任务、再关掉，1 个进程要 2.1 秒，8 个进程要 3.3 秒。数据量小的时候，这点开销就能把并行的收益吃光。

::: confusion 开了 8 个进程，为什么总时间没快 8 倍？
这是并行最常见的落差。设可以并行的部分单进程要 $T_p$ 秒，只能串行的部分要 $T_s$ 秒，用 $n$ 个进程，启动等开销为 $T_o$，总加速比是

$$S(n) = \frac{T_p + T_s}{T_p / n + T_s + T_o}$$

这里，$T_p$ 是预分词，$T_s$ 是合并循环。心算一个例子：$T_p = 12$ 秒、$T_s = 30$ 秒、不计开销，8 个进程时总时间是 $1.5 + 30 = 31.5$ 秒，加速比只有 $42 / 31.5 \approx 1.33$。进程再多也超不过 $42 / 30 = 1.4$。这就是 **Amdahl 定律**（Amdahl's law）：加速比的上限由串行部分决定。

这就像包饺子：八个人一起擀皮、包馅，快得很，可锅只有一口，煮饺子的时间一分钟也省不下来。
:::

它按训练顺序把**全部**合并规则试一遍。CodeBot 只有 743 条规则，还能忍受；StoryBot 有 9,743 条，每个预分词都要调用 9,743 次 `merge`，哪怕这个词只有两三个字节。实测下来，编码验证集开头的 29,642 字节，第 1 章的编码器用了 45.5 秒 CPU 时间，光是 `' accomplishment'` 这一个词就要 15 毫秒。照这个速度粗算，编码 2.2 GB 的训练集要 40 天左右（[验证 4.6-c](#v-4.6-c)）。

### 4.6.2 高效的编码处理

可是，一个预分词里真正用得上的规则屈指可数。以 `' accomplishment'` 为例，9,743 条规则里只有 14 条真正改变了它，其余 9,729 次 `merge` 都是白跑。

改进的想法是：不再按规则表从头试到尾，而是只看序列里**现有**的相邻对，从中挑出优先级最高的那个先合并，重复这个过程，直到没有可合并的对为止。规则的优先级就是它的 id：id 越小，学到得越早，优先级越高。这就像按号叫人：第 1 章的做法是把 9,743 个号码从头喊到尾，看谁在场；新做法是先看在场的有谁，直接叫其中号码最小的那位。

```verify id=4.6-a title="按优先级合并 ' accomplishment'：14 步，id 单调递增"
word = " accomplishment"
ids = list(word.encode("utf-8"))
while len(ids) > 1:
    best = min(bk.count_pairs(ids), key=lambda pair: rules.get(pair, float("inf")))
    if best not in rules:
        break
    ids = bk.merge(ids, best, rules[best])
    print(f"{rules[best]:>5}", [tok.decode([i]) for i in ids])
old_tok = bk.BPETokenizerV1(rules)                     # 第 1 章的编码器：9,743 条规则逐条试
print("第 1 章的编码器:", old_tok._encode_text(word), " 按优先级合并:", ids)
assert ids == old_tok._encode_text(word) == tok._encode_text(word) == [7159]
```

被用到的 14 条规则，id 从 258 一路递增到 7159。这不是巧合，它正是两种做法等价的原因。我们分三步说明：

1. 第 $r$ 条规则把 pair $(a, b)$ 合并成 $256 + r$。$a$ 和 $b$ 在第 $r$ 步之前就已经存在，所以 $a, b < 256 + r$：每条规则只用到比自己“老”的 token。
2. 执行第 $r$ 条规则之后，序列里新出现的相邻对都含有 $256 + r$。由第 1 点，含有 $256 + r$ 的规则一定比第 $r$ 条更晚；而 `merge` 从左到右贪心地合并，不会留下 $(a, b)$。所以第 $r$ 条规则执行之后不会再起作用，也不会让更早的规则重新变得可用。
3. 因此，当前序列里优先级最高（id 最小）的那个 pair，正是按训练顺序往下试时下一条真正起作用的规则。两种做法在每一步执行同一条规则、调用同一个 `merge`，结果逐 token 相同。

验证一下第 1 点在全部 9,743 条规则上都成立：

### 4.7.3 用 np.memmap 高效写出

所有块都编码完之后，主进程先把各块的 token 数加起来，得到总长度，然后创建一个这么长的 `np.memmap`，再按块的顺序把缓存文件逐个拷进去：

```listing ch04/07_encode_parallel.py#L102-L119
```

`np.memmap` 是**内存映射文件**（memory-mapped file）上的数组：用起来与普通的 NumPy 数组一样，数据却直接存在磁盘文件里，操作系统按需把用到的部分调入内存。主进程因此不必同时拿着全部 token。第 6 章读数据时也是同一个办法：`np.memmap(data_path, dtype=np.uint16, mode='r')`，训练时随机取窗口，用到哪里读哪里。

为什么是 `uint16`？它能表示 0 到 65,535 的整数，StoryBot 的词表是 10,000，第 III 部 WebBot 的是 50,000，都装得下。每个 token 只占 2 字节：验证集的 5,465,873 个 token 正好是 10,931,746 字节。换成 Python 列表，光是每个元素的指针就要 8 字节（64 位 Python），还没算整数对象本身。

::: warn uint16 的上限是 65,535
如果哪天把词表加到 65,536 以上，`np.array(ids, dtype=np.uint16)` 在 NumPy 2 里会直接抛出 `OverflowError`，这是好事。危险的是另一种写法：先建一个默认整数类型的数组，再 `.astype(np.uint16)`。它不做任何检查，超出范围的 id 会悄悄回绕（65536 变成 0），数据就这样坏掉了。较老的 NumPy 1.x 在第一种写法上也只给一个 `DeprecationWarning`，同样会回绕（我们用 NumPy 1.26.4 试过）。
:::

```verify id=4.7-c title="uint16：上限 65,535，astype 会悄悄回绕"

    np.array([65535, 65536], dtype=np.uint16)
except OverflowError as e:
    print("np.array(..., dtype=np.uint16):", "OverflowError:", e)
```

我们用 `encode_file` 编码整份验证集，进程数取 1、2、4、8、16，每一次的输出文件都与官方的 `tiny_stories_valid.bin` 逐字节相同（SHA-256 一致），缓存目录也都按时删掉了。耗时（墙钟时间）分别是 205、115、62、43、37 秒，8 个进程快了 4.7 倍，比 4.4 节的预分词明显。原因之一是编码时每个字节要做的计算比预分词多，进程启动这类固定开销的占比就小了。

训练集方向也验证过：把训练集的前 104,856,833 字节（截在一个 `<|endoftext|>` 之前，用 HTTP Range 请求下载）用 16 个进程编码，得到 25,473,389 个 token，与官方 `tiny_stories_train.bin` 开头的 50,946,778 字节逐字节相同。

```localcheck verify/test_ch04.py::test_encode_file_matches_official_bin title="encode_file 编码验证集的前 2 MB，结果与官方 tiny_stories_valid.bin 的开头逐字节相同"
```

最后，在浏览器里把本章的流程从头到尾走一遍：在 52 KB 的样本上用增量版训练一个 600 词表的分词器，用按优先级合并的编码器编码，写成 `uint16` 的 `.bin` 文件，再读回来解码，看它是否与原文一字不差。浏览器里的 Python 跑在一个内存中的虚拟文件系统上，`np.memmap` 的 `flush` 会失败，所以这里用 `_encode_chunk` 同款的 `tofile` 写出、`np.fromfile` 读回，写出的字节完全相同；真正用到 `np.memmap` 的 `encode_file`，由上面的本地验证覆盖。


## 小结

本章没有发明任何新算法。BPE 还是第 1 章的那个 BPE，学到的规则一条不差，编出来的 id 一个不差；变的只是实现。训练这一侧，我们先把重复的预分词折叠成计数（4.1），再只更新受影响的序列（4.2），然后按 `<|endoftext|>` 分块读取、省下内存（4.3），最后把预分词分给多个进程（4.4）。编码这一侧，我们把“逐条试遍所有规则”换成“只合并现有 pair 中优先级最高的”（4.6），再分块并行编码、用 `np.memmap` 写成 `uint16` 的二进制文件（4.7）。

每一步改进都遵循同一个顺序：先证明结果不变，再测量快了多少，最后问剩下的时间花在哪里。这个顺序把我们一路带到了 Amdahl 定律面前：增量更新之后，合并循环里 96.5% 的时间都花在 `max()` 的全表扫描上，而这一部分无法靠多开进程来加速。第 III 部第 7 章会回到这个问题，讨论怎样定位瓶颈、怎样用 Rust/C++ 重写。

本章所学的内容：

- 去重之后按次数加权计数，与逐次出现计数完全相等；配合全序的平票规则，去重版学出的规则与朴素版逐项相同。（[验证 4.1-b](#v-4.1-b)、[验证 4.1-d](#v-4.1-d)）
- 增量更新只修改含有被合并 pair 的序列；只要每一步先减去旧序列的全部 pair、再加上新序列的全部 pair，计数表就始终等于全量重算的结果。（[验证 4.2-b](#v-4.2-b)、[验证 4.2-c](#v-4.2-c)）
- `max` 的 key 必须是全序：只按次数比较时，平票由字典顺序决定，增量版与全量版会分道扬镳；原书比较 id，CS336 比较字节串，两者在第 10 条规则就可能不同。（[验证 4.2-d](#v-4.2-d)、[验证 4.2-e](#v-4.2-e)）
- 整读大文件时，一个 emoji 就能让字符串的内存变成 4 倍；按 `<|endoftext|>` 分块读取，计数与整读完全相同，切在词中间则不然。（[验证 4.3-a](#v-4.3-a)、[验证 4.3-c](#v-4.3-c)）
- 并行只能加速预分词，合并循环始终串行，总加速比受 Amdahl 定律限制。（[验证 4.4-a](#v-4.4-a)）
- 按优先级（id）合并的编码器与逐条套用全部规则的编码器逐 token 相同，因为每条规则只用到比自己早的 token。（[验证 4.6-a](#v-4.6-a)、[验证 4.6-b](#v-4.6-b)）
- 在 `<|endoftext|>` 处分块编码再拼接等于整体编码；`uint16` 每个 token 占 2 字节，上限 65,535，`astype` 越界时会悄悄回绕。（[验证 4.7-a](#v-4.7-a)、[验证 4.7-c](#v-4.7-c)、[验证 4.7-d](#v-4.7-d)）

有了 5.4 亿个 token 的 `tiny_stories_train.bin`，下一章我们来改造模型本身：GPT-2 的骨架不变，换上 RoPE、SwiGLU 和 RMSNorm，看看现代的 LLM 在哪些地方与 2019 年不同。
