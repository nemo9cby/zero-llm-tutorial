从这一章开始，我们动手制作第一个机器人 CodeBot。制作的顺序是“分词器 → 模型 → 训练”，第一站是**分词器**（tokenizer）。语言模型的输入和输出都是整数，而我们手里的训练数据 TinyCodes 是 6.5 MB 的 Python 代码。分词器负责在文字和整数之间来回翻译：训练之前，把文字切成小块、换成整数；生成之后，再把整数还原成文字。

本章的路线是这样的。我们先试两种最朴素的做法：一个字符一个编号（1.1 节），一个字节一个编号（1.2 节），看清它们各自的毛病。接着实现 BPE：从数据里“学”出一张词表（1.3 节），用它编码和解码（1.4 节），再补上特殊 token（1.5 节）和预分词（1.6 节）这两块拼图。最后，我们在 TinyCodes 上训练出 CodeBot 真正使用的分词器（1.7 节），评估它的好坏（1.8 节），并把整份语料编码成第 3 章要用的二进制文件（1.9 节）。

先看终点。本章结束时，`tiny_codes.txt` 的 6,487,033 个字节会变成 2,677,398 个 token，词表大小是 1,000。下面就是这个分词器，你可以先随手试试：改动文字，看它被切成了哪些块、每块的编号是多少。1.8 节我们再回来细看它。

## 1.1 字符级分词器

### 1.1.1 把字符转换为 ID

语言模型的输入是一串整数。在模型做任何“聪明”的事情之前，我们得先回答一个朴素的问题：一段文字，该怎样变成一串整数？承担这项工作的组件就是分词器，它切分出来的每个单位叫作 **token**。

最容易想到的做法，是给每个字符分配一个编号。好在这样的编号早已存在，它就是 Unicode 为每个字符规定的**码位**（code point）。Python 的 `ord()` 把字符变成码位，`chr()` 则把码位变回字符：

```verify id=1.1-a title="字符级分词器：编码与解码互为逆运算"
    def decode(self, ids):
```

### 1.1.3 字符级分词器的问题

看起来一切顺利。那么字符级分词器的问题出在哪里？答案是**词表大小**（vocabulary size）。

语言模型会为词表里的每个 id 准备一个向量，这些向量排成一张表，叫作嵌入矩阵（embedding matrix）。词表有多少个 id，这张表就有多少行。Unicode 的码位从 0 一直排到 `0x10FFFF`，如果每个码位都要占一行，表的行数就是 111 万多。我们在第 3 章训练的 CodeBot，每个 token 用 384 维的向量表示。算一算：

```verify id=1.1-b title="如果词表覆盖全部 Unicode 码位"
vocab_size = 0x10FFFF + 1   # 码位 0 … 0x10FFFF
embed_dim = 384             # CodeBot 的嵌入维度（见第 3 章）
print(f"码位总数      : {vocab_size:,}")
print(f"嵌入矩阵参数量: {vocab_size * embed_dim:,}")
assert vocab_size == 1_114_112

try:
    chr(0x110000)           # 越过最大码位
except ValueError as e:
    print("chr(0x110000) ->", e)

# 只数 Unicode 17.0 实际定义了的字符（159,801 个，见下方 CS336 对照），表也不小
defined = 159_801
print(f"只算已定义的字符: {defined * embed_dim:,} 个参数")
print(f"码位空间是已定义字符的 {vocab_size / defined:.1f} 倍")
# 仍是整个 CodeBot（11,121,640 个参数）的 5 倍多
assert defined * embed_dim > 5 * 11_121_640
```

仅嵌入矩阵就有 4 亿多个参数，而整个 CodeBot 才 11,121,640 个参数（第 2 章会逐项数清）。更糟的是，训练数据里绝大多数码位一次也不会出现，对应的那一行向量根本得不到训练。字符级分词器的路走不通，我们需要一张小而“满”的词表。

## 1.2 字节级分词器

### 1.2.1 UTF-8 编码

### 1.2.3 字节级分词器的问题

词表问题解决了，但代价随之而来：序列变长了。`hello世界😁` 用字符级分词器是 8 个 token，用字节级分词器则是 15 个。对中文来说，序列长度几乎变成原来的 3 倍。序列越长，模型每生成一个 token 要读的东西就越多；而 CodeBot 一次最多只能读 256 个 token，序列变长，能装进去的代码就变少了。

::: warn 并非任意字节序列都能解码
字节级分词器的 `decode` 有一个隐患：UTF-8 对字节的排列有严格的规矩，随便拼出来的一串字节不一定是合法的 UTF-8。语言模型在生成文本时，恰恰是一个 token 一个 token 地“随便拼”，完全可能只吐出半个汉字。
:::

```verify id=1.2-b title="半个汉字无法解码"
half = [228, 184]            # “世” 的前两个字节
try:
    bytes(half).decode("utf-8")
except UnicodeDecodeError as e:
    print("严格解码失败:", e.reason)

# 用 errors="replace" 时，非法字节会变成替换字符 U+FFFD
print("替换后:", repr(bytes(half).decode("utf-8", errors="replace")))
```

后面实现 BPE 分词器的 `decode` 时，我们还会回到这个问题。

字符级分词器的词表太大，字节级分词器的序列太长。有没有办法兼得两者之长：以字节为基础保证任何文字都能编码，同时把经常一起出现的字节合并成一个 token，从而缩短序列？这正是下一节 BPE 的思路。

## 1.3 BPE 的训练算法

**BPE**（Byte Pair Encoding，字节对编码）的想法很简单：在一串 token 里，反复找出最常挨在一起的两个 token，把它们合并成一个新 token。合并一次，序列就短一点，词表就多一项。起点是 256 个字节，所以任何文字都能编码；常见的字节组合被合并成一个 token，所以序列又不会太长。

BPE 原本是一种数据压缩算法，由 Philip Gage 在 1994 年提出（[原文](http://www.pennelynn.com/Documents/CUJ/HTML/94HTML/19940045.HTM)）。2016 年，Sennrich 等人把它用于机器翻译，用来把单词切成更小的“子词”（[arXiv:1508.07909](https://arxiv.org/abs/1508.07909)）。GPT-2 则把它直接用在 UTF-8 字节上，这就是 byte-level BPE（[GPT-2 论文](https://cdn.openai.com/better-language-models/language_models_are_unsupervised_multitask_learners.pdf)，2.2 节）。本章实现的正是这一种。

### 1.3.1 BPE 的处理步骤

BPE 的训练只有三步，反复执行：

1. 数一数：序列里每一对相邻的 token 各出现了几次；
2. 挑出出现次数最多的那一对，给它分配一个新的 id（第一次是 256，然后是 257、258……），记下这条**合并规则**（merge rule）；
3. 把序列里所有这一对都换成新 id，回到第 1 步。

我们先用一串小整数手算一遍。序列 `[1, 2, 3, 1, 2]` 里的相邻对有 `(1, 2)`、`(2, 3)`、`(3, 1)`、`(1, 2)` 四个，其中 `(1, 2)` 出现了 2 次，最多。把它换成新 id 4，序列就变成了 `[4, 3, 4]`：5 个 token 变成了 3 个。

真实的文本也是一样，只是先要用 UTF-8 把它变成 0–255 的字节。下表是原书例句 `"Hello world! This is BPE training."` 的前 4 步，34 个字节最后变成了 27 个 token（[验证 1.3-e](#v-1.3-e) 会逐步复算）：

| 步 | 合并的一对 | 出现次数 | 新 id | 新 token | 合并后的长度 |
|---|---|---|---|---|---|
| 1 | `i` + `s` | 2 | 256 | `'is'` | 32 |
| 2 | `is` + `' '` | 2 | 257 | `'is '` | 30 |
| 3 | `i` + `n` | 2 | 258 | `'in'` | 28 |
| 4 | `H` + `e` | 1 | 259 | `'He'` | 27 |

第 2 步合并的是第 1 步刚造出来的 `'is'` 和一个空格。新 token 可以继续参与合并，所以词表里会逐渐长出越来越长的片段。学到的规则条数决定了词表的大小：256 个字节，加上合并的次数。

两个函数都在浏览器里跑一遍，输出与书中注释对照：

```verify id=1.3-a title="count_pairs 与 merge：书中的两个例子"
from collections import defaultdict

def count_pairs(ids):
    counts = defaultdict(int)
    for pair in zip(ids, ids[1:]):
        counts[pair] += 1
    return counts

def merge(ids, pair, new_id):
    merged_ids = []
    i = 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i+1]) == pair:
            merged_ids.append(new_id)
            i += 2
        else:
            merged_ids.append(ids[i])
            i += 1
    return merged_ids

ids = [1, 2, 3, 1, 2]
print(dict(count_pairs(ids)))
print(merge(ids, (1, 2), 4))
assert dict(count_pairs(ids)) == {(1, 2): 2, (2, 3): 1, (3, 1): 1}
assert merge(ids, (1, 2), 4) == [4, 3, 4]
```

::: confusion count_pairs 数到 2 次，merge 却只换了 1 处？
直觉上，“出现了几次”和“能合并几处”应该是同一个数。对 `[1, 2, 3, 1, 2]` 来说确实如此。

可是换成 `[7, 7, 7]` 试试。`count_pairs` 把位置 0–1 和位置 1–2 各数一次，`(7, 7)` 出现了 2 次；`merge` 从左往右扫描，把位置 0–1 合并之后直接跳到位置 2，只剩一个孤零零的 7，所以只换了 1 处。两个 `(7, 7)` 共用了中间那个 7，它们是**重叠**的。

可以带走的结论是：`count_pairs` 数的是“出现次数”，重叠的也算；`merge` 做的是“不重叠的替换”。两者在连续的相同 token 上会不一致，而代码里最常见的连续相同 token，正是缩进的空格（[验证 1.8-c](#v-1.8-c) 会在 TinyCodes 上量出差距）。
:::

```verify id=1.3-b title="重叠的 pair：计数 2 次，只能替换 1 处"
for ids in ([7, 7, 7], [7, 7, 7, 7]):
    n = count_pairs(ids)[(7, 7)]
    out = merge(ids, (7, 7), 8)
    print(f"{ids}: (7, 7) 数到 {n} 次，合并后 {out}，实际替换 {len(ids) - len(out)} 处")
assert count_pairs([7, 7, 7])[(7, 7)] == 2 and merge([7, 7, 7], (7, 7), 8) == [8, 7]
assert count_pairs([7, 7, 7, 7])[(7, 7)] == 3 and merge([7, 7, 7, 7], (7, 7), 8) == [8, 8]
```

有几处值得留意。`num_merges = vocab_size - 256`：词表里先有 256 个字节，剩下的名额全部留给合并规则。`merge_rules` 是一个字典，键是被合并的一对，值是新 id；Python 3.7 以后的字典保留插入顺序，所以它同时记下了规则学到的先后，1.4 节编码时要用到这个顺序。`if not counts: break` 处理的是文本太短、已经没有相邻对可数的情况。

还有第 50、51 行：真正执行的是 `max(counts, key=counts.get)`，下面被注释掉的那一行，是另一种挑选方法。两行的区别只在“出现次数相同”时才显现出来，这正是下面专栏的话题。

::: column BPE 的平票处理
`max(counts, key=counts.get)` 挑出现次数最多的 pair。如果有好几个 pair 并列第一呢？Python 的 `max` 遇到并列，返回最先遇到的那个；而字典的遍历顺序就是插入顺序，也就是这个 pair 在文中第一次出现的位置。所以第 50 行的规则可以叫作“先出现者胜”。

并列一点也不罕见。原书例句的第 1 步就有三个 pair 都出现了 2 次：

```verify id=1.3-c title="原书例句的第 1 步：三个 pair 并列，三种规则怎么挑"
text = "Hello world! This is BPE training."
counts = count_pairs(list(text.encode("utf-8")))
top = max(counts.values())
# 按插入顺序排列，也就是在文中第一次出现的顺序
tied = [p for p in counts if counts[p] == top]
show = lambda p: repr(bytes(p).decode())
print(f"出现 {top} 次的 pair:", ", ".join(f"{p} {show(p)}" for p in tied))

# ch01/03–06：先出现者胜
first = max(counts, key=counts.get)
# codebot：(次数, 左 id, 右 id) 最大者胜
by_ids = max(counts, key=lambda p: (counts[p], p[0], p[1]))
# CS336：(次数, 左边的字节串, 右边的字节串) 最大者胜
by_bytes = max(counts, key=lambda p: (counts[p], bytes([p[0]]), bytes([p[1]])))
print("先出现者胜     ->", first, show(first))
print("id 最大者胜    ->", by_ids, show(by_ids))
print("字节串最大者胜 ->", by_bytes, show(by_bytes))
assert tied == [(105, 115), (115, 32), (105, 110)]
assert first == (105, 115) and by_ids == by_bytes == (115, 32)
```

注释掉的第 51 行比较的是 `(次数, 左 id, 右 id)`：次数相同就比左边的 id，再相同就比右边的 id。这个规则与字典顺序无关，同一份语料无论怎样遍历，结果都一样。1.7 节整理出的 `codebot/tokenizer.py` 正是改用了这一行。

第三种规则来自斯坦福的 CS336：并列时比较两个 token 的**字节串**，取字典序较大的一对。在第 1 步，所有 token 都是单个字节，id 就是字节值，所以“比 id”和“比字节串”一定一致。分歧出在合并之后：新 token 的 id 按诞生的先后编号，而它的字节串可以是任何内容。下面这份小语料专门制造了这种局面：

```verify id=1.3-d title="新 token 的 id 按诞生先后编号：比 id 选 'aaq'，比字节串选 'zzq'"
def train_rule(docs, num_merges, rule):
    """原书 05 的训练循环（按文档分开数），只把挑选 pair 的那一行换成 rule。"""
    ids_list = [list(d.encode("utf-8")) for d in docs]
    vocab = {i: bytes([i]) for i in range(256)}
    learned = []
    for step in range(num_merges):
        counts = defaultdict(int)
        for ids in ids_list:
            for pair in zip(ids, ids[1:]):
                counts[pair] += 1
        if rule == "first":
            best = max(counts, key=counts.get)
        elif rule == "ids":
            best = max(counts, key=lambda p: (counts[p], p[0], p[1]))
        else:
            best = max(counts, key=lambda p: (counts[p], vocab[p[0]], vocab[p[1]]))
        new_id = 256 + step
        vocab[new_id] = vocab[best[0]] + vocab[best[1]]
        ids_list = [merge(ids, best, new_id) for ids in ids_list]
        learned.append(vocab[new_id].decode())
    return learned

docs = ["zzq"] * 3 + ["zz"] * 3 + ["aaq"] * 3 + ["aa"] * 2
for rule in ["ids", "bytes"]:
    print(f"{rule:5}:", train_rule(docs, 3, rule))
assert train_rule(docs, 3, "ids") == ["zz", "aa", "aaq"]
assert train_rule(docs, 3, "bytes") == ["zz", "aa", "zzq"]
```

手算一下就明白了。`zz` 出现 6 次（`zzq` 里 3 次、`zz` 里 3 次），`aa` 出现 5 次，所以 `zz` 先合并、拿到 id 256，`aa` 后合并、拿到 257。接下来 `(zz, q)` 和 `(aa, q)` 都出现 3 次。比 id 时，`(257, 113)` 大于 `(256, 113)`，选 `aaq`；比字节串时，`b'zz'` 大于 `b'aa'`，选 `zzq`。

这种分歧在真实语料上会发生吗？会，而且来得很早。在 CS336 作业自带的测试语料上（13 万字符，学 243 条规则），原书的规则从第 93 条开始与 CS336 的参考答案不同，243 条里只有 170 条位置相同；只把挑选的那一行换成“比字节串”，243 条就全部对上了。在 TinyCodes 上，“比字节串”从第 290 条开始与原书不同，“先出现者胜”从第 123 条开始不同。1.7.3 节的交互图可以亲眼看到这两处分叉。

## 1.4 用 BPE 编码与解码

上一节学出了合并规则。这一节用它们来编码新的文字，再把 id 解码回文字。

### 1.4.1 实现 BPE 分词器

解码时，我们需要知道每个 id 代表哪几个字节。0–255 就是字节本身；每条合并规则产生的新 id，它的字节串等于被合并的两个 token 的字节串相连。按规则学到的先后依次登记，就得到了完整的对照表 `id_to_bytes`：

```listing ch01/04_bpe_tokenizer.py#L24-L36
```

```verify id=1.4-a title="id_to_bytes：新 token 的字节串是两个旧 token 相连"
class BPETokenizer:
    def __init__(self, merge_rules):
        self.merge_rules = merge_rules
        self.id_to_bytes = {i: bytes([i]) for i in range(256)}
        for (id1, id2), new_id in merge_rules.items():
            self.id_to_bytes[new_id] = self.id_to_bytes[id1] + self.id_to_bytes[id2]
        self.vocab_size = len(self.id_to_bytes)

    def encode(self, text):
        ids = list(text.encode("utf-8"))
        for merge_pair, new_id in self.merge_rules.items():   # 按学到的先后套用
            ids = merge(ids, merge_pair, new_id)
        return ids

    def decode(self, ids):
        byte_list = [self.id_to_bytes[i] for i in ids]
        return b"".join(byte_list).decode("utf-8", errors="replace")

tokenizer = BPETokenizer({(105, 115): 256, (256, 32): 257, (105, 110): 258, (72, 101): 259})
for i in range(256, 260):
    print(i, tokenizer.id_to_bytes[i])
print("vocab_size =", tokenizer.vocab_size)
assert tokenizer.vocab_size == 260 and tokenizer.id_to_bytes[257] == b"is "
```

::: confusion 合并规则的顺序打乱了，会怎样？
规则不就是一张“哪两个合成哪个”的表吗？套用的先后，似乎无关紧要。

其实顺序就是语义的一部分。`(256, 32) → 257` 这条规则，前提是 256 已经存在；如果它排在 `(105, 115) → 256` 前面，套用它的时候文本里还没有 256，这条规则就白白错过了。打乱得再厉害一点，连 `id_to_bytes` 都建不起来：登记 257 时要用到 256 的字节串，而 256 还没有登记。

可以带走的结论是：合并规则是一个**有序**的列表，顺序必须与训练时完全一致。倒着套用，解码照样能还原文字，可编出来的 id 序列与训练时不同，模型从没见过它们。
:::

注意第 55 行的 `errors="replace"`。1.2 节的字节级分词器是严格解码，遇到半个字符会抛出异常；这里改成了把坏字节换成替换字符 `�`（U+FFFD）。为什么要改呢？因为解码的输入往往来自模型。模型一个 token 一个 token 地生成，完全可能停在一个字符的中间；如果这时要把已经生成的部分显示出来，严格解码就会让整个程序崩溃。

## 1.5 支持特殊 token

### 1.5.1 特殊 token 的作用

TinyCodes 不是一篇长文，而是两万多个互不相干的 Python 小程序首尾相接。程序与程序之间，夹着一个分隔符 `<|endoftext|>`：

```verify id=1.5-a title="TinyCodes 的开头：程序之间用 <|endoftext|> 隔开" files=data/ch01/tiny_codes_head10k.txt
with open("data/ch01/tiny_codes_head10k.txt", encoding="utf-8") as f:
    head = f.read()                     # tiny_codes.txt 的前 10,000 个字符
programs = head.split("<|endoftext|>")
n_end = head.count("<|endoftext|>")
print(f"前 10,000 个字符里有 {n_end} 个 <|endoftext|>，切出 {len(programs)} 段")
print("第 1 个程序:")
print(programs[0])
assert n_end == 45 and programs[1].startswith("\nshopping_list = {}")
```

这样的标记叫作**特殊 token**（special token）。它不是正文的一部分，而是告诉模型“一篇结束了，下一篇与上一篇无关”。训练时，模型在每个程序的末尾都会看到它；生成时，模型一旦吐出它，就该停下了。原书的生成函数正是这样做的：

```listing codebot/utils.py#L31-L33
```

所以，`<|endoftext|>` 必须是**一个** token，有自己固定的 id，而不能被拆成 `<`、`|`、`end` 这样的碎片。

### 1.5.2 支持特殊 token 的 BPE 训练

如果不做任何处理，1.3 节的 `train_bpe` 会把 `<|endoftext|>` 的 13 个字节当成普通文字来数。它在语料里每篇一次，出现得很频繁，会被一点一点地合并起来；更糟的是，前一个程序的结尾和后一个程序的开头也会被凑成一对，合并跨过了文档的边界。用 4 个一模一样的小程序试一试：

```verify id=1.5-b title="不先切开：合并跨过了程序的边界，学出 ')<|endoftext|>print('"

joined = "<|endoftext|>".join(docs)
rules = train_bpe(joined, vocab_size=256 + 20)      # 1.3 节的 train_bpe：不认识特殊 token
vocab = {i: bytes([i]) for i in range(256)}

    vocab[new_id] = vocab[a] + vocab[b]

```

第 6 条规则 `')<'` 就已经把上一个程序的右括号和分隔符粘在了一起；到第 19 条，一个 token 横跨了“上一个程序的结尾、分隔符、下一个程序的开头”三段。

解决办法很直接：训练之前，先按 `<|endoftext|>` 把文本切开，每段单独数相邻对。这样既不会拆开特殊 token，也不会跨越文档合并。特殊 token 本身不参与合并，而是在词表的最后单独占一个 id。

### 1.5.3 实现 train_bpe 函数

```listing ch01/05_special_token.py#L30-L59
```

改动有两处。第 32、33 行先切开文本，`ids_list` 里每个程序一段；第 41–43 行把每段的计数累加到同一个 `counts` 里（为此 `count_pairs` 多了一个可选参数 `counts`）。另一处改动在第 36 行：合并次数变成了 `vocab_size - 256 - 1`，多减去的 1，是留给特殊 token 的位置。

```verify id=1.5-c title="05 的 train_bpe：vocab_size=260 只学 3 条规则"
def count_pairs(ids, counts=None):
    if counts is None:
        counts = defaultdict(int)
    for pair in zip(ids, ids[1:]):
        counts[pair] += 1
    return counts

def train_bpe(input_text, vocab_size, end_token="<|endoftext|>"):
    texts = input_text.split(end_token)
    ids_list = [list(text.encode("utf-8")) for text in texts]
    num_merges = vocab_size - 256 - 1
    merge_rules = {}
    for step in range(num_merges):
        counts = defaultdict(int)
        for ids in ids_list:
            counts = count_pairs(ids, counts)
        if not counts:
            break
        best_pair = max(counts, key=counts.get)
        new_id = 256 + step
        merge_rules[best_pair] = new_id
        for i in range(len(ids_list)):
            ids_list[i] = merge(ids_list[i], best_pair, new_id)
    return merge_rules

merge_rules = train_bpe("Hello world!<|endoftext|>This is BPE training.", vocab_size=260)
print(merge_rules)
assert merge_rules == {(105, 115): 256, (256, 32): 257, (105, 110): 258}
```

::: confusion 同样是 `vocab_size=260`，为什么这里只学了 3 条？id 259 到底是谁？
1.3 节用 `vocab_size=260` 学了 4 条规则，259 是 `'He'`；这里同样的参数只学了 3 条，259 变成了 `<|endoftext|>`。同一个数字、同一个 id，含义却变了，难免让人糊涂。

原因在于 `vocab_size` 的定义从这一节起变了。1.3 节的词表是“256 个字节 + 合并规则”，这里是“256 个字节 + 合并规则 + 1 个特殊 token”。260 个名额，扣掉 256 个字节，再扣掉 1 个特殊 token，只剩 3 条规则；特殊 token 排在最后，id 是 256 + 3 = 259。

可以带走的结论是：从 1.5 节起，`vocab_size = 256 + 合并次数 + 1`，特殊 token 的 id 是 `256 + 合并次数`。CodeBot 的 1,000 就是 256 + 743 + 1，特殊 token 的 id 是 999。
:::

```verify id=1.5-e title="05 的分词器：<|endoftext|> 编码成一个 id 259"
class BPETokenizer:
    def __init__(self, merge_rules, end_token="<|endoftext|>"):
        self.merge_rules = merge_rules
        self.end_token = end_token
        self.end_token_id = 256 + len(merge_rules)
        self.id_to_bytes = {i: bytes([i]) for i in range(256)}
        for (id1, id2), new_id in merge_rules.items():
            self.id_to_bytes[new_id] = self.id_to_bytes[id1] + self.id_to_bytes[id2]
        self.id_to_bytes[self.end_token_id] = self.end_token.encode("utf-8")
        self.vocab_size = len(self.id_to_bytes)

    def _encode_text(self, text):
        ids = list(text.encode("utf-8"))
        for merge_pair, new_id in self.merge_rules.items():
            ids = merge(ids, merge_pair, new_id)
        return ids

    def encode(self, input_text):
        pattern = '(' + re.escape(self.end_token) + ')'
        all_ids = []
        for text in re.split(pattern, input_text):
            if text == self.end_token:
                all_ids.append(self.end_token_id)
            else:
                all_ids.extend(self._encode_text(text))
        return all_ids

    def decode(self, ids):
        byte_list = [self.id_to_bytes[i] for i in ids]
        return b"".join(byte_list).decode("utf-8", errors="replace")
```

## 1.6 预分词

### 1.6.1 为什么需要预分词

到目前为止，BPE 在整段文字上合并，单词与单词之间畅通无阻。来看看这样会学出什么。原书 1.6 节的例句里，`hello` 出现了 3 次，前面分别是 `Say`、`Why` 和 `Just`：

```verify id=1.6-a title="不预分词：学出了 'Say hello! Why hello' 这样跨越单词的 token"
sample = "Say hello! Why hello? Just hello."
rules = train_bpe(sample, vocab_size=256 + 13 + 1)     # 1.5 节的 train_bpe：只按特殊 token 切
vocab = {i: bytes([i]) for i in range(256)}
for (a, b), new_id in rules.items():
    vocab[new_id] = vocab[a] + vocab[b]
learned = [vocab[i].decode() for i in rules.values()]
print(learned)
assert "Say hello! Why hello" in learned               # 一个 token 跨过了标点、空格和下一个单词
```

`' hello'`（连同前面的空格）很快就成了一个 token，这没有问题。可后面学到的 token 把标点、空格和下一个单词粘在了一起，它们只是这一句话碰巧的排列，换一句话就用不上了。

问题还不止于此。CS336 的讲义举过一个例子：`dog!` 和 `dog.` 只差一个标点，如果标点能和单词合并成一个 token，这两个几乎同义的写法就会拿到两个毫不相干的 id（A1 §2.4）。我们希望 token 尽量是有意义的片段，比如一个单词、一个单词的前半截，或者一串标点。

解决办法叫作**预分词**（pre-tokenization）：训练 BPE 之前，先用一个粗粒度的规则把文本切成“词”，BPE 只在每个词的内部合并。这样，合并永远不会跨过词的边界。预分词还有一个副产品：相同的词只需要数一次，再乘以出现次数。1.7 节会看到，TinyCodes 的 182 万个词里只有 3 万多种，第 4 章正是利用这一点把训练提速的。

### 1.6.2 GPT-2 的预分词正则

原书使用的切词规则，是 GPT-2 的一个正则表达式：

```listing ch01/06_pretokenize.py#L6-L9
```

这个模式由 6 个分支组成，用 `|` 隔开，从左往右尝试，先匹配上的分支获胜：

| 分支 | 匹配什么 | 例子 |
|---|---|---|
| `'(?:[sdmt]\|ll\|ve\|re)` | 英语的缩约（只认小写） | `'s`、`'ll`、`'re` |
| ` ?\p{L}+` | 一串字母，前面最多带一个空格 | `Say`、` hello`、` 世界` |
| ` ?\p{N}+` | 一串数字，前面最多带一个空格 | ` 2026` |
| ` ?[^\s\p{L}\p{N}]+` | 一串其他符号，前面最多带一个空格 | ` (`、`!`、` ==` |
| `\s+(?!\S)` | 一串空白，但把最后一个留给后面的词 | 缩进里的前几个空格 |
| `\s+` | 剩下的空白 | 行末的换行 |

`\p{L}` 表示任意语言的字母（英文、汉字、假名都算），`\p{N}` 表示任意数字。注意空格总是黏在词的**前面**：`' hello'` 是一个词，而不是 `'hello '`。先看几个例子：

```verify id=1.6-b title="GPT-2 正则的切分：空格黏在后一个词上，缩进留一个空格给下一个词"
import regex as re

def pretokenize(text):
    pattern = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""
    return re.findall(pattern, text)

samples = ["Say hello! Why hello? Just hello.", "x  =   1 + 23456",
           "    return x\n\n", "it's 世界 in 2026 (x) =="]
for s in samples:
    print(pretokenize(s))
assert pretokenize(samples[0]) == \
    ['Say', ' hello', '!', ' Why', ' hello', '?', ' Just', ' hello', '.']
assert pretokenize(samples[2]) == ['   ', ' return', ' x', '\n\n']
assert pretokenize(samples[3]) == \
    ['it', "'s", ' 世界', ' in', ' 2026', ' (', 'x', ')', ' ==']
# 一个字符也不丢：所有的块拼起来就是原文
assert "".join(pretokenize("hello世界😁 e\u0301")) == "hello世界😁 e\u0301"
```

验证单元第 1 行的 `import regex as re` 很关键（原书 06 的第 2 行也是这么写的）。`\p{L}` 这种写法，Python 标准库的 `re` 模块不支持，必须换成第三方的 `regex` 模块。原书在 05 里用的还是标准库 `re`（那里只需要 `split`），到了 06 就悄悄换成了 `regex`，并且起了同一个名字 `re`，后面的代码一行都不用改。

```verify id=1.6-c title="标准库 re 不认识 \p{L}"
import re as std_re
pattern = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""
try:
    std_re.compile(pattern)
except std_re.error as e:
    print("标准库 re:", e)
print("regex 模块:", re.findall(pattern, "I'll pay 100元!"))
```

::: confusion 为什么四个空格的缩进被切成了 `'   '` 和 `' return'`？
直觉上，四个空格是一个整体，应该切成 `'    '` 和 `'return'`。

问题出在第 5 个分支 `\s+(?!\S)`：它匹配一串空白，条件是后面紧跟的不能是非空白字符。四个空格整体后面紧跟着 `r`，条件不满足；于是正则往回让一步，只取前三个空格，这时后面跟的是一个空格，条件满足。剩下的那个空格，被下一个词的分支 ` ?\p{L}+` 收走，成了 `' return'`。

可以带走的结论是：空白串会把最后一个空格让给后面的词。所以缩进之后的 `' return'`，与句子中间的 `' return'` 是同一个词，BPE 只需要学一次。
:::

```verify id=1.6-f title="预分词之后：学到的都是词内的片段，'Say hello!' 编成 3 个 token"
def train_bpe(input_text, vocab_size, end_token="<|endoftext|>"):
    ids_list = []
    for text in input_text.split(end_token):
        for pretoken in pretokenize(text):                     # 预分词
            ids_list.append(list(pretoken.encode("utf-8")))
    num_merges = vocab_size - 256 - 1
    merge_rules = {}
    for step in range(num_merges):
        counts = defaultdict(int)
        for ids in ids_list:
            counts = count_pairs(ids, counts)
        if not counts:
            break
        best_pair = max(counts, key=counts.get)
        new_id = 256 + step
        merge_rules[best_pair] = new_id
        for i in range(len(ids_list)):
            ids_list[i] = merge(ids_list[i], best_pair, new_id)
    return merge_rules

class PretokBPETokenizer(BPETokenizer):          # 1.5 节的分词器，只改 encode

        for text in re.split('(' + re.escape(self.end_token) + ')', input_text):
            if text == self.end_token:
                all_ids.append(self.end_token_id)
            else:
                for pretoken in pretokenize(text):
                    all_ids.extend(self._encode_text(pretoken))
        return all_ids
```

下面在浏览器里载入 CodeBot 的规则。这里的分词器与 `codebot/tokenizer.py` 一样，只有 `_encode_text` 换成了第 4 章的“按优先级合并”写法：每次只合并现有 pair 里学得最早的那一个，而不是把 743 条规则从头试到尾。两种写法的结果逐个 id 相同（本地验证见 1.9 节），这样做只是为了让浏览器里的验证跑得快。

```verify id=1.7-a title="载入 CodeBot 的 743 条规则：vocab_size = 256 + 743 + 1 = 1000" files=data/tokenizers/codebot.json
import json

class CodeBotTokenizer:
    def __init__(self, merge_rules, end_token="<|endoftext|>"):
        self.merge_rules = merge_rules
        self.end_token = end_token
        self.end_token_id = 256 + len(merge_rules)
        self.id_to_bytes = {i: bytes([i]) for i in range(256)}
        for (id1, id2), new_id in merge_rules.items():
            self.id_to_bytes[new_id] = self.id_to_bytes[id1] + self.id_to_bytes[id2]
        self.id_to_bytes[self.end_token_id] = self.end_token.encode("utf-8")
        self.vocab_size = len(self.id_to_bytes)
        self._cache = {}

    @staticmethod
    def load_from(path):
        with open(path, encoding="utf-8") as f:
            flat = json.load(f)["merges"]       # [a0, b0, a1, b1, ...]
        pairs = zip(flat[0::2], flat[1::2])     # 第 i 对合并成 256 + i
        return CodeBotTokenizer({pair: 256 + i for i, pair in enumerate(pairs)})

    def _encode_text(self, text):
        # 第 4 章的写法：每次只合并现有 pair 里学得最早（id 最小）的那一个
        if text not in self._cache:
            rank = lambda p: self.merge_rules.get(p, float("inf"))
            ids = list(text.encode("utf-8"))
            while len(ids) > 1:
                best = min(zip(ids, ids[1:]), key=rank)
                if best not in self.merge_rules:
                    break
                ids = merge(ids, best, self.merge_rules[best])
            self._cache[text] = ids
        return self._cache[text]

    def encode(self, input_text):
        all_ids = []
        for text in re.split('(' + re.escape(self.end_token) + ')', input_text):
            if text == self.end_token:
                all_ids.append(self.end_token_id)
            else:
                for pretoken in pretokenize(text):
                    all_ids.extend(self._encode_text(pretoken))
        return all_ids

    def decode(self, ids):
        data = b"".join(self.id_to_bytes[i] for i in ids)
        return data.decode("utf-8", errors="replace")

codebot = CodeBotTokenizer.load_from("data/tokenizers/codebot.json")
rules = list(codebot.merge_rules.items())
print(f"合并规则 {len(rules)} 条，特殊 token 的 id = {codebot.end_token_id}")
print(f"vocab_size = {codebot.vocab_size}")
print("每条规则只用到比自己小的 id:", all(a < new and b < new for (a, b), new in rules))
assert codebot.vocab_size == 256 + 743 + 1 == 1000 and codebot.end_token_id == 999
assert [new for _, new in rules] == list(range(256, 999))
```

顺序的重要性，在真实的规则上看得更清楚。把 CodeBot 的 743 条规则倒过来套用，同一行代码编出来的 token 几乎翻了一倍：

```verify id=1.7-b title="CodeBot 的规则倒过来套用：8 个 token 变成 14 个"

    out = []
    for pretoken in pretokenize(text):
        ids = list(pretoken.encode("utf-8"))
        for pair, new_id in ordered_rules:
            ids = merge(ids, pair, new_id)
        out.extend(ids)
    return out

backward = encode_in_order(code, rules[::-1])
```

:::

### 1.8.2 测量压缩效率

分词器的好坏，最直接的衡量是**压缩率**（compression ratio）：同一段文字，平均每个 token 代表几个字节。

$$
\text{压缩率} = \frac{\text{字节数}}{\text{token 数}}
$$

这里，字节数是文字的 UTF-8 长度，token 数是编码之后的序列长度。字节级分词器的压缩率恰好是 1；压缩率越高，序列越短，模型一次能看到的内容就越多。原书在 `tiny_codes.txt` 的前 10,000 个字符上测量：

```listing ch01/08_eval.py#L23-L34
```

10,000 个字节编成了 4,709 个 token，所以压缩率是 10,000 ÷ 4,709 ≈ 2.12，平均每个 token 代表两个多字节：

```verify id=1.8-e title="前 10,000 个字符：4,709 个 token，压缩率 2.12"
ids = codebot.encode(head)
byte_count = len(head.encode("utf-8"))
print(f"字节数: {byte_count:,}  token 数: {len(ids):,}  压缩率: {byte_count / len(ids):.2f}")
assert (byte_count, len(ids)) == (10_000, 4_709) and f"{byte_count / len(ids):.2f}" == "2.12"
assert codebot.decode(ids) == head
# 对照：1.2 节的字节级分词器，一个字节一个 token，压缩率恰好是 1
assert byte_count / len(ByteTokenizer().encode(head)) == 1
```

::: confusion 压缩率 2.12 和 2.42，哪个才是 CodeBot 的？
原书在前 10,000 个字符上测得 2.12。可是 1.9 节把整份语料编码之后，6,487,033 个字节变成了 2,677,398 个 token，压缩率是 2.42。同一个分词器，为什么差了 14%？

原因在样本。前 10,000 个字符只是最前面的 46 个程序（最后一个还被截断了），而 TinyCodes 并没有打乱顺序。开头的程序里 `input()` 特别多，每千个字符 5.3 次，全语料平均只有 0.16 次；它们缩进很浅，257 行里缩进 8 格及以上的只有 2 行，而全语料里每 8 行就有 1 行。缩进恰恰是 CodeBot 最擅长压缩的东西，样本里缩进少，压缩率自然就低。

可以带走的结论是：压缩率取决于样本。比较两个分词器时，必须用同一段文字；想代表整个语料，就要在整个语料（或者打乱后的随机样本）上测量。

为什么用 `uint16`？它能表示 0 到 65,535，CodeBot 最大的 id 是 999，绰绰有余。每个 token 只占 2 个字节，整份语料是 2,677,398 × 2 = 5,354,796 个字节；如果用 8 个字节的 `int64`，文件会大 4 倍。不过，`uint16` 也有上限：词表一旦超过 65,536，id 就装不下了。装不下的时候会发生什么，取决于你怎么转换：


在浏览器里的 NumPy 2 中，原书的写法遇到超过 65,535 的 id 会直接报错，这是好事。可在原书仓库锁定的 NumPy 1.26 中，同一行代码只会发出一个 `DeprecationWarning`，然后把 65,536 悄悄变成 0；而 `astype` 不论哪个版本都会悄悄回绕。如果你以后训练更大的词表，保存之前最好先断言一句 `max(ids) < 65536`。

## 小结

本章从“一个字符一个编号”出发。字符级分词器的词表要覆盖 111 万个码位，太大；字节级分词器的词表只有 256，序列却变长了。BPE 在两者之间找到了平衡：以字节为起点，反复合并最常挨在一起的一对，从数据里学出一张小而满的词表。为了让它真正能用，我们给它补上了几样东西：有序的合并规则和容错的解码，把文档隔开的特殊 token，以及让合并不跨越单词的预分词。最后，我们在 TinyCodes 上训练出 CodeBot 的分词器，词表 1,000，全语料的压缩率 2.42，并把 6.5 MB 的代码编码成了 2,677,398 个 `uint16`。

一路上，我们也看到了不少容易踩的坑：并列时挑哪一对，会改变 token 的编号；合并规则的顺序就是语义；用户的输入里可能藏着特殊 token；Windows 的换行符会悄悄改变训练结果。还有一件事要承认：原书的实现为了清楚而写得很朴素，训练要一个小时。第 4 章会在不改变任何结果的前提下，把训练缩短到 20 秒以内。

**本章所学的内容**

- 字符级分词器的词表要覆盖 1,114,112 个码位，仅嵌入矩阵就超过 4 亿参数；字节级分词器的词表只有 256，代价是序列变长，汉字是原来的 3 倍（[验证 1.1-b](#v-1.1-b)、[验证 1.2-a](#v-1.2-a)）
- BPE 反复合并出现次数最多的相邻 pair，计数会数到重叠的 pair；并列时有三种挑法（先出现、比 id、比字节串），新 token 的 id 按诞生先后编号，所以比 id 与比字节串会分叉（[验证 1.3-b](#v-1.3-b)、[验证 1.3-d](#v-1.3-d)、[验证 1.3-e](#v-1.3-e)）
- 编码按学到的先后套用合并规则，顺序就是语义；解码用 `errors="replace"`，因为单个 token 可能只是半个字符（[验证 1.4-c](#v-1.4-c)、[验证 1.4-d](#v-1.4-d)、[验证 1.4-e](#v-1.4-e)）
- 从 1.5 节起 `vocab_size = 256 + 合并次数 + 1`，特殊 token 排在最后；`re.split` 要有捕获组才会留下它，用户文本里的 `<|endoftext|>` 同样会被编码成特殊 id（[验证 1.5-c](#v-1.5-c)、[验证 1.5-d](#v-1.5-d)、[验证 1.5-f](#v-1.5-f)）
- GPT-2 的预分词正则让合并不跨越单词，但在代码上会切出 `'d`、切断 `snake_case`，而且必须用 `regex` 模块（[验证 1.6-b](#v-1.6-b)、[验证 1.6-c](#v-1.6-c)、[验证 1.6-d](#v-1.6-d)）
- CodeBot 的分词器：743 条规则，vocab 1,000，最早学到的是缩进；压缩率在前 10,000 个字符上是 2.12，在全语料上是 2.42（[验证 1.7-a](#v-1.7-a)、[验证 1.8-a](#v-1.8-a)、[验证 1.8-e](#v-1.8-e)、[验证 1.8-f](#v-1.8-f)）
- 编码结果存成 `uint16`，与原书的 `tiny_codes.bin` 逐字节相同；id 超过 65,535 时，NumPy 2 报错，`astype` 则悄悄回绕（[验证 1.9-a](#v-1.9-a)、[验证 1.9-b](#v-1.9-b)）

分词器把文字变成了整数，可这些整数本身毫无意义：990 号是“一个空格加两个单引号”，991 号是 `Error`，编号挨着，意思却毫不相干。下一章，我们来造一个能从这串整数里读出意思的东西：Transformer。
