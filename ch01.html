分词器【基础篇】：把文字变成数字

语言模型只认识整数。本章从“一个字符一个编号”这个最朴素的想法出发，一路走到 GPT 系列所用的 BPE 分词器，最后用它把 CodeBot 的训练数据编码成 token 序列。

从这一章开始，我们动手制作第一个机器人 CodeBot。第 I 部的 I.1 节 说过，它要经过“分词器 → 模型 → 训练”三步才能做出来，第一站就是分词器（tokenizer）。语言模型读进来的是一串整数，算出来的是“下一个整数是谁”的概率；而我们手里的训练数据 TinyCodes 是 6.5 MB 的 Python 代码。分词器负责在文字和整数之间来回翻译：训练之前，把文字切成小块、换成整数；生成时，模型按概率选出一个个整数，再由分词器把它们还原成文字。

本章的路线是这样的。我们先试两种最朴素的做法：一个字符一个编号（1.1 节），一个字节一个编号（1.2 节），看清它们各自的毛病。接着实现 BPE：从数据里“学”出一张词表（1.3 节），用它编码和解码（1.4 节），再补上特殊 token（1.5 节）和预分词（1.6 节）这两块拼图。最后，我们在 TinyCodes 上训练出 CodeBot 真正使用的分词器（1.7 节），评估它的好坏（1.8 节），并把整份语料编码成第 3 章要用的二进制文件（1.9 节）。

先看终点。本章结束时，tiny_codes.txt 的 6,487,033 个字节会变成 2,677,398 个 token，词表大小是 1,000。下面就是这个分词器，你可以先随手试试：改动文字，看它被切成了哪些块、每块的编号是多少。1.8 节我们再回来细看它。

1.1 字符级分词

1.1.1 把字符转换为 ID

语言模型的输入是一串整数。在模型做任何“聪明”的事情之前，我们得先回答一个朴素的问题：一段文字，该怎样变成一串整数？承担这项工作的组件就是分词器，它切分出来的每个单位叫作 token。

最容易想到的做法，是给每个字符分配一个编号。好在这样的编号早已存在，它就是 Unicode 为每个字符规定的码位（code point）。Python 的 ord() 把字符变成码位，chr() 则把码位变回字符：

list(text) 把字符串拆成了 8 个字符。😁 恰好是一个码位，所以也是完整的一个；不过，👨‍👩‍👧 这样的组合 emoji 由 5 个码位拼成，list() 会把它拆成 5 个（验证 1.1-a）。

1.1.2 实现字符级分词器

把 ord 和 chr 包装成两个方法，就得到了一个完整的分词器：encode 把文字变成 id 列表，decode 把 id 列表还原成文字。

先在浏览器里亲手确认两件事：encode 与 decode 互为逆运算；得到的 id 与书中代码注释里写的完全一致。点击右侧的印章或“在浏览器中运行”即可，第一次运行需要十几秒来加载浏览器内的 Python。

验证 1.1-a字符级分词器：编码与解码互为逆运算
class CharTokenizer:
    def encode(self, text):
        return [ord(char) for char in text]

    def decode(self, ids):
        return ''.join([chr(i) for i in ids])

tok = CharTokenizer()
text = "hello世界😁"
ids = tok.encode(text)
print(ids)
assert ids == [104, 101, 108, 108, 111, 19990, 30028, 128513]
assert tok.decode(ids) == text

# 组合 emoji：三个人像用两个零宽连接符（U+200D）连起来，是 5 个码位
family = "\N{ZERO WIDTH JOINER}".join("👨👩👧")
print(family, "->", [f"U+{i:04X}" for i in tok.encode(family)])
assert len(list(family)) == 5 and tok.decode(tok.encode(family)) == family

1.1.3 字符级分词器的问题

看起来一切顺利。那么字符级分词器的问题出在哪里？答案是词表大小（vocabulary size）。

语言模型会为词表里的每个 id 准备一个向量，这些向量排成一张表，叫作嵌入矩阵（embedding matrix）。词表有多少个 id，这张表就有多少行。Unicode 的码位从 0 一直排到 0x10FFFF，如果每个码位都要占一行，表的行数就是 111 万多。我们在第 3 章训练的 CodeBot，每个 token 用 384 维的向量表示。算一算：

1.2 字节级分词

1.2.1 UTF-8 编码

既然码位太多，那就往下走一层，看看字符在计算机里究竟是怎样存储的。Python 的 str.encode("utf-8") 会给出字符的 UTF-8 编码，也就是一串字节（byte）。一个字节只有 256 种取值，于是“词表”一下子缩小到了 256：

A 只占一个字节 65，与它的码位相同；日文假名 あ 却变成了 227、129、130 三个字节。UTF-8 是一种变长编码（variable-length encoding）：ASCII 字符占 1 个字节，é 这样带附加符号的拉丁字母占 2 个，大多数汉字和假名占 3 个，😁 这样的 emoji 占 4 个。emoji 并不都是 4 个字节：✅、❤ 这几个码位较小的只占 3 个，用零宽连接符拼起来的组合 emoji 就更长了。

下面这张图可以任意改动文字。同一个字符和它拆出来的字节颜色相同；在电脑上把鼠标移到某个字符上，或者按 Tab 键把焦点移到它上面，对应的字节还会加框。

码位究竟是按什么规则变成字节的，为什么结果总落在 0–255 之间，附录 A 会打开这个黑盒。本章只需要记住两条性质：任何文字都能写成一串 0–255 的整数，这串整数还能原样变回文字。

1.2.3 字节级分词器的问题

词表问题解决了，但代价随之而来：序列变长了。hello世界😁 用字符级分词器是 8 个 token，用字节级分词器则是 15 个。对中文来说，序列长度几乎变成原来的 3 倍。序列越长，模型每生成一个 token 要读的东西就越多；而 CodeBot 一次最多只能读 256 个 token，序列变长，能装进去的代码就变少了。

注意并非任意字节序列都能解码

字节级分词器的 decode 有一个隐患：UTF-8 对字节的排列有严格的规矩，随便拼出来的一串字节不一定是合法的 UTF-8。语言模型在生成文本时，恰恰是一个 token 一个 token 地“随便拼”，完全可能只吐出半个汉字。

1.3 BPE 的训练算法

BPE（Byte Pair Encoding，字节对编码）的想法很简单：在一串 token 里，反复找出最常挨在一起的两个 token，把它们合并成一个新 token。合并一次，序列就短一点，词表就多一项。起点是 256 个字节，所以任何文字都能编码；常见的字节组合被合并成一个 token，所以序列又不会太长。

这有点像速记员给常用词组造简写：几个字总是挨在一起出现，就造一个新符号代替它们，以后写起来就短了。严格地讲，BPE 并不认识“词”，它只数相邻两个 token 一起出现了几次，而且一条规则只合并一对 token。长一点的片段是一对一对拼出来的：下面例子里的 'is␣'，就是先合成 'is'，再接上一个空格（空格不显眼，本章常把它写成 ␣）。

BPE 原本是一种数据压缩算法，由 Philip Gage 在 1994 年提出（原文，存档）。2016 年，Sennrich 等人把它用于机器翻译，用来把单词切成更小的“子词”（arXiv:1508.07909）。GPT-2 则把它直接用在 UTF-8 字节上，这就是 byte-level BPE（GPT-2 论文，2.2 节）。本章实现的正是这一种。

1.3.1 BPE 的处理步骤

BPE 的训练只有三步，反复执行：

  1. 数一数：序列里每一个相邻对（pair，挨在一起的两个 token）各出现了几次；
  2. 挑出出现次数最多的那一对，给它分配一个新的 id（第一次是 256，然后是 257、258……），记下这条合并规则（merge rule）；
  3. 把序列里所有这一对都换成新 id，回到第 1 步。

我们先用一串小整数手算一遍。序列 [1, 2, 3, 1, 2] 里的 pair 有 (1, 2)、(2, 3)、(3, 1)、(1, 2) 四个，其中 (1, 2) 出现了 2 次，最多。把它换成新 id 4，序列就变成了 [4, 3, 4]：5 个 token 变成了 3 个。

真实的文本也是一样，只是先要用 UTF-8 把它变成 0–255 的字节。下表是原书例句 "Hello world! This is BPE training." 的前 4 步，34 个字节最后变成了 27 个 token（验证 1.3-e 会逐步复算）：

步 合并（新 id） 出现次数 合并后的长度
1 i + s → 'is'（256） 2 32
2 is + ␣ → 'is␣'（257） 2 30
3 i + n → 'in'（258） 2 28
4 H + e → 'He'（259） 1 27

from collections import defaultdict

def count_pairs(ids):
    counts = defaultdict(int)
    for pair in zip(ids, ids[1:]):
        counts[pair] += 1
    return counts

def merge(ids, pair, new_id):
    merged_ids = []
    i = 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i+1]) == pair:
            merged_ids.append(new_id)
            i += 2
        else:
            merged_ids.append(ids[i])
            i += 1
    return merged_ids

注释掉的第 51 行比较的是 (次数, 左 id, 右 id)：次数相同就比左边的 id，再相同就比右边的 id。这个规则与字典顺序无关，同一份语料无论怎样遍历，结果都一样。1.7 节整理出的 codebot/tokenizer.py 正是改用了这一行。

def train_rule(docs, num_merges, rule):
    """原书 05 的训练循环（按文档分开数），只把挑选 pair 的那一行换成 rule。"""
    ids_list = [list(d.encode("utf-8")) for d in docs]
    vocab = {i: bytes([i]) for i in range(256)}
    learned = []
    for step in range(num_merges):
        counts = defaultdict(int)
        for ids in ids_list:
            for pair in zip(ids, ids[1:]):
                counts[pair] += 1
        if rule == "first":
            best = max(counts, key=counts.get)
        elif rule == "ids":
            best = max(counts, key=lambda p: (counts[p], p[0], p[1]))
        else:
            best = max(counts, key=lambda p: (counts[p], vocab[p[0]], vocab[p[1]]))
        new_id = 256 + step
        vocab[new_id] = vocab[best[0]] + vocab[best[1]]
        ids_list = [merge(ids, best, new_id) for ids in ids_list]
        learned.append(vocab[new_id].decode())
    return learned

1.4.1 实现 BPE 分词器

解码时，我们需要知道每个 id 代表哪几个字节。0–255 就是字节本身；每条合并规则产生的新 id，它的字节串等于被合并的两个 token 的字节串相连。按规则学到的先后依次登记，就得到了完整的对照表 id_to_bytes：

class BPETokenizer:
    def __init__(self, merge_rules):
        self.merge_rules = merge_rules
        self.id_to_bytes = {i: bytes([i]) for i in range(256)}
        for (id1, id2), new_id in merge_rules.items():
            self.id_to_bytes[new_id] = self.id_to_bytes[id1] + self.id_to_bytes[id2]
        self.vocab_size = len(self.id_to_bytes)

    def encode(self, text):
        ids = list(text.encode("utf-8"))
        for merge_pair, new_id in self.merge_rules.items():   # 按学到的先后套用
            ids = merge(ids, merge_pair, new_id)
        return ids

    def decode(self, ids):
        byte_list = [self.id_to_bytes[i] for i in ids]
        return b"".join(byte_list).decode("utf-8", errors="replace")

如果你读过《深度学习进阶：自然语言处理》2.3.1 节，那里的 preprocess 函数按空格切出单词，再给每个单词一个 ID。单词级的词表总有装不下的词，那本书用的 PTB 语料就把稀有词统一换成了 <unk>。字节级 BPE 从 256 个字节出发，任何文字都有退路，用不着 <unk> 这样的记号。

你可能会困惑合并规则的顺序打乱了，会怎样？

规则不就是一张“哪两个合成哪个”的表吗？套用的先后，似乎无关紧要。

其实顺序就是语义的一部分。(256, 32) → 257 这条规则，前提是 256 已经存在。如果编码时先套用它、后套用 (105, 115) → 256，套用它的时候文本里还没有 256，这条规则就白白错过了。如果保存下来的规则本身就是这个顺序，问题暴露得更早：建 id_to_bytes 时，登记 257 要用到 256 的字节串，而 256 还没有登记。

可以带走的结论是：合并规则是一个有序的列表，顺序必须与训练时完全一致。倒着套用，解码照样能还原文字，可编出来的 id 序列与训练时不同：模型在训练时从没见过这种切法。

1.5.3 实现 train_bpe 函数

与 1.3 节相比，循环的骨架没变，变的是数据的形状和合并的次数。数据从一条序列变成了一组序列。第 32、33 行先切开文本，ids_list 里每个程序一段。第 41–43 行把每段的计数累加到同一个 counts 里，为此 count_pairs 多了一个可选参数 counts。第 56、57 行再对每一段分别合并。合并的次数在第 36 行变成了 vocab_size - 256 - 1，多减去的 1，是留给特殊 token 的位置。

验证 1.5-c05 的 train_bpe：vocab_size=260 只学 3 条规则
def count_pairs(ids, counts=None):
    if counts is None:
        counts = defaultdict(int)
    for pair in zip(ids, ids[1:]):
        counts[pair] += 1
    return counts

def train_bpe(input_text, vocab_size, end_token="<|endoftext|>"):
    texts = input_text.split(end_token)
    ids_list = [list(text.encode("utf-8")) for text in texts]
    num_merges = vocab_size - 256 - 1
    merge_rules = {}
    for step in range(num_merges):
        counts = defaultdict(int)
        for ids in ids_list:
            counts = count_pairs(ids, counts)
        if not counts:
            break
        best_pair = max(counts, key=counts.get)
        new_id = 256 + step
        merge_rules[best_pair] = new_id
        for i in range(len(ids_list)):
            ids_list[i] = merge(ids_list[i], best_pair, new_id)
    return merge_rules

你可能会困惑同样是 vocab_size=260，为什么这里只学了 3 条？id 259 到底是谁？

1.3 节用 vocab_size=260 学了 4 条规则，259 是 'He'；这里同样的参数只学了 3 条，259 变成了 <|endoftext|>。同一个数字、同一个 id，含义却变了，难免让人糊涂。

原因在于 vocab_size 的定义从这一节起变了。1.3 节的词表是“256 个字节 + 合并规则”，这里是“256 个字节 + 合并规则 + 1 个特殊 token”。260 个名额，扣掉 256 个字节，再扣掉 1 个特殊 token，只剩 3 条规则；特殊 token 排在最后，id 是 256 + 3 = 259。

可以带走的结论是：从 1.5 节起，vocab_size = 256 + 合并次数 + 1，特殊 token 的 id 是 256 + 合并次数。CodeBot 的 1,000 就是 256 + 743 + 1，特殊 token 的 id 是 999。

class BPETokenizer:
    def __init__(self, merge_rules, end_token="<|endoftext|>"):
        self.merge_rules = merge_rules
        self.end_token = end_token
        self.end_token_id = 256 + len(merge_rules)
        self.id_to_bytes = {i: bytes([i]) for i in range(256)}
        for (id1, id2), new_id in merge_rules.items():
            self.id_to_bytes[new_id] = self.id_to_bytes[id1] + self.id_to_bytes[id2]
        self.id_to_bytes[self.end_token_id] = self.end_token.encode("utf-8")
        self.vocab_size = len(self.id_to_bytes)

    def _encode_text(self, text):
        ids = list(text.encode("utf-8"))
        for merge_pair, new_id in self.merge_rules.items():
            ids = merge(ids, merge_pair, new_id)
        return ids

    def encode(self, input_text):
        pattern = '(' + re.escape(self.end_token) + ')'
        all_ids = []
        for text in re.split(pattern, input_text):
            if text == self.end_token:
                all_ids.append(self.end_token_id)
            else:
                all_ids.extend(self._encode_text(text))
        return all_ids

    def decode(self, ids):
        byte_list = [self.id_to_bytes[i] for i in ids]
        return b"".join(byte_list).decode("utf-8", errors="replace")

问题还不止于此。CS336 的讲义举过一个例子：dog! 和 dog. 只差一个标点，如果标点能和单词合并成一个 token，这两个几乎同义的写法就会拿到两个毫不相干的 id（A1 §2.4）。我们希望 token 尽量是有意义的片段，比如一个单词、一个单词的前半截，或者一串标点。

解决办法叫作预分词（pre-tokenization）：训练 BPE 之前，先用一个粗粒度的规则把文本切成“词”，BPE 只在每个词的内部合并。这样，合并永远不会跨过词的边界。预分词还有一个副产品：相同的词只需要数一次，再乘以出现次数。1.7 节会看到，TinyCodes 的 182 万个词里只有 3 万多种，第 4 章正是利用这一点把训练提速的。

1.6.2 GPT-2 的预分词正则

原书使用的切词规则，是 GPT-2 的一个正则表达式：

这个模式由 6 个分支组成，用 | 隔开，从左往右尝试，先匹配上的分支获胜：

分支 匹配什么 例子
'(?:[sdmt]|ll|ve|re) 英语的缩约（只认小写） 's、'll、're
␣?\p{L}+ 一串字母，前面最多带一个空格 'Say'、'␣hello'、'␣世界'
␣?\p{N}+ 一串数字，前面最多带一个空格 '␣2026'
␣?[^\s\p{L}\p{N}]+ 一串其他符号，前面最多带一个空格 '␣('、'!'、'␣=='
\s+(?!\S) 一串空白，但把最后一个留给后面的词；文本末尾的空白也归这一支 '\n␣␣␣␣return' 里的 '\n␣␣␣'
\s+ 剩下的空白 下一行不缩进时，行末的 '\n'

表中的 ␣ 表示一个空格，在正则里它就是一个普通的空格字符。\p{L} 表示任意语言的字母（英文、汉字、假名都算），\p{N} 表示任意数字。注意空格总是黏在词的前面：'␣hello' 是一个词，而不是 'hello␣'。先看几个例子，顺便标出每一块是哪个分支匹配的：

你可能会困惑为什么四个空格的缩进被切成了 '␣␣␣' 和 '␣return'？

直觉上，四个空格是一个整体，应该切成 '␣␣␣␣' 和 'return'。

问题出在第 5 个分支 \s+(?!\S)：它匹配一串空白，但要求这串空白后面紧跟的还是空白，或者已经到了文本末尾。四个空格整体后面紧跟着 r，条件不满足。于是正则往回让一步，只取前三个空格，这时后面跟的是第四个空格，条件满足。第四个空格被下一个词的分支 ␣?\p{L}+ 收走，成了 '␣return'（验证 1.6-b 的第三行输出）。

def train_bpe(input_text, vocab_size, end_token="<|endoftext|>"):
    ids_list = []
    for text in input_text.split(end_token):
        for pretoken in pretokenize(text):                     # 预分词
            ids_list.append(list(pretoken.encode("utf-8")))
    num_merges = vocab_size - 256 - 1
    merge_rules = {}
    for step in range(num_merges):
        counts = defaultdict(int)
        for ids in ids_list:
            counts = count_pairs(ids, counts)
        if not counts:
            break
        best_pair = max(counts, key=counts.get)
        new_id = 256 + step
        merge_rules[best_pair] = new_id
        for i in range(len(ids_list)):
            ids_list[i] = merge(ids_list[i], best_pair, new_id)
    return merge_rules

import json

class CodeBotTokenizer:
    def __init__(self, merge_rules, end_token="<|endoftext|>"):
        self.merge_rules = merge_rules
        self.end_token = end_token
        self.end_token_id = 256 + len(merge_rules)
        self.id_to_bytes = {i: bytes([i]) for i in range(256)}
        for (id1, id2), new_id in merge_rules.items():
            self.id_to_bytes[new_id] = self.id_to_bytes[id1] + self.id_to_bytes[id2]
        self.id_to_bytes[self.end_token_id] = self.end_token.encode("utf-8")
        self.vocab_size = len(self.id_to_bytes)
        self._cache = {}

    @staticmethod
    def load_from(path):
        with open(path, encoding="utf-8") as f:
            flat = json.load(f)["merges"]       # [a0, b0, a1, b1, ...]
        pairs = zip(flat[0::2], flat[1::2])     # 第 i 对合并成 256 + i
        return CodeBotTokenizer({pair: 256 + i for i, pair in enumerate(pairs)})

    def _encode_text(self, text):
        # 第 4 章的写法：每次只合并现有 pair 里学得最早（id 最小）的那一个
        if text not in self._cache:
            rank = lambda p: self.merge_rules.get(p, float("inf"))
            ids = list(text.encode("utf-8"))
            while len(ids) > 1:
                best = min(zip(ids, ids[1:]), key=rank)
                if best not in self.merge_rules:
                    break
                ids = merge(ids, best, self.merge_rules[best])
            self._cache[text] = ids
        return self._cache[text]

    def encode(self, input_text):
        all_ids = []
        for text in re.split('(' + re.escape(self.end_token) + ')', input_text):
            if text == self.end_token:
                all_ids.append(self.end_token_id)
            else:
                for pretoken in pretokenize(text):
                    all_ids.extend(self._encode_text(pretoken))
        return all_ids

    def decode(self, ids):
        data = b"".join(self.id_to_bytes[i] for i in ids)
        return data.decode("utf-8", errors="replace")

注意Windows 上的陷阱之一：CRLF 换行

原书仓库里存的 tiny_codes.txt 是 LF 换行，可检出到 Windows 的磁盘上时可能会变。Windows 版 Git 的安装程序默认把 core.autocrlf 设成 true（安装程序源码），这时检出的 tiny_codes.txt 里，每个换行 \n 都会变成 \r\n；设成 input 或 false，则原样检出（git 文档）。

原书第 1 章用文本模式读文件，Python 会自动把 \r\n 换回 \n，所以不受影响；可第 4 章的快速训练器以二进制模式读文件，\r 就原样进了语料。结果是第 2 条规则从 '␣␣␣␣'（4 个空格）变成了 '\r\n'，后面的编号也就跟着错开了。克隆时写 git clone -c core.autocrlf=false <仓库地址>，或者事先执行 git config --global core.autocrlf false，就能避开这个问题。已经检出成 CRLF 的，光改设置还不够，要把文件重新检出一遍，命令见第 0 章 0.7 节。

    ids_list = [list(p.encode("utf-8"))

    return learned

1.8.2 测量压缩效率

分词器的好坏，最直接的衡量是压缩率（compression ratio）：同一段文字，平均每个 token 代表几个字节。

\text{压缩率} = \frac{\text{字节数}}{\text{token 数}}

这里，字节数是文字的 UTF-8 长度，token 数是编码之后的序列长度。字节级分词器的压缩率恰好是 1；压缩率越高，序列越短，模型一次能看到的内容就越多。原书在 tiny_codes.txt 的前 10,000 个字符上测量：

编码好的序列里，<|endoftext|>（999）恰好出现了 21,835 次，与原文里分隔符的个数相同。到了第 3 章，这 2,677,398 个整数就是模型预训练的全部食粮。这里先算两个数，给第 3 章的训练定个基准。

训练时盯着看的 loss，是第 2 章要讲的交叉熵：取模型给正确答案的概率，求负对数，再对所有位置求平均。用自然对数 ln 计算时，它的单位叫 nats（2.4 节会讲它和 bits 怎么换算）。如果模型在 1,000 个 token 里均匀地瞎猜，正确答案的概率永远是 1/1000，loss 就是 ln 1000 ≈ 6.91。刚初始化的 CodeBot 就在这附近（实际略高一点，约 7.0，原因见 2.10 节）。

如果模型不看上下文，每次都按词频来猜，平均 loss 就是词频分布的熵（entropy）：

H = -\sum_i p_i \ln p_i

这里，p_i 是 id 为 i 的 token 在 tiny_codes.bin 里出现的比例。举个能心算的例子：假如只有 3 种 token，比例是 1/2、1/4、1/4，那么 H = \tfrac12\ln 2 + \tfrac14\ln 4 + \tfrac14\ln 4 \approx 1.04，比均匀瞎猜的 \ln 3 \approx 1.10 低一点。

可以证明，不看上下文的猜法里，按词频猜是最好的，换成别的分布，平均 loss 只会更高（吉布斯不等式，证明见附录 E 的 E.1 节）。tiny_codes.bin 的词频很不均匀，1,000 个 id 里只有 839 个出现过，所以 H 只有 5.76，比 ln 1000 低了 1.15。训练要做的，是让模型学会看上下文，从这里继续往下降。

小结

本章从“一个字符一个编号”出发。字符级分词器的词表要覆盖 111 万个码位，太大；字节级分词器的词表只有 256，序列却变长了。BPE 在两者之间找到了平衡：以字节为起点，反复合并最常挨在一起的一对，从数据里学出一张小而满的词表。为了让它真正能用，我们给它补上了几样东西：有序的合并规则和容错的解码，把文档隔开的特殊 token，以及让合并不跨越单词的预分词。最后，我们在 TinyCodes 上训练出 CodeBot 的分词器，词表 1,000，全语料的压缩率 2.42，并把 6.5 MB 的代码编码成了 2,677,398 个 uint16。

一路上，我们也看到了不少容易踩的坑：并列时挑哪一对，会改变 token 的编号；合并规则的顺序就是语义；用户的输入里可能藏着特殊 token；Windows 的换行符会悄悄改变训练结果。还有一件事要承认：原书的实现为了清楚而写得很朴素，训练要一个多小时。第 4 章会在不改变任何结果的前提下，把训练缩短到一分钟以内。

本章所学的内容

  • 字符级分词器的词表要覆盖 1,114,112 个码位，仅 embedding 矩阵就超过 4 亿参数；字节级分词器的词表只有 256，代价是序列变长，汉字是原来的 3 倍（验证 1.1-b、验证 1.2-a）
  • BPE 反复合并出现次数最多的 pair，计数会数到重叠的 pair；并列时有三种挑法（先出现、比 id、比字节串），新 token 的 id 按诞生先后编号，所以比 id 与比字节串会分叉（验证 1.3-b、验证 1.3-d、验证 1.3-e）
  • 编码按学到的先后套用合并规则，顺序就是语义；解码用 errors="replace"，因为单个 token 可能只是半个字符（验证 1.4-c、验证 1.4-d、验证 1.4-e）
  • 从 1.5 节起 vocab_size = 256 + 合并次数 + 1，特殊 token 排在最后；re.split 要有捕获组才会留下它，用户文本里的 <|endoftext|> 同样会被编码成特殊 id（验证 1.5-c、验证 1.5-d、验证 1.5-f）
  • GPT-2 的预分词正则让合并不跨越单词，但在代码上会切出 'd、切断 snake_case，而且必须用 regex 模块（验证 1.6-b、验证 1.6-c、验证 1.6-d）
  • CodeBot 的分词器：743 条规则，vocab 1,000，最早学到的是缩进；压缩率在前 10,000 个字符上是 2.12，在全语料上是 2.42（验证 1.7-a、验证 1.8-a、验证 1.8-e、验证 1.8-f）
  • 编码结果存成 uint16，与原书的 tiny_codes.bin 逐字节相同；id 超过 65,535 时，NumPy 2 报错，astype 则悄悄回绕（验证 1.9-a、验证 1.9-b）

分词器把文字变成了整数，可这些整数本身毫无意义：990 号是“一个空格加两个单引号”，991 号是 Error，编号挨着，意思却毫不相干。下一章，我们来造一个能从这串整数里读出意思的东西：Transformer。
