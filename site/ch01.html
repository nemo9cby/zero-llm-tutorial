分词器【基础篇】：把文字变成数字

语言模型只认识整数。本章从“一个字符一个编号”这个最朴素的想法出发，一路走到 GPT 系列所用的 BPE 分词器，最后用它把 CodeBot 的训练数据编码成 token 序列。

1.1 字符级分词器

语言模型的输入是一串整数。在模型做任何“聪明”的事情之前，我们得先回答一个朴素的问题：一段文字，该怎样变成一串整数？承担这项工作的组件叫作分词器（tokenizer），它切分出来的每个单位叫作 token。

最容易想到的做法，是给每个字符分配一个编号。好在这样的编号早已存在，它就是 Unicode 为每个字符规定的码位（code point）。Python 的 ord() 把字符变成码位，chr() 则把码位变回字符：

list(text) 把字符串拆成了 8 个字符，连 emoji 也是完整的一个。把 ord 和 chr 包装成两个方法，就得到了一个完整的分词器：encode 把文字变成 id 列表，decode 把 id 列表还原成文字。

先在浏览器里亲手确认两件事：encode 与 decode 互为逆运算；得到的 id 与书中代码注释里写的完全一致。点击右侧的印章或“在浏览器中运行”即可，第一次运行需要十几秒来加载浏览器内的 Python。

验证 1.1-a字符级分词器：编码与解码互为逆运算
class CharTokenizer:
    def encode(self, text):
        return [ord(char) for char in text]

    def decode(self, ids):
        return ''.join([chr(i) for i in ids])

tok = CharTokenizer()
text = "hello世界😁"
ids = tok.encode(text)
print(ids)
assert ids == [104, 101, 108, 108, 111, 19990, 30028, 128513]
assert tok.decode(ids) == text
构建时的输出（Python 3.14 + NumPy 2.4.6）
[104, 101, 108, 108, 111, 19990, 30028, 128513]
验

看起来一切顺利。那么字符级分词器的问题出在哪里？答案是词表大小（vocabulary size）。

语言模型会为词表里的每个 id 准备一个向量，这些向量排成一张表，叫作嵌入矩阵（embedding matrix）。词表有多少个 id，这张表就有多少行。Unicode 的码位从 0 一直排到 0x10FFFF，如果每个码位都要占一行，表的行数就是 111 万多。我们在第 3 章训练的 CodeBot，每个 token 用 384 维的向量表示。算一算：

验证 1.1-b如果词表覆盖全部 Unicode 码位
vocab_size = 0x10FFFF + 1   # 码位 0 … 0x10FFFF
embed_dim = 384             # CodeBot 的嵌入维度（见第 3 章）
print(f"码位总数      : {vocab_size:,}")
print(f"嵌入矩阵参数量: {vocab_size * embed_dim:,}")
assert vocab_size == 1_114_112

try:
    chr(0x110000)           # 越过最大码位
except ValueError as e:
    print("chr(0x110000) ->", e)
构建时的输出（Python 3.14 + NumPy 2.4.6）
码位总数      : 1,114,112
嵌入矩阵参数量: 427,819,008
chr(0x110000) -> chr() arg not in range(0x110000)
验

仅嵌入矩阵就有 4 亿多个参数，而整个 CodeBot 也才一千万出头。更糟的是，训练数据里绝大多数码位一次也不会出现，对应的那一行向量根本得不到训练。字符级分词器的路走不通，我们需要一张小而“满”的词表。

CS336 对照A1 §2.1 Unicode 标准

CS336 作业 1 的第一组小题，问的正是这几件事：chr(0) 是什么字符、它的 repr 为什么和打印出来的样子不同、码位总共有多少个。思路和本节完全一致：在动手写分词器之前，先摸清 Unicode 的底细。

1.2 字节级分词器

既然码位太多，那就往下走一层，看看字符在计算机里究竟是怎样存储的。Python 的 str.encode("utf-8") 会给出字符的 UTF-8 编码，也就是一串字节（byte）。一个字节只有 256 种取值，于是“词表”一下子缩小到了 256：

A 只占一个字节 65，与它的码位相同；日文假名 あ 却变成了 227、129、130 三个字节。UTF-8 是一种变长编码：ASCII 字符占 1 个字节，大多数汉字和假名占 3 个字节，emoji 占 4 个字节。下面这张图可以任意改动文字，把鼠标移到某个字符上，就能看到它被拆成了哪几个字节。

把 encode 和 decode 换成 UTF-8 编解码，就是字节级分词器：

同样亲手验证一遍。这一次，除了确认编解码互逆，我们还数一数每个字符占了几个字节：

验证 1.2-aUTF-8 是变长编码：1、3、4 个字节
class ByteTokenizer:
    def encode(self, text):
        return list(text.encode("utf-8"))

    def decode(self, ids):
        return bytes(ids).decode("utf-8")

tok = ByteTokenizer()
for ch in ["A", "é", "あ", "世", "😁"]:
    print(f"{ch!r:6} 码位 {ord(ch):>6}  ->  字节 {tok.encode(ch)}")

ids = tok.encode("hello世界😁")
assert ids == [104, 101, 108, 108, 111, 228, 184, 150, 231, 149, 140, 240, 159, 152, 129]
assert tok.decode(ids) == "hello世界😁"
assert all(0 <= i < 256 for i in ids)
构建时的输出（Python 3.14 + NumPy 2.4.6）
'A'    码位     65  ->  字节 [65]
'é'    码位    233  ->  字节 [195, 169]
'あ'    码位  12354  ->  字节 [227, 129, 130]
'世'    码位  19990  ->  字节 [228, 184, 150]
'😁'    码位 128513  ->  字节 [240, 159, 152, 129]
验

词表问题解决了，但代价随之而来：序列变长了。hello世界😁 用字符级分词器是 8 个 token，用字节级分词器则是 15 个。对中文来说，序列长度几乎变成原来的 3 倍。后面我们会看到，Transformer 的计算量随序列长度增长得很快，一次能看到的上下文长度也有上限，因此序列变长是实打实的损失。

注意并非任意字节序列都能解码

字节级分词器的 decode 有一个隐患：UTF-8 对字节的排列有严格的规矩，随便拼出来的一串字节不一定是合法的 UTF-8。语言模型在生成文本时，恰恰是一个 token 一个 token 地“随便拼”，完全可能只吐出半个汉字。

验证 1.2-b半个汉字无法解码
half = [228, 184]            # “世” 的前两个字节
try:
    bytes(half).decode("utf-8")
except UnicodeDecodeError as e:
    print("严格解码失败:", e.reason)

# 用 errors="replace" 时，非法字节会变成替换字符 U+FFFD
print("替换后:", repr(bytes(half).decode("utf-8", errors="replace")))
构建时的输出（Python 3.14 + NumPy 2.4.6）
严格解码失败: unexpected end of data
替换后: '�'
验

后面实现 BPE 分词器的 decode 时，我们还会回到这个问题。

字符级分词器的词表太大，字节级分词器的序列太长。有没有办法兼得两者之长：以字节为基础保证任何文字都能编码，同时把经常一起出现的字节合并成一个 token，从而缩短序列？这正是下一节 BPE 的思路。
