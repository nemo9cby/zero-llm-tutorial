原书代码的已知问题与修复

把原书仓库的脚本逐个跑过、拆开来测之后，我们整理出了 50 个问题。每一条都写明严重度、能重跑的最小复现、修法，以及它会不会改变书中的结果。

写这个教程的过程中，我们把 DLFS6 仓库（固定在 commit c9b6e2e）里的脚本逐个跑了一遍，把关键函数一个个拿出来单独测试，还拿斯坦福 CS336 的公开测试去对照了一遍。绝大多数代码都经得起这样的折腾，但也碰到了一些问题：有的会让第 3 章 GRPO 的准确率在前 200 轮里低 20 到 40 个百分点，有的会让第 6 章的脚本在某种用法下根本跑不起来，更多的是注释过期、边界情况没有处理之类的小毛病。

“逐个跑了一遍”要说清楚范围。规模大的、或者要花钱调用 API 的脚本，我们没有全部原样跑完。下表是每一类脚本实际的运行方式：

脚本 我们怎么跑的
第 3 章的预训练、SFT、GRPO 本机的 RTX 3060 Ti，原样跑完（运行记录 codebot-3060ti）
第 6 章的预训练、生成、DPO Modal 的一张 H100，原样跑完（运行记录 storybot-h100）
第 4 章的 BPE 训练与编码 在 TinyStories 的切片和完整的验证集上运行，产物与官方文件逐字节相同；2.2 GB 的完整训练集没有跑
第 7 章的 BPE 训练与编码 换成 OWT 验证集的前 30 MiB
第 6 章的两个 LLM-as-a-Judge 脚本 用离线的模拟评审打通流程，没有调用付费的 API

原书 README 里写着正误表的地址（…/wiki/errata），可是这个页面并不存在：2026-10-12 访问时，它先被重定向到 /wiki，再回到仓库首页。GitHub 上的 issue 也只有寥寥几条。于是有了这一页。这里只收代码本身的问题。DLFS6 与 CS336 在设计上的取舍不同（比如学习率按线性衰减到 0，而不是 cosine），那不是错误，放在 CS336 对照总表里讨论。

每一条都配了复现：能在浏览器里演示的，写成带“验”字印章的验证单元；需要 PyTorch 或真实权重的，写成本地测试（verify/test_reference.py 里名为 test_eNN_… 的函数），页面上可以展开看到测试源码。先看一览表，再按严重度逐条展开。

Z.2 原书注释即断言

先从一个整体的体检说起。DLFS6 的脚本有个好习惯：很多 print 的后面直接用注释写出了期望的输出，比如 print(ids) # [259, 108, ...]。这些注释其实就是一条条断言，只是没有人去运行它们。我们写了一个测试，把它们全部找出来，改写成断言再运行。

具体做法是：用 Python 的 ast 与 tokenize 模块找出所有“只有一个参数、并且带期望输出注释”的 print，一共 38 处（35 处写在同一行，3 处写在下方的注释块里）；把每个 print(x) 改写成记录 x 的函数调用，在仓库的临时副本里运行脚本（不往 third_party/dlfs6 写任何东西），最后逐条比较。比较分几档：打印出来的文字与注释逐字相同，算“逐字一致”；注释写的是 repr 而 print 显示的是 str（如 'h' 与 h），或者注释省掉了 defaultdict(...)、torch.Size(...) 这层外壳，算“表示形式不同”；其余都算不一致。

验证 Z.2-a38 处注释：30 处逐字一致，7 处只是写法不同，1 处过期

Z.3 高：会改变结果，或让主线脚本跑不起来

E01 GRPO 更新时，策略模型还开着 dropout

在我们找到的问题里，这一个对结果的影响最大。第 3 章的 GRPO 脚本里有两份模型：用来采样的 old_model，和被更新的 model。前者显式调用了 eval()，后者没有：

GPT.load_from 返回的模型处于 PyTorch 的默认状态，也就是训练模式，CodeBot 的 dropout（比率 0.1）是开着的。于是在计算 loss 时，分子 probs 来自一个“随机丢掉一部分神经元”的模型，分母 old_probs 来自完整的模型：

按 PPO 的设计，每批数据的第一次更新时两份模型的权重完全相同，比值 ratio 应该处处等于 1，裁剪（clip）还不起作用。可是有了 dropout，ratio 变成了一个随机数。我们拿作者在 Hugging Face 上发布的 SFT 权重 model_sft.pt（codebot/download.sh 里这一行被注释掉了，要手动下载），把 81 道加法题的正确答案当作回答喂进去（共 117 个回答 token），实测在训练模式下，约一半的 token 的 ratio 落在裁剪区间 [0.8, 1.2] 之外（换 20 个随机种子，这个比例在 42% 到 58% 之间，平均 48%）；切到 eval 模式后，这个比例是 0，ratio 与 1 的最大偏差不到 10^{-5}。

def test_e01_grpo_policy_updates_in_train_mode(dlfs6_path):
    """09_grpo.py: model comes out of load_from in train mode (dropout 0.1), old_model is eval()."""
    from codebot.model import GPT
    from codebot.tokenizer import BPETokenizer

    g = load_defs("ch03/09_grpo.py", names={"GRPODataset", "compute_probs"})
    tok = BPETokenizer.load_from(str(DLFS6 / "codebot" / "merge_rules.pkl"))
    model = GPT.load_from(str(DLFS6 / "codebot" / "model_sft.pt"))
    old = GPT.load_from(str(DLFS6 / "codebot" / "model_sft.pt"))
    old.eval()
    assert model.training and not old.training                      # exactly as in the script

    ds = g["GRPODataset"](tok)                                      # the 81 prompts i+j=
    ids, mask = ds.get_batch([p for p, _ in ds.data], [str(gt) for _, gt in ds.data], CPU)
    on = mask[:, 1:].bool()
    outside = lambda r: ((r < 0.8) | (r > 1.2)).float().mean().item()     # PPO clip range, eps=0.2
    with torch.no_grad():
        p_old = g["compute_probs"](old, ids)
        fractions = []
        for seed in range(20):                                      # 20 dropout masks, same weights
            torch.manual_seed(seed)
            r_train = (g["compute_probs"](model, ids) / (p_old + 1e-8))[on]    # the first update's ratio
            fractions.append(outside(r_train))
        model.eval()
        r_eval = (g["compute_probs"](model, ids) / (p_old + 1e-8))[on]
    assert r_train.numel() == 117
    assert round(sum(fractions) / 20, 2) == 0.48 and 0.41 < min(fractions) and max(fractions) < 0.59
    assert outside(r_eval) == 0 and (r_eval - 1).abs().max() < 1e-5

def train_bpe_toy(text, n_merges):

    vocab = {i: bytes([i]) for i in range(256)}

        for w, c in words.items():

                else:

    return [vocab[i] for i in range(256, 256 + n_merges)]

问题在于 itertools.cycle 的工作方式：它把第一遍迭代吐出的每个元素都存下来，第一遍结束后，不再重新调用 iter()，而是把存下来的元素按原来的顺序一遍遍重放。DataLoader 的 shuffle=True 只在每次 iter() 时生效，于是只有第一遍是洗过牌的，此后每一遍的 batch 都与第一遍一模一样：

import random
from itertools import cycle

class ShuffledLoader:                      # 与 DataLoader(shuffle=True) 一样：每次 iter() 重新洗牌
    def __init__(self, data, batch_size, seed=0):
        self.data, self.bs, self.rng = list(data), batch_size, random.Random(seed)

    def __iter__(self):
        idx = self.data[:]
        self.rng.shuffle(idx)
        return iter([idx[i:i + self.bs] for i in range(0, len(idx), self.bs)])

it = cycle(ShuffledLoader(range(10), 3))   # 每个 epoch 4 个 batch

E20 EOS 不在 GRPO 的学习目标里

generate() 遇到结束 token 就停止，而且不把它放进返回的文本；GRPO 再把回答文本重新编码，得到的 token 序列里没有 EOS（见 E01 前后的代码）。所以 EOS 本身不在目标里，“答完就停”从来不被直接奖励。

这并不等于“多写”不受惩罚。回答里所有的 token 都在掩码之内（mask = [0] * len(prompt_ids) + [1] * len(response_ids)），包括答案后面多写的那些。比如正确答案是 7，模型回答 '7 8'，奖励按最后一个整数算是 0；只要这一组里有答对的回答，它就拿到负的 advantage，多写的 ' 8' 的概率会被压低，结束 token 的概率也就间接抬高了。缺的只是对 EOS 这个 token 的直接奖励。

E49 no_sync() 只包住 backward，每个 micro-step 都在通信

第 9 章把梯度累积和 DDP 合在一起用。原书的想法是：前 3 个 micro-step 先不通信，只在最后一个 micro-step 做一次 all-reduce。model.no_sync() 就是“这一次先别通信”的意思：

问题在于 no_sync() 只包住了 loss.backward()，前向在它外面，而 DDP 在前向时就决定了随后的 backward 要不要通信。于是每个 micro-step 都照样做了 all-reduce。结果并没有错：每张卡最后得到的梯度相同，也等于单卡把全部 micro-batch 当成一个大 batch 算出的梯度；只是通信多了 3 倍，每步 4 次而不是 1 次。我们用 gloo 后端在 CPU 上起了 2 个真正的进程，用一个通信钩子数 all-reduce 的次数：原书的写法是 [1, 1, 1, 1]，把前向也放进 no_sync() 是 [0, 0, 0, 1]（细节见 9.3 节）。

小结

50 个问题里，真正影响书中结果的只有少数几个，影响最大的是 E01：GRPO 更新时开着 dropout。在本书的 GPU 运行里，原样跑满 500 轮停在 86.4%；从同一个 SFT checkpoint 出发、只加一行 model.eval()，第 51 轮就到了 98.8%，第 131 轮起一直是 100%。其次是几个只在特定用法下出现、后果却不小的问题：用 HF 上下载的 StoryBot 权重，第 6 章的脚本一加载就报错（E02）；把 git 检出的文本交给第 4 章的分词器，CRLF 会悄悄改变词表（E03）；用 8 张卡原样运行 WebBot 的预训练，读的 token 和用掉的 GPU 时间都变成 8 倍（E50）。

其余大多是在边界情况下静默出错的问题。它们的共同特点是“不报错”：位置被冻结（E04）、位置被广播（E05）、掩码缺失（E06）、洗牌失效（E07）、错误被吞掉（E09）。这也是我们坚持给每个结论配一个可以重跑的检查的原因：不报错的问题，只有去测才会发现。

这一页的问题，大多来自把代码放到书中没有设想过的场景里：更长的输入、不同的平台、更多的卡、拿去对接别的测试。CS336 对照总表记录的就是最后一种：我们把 DLFS6 的实现接到斯坦福 CS336 的测试上，看哪些能通过、哪些不能，以及为什么。

本章所学的内容：

  • 原书 38 处“写在注释里的期望输出”中，30 处逐字一致，7 处只是写法不同，1 处已经过期（验证 Z.2-a）。
  • GRPO 更新时开着 dropout：原样跑满 500 轮停在 86.4%，只加一行 model.eval()，第 51 轮就到 98.8%，第 131 轮起一直是 100%（验证 Z.3-a）。
  • 二进制模式读取会保留 CRLF 里的 \r，BPE 会把 \r\n 学成一个 token；书中的流程恰好不会把检出的文件交给这样的读取（验证 Z.4-b）。
  • StoryBot 的 RoPE 把超出范围的位置夹在最后：生成时位置被冻结，输入恰好多 1 个 token 时位置被广播（验证 Z.4-c、验证 Z.4-d）。
  • itertools.cycle 只迭代一次并缓存所有元素，所以 shuffle=True 只在第一个 epoch 生效（验证 Z.4-e）。
  • max_iters 写死时，加卡不会更快，只会读更多的 token（验证 Z.4-i）。
  • 概率空间的 ratio 在 p = 1e-8 时只有 0.5；对数空间没有这个问题（验证 Z.5-d）。

这是本书的最后一页。如果你在原书代码里发现了新的问题，不妨照这一页的格式记下来：一个最小复现、一个修法，再加一个谁都能重跑的检查。
