模型【挑战篇】：规模、Attention 加速与 MoE

WebBot 的骨架与 StoryBot 相同，参数却是它的 6.7 倍，上下文是它的 4 倍。规模一变，问题也跟着变：模型该多大，Attention 和 KV cache 占多少显存，能不能参数多而计算少，上下文能不能拉长。书里有代码的地方，我们去读、去对拍；没有代码的地方，就用 NumPy 自己写一个最小版本。

第 7 章读懂并核对了 WebBot 的分词器：原书在 OpenWebText 约 11.9 GB 的样本上学出了 50,000 个 token 的词表，我们在小样本上重现了它最先学到的合并规则，也确认了 owt_valid.bin 正是这份规则的产物。数据和词表都已备齐，接下来轮到模型。第 5 章的 StoryBot 已经具备现代 LLM 的骨架：RoPE、SwiGLU、RMSNorm，生成时还有 KV cache。WebBot 继承了这副骨架，代码上的改动都在 Attention 里（8.2、8.3、8.6 节）。其余都是规模上的放大：参数从 2,270 万增加到 1.52 亿，上下文从 256 拉长到 1,024。

模型该做多大，数据该喂多少？Attention 那个 T\times T 的分数矩阵（T 是序列长度）还放得下吗？生成时 KV cache 要吃掉多少显存？在 StoryBot 的尺度上，这些问题都可以不管；到了 WebBot，就一个也绕不开。

本章按原书目录逐个回答。8.1 节先用 scaling law 给模型定尺寸。8.2 节和 8.3 节给 Attention 减负：Flash Attention 省掉训练时的分数矩阵，GQA 缩小生成时的 KV cache。8.4 节的 MoE 让参数量与计算量脱钩，8.5 节的 torch.compile 让同样的计算跑得更快。最后，8.6 节讨论上下文超过 1,024 时会发生什么、又该怎样扩展。

8.1 选择模型规模

给 WebBot 选尺寸，本质上是在回答一个预算问题：手里的算力是固定的，应该把它花在更大的模型上，还是花在更多的数据上？回答之前，我们先把账算清楚：WebBot 到底有多少参数，训练一遍要花多少计算量。

把参数一个一个数出来

WebBot 的每个 Transformer 块（代码里的 Block）由 Attention、SwiGLU 和两个 RMSNorm 组成，所有线性层都不带 bias。于是一个 Block 的参数量可以写成：

\begin{aligned} N_\text{block} &= \underbrace{2d\,d_h H + 2d\,d_h H_{kv}}_{\text{Attention}} \\ &\quad + \underbrace{3d\,d_\text{ff}}_{\text{SwiGLU}} + \underbrace{2d}_{\text{RMSNorm}} \end{aligned}

这里，d 是 embedding 维度（embed_dim，768，代码里写作 E），也就是后面 12Ld^2 里的 d；d_h 是每个头的维度（head_dim，64）。H 和 H_{kv} 分别是 query 头和 KV 头的个数（12 和 4），d_\text{ff} 是 SwiGLU 的隐藏层宽度（ff_dim，2,048）。第一项是 W_q 和 W_o，第二项是 W_k 和 W_v。代入数字：Attention 是 2\times768\times64\times12 + 2\times768\times64\times4 = 1{,}179{,}648 + 393{,}216 = 1{,}572{,}864，SwiGLU 是 3\times768\times2048 = 4{,}718{,}592，再加上 1,536 个 RMSNorm 权重，每层合计 6,292,992。12 层之外，还有输入 embedding 和输出层 unembed（都是 50,000×768），以及最后一个 RMSNorm。

import numpy as np

def webbot_params(V=50000, E=768, H=12, KV=4, L=12, FF=2048):
    D = E // H                                       # 每个头的维度 head_dim = 64
    attn = E * H * D + 2 * E * KV * D + H * D * E    # W_q；W_k 与 W_v；W_o（都没有 bias）
    ffn = 3 * E * FF                                 # SwiGLU 的 W、V、O
    block = attn + ffn + 2 * E                       # 再加两个 RMSNorm 的权重
    return {"embed": V * E, "blocks": L * block, "norm": E, "unembed": E * V,
            "attn": attn, "ffn": ffn, "block": block}

def total_params(p):
    return p["embed"] + p["blocks"] + p["norm"] + p["unembed"]

你可能会困惑12·L·d² 里的 d 到底是哪个数？

读 scaling law 的文献，常会看到一个估算：不计 embedding 的参数量 N \approx 12\,L\,d^2（Kaplan 等，arXiv:2001.08361 2.1 节）。看到 d，自然会犹豫：它是 embed_dim、hidden_size，还是 d_model？其实这几个是同一个量，只是不同代码库起的名字不同：DLFS6 叫 embed_dim，Kaplan 的论文和 CS336 叫 d_\text{model}，Hugging Face 的配置叫 hidden_size，GPT-2 的配置叫 n_embd。它们都指残差流的宽度，在 WebBot 里是 768。

系数 12 又从哪来？Kaplan 假设的是 GPT-2 式的 Block：Attention 的 Q、K、V、O 四个 d\times d 矩阵共 4d^2，FFN 的两个 d\times 4d 矩阵共 8d^2，合计 12d^2。WebBot 的 Block 不完全一样。SwiGLU 有三个矩阵，但宽度只有 \tfrac{8}{3}d，3\times\tfrac{8}{3}d^2 恰好也是 8d^2；GQA 让 K、V 只剩 4 个头，各自缩成 d^2/3，于是 Attention 只有 2d^2 + 2\cdot\tfrac{d^2}{3} = \tfrac{8}{3}d^2。每层合计约 10.67d^2，比 12d^2 少 11%。可以带走的结论是：12Ld^2 是 GPT-2 式结构的速算，换了结构就要重新数。

训练一遍要多少计算量：6ND

参数数清楚了，再来算计算量。训练时，每个参数在每个 token 上大约要花 6 次浮点运算，所以训练一遍的总计算量是

C \approx 6ND

这里，N 是参数量，D 是训练用的 token 数，C 的单位是 FLOP（做一次乘法或一次加法，记作一次）。那么，6 是从哪里来的？前向时，每个权重对每个 token 做一次乘法和一次加法，这是 2 次。反向时，要分别求对输入的梯度和对权重的梯度，各是一次与前向同样大小的矩阵乘法，于是是前向的 2 倍，也就是 4 次。2 + 4 = 6。

我们用一个 4→3 的线性层把这笔账逐项核对一遍，顺便用数值微分确认，反向的那两次矩阵乘法算的确实是对输入和对权重的梯度：

验证 8.1-c反向传播恰好是两次与前向同样大小的矩阵乘法，所以是 6ND
rng = np.random.default_rng(0)
T, d_in, d_out = 5, 4, 3                 # 5 个 token 经过一个 4→3 的线性层
X = rng.normal(size=(T, d_in))           # (T, d_in)
W = rng.normal(size=(d_in, d_out))       # (d_in, d_out)：12 个参数
dY = rng.normal(size=(T, d_out))         # 上游传回来的梯度

def matmul_flops(a, b):                  # (m×k)@(k×n)：m·n 个输出，各做 k 次乘法和 k 次加法
    m, k = a.shape
    return 2 * m * k * b.shape[1]

fwd = matmul_flops(X, W)                              # 前向 Y = XW
bwd = matmul_flops(dY, W.T) + matmul_flops(X.T, dY)   # 反向 dX = dY·Wᵀ，dW = Xᵀ·dY
print(f"前向 {fwd} FLOPs，反向 {bwd} FLOPs，合计 = {(fwd + bwd) // (T * W.size)} × token 数 × 参数量")
assert bwd == 2 * fwd and fwd + bwd == 6 * T * W.size

# 用中心差分确认：loss = Σ (XW)⊙dY 对 W 的梯度是 Xᵀ·dY，对 X 的梯度是 dY·Wᵀ
loss = lambda X_, W_: np.sum((X_ @ W_) * dY)

def numgrad(f, A, eps=1e-6):             # 逐个元素加减 eps
    g = np.zeros_like(A)
    for idx in np.ndindex(A.shape):
        e = np.zeros_like(A)
        e[idx] = eps
        g[idx] = (f(A + e) - f(A - e)) / (2 * eps)
    return g

err_W = np.abs(numgrad(lambda W_: loss(X, W_), W) - X.T @ dY).max()
err_X = np.abs(numgrad(lambda X_: loss(X_, W), X) - dY @ W.T).max()
assert err_W < 1e-6 and err_X < 1e-6     # 最后几位与机器有关，只断言上界
print("dW 与 dX 都与数值梯度一致：最大差小于 1e-6")

Kaplan 等人的论文正是这样定义训练计算量的：前向约 2N，反向约是前向的两倍，合计每个 token 6N。本节的 N 取全部 1.52 亿个参数，后面的 Chinchilla 也是这样数的。严格地讲，这个数法有两处粗糙。一是输入 embedding 只是查表，不做矩阵乘（RMSNorm 的权重也只做逐元素乘法，不过一共只有 1.9 万个）；二是 Attention 里“Q 乘 K^\top”和“乘 V”这两步不涉及参数，会另外多出一项与上下文长度成正比的计算。只数做矩阵乘的参数（1.14 亿），在 1,024 的上下文下，Attention 这一项约为参数部分的 8%；两者相加，每个 token 约 7.4 亿次运算，比 6N 少约两成（验证 8.6-d）。第 9 章算 MFU 时用的是这个口径；8.6 节还会看到，上下文一长，Attention 这一项就不能忽略了。

拿什么来衡量“86 个 token/参数”是多还是少？答案是 Chinchilla。2022 年，Hoffmann 等人训练了 400 多个模型后得出结论：在算力固定时，模型大小每翻一倍，训练 token 也应该翻一倍（arXiv:2203.15556）。他们按这个结论训练的 Chinchilla 有 700 亿参数、1.4 万亿 token，正好每个参数 20 个 token，“20 token/参数”从此成了常用的经验值。论文附录 F 注明，参数量把 embedding 也算在内，所以我们拿 WebBot 的全部 1.52 亿参数来比。

这样一比，StoryBot 的 14.4 略低于 20，WebBot 的 86 则是它的 4 倍多。如果只追求“这点算力下 loss 最低”，同样的 1.2\times10^{19} FLOPs 应该分给一个约 3 亿参数的模型、约 63 亿个 token。

要看目标是什么。Chinchilla 回答的是“训练花多少，loss 最低”，没有算推理的成本。模型一旦训练好，要被调用成千上万次，每次生成的开销都与参数量成正比。LLaMA 的论文就明确站在推理这一边：作者认为最理想的模型不是训练最快的，而是推理最快的，一个小模型训练得更久，最终在推理上更省（arXiv:2302.13971）。LLaMA-7B（论文表 2 记为 6.7B）用了 1.0 万亿 token，约 149 token/参数。WebBot 的 86 也是“小模型、多训练”这条路。

另一个约束是数据量。OWT 样本只有 26.5 亿个 token，WebBot 要把它重复看约 4.95 遍。Muennighoff 等人发现，重复不超过 4 遍时，loss 和全用新数据几乎一样；重复更多，追加算力的收益会逐渐趋近于零（arXiv:2305.16264）。WebBot 刚好越过这条线一点。

IsoFLOP：同样的算力，换不同的分法

“20 token/参数”只是一条经验规则。它背后的方法值得看一眼，因为 CS336 的作业 3 让学生亲手做的正是这件事。Chinchilla 论文的第二种方法是画等算力曲线（IsoFLOP）：固定一个计算预算 C，训练一系列大小不同的模型。模型越大，能分到的 token 就越少（D = C/6N）。把每个模型最终的 loss 画成 N 的函数，会得到一条 U 形曲线：模型太小，容量不够；模型太大，数据不够。曲线的最低点，就是这个预算下的最优规模 N_\text{opt}(C)。换几个 C 重复一遍，就能拟合出 N_\text{opt} 随 C 增长的规律，论文给出的是 N_\text{opt} \propto C^{0.49}，几乎就是平方根。

我们没有算力训练几百个模型，但可以借用别人拟合好的结果。Chinchilla 论文的第三种方法把 loss 直接写成 N 和 D 的函数：

L(N, D) = E_0 + \frac{A}{N^\alpha} + \frac{B}{D^\beta}

这里，E_0 是数据本身的熵，也就是无限大的模型、无限多的数据也降不下去的部分；第二项是“模型太小”的代价，第三项是“数据太少”的代价。常数取 Besiroglu 等人 2024 年的复现拟合：E_0 = 1.8172，A = 482.01，B = 2085.43，\alpha = 0.3478，\beta = 0.3658（arXiv:2404.10102）。不用原论文的常数，是因为复现论文指出：原常数推出的最优比例约为每参数 70 个 token，与 Chinchilla 自己采用的 20 对不上，而重新拟合的结果约为 20。

在 D = C/6N 的约束下对 N 求导，令导数为 0，可以解出最低点：

\begin{gathered} N_\text{opt}(C) = G\left(\frac{C}{6}\right)^{\frac{\beta}{\alpha+\beta}} \\ G = \left(\frac{\alpha A}{\beta B}\right)^{\frac{1}{\alpha+\beta}} \end{gathered}

这里，G 只是由四个常数凑成的系数，约为 0.1196；指数 \beta/(\alpha+\beta) 约为 0.513。把 WebBot 的 C \approx 1.2\times10^{19} 代进去，C/6 \approx 2.0\times10^{18}，它的 0.513 次方约为 2.4\times10^{9}，乘以 0.1196，得到 N_\text{opt} \approx 2.9 亿。与“20 倍规则”给出的 3.2 亿相差不远。

def test_naive_attention_under_bf16_autocast_saves_fp32_softmax(sb):
    """StoryBot 的手写 Attention 换成 WebBot 的尺寸、在 ch09 的 bf16 autocast 下训练时，为反向传播存下了什么。

    本机不用 GPU：FakeTensorMode 里的“CUDA 张量”只有形状和 dtype，不分配显存；
    autocast(device_type='cuda') 在没有 CUDA 时会自动关闭，所以直接打开 CUDA 的 autocast 状态。
    """
    from torch._subclasses.fake_tensor import FakeTensorMode

    B, H, T, D = 32, 12, 1024, 64                            # WebBot 训练时的一个 micro-batch
    saved = []                                               # 每个留给反向传播的张量：(形状, dtype, 字节数)

    def pack(t):
        saved.append((tuple(t.shape), t.dtype, t.numel() * t.element_size()))
        return t

    with FakeTensorMode(), torch.device("cuda"):
        attn = sb.MultiHeadAttention(H * D, H, D, rope=sb.RoPE(10000, D, T))
        x = torch.empty(B, T, H * D, requires_grad=True)
        before = torch.is_autocast_enabled("cuda"), torch.get_autocast_dtype("cuda")
        torch.set_autocast_enabled("cuda", True)            # 相当于 ch09 的 autocast(device_type='cuda', dtype=bf16)
        torch.set_autocast_dtype("cuda", torch.bfloat16)
        try:
            with torch.autograd.graph.saved_tensors_hooks(pack, lambda t: t):
                out = attn(x)
        finally:
            torch.set_autocast_enabled("cuda", before[0])
            torch.set_autocast_dtype("cuda", before[1])
    assert out.dtype == torch.bfloat16

注意decode 时为什么必须是 is_causal=False

关键的一步：online softmax

直观上，Flash Attention 像是在一张小书桌上读一本厚书：桌子摊不开整本书，就一章一章地读，边读边改笔记，读完最后一章，笔记也就定稿了。严格地讲，它把 Q、K、V 切成小块，每次只把一小块搬进 GPU 芯片上又小又快的 SRAM 里计算，从而大大减少对显存（HBM）的读写（Dao 等，arXiv:2205.14135）。它算出的结果与普通 Attention 相同（只差浮点舍入），不是近似。

难点在 softmax。softmax 的分母要对一整行求和，还要先知道这一行的最大值（为了数值稳定）。如果一次只看得到一小块分数，怎么办？

如果你读过《深度学习入门》3.5.2 节，会记得 softmax 的溢出对策：先减去最大值再取指数，结果不变。在线 softmax（online softmax）把这个技巧往前推了一步（Milakov 与 Gimelshein，arXiv:1805.02867）：最大值不必事先知道，可以边读边更新。读到更大的值时，就把之前累加的和乘上 e^{m - m'}，换算到新的基准上：旧和里的每一项都是 e^{x-m}，乘上 e^{m-m'} 就变成了 e^{x-m'}。

\begin{gathered} m' = \max\Big(m,\ \max_j x_j\Big) \\ \ell' = \ell\, e^{m - m'} + \sum_j e^{x_j - m'} \end{gathered}

这里，m 和 \ell 是读到目前为止的最大值，以及以 m 为基准的指数和；带撇的是读完新的一块之后的值，x_j 是这一块里的数。读完最后一块，\ell 就等于 \sum e^{x - \max x}，与一次性计算的结果相同。我们手算 x = [1, 3, 2, 5]，分两块读：

  • 读完 [1, 3]：m = 3，\ell = e^{1-3} + e^{0} = 1.1353。
  • 读完 [2, 5]：m' = 5，\ell' = 1.1353\times e^{3-5} + e^{2-5} + e^{0} = 0.15365 + 0.04979 + 1 = 1.20344。
  • 一次性计算：e^{-4} + e^{-2} + e^{-3} + e^{0} = 1.20344，相同。
验证 8.2-bonline softmax：分块读、边读边修正，结果与一次性计算相同

分块计算 Attention

同样的技巧可以用在 Attention 的输出上。输出是 softmax 权重与 V 的加权和，我们维护一个没有归一化的累加器 O，每当最大值变大，就像对 \ell 那样把它也乘上 e^{m - m'}，最后再整体除以 \ell。对第 i 块 query 和第 j 块 key，一次更新是：

\begin{gathered} S = \frac{Q_i K_j^\top}{\sqrt{d_h}} \\ m' = \max\big(m, \operatorname{rowmax}(S)\big) \\ P = e^{S - m'} \end{gathered}
\begin{gathered} \ell' = e^{m - m'}\,\ell + \operatorname{rowsum}(P) \\ O' = e^{m - m'}\,O + P\,V_j \end{gathered}

这里，Q_i 是第 i 块 query（B_r 行），K_j、V_j 是第 j 块 key 和 value（B_c 行），m、\ell、O 都按行维护；全部块处理完后，令 O \leftarrow O/\ell。这就是 FlashAttention-2 论文中前向算法的骨架（arXiv:2307.08691）。加上因果掩码时还有一个额外的好处：完全落在对角线右上方的块里全是 -\infty，可以整块跳过。我们用 NumPy 实现它，再和朴素的写法对拍：

验证 8.2-c分块 + online softmax 与朴素 Attention 相同（误差 1e-16 量级），且只用到 Br×Bc 个分数
def attention_naive(Q, K, V, causal=True):
    T, d = Q.shape
    S = Q @ K.T / np.sqrt(d)                          # (T, T)：一次摆出全部分数
    if causal:
        S = np.where(np.tril(np.ones((T, len(K)), dtype=bool)), S, -np.inf)
    P = np.exp(S - S.max(axis=1, keepdims=True))
    return (P / P.sum(axis=1, keepdims=True)) @ V

def attention_flash(Q, K, V, causal=True, Br=16, Bc=16):
    T, d = Q.shape
    O, lse = np.empty_like(Q), np.empty(T)
    stats = {"tiles": 0, "peak": 0}
    for i0 in range(0, T, Br):                        # 外层：一块 query（Br 行）
        q = Q[i0:i0 + Br]
        rows = np.arange(i0, i0 + len(q))[:, None]
        m = np.full(len(q), -np.inf)                  # 每行的当前最大值
        l = np.zeros(len(q))                          # 每行的指数和
        acc = np.zeros_like(q)                        # 每行还没归一化的输出
        for j0 in range(0, len(K), Bc):               # 内层：一块 key / value（Bc 行）
            if causal and j0 > rows[-1, 0]:
                break                                 # 整块都在对角线右上方：跳过
            k, v = K[j0:j0 + Bc], V[j0:j0 + Bc]
            s = q @ k.T / np.sqrt(d)                  # (Br, Bc)：只算这一小块
            if causal:
                cols = np.arange(j0, j0 + len(k))[None, :]
                s = np.where(cols <= rows, s, -np.inf)
            m_new = np.maximum(m, s.max(axis=1))
            p = np.exp(s - m_new[:, None])
            scale = np.exp(m - m_new)                 # 最大值变了，旧的累加量要重新缩放
            l = scale * l + p.sum(axis=1)
            acc = scale[:, None] * acc + p @ v
            m = m_new
            stats["tiles"] += 1
            stats["peak"] = max(stats["peak"], s.size)
        O[i0:i0 + Br] = acc / l[:, None]
        lse[i0:i0 + Br] = m + np.log(l)               # 每行的 log-sum-exp，留给反向传播
    return O, lse, stats

反向传播怎么办

朴素实现会把 softmax 的结果 P（每个头 T\times T 个数）留给反向传播。Flash Attention 不保存 P，只为每一行保存一个数，即 log-sum-exp：\text{lse} = m + \log \ell。反向传播时，再从 Q、K 逐块重算分数，用 P = e^{S - \text{lse}} 把概率原样恢复出来。以 8.2-b 的 x = [1, 3, 2, 5] 为例：\text{lse} = 5 + \ln 1.2034 \approx 5.185，于是 5 这一项的概率是 e^{5-5.185} \approx 0.831，与直接做 softmax 的结果相同。多算一遍矩阵乘法，换来不必存、也不必读那个 T\times T 的矩阵。

8.3 Grouped-Query Attention（GQA）

训练时那个 T\times T 的分数矩阵，Flash Attention 已经解决了。生成文本时还有另一笔开销：第 5 章的 KV cache。生成每一个新 token，Attention 都要用到前面所有 token 的 K 和 V，所以我们把它们缓存下来。每多一个 token，缓存就多出

\text{每 token 字节数} = 2 \cdot L \cdot H_{kv} \cdot d_h \cdot b

这里，2 表示 K 和 V 各一份，L 是层数，H_{kv} 是 KV 头的个数，d_h 是每个头的维度，b 是每个数的字节数（bf16 为 2）。假如 WebBot 用普通的多头 Attention（multi-head attention，MHA），每个 query 头都有自己的 K、V，H_{kv} = 12，那么每个 token 要 2\times12\times12\times64\times2 = 36{,}864 字节，也就是 36 KiB；1,024 个 token 是 36 MiB，batch 为 32 时超过 1 GiB。

占地方还不是全部。生成时每走一步，都要把整个缓存从显存里读一遍，而这一步的计算量却很小，速度于是卡在显存带宽上。Shazeer 在 2019 年提出的多查询注意力（multi-query attention，MQA）让所有头共用一份 K、V，大大减少了这部分读取，代价是质量略有下降（arXiv:1911.02150）。分组查询注意力（grouped-query attention，GQA）取两者之间：把 query 头分成几组，每组共用一份 K、V（Ainslie 等，arXiv:2305.13245）。论文的结论是，经过少量继续训练（uptraining）的 GQA，质量接近 MHA，速度接近 MQA。

WebBot 用的是 12 个 query 头、4 个 KV 头，每 3 个 query 头共用一份 K、V。代码上的改动只有两处：K、V 投影的输出维度从 H * D 变成 KV * D，

第 h 个 query 头用哪个 KV 头？

12 个 query 头、4 个 KV 头，谁和谁一组？PyTorch 的约定是：第 h 个 query 头使用第 \lfloor h / (H/H_{kv}) \rfloor 个 KV 头。以 6 个 query 头、2 个 KV 头为例，分组是 [0, 0, 0, 1, 1, 1]：相邻的头一组。WebBot 的 12 个头就是 [0,0,0,1,1,1,2,2,2,3,3,3]。SDPA 的文档字符串给出了等价的参考实现，enable_gqa 那两行用的正是 repeat_interleave，即把每个 KV 头复制 3 份、挨着排放。如果手写时误用了 repeat（整体平铺），6 个头得到的是 [0, 1, 0, 1, 0, 1]，也就是另一种分组。

    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)

    s = q @ k.T / np.sqrt(q.shape[-1])
    s = np.where(np.tril(np.ones((len(q), len(k)), dtype=bool)), s, -np.inf)
    return softmax(s) @ v

8.4 Mixture of Experts（MoE）

8.1 节说，模型越大，loss 越低；可是每个 token 的计算量也跟着参数量涨（6N）。有没有办法让参数变多，而每个 token 的计算量不变？混合专家（Mixture of Experts，MoE）的想法是：把一个 FFN 换成 E 个结构相同、参数各自独立的 FFN，称为专家（expert），每个 token 只交给其中 k 个专家处理，由一个小小的路由器（router）决定交给谁。本节的 E 都是指专家的个数。

直观上，router 像医院的分诊台：病人很多，科室也很多，分诊台看一眼症状，把每个人送到最合适的一两个科室，其余科室这位病人就不用去了。严格地讲，router 是一个从 d 维映射到 E 维的线性层 W_g，对它的输出取最大的 k 个，再做 softmax 作为权重。Mixtral 8x7B 的 MoE 层写作（arXiv:2401.04088 2.1 节）：

\begin{gathered} y = \sum_{i=0}^{E-1} g_i \cdot \operatorname{SwiGLU}_i(x) \\ g = \operatorname{softmax}\big(\operatorname{Top}k(x W_g)\big) \end{gathered}

这里，x 是一个 token 的向量，g 是门控权重：\operatorname{Top}k 只保留最大的 k 个 logits，其余视为 -\infty（softmax 后就是 0）。\operatorname{SwiGLU}_i 是第 i 个专家，结构与 WebBot 的 FFN 相同。Mixtral 有 8 个专家，每个 token 选 2 个。手算一个例子：某个 token 对 4 个专家的 logits 是 [2.0, 1.0, 0.5, -1.0]，取前 2 名，即专家 0 和 1，权重为 \operatorname{softmax}([2, 1]) = [0.731, 0.269]。它与“先对 4 个数做 softmax，再在前 2 名上重新归一化”是同一回事。

验证 8.4-a先取 top-k 再 softmax，等于先 softmax 再在 top-k 上重新归一化

一个最小的 MoE 层

实现 MoE 层，最直白的写法是让每个专家都算一遍全部 token，再按门控权重加权求和。这样结果正确，却把省下的计算全浪费了。真正的实现是“分派”：每个专家只处理分给自己的 token。我们把两种写法都写出来，确认结果相同：

验证 8.4-b只算被选中的专家（稀疏分派）与全部都算（稠密）结果相同，计算量只有 k/E
rng = np.random.default_rng(2)
T, d, ff, E, k = 12, 8, 16, 4, 2             # 12 个 token，4 个专家，每个 token 选 2 个
X = rng.normal(size=(T, d))
Wg = rng.normal(size=(d, E))                 # router 的权重
experts = [{n: rng.normal(size=s) * 0.3 for n, s in [("W", (d, ff)), ("V", (d, ff)), ("O", (ff, d))]}
           for _ in range(E)]

def swiglu(x, e):                            # 与 WebBot 的 SwiGLU 同一个结构
    a = x @ e["W"]
    return (a / (1 + np.exp(-a)) * (x @ e["V"])) @ e["O"]

logits = X @ Wg                              # (T, E)
top = np.argsort(-logits, axis=1)[:, :k]     # (T, k)：每个 token 选中的专家
gate = np.zeros((T, E))
for t in range(T):
    gate[t, top[t]] = softmax(logits[t, top[t]])

dense = sum(gate[:, [e]] * swiglu(X, experts[e]) for e in range(E))   # 每个专家都算全部 token
sparse, load = np.zeros_like(X), []
for e in range(E):                           # 每个专家只算分给自己的 token
    idx = np.nonzero(gate[:, e])[0]
    load.append(len(idx))
    if len(idx):
        sparse[idx] += gate[idx, e:e + 1] * swiglu(X[idx], experts[e])
print(f"稀疏与稠密的最大差: {np.abs(sparse - dense).max():.1e}")
print(f"各专家处理的 token 数: {load}，合计 {sum(load)} = {T} × {k}（稠密做法是 {T * E}）")
assert np.abs(sparse - dense).max() < 1e-12

负载均衡

如果 router 偏爱少数几个专家，这几个专家收到的 token 最多，得到的训练也最多，于是变得更好，router 就更偏爱它们；其余专家几乎学不到东西。这种自我强化的失衡，Shazeer 等人 2017 年在门控网络上就观察到了（arXiv:1701.06538 第 4 节）。Switch Transformer 用一个辅助 loss 来对抗这种“富者愈富”（Fedus 等，arXiv:2101.03961 式 (4)）：

\mathcal{L}_\text{aux} = \alpha \cdot E \cdot \sum_{i=1}^{E} f_i\, P_i

这里，f_i 是这一批 token 里（按 router 的最大值）被分给第 i 个专家的比例，P_i 是 router 给第 i 个专家的平均概率，\alpha 是这项 loss 的权重，论文取 10^{-2}。我们先手算两种情形。完全均匀时，f_i = P_i = 1/E，E\sum f_i P_i = E\cdot E\cdot\frac{1}{E^2} = 1；全部挤到一个专家时，f_1 = P_1 = 1，其余为 0，结果是 E，这也是它能取到的最大值。1 却不是最小值：f 与 P 一致时，E\sum f_iP_i = E\sum P_i^2 \ge 1，只在完全均匀时取到 1；两者不一致时，它可以略低于 1。f_i 是计数得来的，不可导，梯度只经过 P_i：\partial\mathcal{L}_\text{aux}/\partial P_i = \alpha E f_i。负载越重的专家，它的概率被往下压得越狠。

验证 8.4-c负载均衡 loss：均匀时为 1，全部挤到一个专家时为 E，梯度与负载成正比
def aux_loss(probs, assign, E):
    f = np.bincount(assign, minlength=E) / len(assign)   # 实际分到每个专家的 token 比例
    P = probs.mean(axis=0)                               # router 给每个专家的平均概率
    return E * np.sum(f * P), f, P                       # Switch Transformer 式 (4)，不含 α

除了辅助 loss，实际的系统还会给每个专家设一个容量（capacity）：一批 token 里，每个专家最多处理多少个。Switch Transformer 的定义是“每批 token 数 ÷ 专家数 × capacity factor”（式 (3)）；超出容量的 token 被丢弃，它跳过这一层的专家，只经由残差连接原样传到下一层。

def moe_params(dim, layers, heads, kv, head_dim, hidden, vocab, n_exp, topk):
    attn = 2 * dim * heads * head_dim + 2 * dim * kv * head_dim
    expert = 3 * dim * hidden                    # 一个 SwiGLU 专家

            shared + layers * (per_layer + topk * expert))      # 每个 token 激活的参数

前面几节改的都是“算什么”。这一节换个角度：同样的计算，能不能算得更快？ch09/01_pretrain.py 里有一行看起来毫不起眼的代码，就是下面清单里的第 150 行（モデル＝模型）：

如果你读过《深度学习入门2：自制框架》的专栏 B，会记得深度学习框架分两类：Define-by-Run（边执行边建立计算图，好调试，能直接写 if 和 for）和 Define-and-Run（先定义整张图再执行，便于优化，比如把乘法和加法融合成一步）。PyTorch 平时属于前者，即所谓的 eager 模式：每个运算一执行就交给一个独立的 kernel。torch.compile 让它在不改代码的前提下获得后者的好处。按 PyTorch 2.0 的官方介绍（pytorch.org/get-started/pytorch-2.0），它由几部分组成：

  • TorchDynamo 借助 Python 的帧求值钩子，把 Python 代码捕获成一张图；
  • AOTAutograd 提前把反向传播也追踪成图；
  • TorchInductor 把图编译成更快的代码：在 GPU 上生成 Triton kernel，在 CPU 上生成多线程的 C++ 代码。

融合省下的是什么

有了整张图，编译器就能把相邻的运算融合（fusion）成一个 kernel。以 SwiGLU 里的 F.silu(a) * b 为例：eager 模式下这是两个 kernel，silu 读入 a、写出中间结果，乘法再读入中间结果和 b、写出结果；融合之后只需读入 a 和 b、写出一次结果。这类逐元素运算，每个数只做几次乘加，时间几乎全花在显存读写上，所以少搬多少数据，大致就快多少。这是直观的估计，真实的加速要在 GPU 上测。

8.6 扩展上下文长度

前五节都在 1,024 个 token 的窗口里打转。最后一节问：这个窗口能不能更大？具体是三个问题：这个数从哪来？超过它会发生什么？能不能不重新预训练，就把它拉长？

你可能会困惑1024 这个上限是谁规定的？

第 5 章的专栏“这些长度上限是谁定的？”已经顺着代码找过一次（5.5.5 节）：1,024 是 ch09/01_pretrain.py 里的 context_len（8.1 节的代码清单），作为 max_context_len 传给 GPT。这里把它起作用的三处对上 WebBot 的代码：

  1. 训练时，get_batch 每次切出长 1,024 的窗口，模型从来没见过 1,024 及以后的位置；
  2. RoPE 的 cos、sin 表正好有 1,024 行（见下面的代码清单）；
  3. 生成时，KV cache 最多保留 1,024 个位置。

至于为什么偏偏是 1,024：WebBot 的宽度 768、12 层、12 个头、上下文 1,024，与 GPT-2 small 的配置完全相同（Hugging Face 上的 config.json：n_embd 768、n_layer 12、n_head 12、n_ctx 1024）。代码里没有说明，看起来是有意对齐。可以带走的结论是：上下文长度不是模型的天性，而是训练时定下的一组约定，想改就得在这三处一起动手。

第 5 章（验证 5.5-i）已经在 StoryBot 上看过这段 RoPE：decode 时位置停在上限减 1；prompt 比上限多 1 个 token 时，所有 token 都被当成最后一格，多 2 个才报错。WebBot 用的是同一段代码（「offsetを考慮して位置エンコーディングを取得」＝考虑 offset 来取位置编码）：

第 33–34 行是关键：如果 offset + context_len 超出表的长度，就把 offset 钳在 max_context_len - context_len。生成时每次只送入 1 个 token（context_len 为 1），所以过了第 1,024 个位置之后，每一个新 token 都被当作位置 1,023 来旋转。prompt 的差一位也照样存在：webbot/utils.py 第 18–19 行截断的是 ids，送进模型的却是整段 prompt，所以 1,025 个 token 的 prompt 不报错、悄悄算错，1,026 个才报错。再看 KV cache 的处理（「コンテキスト長制限: キャッシュが長すぎる場合は古い部分を切り捨て」＝上下文长度限制：缓存过长时，丢掉最旧的部分）：

def rope_cache(theta, D, max_len, pos_scale=1.0):
    inv_freq = 1.0 / theta ** (2.0 * np.arange(D // 2) / D)          # (D/2,)
    angles = (np.arange(max_len) / pos_scale)[:, None] * inv_freq     # (max_len, D/2)
    return np.cos(angles), np.sin(angles)

def rope(x, cos, sin, offset=0):            # x: (T, D)，逐行照搬 webbot/model.py 的 RoPE.forward
    T = x.shape[0]
    if offset + T > cos.shape[0]:            # 第 33–34 行：超出表的长度，就把 offset 钳住
        offset = cos.shape[0] - T
    c, s = cos[offset:offset + T], sin[offset:offset + T]
    xe, xo = x[:, 0::2], x[:, 1::2]
    out = np.empty_like(x)
    out[:, 0::2] = xe * c - xo * s
    out[:, 1::2] = xe * s + xo * c
    return out

为什么不能直接外推

那为什么不干脆把 cos、sin 表算长一点，让位置继续往后走？回忆第 5 章：RoPE 把向量的维度两两配成一对，第 i 对在位置 m 处旋转的角度是 m\,\omega_i，其中 \omega_i = \theta^{-2i/d_h}。i 小的那几对转得快，1,024 个位置内要转好多圈，什么角度都见过；i 大的那几对转得慢，波长（wavelength）2\pi/\omega_i 比 1,024 还长，训练时只转过了圆周的一部分。外推到 1,024 之后，这些慢的维度会转到训练时从未见过的角度上。

两种扩展方法：位置插值与 NTK-aware

第一种方法是位置插值（Position Interpolation，简称 PI，Chen 等，arXiv:2306.15595）。想把上下文从 L 扩到 L'，就令 s = L'/L，把位置 m 换成 m/s。这样一来，所有位置都被压回训练时的范围 [0, L) 之内，没有任何一个角度是陌生的。代价是相邻 token 的间隔从 1 变成了 1/s：转得最快、本来负责区分相邻 token 的那几对维度，分辨率也跟着降低了。论文用不超过 1,000 步的微调来适应这一点，把 LLaMA 的上下文扩到了 32,768。

第二种方法叫 NTK-aware，最早出自 bloc97 在 2023 年发表的一篇网络帖子，后来 YaRN 的论文把它整理成了式子（Peng 等，arXiv:2309.00071）。名字里的 NTK 指神经正切核（Neural Tangent Kernel）理论：输入的维度低、对应的 embedding 里又缺少高频成分时，深度网络很难学到高频的信息，所以高频的那几对维度不宜压缩（YaRN 论文 3.1 节）。这里只借用这个直觉。它不动位置，而是改 RoPE 的底数：

\theta' = \theta \cdot s^{\frac{d_h}{d_h - 2}}

这里，\theta 是原来的底数（WebBot 是 10,000），d_h 是每个头的维度，s 同上。这个指数选得很巧。最快的那一对（i = 0）的 \omega_0 = \theta'^{0} = 1，完全不变。最慢的那一对（i = d_h/2 - 1）的指数是 -(d_h-2)/d_h，代入 \theta' 得 \omega'_\text{last} = \theta^{-(d_h-2)/d_h}\,s^{-1} = \omega_\text{last}/s，恰好被放慢 s 倍，在 L' 个位置内转过的角度与训练时大致相同。中间的各对平滑过渡。用 YaRN 论文的话说，它把插值的压力分摊到各个维度上：高频少缩，低频多缩。以 WebBot 为例，s = 2 时 \theta' = 10000 \times 2^{64/62} \approx 20{,}452。

def test_context_extension_on_storybot(sb, storybot, valid_tokens):
    name, (V, C, E, H, L, FF, theta), sd = storybot          # 两份权重各跑一遍
    D = E // H
    n, T = 8, 2 * C                                           # 8 个长 512 的窗口：训练长度的 2 倍
    x, y = windows(valid_tokens, n, T, len(valid_tokens) // n - 600, start=777)
    s = T / C

    def extended(pos_scale=1.0, base=theta):
        model = sb.GPT(V, T, E, H, L, FF, base).eval()
        model.load_state_dict({k: w for k, w in sd.items() if "_cache" not in k}, strict=False)
        inv_freq = 1.0 / base ** (2.0 * torch.arange(D // 2) / D)          # 与 RoPE.__init__ 相同
        angles = (torch.arange(T) / pos_scale)[:, None] * inv_freq[None, :]  # PI：位置 m 换成 m/s
        rope = model.blocks[0].attn.rope                                     # 各层共用同一个 RoPE
        rope.cos_cache.copy_(torch.cos(angles))
        rope.sin_cache.copy_(torch.sin(angles))
        return model

    def halves(model):                                        # 前 256 个位置与后 256 个位置的平均 loss
        with torch.no_grad():
            loss = F.cross_entropy(model(x).reshape(-1, V), y.reshape(-1), reduction="none").view(n, T)
        return loss[:, :C].mean().item(), loss[:, C:].mean().item()

    results = {
        "extrapolate": halves(extended()),
        "pi": halves(extended(pos_scale=s)),
        "ntk": halves(extended(base=theta * s ** (D / (D - 2)))),
    }
    original = sb.GPT(V, C, E, H, L, FF, theta).eval()
    original.load_state_dict(sd)
    with torch.no_grad():
        results["reference"] = tuple(
            F.cross_entropy(original(x[:, a:a + C]).reshape(-1, V), y[:, a:a + C].reshape(-1)).item() for a in (0, C))
    print(name, {k: tuple(round(v, 3) for v in pair) for k, pair in results.items()})

长上下文的账单

能扩展，并不等于扩展是免费的。KV cache 随上下文长度线性增长（8.3 节）；Attention 的计算量也随长度增长。第 t 个 token 在一个头里要和 t 个 key 做内积（2t\,d_h 次运算），再对 t 个 value 加权求和（又是 2t\,d_h 次）。H 个头合起来是 4t\,d，在因果掩码下对 t 取平均约为 2Td（T 为上下文长度），这是前向；训练再乘 3（反向是前向的两倍，与 6N 的道理相同），L 层合计约 6LTd。以 WebBot 为例，6\times12\times1024\times768 \approx 5{,}660 万。参数部分这里只数参与矩阵乘的参数（输入 embedding 只是查表，RMSNorm 的权重只做逐元素乘法，都不算在内），6N_\text{mm} 约 6.83 亿，前者约为后者的 8%。T 一长，前者就会反超后者。

在 1,024 的上下文下，Attention 只占参数部分的 8%；到 4,096 是 33%；超过约 12,000 以后，Attention 就成了大头。Flash Attention 让显存只随长度线性增长，计算量却仍然随长度的平方增长。这就是长上下文昂贵的根本原因。

你可能会困惑上下文只有 1,024，为什么一段对话能处理几千个 token？

第 5 章的专栏已经算过一次（验证 5.5-k）：窗口管的是单次请求里每一次前向能看到多少个 token，累计消耗算的是所有请求之和。一次请求也不只是一次前向：先 prefill 整段 prompt，之后每生成一个 token 再前向一次，每一次都只看得到缓存里最多 1,024 个位置。这里用 WebBot 的数字再走一遍，并补上两点。

比如每轮新增 100 个 token、聊 10 轮：第 10 轮的请求是 1,000 个 token，没有超过窗口；10 次请求加起来却处理了 5,500 个。第一，如果每轮都复用上一轮的 KV cache，真正需要计算的只有 1,000 个，缓存最多占 1,000 × 12 KiB ≈ 11.7 MiB（8.3 节）。第二，训练时的长度也不等于推理时的窗口：前面实验里的 StoryBot 只在 256 个 token 的窗口上训练过，换成 NTK-aware 就能在 512 的窗口里工作。可以带走的结论是：窗口、训练长度、累计消耗是三个不同的量。扩展上下文，扩的是第一个。

小结

本章给 WebBot 的模型定了尺寸，并看了大模型常用的几样工具。我们先把 1.52 亿个参数逐个数清，用 6ND 算出训练要 1.2\times10^{19} 次运算，再用 Chinchilla 的 20 token/参数和 IsoFLOP 曲线看出：WebBot 走的是“小模型、多训练”的路，代价很小；H100 上的 200 步实测又给出了真实的耗时。接着，Flash Attention 用 online softmax 把 Attention 切成小块计算，结果与普通写法一致，显存却从平方降到线性；GQA 让每 3 个 query 头共用一份 K、V，KV cache 从 36 KiB/token 降到 12 KiB/token。

原书没有代码的 MoE，我们用 NumPy 做了一个最小版本：它让总参数多出几倍，每个 token 的激活参数却几乎不变，代价是显存和通信。8.5 节换了一个角度：torch.compile 不改变算什么，只是把整张图交给编译器去融合；我们在 CPU 上确认它把 WebBot 捕获成一张图、结果与 eager 逐位相同，并算清了原书的训练会编译 3 次。最后，我们在 StoryBot 的两份真实权重（原书发布的与我们自己训练的）上试了上下文扩展：原书代码过了 256 就把位置钳住，loss 大幅上升；NTK-aware 不做微调也能把上下文翻倍。

模型准备好了，但 131 亿个 token 还没有喂进去。下一章，我们要面对的是训练本身的规模问题：一张卡放不下一个 batch 怎么办，多张卡怎样协同。

本章所学的内容

  • WebBot 的 152,316,672 个参数可以完全手算，一半在 embedding 与输出层，12Ld^2 只是 GPT-2 式结构的速算；训练计算量 C \approx 6ND，因为反向恰好是两次与前向同样大小的矩阵乘法（验证 8.1-a、验证 8.1-b、验证 8.1-c）。
  • WebBot 每个参数看 86 个 token，是 Chinchilla 20 的 4 倍多；按 Chinchilla 数据的拟合，IsoFLOP 曲线的谷底很平，WebBot 的规模只多付出约 0.03（只说明形状）。H100 上实测每步 0.317 秒，加上 101 次评估，原样训练约 10.4 小时（验证 8.1-d、验证 8.1-e、验证 8.1-g）。
  • Flash Attention 靠 online softmax 分块计算，结果与普通 Attention 相同，只需保存每行一个 log-sum-exp（验证 8.2-c、验证 8.2-d）。
  • GQA 的分组是 repeat_interleave，不是 repeat；WebBot 的 KV cache 从 36 KiB/token 降到 12 KiB/token（验证 8.3-a、验证 8.3-b）。
  • MoE 的稀疏分派与稠密计算结果相同，计算量只有 k/E；负载均衡 loss 在均匀时为 1、坍缩时为 E（验证 8.4-b、验证 8.4-c）。
  • torch.compile 先把整张图捕获下来，再融合逐元素运算：silu(a)*b 的显存搬运从 5 个张量降到 3 个；原书的训练会编译 3 次：训练、第一次评估、评估的最后一个小 batch（验证 8.5-a、验证 8.5-b）。
  • 超过 max_context_len 后，原书代码把位置钳在最后一格；NTK-aware 改底数，保持最高频不变、最低频恰好放慢 s 倍（验证 8.6-a、验证 8.6-c）。

实测的 200 步探针给出每步 0.317 秒：一张 H100 光训练步就要连续跑约 8.8 小时，再加上 101 次全量评估，合计十个多小时。能不能拆给 8 张卡，在约 1/8 的时间里读完同样多的 token？这就是第 9 章的故事。
